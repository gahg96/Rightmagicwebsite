通信模式说明：

  • All-Gather：合并分散在多个 GPU 上的数据（如 Q 矩阵）
  • All-Reduce：汇总各 GPU 的计算结果（如 Attention 输出）
  • Reduce-Scatter：将汇总结果切分回各 GPU（用于 MoE）
  • Broadcast：广播控制信息（如采样参数）

2.7 核心组件深度介绍

硬件组件

组件 作用
DGX Spark (GB10) 单卡算力约 1 PFLOPS（FP8），128GB 统一内存，适合大模型推理
QSFP112 DAC 线缆 200GbE 直连，无需交换机，延迟极低（实测 1.6µs）
ConnectX-7 网卡 支持 RoCEv2，每端口 200Gbps，支持 GPUDirect RDMA
管理网络 (Wi-Fi/有线) 用于 SSH、Docker 控制、日志传输，不参与推理数据流

软件组件

组件 作用
vLLM 高吞吐推理引擎，支持 PagedAttention、Continuous Batching、张量并行
NCCL NVIDIA 集合通信库，实现 GPU 间 All-Gather、All-Reduce 等操作
RDMA (RoCEv2) 绕过 CPU，网卡直接读写 GPU 显存，降低延迟
Docker 容器化部署，环境隔离，便于快速复制
启动脚本 自动化部署，同步配置，管理双机生命周期

张量并行 (TP=2) 工作原理

  • 模型权重按列切分，GPU0 负责前一半注意力头/MoE 专家，GPU1 负责后一半
  • 每层计算后通过 NCCL 同步中间结果
  • KV Cache 也按分片存储，节省显存

三、详细步骤与踩坑记录

第01章：硬件准备与拓扑

操作步骤

  1. 准备硬件：两台 DGX Spark 插电开机，用一根 QSFP112 DAC 线直连两台机器的 QSFP 口。
  2. 连接管理网络：将两台机器通过有线或 Wi-Fi 接入同一局域网。
  3. 物理口映射确认（关键）：

    每台 DGX Spark 有 2 个 QSFP 物理口，每个物理口在 Linux 下映射为 2 个网口：

    物理口 链路0 (100G) 链路1 (100G)
    Port 0 enp1s0f0np0 / rocep1s0f0 enP2p1s0f0np0 / roceP2p1s0f0
    Port 1 enp1s0f1np1 / rocep1s0f1 enP2p1s0f1np1 / roceP2p1s0f1
  4. 检查接线状态： 
    ip -br link show | grep -E "enp1s0f|enP2p1s0f"
sudo ethtool <网口名> | grep -E "Speed|Link detected"

    预期：插线的物理口两个链路均为 Speed: 200000Mb/s 且 Link detected: yes。

⚠️ 踩坑记录

问题 原因 解决方案
测速只有 25 Gbps 网络计划尚未生效 线保持插着，重启两台机器，然后 Run Test Again
线缆不识别 线缆型号不匹配 必须使用官方列出的 QSFP112 DAC 型号（如 Amphenol NJAAKK-N911）
物理口对应错误 两台机器插了不同的物理口 Cluster Assistant 会自动识别，但 NCCL 配置需按实际口位填写

第02章：系统初始化与 OTA 升级

操作步骤

  1. 首次启动：接电源、显示器/键盘，完成 NVIDIA 首启向导。
  2. 确认系统版本： 
    cat /etc/dgx-release
cat /etc/os-release | head -2
  3. 执行官方 OTA 升级（关键——不要用 apt upgrade 代替）： 
    sudo apt update
sudo apt dist-upgrade        # 官方是 dist-upgrade，不是 apt upgrade！
sudo fwupdmgr refresh
sudo fwupdmgr upgrade
sudo reboot
  4. 重启后确认版本 ≥ 2026-04： 
    cat /etc/dgx-release          # OTA 应用后才有 DGX_OTA_VERSION
LC_ALL=C apt-cache policy dgx-spark-ota-update-meta   # Installed 行 ≥ 26.04.1

⚠️ 踩坑记录

问题 原因 解决方案
nvidia-smi 报 "No devices found" 用 apt upgrade 代替了 apt dist-upgrade 重新执行官方 OTA 升级路径
nvidia-spark-ota-check: command not found 误解了该工具的作用 它是 OTA 升级过程中随软件包一并安装的校验工具

第03章：基础配置（用户、SSH、网络与代理）

操作步骤

  1. 创建统一用户并配置 sudo 免密（两台机器）： 
    sudo useradd -m -s /bin/bash -u 1000 <USER>
sudo tee /etc/sudoers.d/<USER>-nopasswd <<< "<USER> ALL=(ALL) NOPASSWD:ALL"
sudo chmod 440 /etc/sudoers.d/<USER>-nopasswd
  2. 双向 SSH 免密配置：
    • 在 head 上生成密钥并分发到自身和 worker： 
      ssh-keygen -t ed25519 -N "" -f ~/.ssh/id_ed25519
ssh-copy-id <USER>@<IP_MGMT_B>
cat ~/.ssh/id_ed25519.pub >> ~/.ssh/authorized_keys
    • 在 worker 上生成密钥并信任自己： 
      ssh-keygen -t ed25519 -N "" -f ~/.ssh/id_ed25519
cat ~/.ssh/id_ed25519.pub >> ~/.ssh/authorized_keys
  3. 配置 /etc/hosts（两台机器都加）： 
    <IP_MGMT_A>  <HOSTNAME_A>  spark-a
<IP_MGMT_B>  <HOSTNAME_B>  spark-b
  4. 配置 ~/.ssh/config（head 上）： 
    Host spark-b
  HostName <IP_MGMT_B>
  User <USER>
  5. 验证：ssh spark-b hostname 应免密直达。
  6. 记录管理 IP： 
    ip -4 addr show <MGMT_IF>   # enP7s7 或 wlP9s9

⚠️ 踩坑记录

问题 原因 解决方案
UID/GID 不一致 创建用户时未指定 -u 1000 使用 sudo useradd -m -s /bin/bash -u 1000 <USER> 统一 UID
管理网口名称错误 直接用了文档示例 enP7s7 先用 ip -4 addr show 查看实际网口名，本次部署是 wlP9s9（Wi-Fi）

第04章：双机集群（NVIDIA Sync + Cluster Assistant）

操作步骤

  1. 安装 NVIDIA Sync：macOS 下载 nvidia-sync.dmg，打开后添加两台设备。
  2. 创建集群：Sync → Settings → Cluster Assistant → Add New Cluster。
  3. Link Speed Test：逐链路测速，要求下限 184 Gbit/s。
  4. 配置产物：Cluster Assistant 写入 /etc/netplan/99-nvidia-sync-cluster.yaml，分配 IP：
    节点 链路0 链路1
    head 10.100.216.1/24 10.100.217.1/24
    worker 10.100.216.2/24 10.100.217.2/24

⚠️ 踩坑记录

问题 原因 解决方案
首次测速只有 25 Gbps 网络计划刚写入尚未生效 线保持插着，重启两台机器，然后 Run Test Again
反复插拔线缆无效 配置未生效 重启才是关键，不是插拔线缆

第05章：NCCL 编译与双机验证

操作步骤

  1. 安装依赖（两台机器）： 
    sudo apt-get update && sudo apt-get install -y libopenmpi-dev
  2. 编译 NCCL（两台机器，约 10-20 分钟）： 
    git clone -b v2.30.7-1 https://github.com/NVIDIA/nccl.git ~/nccl
cd ~/nccl
make -j$(nproc) src.build NVCC_GENCODE="-gencode=arch=compute_121,code=sm_121"
  3. 编译 nccl-tests（两台机器）： 
    git clone https://github.com/NVIDIA/nccl-tests.git ~/nccl-tests
cd ~/nccl-tests
export CUDA_HOME=/usr/local/cuda
export MPI_HOME=/usr/lib/aarch64-linux-gnu/openmpi
export NCCL_HOME=$HOME/nccl/build/
export LD_LIBRARY_PATH=$NCCL_HOME/lib:$CUDA_HOME/lib64/:$MPI_HOME/lib:$LD_LIBRARY_PATH
make -j$(nproc) MPI=1
  4. 确认 RoCE 设备与 GID： 
    ibdev2netdev                    # 查看物理口 → 网口映射
rdma link show                  # 期望 state ACTIVE / LINK_UP

# GID 表：找到 IPv4 的 RoCE v2 索引
for i in 0 1 2 3 4 5; do
  echo "idx$i: $(cat /sys/class/infiniband/<HCA>/ports/1/gids/$i) $(cat /sys/class/infiniband/<HCA>/ports/1/gid_attrs/types/$i)"
done

    预期：IPv4 映射的 GID（::ffff:）位于 idx3（RoCE v2）。

  5. 双机 all_gather 测试（在 head 上执行）： 
    export CUDA_HOME=/usr/local/cuda
export MPI_HOME=/usr/lib/aarch64-linux-gnu/openmpi
export NCCL_HOME=$HOME/nccl/build/
export LD_LIBRARY_PATH=$NCCL_HOME/lib:$CUDA_HOME/lib64/:$MPI_HOME/lib:$LD_LIBRARY_PATH

mpirun -np 2 -H <IP_MGMT_A>:1,<IP_MGMT_B>:1   --mca plm_rsh_agent "ssh -o UserKnownHostsFile=/dev/null -o StrictHostKeyChecking=no"   -x LD_LIBRARY_PATH=$LD_LIBRARY_PATH   -x UCX_NET_DEVICES=<MGMT_IF>   -x NCCL_SOCKET_IFNAME=<MGMT_IF>   -x OMPI_MCA_btl_tcp_if_include=<MGMT_IF>   $HOME/nccl-tests/build/all_gather_perf -b 16G -e 16G -f 2

    预期：两个 rank 各识别一块 GB10，#wrong = 0，busbw 约 21 GB/s。

问题 原因 解决方案

九、性能压测与并发对比分析 (10 并发 vs 20 并发)

9.1 核心指标对比总览

指标 10 并发 20 并发 变化与趋势
总吞吐量 (aggregate_tok_s) 65.35 tok/s 84.86 tok/s ⬆️ +29.9% (吞吐量提升显著)
总耗时 384.32 秒 673.97 秒 ⬇️ -43.0% (整体跑完耗时增加)
中位 TTFT (首 Token 延迟) 23.93 秒 285.34 秒 ⬇️ -91.6% (20并发延迟剧增 11.9倍)
中位输出速度 (output_tok_s) 13.48 tok/s 15.31 tok/s 基本持平 (Decode 阶段非瓶颈)
中位 Prefill 速度 15.00 tok/s 1.27 tok/s ⬇️ -91.5% (KV池爆满导致排队)

9.2 详细现象与调度机制解读

🧠 vLLM 调度模型与并发排队逻辑
┌─────────────────────────────────────────────────────────────┐
│                     vLLM 调度模型                            │
│                                                             │
│  并发数  ──►  活跃槽位 (MAX_NUM_SEQS=6)  ──►  队列长度     │
│                                                             │
│  10     ──►  6 个活跃 + 4 个排队                         │
│  20     ──►  6 个活跃 + 14 个排队  ⬅️ 排队越长，TTFT越高 │
│                                                             │
│  总吞吐量受 GPU 利用率影响，20 并发 GPU 更忙，总吞吐量更高 │
└─────────────────────────────────────────────────────────────┘
  • 总吞吐量： 20 并发达 84.86 tok/s（高于 10 并发的 65.35 tok/s）。由于并发数增加，GPU 在整个压测周期内的空闲等待时间被大幅压缩，整体算力输出更充分。
  • TTFT（首 Token 延迟）： 10 并发（23.93s）大幅优于 20 并发（285.34s）。20 并发时超出活跃槽位（MAX_NUM_SEQS=6）的请求达到 14 个，导致后面的请求严重卡在 Prefill 排队阶段。
  • 单流生成速度： 均保持在 13~16 tok/s 范围，说明 Decode 计算阶段并非瓶颈，系统真正的限制在于 Prefill 阶段的 KV Cache 资源与排队。
