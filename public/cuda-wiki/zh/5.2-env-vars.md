# 5.2 CUDA 环境变量

本节列出 CUDA 环境变量。与多进程服务（MPS）相关的环境变量记录在《GPU 部署与管理指南》中。

## 5.2.1 设备枚举与属性

### 5.2.1.1 CUDA_VISIBLE_DEVICES

该环境变量控制 CUDA 应用程序可见的 GPU 设备，以及枚举这些设备的顺序。

- 若未设置该变量，则所有 GPU 设备均可见。
- 若该变量设为空字符串，则没有 GPU 设备可见。

可能的值：以逗号分隔的 GPU 标识符序列。

GPU 标识符的表示形式：

- 整数索引：对应系统中 GPU 的序号，由 `nvidia-smi` 确定，从 0 开始。例如，设置 `CUDA_VISIBLE_DEVICES=2,1` 会使设备 0 不可见，并先枚举设备 2、再枚举设备 1。
  - 若遇到无效索引，则只有出现在该无效索引之前的设备可见。例如，设置 `CUDA_VISIBLE_DEVICES=0,2,-1,1` 会使设备 0 和 2 可见，而设备 1 不可见，因为它出现在无效索引 -1 之后。
- GPU UUID 字符串：应采用与 `nvidia-smi -L` 给出相同的格式，例如 `GPU-8932f937-d72c-4106-c12f-20bd9faed9f6`。为方便起见，允许使用缩写形式；只需从 GPU UUID 开头指定足够多的字符，能在目标系统中唯一标识该 GPU 即可。例如，`CUDA_VISIBLE_DEVICES=GPU-8932f937` 可能是引用上述 GPU UUID 的有效方式，前提是系统中没有其他 GPU 共享此前缀。
- 多实例 GPU（MIG）支持：`MIG-<GPU-UUID>/<GPU 实例 ID>/<计算实例 ID>`。例如，`MIG-GPU-8932f937-d72c-4106-c12f-20bd9faed9f6/1/2`。仅支持枚举单个 MIG 实例。

`cudaGetDeviceCount()` API 返回的设备数量仅包含可见设备，因此使用整数设备标识符的 CUDA API 仅支持 `[0, 可见设备数量 - 1]` 范围内的序号。GPU 设备的枚举顺序决定序号值。例如，设置 `CUDA_VISIBLE_DEVICES=2,1` 后，调用 `cudaSetDevice(0)` 会将设备 2 设为当前设备，因为它最先被枚举并被赋予序号 0。此后调用 `cudaGetDevice(&device_ordinal)` 也会将 `device_ordinal` 设为 0，对应设备 2。

示例：

```
nvidia-smi -L # 获取 GPU UUID 列表
CUDA_VISIBLE_DEVICES=0,1
CUDA_VISIBLE_DEVICES=GPU-8932f937-d72c-4106-c12f-20bd9faed9f6
CUDA_VISIBLE_DEVICES=MIG-GPU-8932f937-d72c-4106-c12f-20bd9faed9f6/1/2
```

### 5.2.1.2 CUDA_DEVICE_ORDER

该环境变量控制 CUDA 枚举可用设备的顺序。

可能的值：

- `FASTEST_FIRST`：使用简单的启发式方法，按从快到慢的顺序枚举可用设备（默认值）。
- `PCI_BUS_ID`：按 PCI 总线 ID 升序枚举可用设备。PCI 总线 ID 可通过 `nvidia-smi --query-gpu=name,pci.bus_id` 获取。

示例：

```
CUDA_DEVICE_ORDER=FASTEST_FIRST
CUDA_DEVICE_ORDER=PCI_BUS_ID
nvidia-smi --query-gpu=name,pci.bus_id # 获取 PCI 总线 ID 列表
```

### 5.2.1.3 CUDA_MANAGED_FORCE_DEVICE_ALLOC

该环境变量改变多 GPU 系统中统一内存（Unified Memory）的物理存储方式。

可能的值：数值，零或非零。

- 非零值：强制驱动使用设备内存作为物理存储。进程中使用的、支持托管内存的所有设备必须支持点对点（P2P）互访，否则返回 `cudaErrorInvalidDevice`。
- 0：默认行为。

示例：

```
CUDA_MANAGED_FORCE_DEVICE_ALLOC=0
CUDA_MANAGED_FORCE_DEVICE_ALLOC=1 # 强制使用设备内存
```

## 5.2.2 JIT 编译

### 5.2.2.1 CUDA_CACHE_DISABLE

该环境变量控制磁盘即时（JIT）编译缓存的行为。禁用 JIT 缓存会强制 CUDA 应用程序在每次执行时都进行 PTX 到 CUBIN 的编译，除非在二进制文件中找到了运行架构对应的 CUBIN 代码。同一缓存也用于存储已终结（finalized）的 cubin，设置该环境变量还会强制对 cubin 进行终结（如有必要）。

禁用 JIT 缓存会增加应用程序首次执行时的加载时间，但有助于减少应用程序占用的磁盘空间，以及诊断不同驱动版本或构建标志之间的差异。

可能的值：

- 1：禁用 PTX JIT 缓存和二进制终结缓存。
- 0：启用 PTX JIT 缓存（默认值）。

示例：

```
CUDA_CACHE_DISABLE=1 # 禁用缓存
CUDA_CACHE_DISABLE=0 # 启用缓存
```

### 5.2.2.2 CUDA_CACHE_PATH

该环境变量指定即时（JIT）编译缓存的目录路径。同一缓存也用于存储已终结的 cubin。

可能的值：缓存目录的绝对路径（需具备相应的访问权限）。默认值如下：

- Windows 上为 `%APPDATA%\NVIDIA\ComputeCache`
- Linux 上为 `~/.nv/ComputeCache`

示例：

```
CUDA_CACHE_PATH=~/tmp
```

### 5.2.2.3 CUDA_CACHE_MAXSIZE

该环境变量以字节为单位指定即时（JIT）编译缓存的大小。超过该大小的二进制文件不会被缓存。如有需要，较旧的二进制文件会从缓存中逐出，为新的腾出空间。同一缓存也用于存储已终结的 cubin。

可能的值：字节数。默认值如下：

- 桌面/服务器平台为 1073741824（1 GiB）
- 嵌入式平台为 268435456（256 MiB)

4294967296（4 GiB）为最大允许值。

示例：

```
CUDA_CACHE_MAXSIZE=268435456 # 256 MiB
```

### 5.2.2.4 CUDA_FORCE_PTX_JIT 与 CUDA_FORCE_JIT

这两个环境变量指示 CUDA 驱动忽略应用程序中嵌入的 CUBIN，转而对嵌入的 PTX 代码执行即时（JIT）编译。

强制 JIT 编译会增加应用程序首次执行时的加载时间，但可用于验证应用程序中嵌入了 PTX 代码且其即时编译功能正常。这能确保与未来架构的前向兼容性。

`CUDA_FORCE_PTX_JIT` 优先于 `CUDA_FORCE_JIT`。

可能的值：

- 1：强制 PTX JIT 编译。
- 0：默认行为。

示例：

```
CUDA_FORCE_PTX_JIT=1
```

### 5.2.2.5 CUDA_DISABLE_PTX_JIT 与 CUDA_DISABLE_JIT

这两个环境变量禁用嵌入 PTX 代码的即时（JIT）编译，改用应用程序中嵌入的兼容 CUBIN。

如果核函数没有嵌入二进制代码，或嵌入的二进制代码是为不兼容架构编译的，核函数将加载失败。这两个环境变量可用于验证应用程序是否为每个核函数生成了兼容的 CUBIN 代码。更多细节参见"二进制兼容性"一节。

`CUDA_DISABLE_PTX_JIT` 优先于 `CUDA_DISABLE_JIT`。

可能的值：

- 1：禁用 PTX JIT 编译。
- 0：默认行为。

示例：

```
CUDA_DISABLE_PTX_JIT=1
```

### 5.2.2.6 CUDA_FORCE_PRELOAD_LIBRARIES

该环境变量影响 NVVM 与即时（JIT）编译所需库的预加载。

可能的值：

- 1：强制驱动在初始化期间预加载 NVVM 与即时（JIT）编译所需的库。这会增加内存占用和 CUDA 驱动初始化所需的时间。设置该环境变量是避免某些涉及多线程的死锁情形所必需的。
- 0：默认行为。

示例：

```
CUDA_FORCE_PRELOAD_LIBRARIES=1
```

## 5.2.3 执行

### 5.2.3.1 CUDA_LAUNCH_BLOCKING

该环境变量指定禁用还是启用异步核函数启动。禁用异步执行会使执行变慢，但便于调试。它迫使 GPU 工作从 CPU 的视角同步运行，从而可以在触发错误的 API 调用处精确观察到 CUDA API 错误，而不是在后续执行中才暴露。同步执行有助于调试。

可能的值：

- 1：禁用异步执行。
- 0：异步执行（默认值）。

示例：

```
CUDA_LAUNCH_BLOCKING=1
```

### 5.2.3.2 CUDA_DEVICE_MAX_CONNECTIONS

该环境变量控制并发计算连接与拷贝引擎连接（工作队列）的数量，两者均设为指定值。如果从不同 CUDA 流启动的独立 GPU 任务（即核函数或拷贝操作）映射到同一工作队列，就会产生虚假依赖，导致 GPU 工作串行化，因为使用了相同的底层资源。为降低此类虚假依赖的概率，建议将该环境变量控制的工作队列数量设为大于或等于每个上下文的活跃 CUDA 流数量。

设置该环境变量也会修改拷贝连接的数量，除非已通过 `CUDA_DEVICE_MAX_COPY_CONNECTIONS` 环境变量显式设置了拷贝连接数。

可能的值：1 到 32 个连接，默认值为 8（假设未使用 MPS）。

示例：

```
CUDA_DEVICE_MAX_CONNECTIONS=16
```

### 5.2.3.3 CUDA_DEVICE_MAX_COPY_CONNECTIONS

该环境变量控制参与拷贝操作的并发拷贝连接（工作队列）数量。仅影响计算能力 8.0 及以上的设备。

若同时设置了 `CUDA_DEVICE_MAX_COPY_CONNECTIONS` 与 `CUDA_DEVICE_MAX_CONNECTIONS`，前者会覆盖后者设置的拷贝连接数值。

可能的值：1 到 32 个连接，默认值为 8（假设未使用 MPS）。

示例：

```
CUDA_DEVICE_MAX_COPY_CONNECTIONS=16
```

### 5.2.3.4 CUDA_SCALE_LAUNCH_QUEUES

该环境变量指定可用于启动工作（命令缓冲区）的队列大小的缩放系数，即设备上可排队的待处理核函数或主机/设备拷贝操作总数。

可能的值：0.25x、0.5x、2x、4x。

- 除 0.25x、0.5x、2x、4x 之外的任何值均按 1x 处理。

示例：

```
CUDA_SCALE_LAUNCH_QUEUES=2x
```

### 5.2.3.5 CUDA_GRAPHS_USE_NODE_PRIORITY

该环境变量控制 CUDA 图的执行优先级：是沿用其启动所在流的流优先级，还是使用节点优先级。

`CUDA_GRAPHS_USE_NODE_PRIORITY` 会覆盖图实例化时的 `cudaGraphInstantiateFlagUseNodePriority` 标志。

可能的值：

- 0：继承图所启动到的流的优先级（默认值）。
- 1：采用按节点设置的启动优先级。CUDA 运行时将节点级优先级视为可运行图节点的调度提示。

示例：

```
CUDA_GRAPHS_USE_NODE_PRIORITY=1
```

### 5.2.3.6 CUDA_DEVICE_WAITS_ON_EXCEPTION

该环境变量控制 CUDA 应用程序在发生异常（错误）时的行为。启用后，CUDA 应用程序在发生设备端异常时会挂起等待，以便附加调试器（如 cuda-gdb），在进程退出或继续之前检查实时的 GPU 状态。

可能的值：

- 0：默认行为。
- 1：发生设备异常时挂起。

示例：

```
CUDA_DEVICE_WAITS_ON_EXCEPTION=1
```

### 5.2.3.7 CUDA_DEVICE_DEFAULT_PERSISTING_L2_CACHE_PERCENTAGE_LIMIT

该环境变量控制 GPU L2 缓存中默认为持久化访问预留的"预留"部分，以 L2 大小的百分比表示。

它适用于支持持久化 L2 缓存的 GPU，具体指计算能力 8.0 及以上、使用 CUDA 多进程服务（MPS）的设备。该环境变量必须在启动 CUDA MPS 控制守护进程之前设置，即在运行 `nvidia-cuda-mps-control -d` 命令之前。

可能的值：0 到 100 之间的百分比值，默认值为 0。

示例：

```
CUDA_DEVICE_DEFAULT_PERSISTING_L2_CACHE_PERCENTAGE_LIMIT=25 # 25%
```

### 5.2.3.8 CUDA_DISABLE_PERF_BOOST

在 Linux 主机上，将该环境变量设为 1 可阻止提升设备性能状态（pstate），而是基于多种启发式策略隐式选择 pstate。该选项可用于降低功耗，但由于动态选择性能状态，在某些场景下可能导致更高的延迟。

示例：

```
CUDA_DISABLE_PERF_BOOST=1 # 禁用 perf boost，仅限 Linux。
CUDA_DISABLE_PERF_BOOST=0 # 默认行为
```

### 5.2.3.9 CUDA_PREFER_SPINLOCKS_ON_HOST

该环境变量向 CUDA 驱动和运行时提供提示：在某些内部主机端同步路径上优先使用基于自旋的锁定模式。在该模式下，内部锁可能主动轮询等待可用，而不是阻塞并让出 CPU。这可以减少短持有锁的同步延迟，避免内核态切换和唤醒开销，在低到中等竞争下提升快路径性能（例如多个主机线程竞争同一 CUDA 对象或执行上下文时）。基于自旋的锁定不提供调度器辅助的公平性或优先级继承。在主机线程被抢占、超配或混合负载下，启用基于自旋的锁定可能增加优先级反转、饥饿或系统响应性下降的风险。

可能的值：

- 0：默认行为。
- 1：内部同步优先使用自旋锁。

示例：

```
CUDA_PREFER_SPINLOCKS_ON_HOST=1
```

### 5.2.3.10 CUDA_AUTO_BOOST（已弃用）

该环境变量影响 GPU 时钟"自动加速"行为，即动态时钟加速。它会覆盖 `nvidia-smi` 工具的"自动加速"选项，即 `nvidia-smi --auto-boost-default=0`。

> **注**
>
> 该环境变量已弃用。强烈建议改用 `nvidia-smi --applications-clocks=<memory,graphics>` 或 NVML API，而非 `CUDA_AUTO_BOOST` 环境变量。

## 5.2.4 模块加载

### 5.2.4.1 CUDA_MODULE_LOADING

该环境变量影响 CUDA 运行时加载模块的方式，具体指设备代码的初始化方式。

可能的值：

- `DEFAULT`：默认行为，等同于 `LAZY`。
- `LAZY`：将特定核函数的加载推迟到通过 `cuModuleGetFunction()` 或 `cuKernelGetFunction()` API 调用提取 CUDA 函数句柄 `CUfunc` 时。在这种情况下，CUBIN 中的数据在加载该 CUBIN 中的第一个核函数、或访问该 CUBIN 中的第一个变量时才加载。
  - 驱动在首次调用核函数时加载所需的代码，后续调用不再产生额外开销。这减少了启动时间和 GPU 内存占用。
- `EAGER`：在程序初始化时完整加载 CUDA 模块和核函数。CUBIN、FATBIN 或 PTX 文件中的所有核函数和数据，在相应的 `cuModuleLoad*` 和 `cuLibraryLoad*` 驱动 API 调用时即被完整加载。
  - 启动时间和 GPU 内存占用更高，核函数启动开销可预测。

示例：

```
CUDA_MODULE_LOADING=EAGER
CUDA_MODULE_LOADING=LAZY
```

### 5.2.4.2 CUDA_MODULE_DATA_LOADING

该环境变量影响 CUDA 运行时加载与模块相关联的数据的方式。

这是对 `CUDA_MODULE_LOADING` 中以核函数为中心的设置的补充。该环境变量不影响核函数的 `LAZY` 或 `EAGER` 加载。若未设置该环境变量，数据加载行为继承自 `CUDA_MODULE_LOADING`。

可能的值：

- `DEFAULT`：默认行为，等同于 `LAZY`。
- `LAZY`：将模块数据的加载推迟到需要 CUDA 函数句柄 `CUfunc` 时。在这种情况下，CUBIN 中的数据在加载该 CUBIN 中的第一个核函数、或访问该 CUBIN 中的第一个变量时才加载。
  - 延迟数据加载可能需要上下文同步，从而拖慢并发执行。
- `EAGER`：CUBIN、FATBIN 或 PTX 文件中的所有数据，在相应的 `cuModuleLoad*` 和 `cuLibraryLoad*` API 调用时即被完整加载。

示例：

```
CUDA_MODULE_DATA_LOADING=EAGER
```

### 5.2.4.3 CUDA_BINARY_LOADER_THREAD_COUNT

设置加载设备二进制文件时使用的 CPU 线程数。设为 0 时，使用的 CPU 线程数为默认值 1。

可能的值：

- 要使用的线程数的整数值。默认为 0，即使用 1 个线程。

示例：

```
CUDA_BINARY_LOADER_THREAD_COUNT=4
```

### 5.2.4.4 CUDA_DEVICE_DEFAULT_STACK_SIZE_MAX

将该环境变量设为 1 时，驱动会在相应的 `cuModuleLoad*` 调用期间，根据该模块中所有函数的最坏情况需求，预分配每线程栈内存。默认情况下，CUDA 驱动按需分配每线程栈内存：当核函数启动所需的栈超过当前可用量时，驱动会在执行前扩充分配。

可能的值：

- 0 或未设置：核函数启动时按需扩充栈内存（默认值）。
- 1：在模块加载时预分配最大栈内存。

示例：

```
CUDA_DEVICE_DEFAULT_STACK_SIZE_MAX=1
```

## 5.2.5 CUDA 错误日志管理

### 5.2.5.1 CUDA_LOG_FILE

该环境变量指定一个位置：当受支持的 CUDA API 调用返回错误时，描述性错误日志消息将在发生时打印到该位置。

例如，若尝试以无效的网格配置启动核函数，如 `kernel<<<1, dim3(1,1,128)>>>(...)`，该核函数将启动失败，`cudaGetLastError()` 返回通用的非法配置参数错误。若设置了 `CUDA_LOG_FILE` 环境变量，用户可在日志中看到如下描述性错误消息：`[CUDA][E] Block Dimensions (1,1,128) include one or more values that exceed the device limit of (1024,1024,64)`，从而很容易判断是线程块的 z 维度指定非法。更多细节参见"错误日志管理"。

可能的值：`stdout`、`stderr` 或有效的文件路径（需具备相应的访问权限）。

示例：

```
CUDA_LOG_FILE=stdout
CUDA_LOG_FILE=/tmp/dbg_cuda_log
```
