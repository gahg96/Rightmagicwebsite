# 3.3 CUDA 驱动 API（The CUDA Driver API）

本指南前面的章节介绍的是 CUDA 运行时。本指南在 CUDA 运行时 API 与 CUDA 驱动 API 中提到，CUDA 运行时是构建在更底层的 CUDA 驱动 API 之上的。本节介绍 CUDA 运行时与驱动 API 之间的一些差异，以及如何将两者混用。大多数应用可以在完全不与 CUDA 驱动 API 交互的情况下达到满性能。不过，新接口有时会在驱动 API 中先于运行时 API 提供，而有些高级接口（如虚拟内存管理）只在驱动 API 中暴露。

驱动 API 实现在 `cuda` 动态库（`cuda.dll` 或 `cuda.so`）中，该库在安装设备驱动时复制到系统上。它的所有入口点都以 `cu` 为前缀。它是基于句柄的命令式 API：大多数对象由不透明句柄引用，可以将这些句柄传给函数来操纵对象。

驱动 API 中可用的对象汇总于表 6。

**表 6：CUDA 驱动 API 中可用的对象**

| 对象 | 句柄 | 描述 |
|---|---|---|
| Device | CUdevice | 支持 CUDA 的设备 |
| Context | CUcontext | 大致相当于 CPU 进程 |
| Module | CUmodule | 大致相当于动态库 |
| Function | CUfunction | 核函数 |
| Heap memory | CUdeviceptr | 指向设备内存的指针 |
| CUDA array | CUarray | 设备上一维或二维数据的不透明容器，可通过纹理或表面引用读取 |
| Texture object | CUtexref | 描述如何解释纹理内存数据的对象 |
| Surface reference | CUsurfref | 描述如何读写 CUDA 数组的对象 |
| Stream | CUstream | 描述 CUDA 流的对象 |
| Event | CUevent | 描述 CUDA 事件的对象 |

驱动 API 必须先用 `cuInit()` 初始化，才能调用驱动 API 的任何函数。然后必须创建一个与特定设备关联的 CUDA 上下文，并使其成为调用主机线程的当前上下文，详见上下文一节。

在 CUDA 上下文中，核函数由主机代码作为 PTX 或二进制对象显式加载，详见模块一节。用 C++ 编写的核函数因此必须先分别编译成 PTX 或二进制对象。核函数使用核函数执行一节中介绍的 API 入口点启动。

任何希望在未来设备架构上运行的应用程序都必须加载 PTX，而不是二进制代码。这是因为二进制代码是架构相关的，因此与未来架构不兼容，而 PTX 代码在加载时由设备驱动编译为二进制代码。

以下是核函数一节中示例的主机代码，用驱动 API 编写：

```c
int main()
{
    int N = ...;
    size_t size = N * sizeof(float);

     // 在主机内存中分配输入向量 h_A 和 h_B
     float* h_A = (float*)malloc(size);
     float* h_B = (float*)malloc(size);

     // 初始化输入向量
     ...

      // 初始化
      cuInit(0);

      // 获取支持 CUDA 的设备数量
      int deviceCount = 0;
      cuDeviceGetCount(&deviceCount);
      if (deviceCount == 0) {
          printf("There is no device supporting CUDA.\n");
          exit (0);
      }

      // 获取设备 0 的句柄
      CUdevice cuDevice;
      cuDeviceGet(&cuDevice, 0);

      // 创建上下文
      CUcontext cuContext;
      cuCtxCreate(&cuContext, 0, cuDevice);

      // 从二进制文件创建模块
      CUmodule cuModule;
      cuModuleLoad(&cuModule, "VecAdd.ptx");

      // 在设备内存中分配向量
      CUdeviceptr d_A;
      cuMemAlloc(&d_A, size);
      CUdeviceptr d_B;
      cuMemAlloc(&d_B, size);
      CUdeviceptr d_C;
      cuMemAlloc(&d_C, size);

      // 将向量从主机内存复制到设备内存
      cuMemcpyHtoD(d_A, h_A, size);
      cuMemcpyHtoD(d_B, h_B, size);

      // 从模块中获取函数句柄
      CUfunction vecAdd;
      cuModuleGetFunction(&vecAdd, cuModule, "VecAdd");

      // 调用核函数
      int threadsPerBlock = 256;
      int blocksPerGrid =
              (N + threadsPerBlock - 1) / threadsPerBlock;
      void* args[] = { &d_A, &d_B, &d_C, &N };
      cuLaunchKernel(vecAdd,
                     blocksPerGrid, 1, 1, threadsPerBlock, 1, 1,
                     0, 0, args, 0);

      ...
}
```

完整代码见 vectorAddDrv CUDA 示例。

## 3.3.1 上下文（Context）

CUDA 上下文类似于 CPU 进程。在驱动 API 中执行的所有资源和操作都封装在 CUDA 上下文内，上下文销毁时系统会自动清理这些资源。除了模块、纹理或表面引用等对象外，每个上下文都有各自独立的地址空间。因此，来自不同上下文的 `CUdeviceptr` 值引用的是不同的内存位置。

一个主机线程一次只能有一个设备上下文为当前上下文。用 `cuCtxCreate()` 创建上下文时，它会成为调用主机线程的当前上下文。在某个上下文中操作的 CUDA 函数（大多数不涉及设备枚举或上下文管理的函数），如果该线程没有有效的当前上下文，就会返回 `CUDA_ERROR_INVALID_CONTEXT`。

每个主机线程都有一个当前上下文栈。`cuCtxCreate()` 将新上下文压入栈顶。可以调用 `cuCtxPopCurrent()` 将上下文从主机线程解绑。此时上下文处于"浮动"状态，可以被压入任意主机线程作为当前上下文。`cuCtxPopCurrent()` 还会恢复之前的当前上下文（如果有）。

每个上下文还维护一个使用计数。`cuCtxCreate()` 创建使用计数为 1 的上下文。`cuCtxAttach()` 增加使用计数，`cuCtxDetach()` 减少使用计数。当调用 `cuCtxDetach()` 或 `cuCtxDestroy()` 时使用计数归零，上下文即被销毁。

驱动 API 与运行时是互操作的，可以通过 `cuDevicePrimaryCtxRetain()` 从驱动 API 访问运行时管理的主上下文（见运行时初始化）。

使用计数便于在同一上下文中协作的第三方代码之间互操作。例如，如果有三个库加载到同一上下文中使用，每个库都会调用 `cuCtxAttach()` 增加使用计数，库用完上下文时调用 `cuCtxDetach()` 减少使用计数。对于大多数库，预期应用程序会在加载或初始化库之前先创建好上下文；这样，应用程序可以用自己的策略创建上下文，而库只对传给它的上下文进行操作。希望创建自己的上下文的库（其 API 客户端是否创建了上下文并不为其所知）会使用 `cuCtxPushCurrent()` 和 `cuCtxPopCurrent()`，如下图所示。

## 3.3.2 模块（Module）

模块是设备代码和数据的动态可加载包，类似于 Windows 中的 DLL，由 nvcc 输出（见用 NVCC 编译）。所有符号的名称，包括函数、全局变量以及纹理或表面引用，都维护在模块作用域内，这样独立第三方编写的模块就可以在同一个 CUDA 上下文中互操作。

下面的代码示例加载一个模块，并获取某个核函数的句柄：

```c
CUmodule cuModule;
cuModuleLoad(&cuModule, "myModule.ptx");
CUfunction myKernel;
cuModuleGetFunction(&myKernel, cuModule, "MyKernel");
```

下面的代码示例从 PTX 代码编译并加载一个新模块，并解析编译错误：

```c
#define BUFFER_SIZE 8192
CUmodule cuModule;
CUjit_option options[3];
void* values[3];
char* PTXCode = "some PTX code";
char error_log[BUFFER_SIZE];
int err;
options[0] = CU_JIT_ERROR_LOG_BUFFER;
values[0] = (void*)error_log;
options[1] = CU_JIT_ERROR_LOG_BUFFER_SIZE_BYTES;
values[1] = (void*)BUFFER_SIZE;
options[2] = CU_JIT_TARGET_FROM_CUCONTEXT;
values[2] = 0;
err = cuModuleLoadDataEx(&cuModule, PTXCode, 3, options, values);
if (err != CUDA_SUCCESS)
    printf("Link error:\n%s\n", error_log);
```

下面的代码示例从多个 PTX 代码编译、链接并加载一个新模块，并解析链接和编译错误：

```c
#define BUFFER_SIZE 8192
CUmodule cuModule;
CUjit_option options[6];
void* values[6];
float walltime;
char error_log[BUFFER_SIZE], info_log[BUFFER_SIZE];
char* PTXCode0 = "some PTX code";
char* PTXCode1 = "some other PTX code";
CUlinkState linkState;
int err;
void* cubin;
size_t cubinSize;
options[0] = CU_JIT_WALL_TIME;
values[0] = (void*)&walltime;
options[1] = CU_JIT_INFO_LOG_BUFFER;
values[1] = (void*)info_log;
options[2] = CU_JIT_INFO_LOG_BUFFER_SIZE_BYTES;
values[2] = (void*)BUFFER_SIZE;
options[3] = CU_JIT_ERROR_LOG_BUFFER;
values[3] = (void*)error_log;
options[4] = CU_JIT_ERROR_LOG_BUFFER_SIZE_BYTES;
values[4] = (void*)BUFFER_SIZE;
options[5] = CU_JIT_LOG_VERBOSE;
values[5] = (void*)1;
cuLinkCreate(6, options, values, &linkState);
err = cuLinkAddData(linkState, CU_JIT_INPUT_PTX,
                    (void*)PTXCode0, strlen(PTXCode0) + 1, 0, 0, 0, 0);
if (err != CUDA_SUCCESS)
    printf("Link error:\n%s\n", error_log);
err = cuLinkAddData(linkState, CU_JIT_INPUT_PTX,
                    (void*)PTXCode1, strlen(PTXCode1) + 1, 0, 0, 0, 0);
if (err != CUDA_SUCCESS)
    printf("Link error:\n%s\n", error_log);
cuLinkComplete(linkState, &cubin, &cubinSize);
printf("Link completed in %fms. Linker Output:\n%s\n", walltime, info_log);
cuModuleLoadData(cuModule, cubin);
cuLinkDestroy(linkState);
```

可以使用多线程加速模块链接/加载过程的某些部分，包括加载 cubin 时。下面的代码示例使用 `CU_JIT_BINARY_LOADER_THREAD_COUNT` 加速模块加载。

```c
#define BUFFER_SIZE 8192
CUmodule cuModule;
CUjit_option options[3];
void* values[3];
char* cubinCode = "some cubin code";
char error_log[BUFFER_SIZE];
int err;
options[0] = CU_JIT_ERROR_LOG_BUFFER;
values[0] = (void*)error_log;
options[1] = CU_JIT_ERROR_LOG_BUFFER_SIZE_BYTES;
values[1] = (void*)BUFFER_SIZE;
options[2] = CU_JIT_BINARY_LOADER_THREAD_COUNT;
values[2] = 0; // 使用与机器 CPU 数量相同的线程数
err = cuModuleLoadDataEx(&cuModule, cubinCode, 3, options, values);
if (err != CUDA_SUCCESS)
    printf("Link error:\n%s\n", error_log);
```

完整代码见 ptxjit CUDA 示例。

## 3.3.3 核函数执行（Kernel Execution）

`cuLaunchKernel()` 用给定的执行配置启动核函数。

参数可以按指针数组传递（`cuLaunchKernel()` 的倒数第二个参数），其中第 n 个指针对应第 n 个参数，指向参数拷贝来源的内存区域；也可以作为额外选项之一传递（`cuLaunchKernel()` 的最后一个参数）。当参数作为额外选项传递（`CU_LAUNCH_PARAM_BUFFER_POINTER` 选项）时，它们以单个缓冲区的指针传递，参数在该缓冲区中按设备代码中各参数类型的对齐要求彼此正确偏移。

设备代码中内置向量类型的对齐要求列在表 43 中。对于所有其他基本类型，设备代码中的对齐要求与主机代码中的对齐要求相同，因此可以用 `__alignof()` 获取。唯一的例外是：主机编译器将 `double` 和 `long long`（以及 64 位系统上的 `long`）按单字边界对齐，而非双字边界（例如使用 gcc 的编译标志 `-mno-align-double`），因为在设备代码中这些类型始终按双字边界对齐。

`CUdeviceptr` 是整数，但表示指针，因此其对齐要求为 `__alignof(void*)`。

以下代码示例使用一个宏（`ALIGN_UP()`）调整每个参数的偏移以满足其对齐要求，再用另一个宏（`ADD_TO_PARAM_BUFFER()`）将每个参数添加到传给 `CU_LAUNCH_PARAM_BUFFER_POINTER` 选项的参数缓冲区。

```c
#define ALIGN_UP(offset, alignment) \
      (offset) = ((offset) + (alignment) - 1) & ~((alignment) - 1)

char paramBuffer[1024];
size_t paramBufferSize = 0;

#define ADD_TO_PARAM_BUFFER(value, alignment)                    \
    do {                                                         \
         paramBufferSize = ALIGN_UP(paramBufferSize, alignment); \
         memcpy(paramBuffer + paramBufferSize,                   \
                &(value), sizeof(value));                        \
         paramBufferSize += sizeof(value);                        \
    } while (0)

int i;
ADD_TO_PARAM_BUFFER(i, __alignof(i));
float4 f4;
ADD_TO_PARAM_BUFFER(f4, 16); // float4 的对齐要求是 16
char c;
ADD_TO_PARAM_BUFFER(c, __alignof(c));
float f;
ADD_TO_PARAM_BUFFER(f, __alignof(f));
CUdeviceptr devPtr;
ADD_TO_PARAM_BUFFER(devPtr, __alignof(devPtr));
float2 f2;
ADD_TO_PARAM_BUFFER(f2, 8); // float2 的对齐要求是 8

void* extra[] = {
    CU_LAUNCH_PARAM_BUFFER_POINTER, paramBuffer,
    CU_LAUNCH_PARAM_BUFFER_SIZE,    &paramBufferSize,
    CU_LAUNCH_PARAM_END
};
cuLaunchKernel(cuFunction,
               blockWidth, blockHeight, blockDepth,
               gridWidth, gridHeight, gridDepth,
               0, 0, 0, extra);
```

结构体的对齐要求等于其各字段对齐要求的最大值。包含内置向量类型、`CUdeviceptr`，或非对齐 `double` 和 `long long` 的结构体的对齐要求，在设备代码和主机代码中可能不同。这类结构体的填充方式也可能不同。例如，下面的结构体在主机代码中完全不填充，但在设备代码中字段 `f` 后面填充了 12 字节，因为字段 `f4` 的对齐要求是 16。

```c
typedef struct {
    float f;
    float4 f4;
} myStruct;
```

## 3.3.4 运行时与驱动 API 的互操作性

应用程序可以混用运行时 API 代码和驱动 API 代码。

如果通过驱动 API 创建并设为当前上下文，后续的运行时调用会使用这个上下文，而不是创建新上下文。

如果运行时已初始化，可以用 `cuCtxGetCurrent()` 检索初始化时创建的上下文。后续的驱动 API 调用可以使用这个上下文。

运行时隐式创建的上下文称为主上下文（见运行时初始化）。可以用主上下文管理函数从驱动 API 管理它。

可以用任一 API 分配和释放设备内存。`CUdeviceptr` 可以转换为常规指针，反之亦然：

```c
CUdeviceptr devPtr;
float* d_data;

// 使用驱动 API 分配
cuMemAlloc(&devPtr, size);
d_data = (float*)devPtr;

// 使用运行时 API 分配
cudaMalloc(&d_data, size);
devPtr = (CUdeviceptr)d_data;
```

特别地，这意味着用驱动 API 编写的应用程序可以调用用运行时 API 编写的库（如 cuFFT、cuBLAS 等）。

参考手册中设备管理和版本管理章节的所有函数都可以互换使用。
