# 3.4 多 GPU 系统编程

多 GPU 编程让应用程序能够解决更大的问题规模，并达到单个 GPU 无法实现的性能水平——借助多 GPU 系统更大的聚合算术性能、内存容量和内存带宽。

CUDA 通过主机端 API、驱动基础设施和支持性的 GPU 硬件技术实现多 GPU 编程：

- 主机端线程 CUDA 上下文管理
- 系统中所有处理器的统一内存寻址
- GPU 之间的点对点（P2P）大块内存传输
- 细粒度的点对点（P2P）GPU load/store 内存访问
- 更高级的抽象与支持性系统软件，例如 CUDA 进程间通信、基于 NCCL 的并行归约，以及使用 NVLink 和/或 GPU-Direct RDMA 并通过 NVSHMEM、MPI 等 API 进行的通信

在最基本的层面上，多 GPU 编程要求应用程序同时管理多个活动的 CUDA 上下文，把数据分发到各 GPU，在 GPU 上启动核函数完成各自的工作，并通信或汇总结果，以便应用程序据此采取行动。

具体做法的细节，取决于如何将应用的算法、可用并行度和现有代码结构映射为合适的多 GPU 编程方案。一些最常见的多 GPU 编程方案包括：

- 单个主机端线程驱动多个 GPU
- 多个主机端线程，每个线程驱动自己的 GPU
- 多个单线程主机端进程，每个进程驱动自己的 GPU
- 多个主机端进程各含多个线程，每个线程驱动自己的 GPU
- NVLink 连接的多节点集群，各节点操作系统实例中运行的线程和进程驱动各 GPU

各 GPU 可以通过设备内存之间的内存传输和点对点访问相互通信，这适用于上面列出的所有多设备工作分配方案。查询并启用点对点 GPU 内存访问，并利用 NVLink 实现设备之间的高带宽传输和细粒度 load/store 操作，即可支持高性能、低延迟的 GPU 通信。

CUDA 统一虚拟寻址允许同一主机端进程内的多个 GPU 之间以最少的额外步骤进行通信——只需查询并启用高性能点对点内存访问和传输（例如通过 NVLink）。

由不同主机端进程管理的多个 GPU 之间的通信，则通过进程间通信（IPC）和虚拟内存管理（VMM）API 来支持。高级 IPC 概念介绍和节点内 CUDA IPC API 参见"进程间通信"一节。高级虚拟内存管理（VMM）API 同时支持节点内和跨节点 IPC，可用于 Linux 和 Windows 操作系统，并允许以每次分配为粒度控制内存缓冲区的 IPC 共享，详见"虚拟内存管理"。

计算结构传输（Compute Fabric Transport）采用了不同的方法，面向 NVLink 结构上的 GPU：不再像上述方法那样通过映射的虚拟地址访问对端内存，而是用一个逻辑端点 ID（logical endpoint id）命名一组资源、用偏移量命名该组内的某个资源，再用显式的异步结构操作访问该资源。详见下文"计算结构传输"。

CUDA 本身提供了在 GPU 组（可能包括主机端）内实现集合操作所需的 API，但它本身并不提供高级多 GPU 集合 API。多 GPU 集合操作由 NCCL、NVSHMEM 等更高级的 CUDA 通信库提供。

## 3.4.1 多设备上下文与执行管理

应用程序使用多个 GPU 的首要步骤是：枚举可用的 GPU 设备，根据硬件属性、CPU 亲和性以及与对端设备的连通性在可用设备中做适当选择，并为应用将使用的每个设备创建 CUDA 上下文。

### 3.4.1.1 设备枚举

以下代码示例展示了如何查询支持 CUDA 的设备数量、枚举每个设备并查询其属性。

```c
int deviceCount;
cudaGetDeviceCount(&deviceCount);
int device;
for (device = 0; device < deviceCount; ++device) {
    cudaDeviceProp deviceProp;
    cudaGetDeviceProperties(&deviceProp, device);
    printf("Device %d has compute capability %d.%d.\n",
            device, deviceProp.major, deviceProp.minor);
}
```

### 3.4.1.2 设备选择

主机端线程可随时调用 `cudaSetDevice()` 设置其当前操作的设备。设备内存分配和核函数启动都在当前设备上进行；流和事件则与当前设置的设备关联创建。在主机端线程调用 `cudaSetDevice()` 之前，当前设备默认为设备 0。

以下代码示例说明了设置当前设备如何影响随后的内存分配和核函数执行操作。

```c
size_t size = 1024 * sizeof(float);
cudaSetDevice(0);            // 将设备 0 设为当前设备
float* p0;
cudaMalloc(&p0, size);       // 在设备 0 上分配内存
MyKernel<<<1000, 128>>>(p0); // 在设备 0 上启动核函数

cudaSetDevice(1);            // 将设备 1 设为当前设备
float* p1;
cudaMalloc(&p1, size);       // 在设备 1 上分配内存
MyKernel<<<1000, 128>>>(p1); // 在设备 1 上启动核函数
```

### 3.4.1.3 多设备流、事件与内存拷贝行为

如果把核函数启动到与当前设备无关联的流中，启动将失败，如以下代码示例所示。

```c
cudaSetDevice(0);               // 将设备 0 设为当前设备
cudaStream_t s0;
cudaStreamCreate(&s0);          // 在设备 0 上创建流 s0
MyKernel<<<100, 64, 0, s0>>>(); // 在设备 0 的流 s0 中启动核函数

cudaSetDevice(1);               // 将设备 1 设为当前设备
cudaStream_t s1;
cudaStreamCreate(&s1);          // 在设备 1 上创建流 s1
MyKernel<<<100, 64, 0, s1>>>(); // 在设备 1 的流 s1 中启动核函数

// 该核函数启动将失败，因为流 s0 与设备 1 无关联：
MyKernel<<<100, 64, 0, s0>>>(); // 在设备 1 的流 s0 中启动核函数
```

即使把内存拷贝发到与当前设备无关联的流中，拷贝也会成功。

如果输入的事件和输入的流关联到不同的设备，`cudaEventRecord()` 将失败。

如果两个输入事件关联到不同的设备，`cudaEventElapsedTime()` 将失败。

即使输入事件关联到与当前设备不同的设备，`cudaEventSynchronize()` 和 `cudaEventQuery()` 也会成功。

即使输入的流和输入的事件关联到不同的设备，`cudaStreamWaitEvent()` 也会成功。因此，`cudaStreamWaitEvent()` 可用于在多个设备之间做同步。

每个设备都有自己的默认流，因此发到一个设备默认流的命令可能相对于发到任何其他设备默认流的命令乱序执行或并发执行。

## 3.4.2 多设备点对点传输与内存访问

### 3.4.2.1 点对点内存传输

在点对点内存访问可用的情况下，CUDA 可以在设备之间进行内存传输，并利用专用拷贝引擎和 NVLink 硬件来最大化性能。`cudaMemcpy` 可与拷贝类型 `cudaMemcpyDeviceToDevice` 或 `cudaMemcpyDefault` 一起使用。否则，必须使用 `cudaMemcpyPeer()`、`cudaMemcpyPeerAsync()`、`cudaMemcpy3DPeer()` 或 `cudaMemcpy3DPeerAsync()` 进行拷贝，如以下代码示例所示。

```c
cudaSetDevice(0);                   // 将设备 0 设为当前设备
float* p0;
size_t size = 1024 * sizeof(float);
cudaMalloc(&p0, size);              // 在设备 0 上分配内存

cudaSetDevice(1);                               // 将设备 1 设为当前设备
float* p1;
cudaMalloc(&p1, size);                          // 在设备 1 上分配内存

cudaSetDevice(0);                               // 将设备 0 设为当前设备
MyKernel<<<1000, 128>>>(p0);                    // 在设备 0 上启动核函数

cudaSetDevice(1);                   // 将设备 1 设为当前设备
cudaMemcpyPeer(p1, 1, p0, 0, size); // 把 p0 拷贝到 p1
MyKernel<<<1000, 128>>>(p1);        // 在设备 1 上启动核函数
```

两个不同设备内存之间的一次拷贝（在隐式 NULL 流中）：

- 只有在之前发到任一设备的所有命令都完成后才开始；
- 拷贝完全完成后，之后发到任一设备的命令（见"异步执行"）才能开始。

与流的常规行为一致，两个设备内存之间的异步拷贝可以与另一个流中的拷贝或核函数重叠。

如果在两个设备之间启用了点对点访问（例如如"点对点内存访问"中所述），这两个设备之间的点对点内存拷贝就不再需要经由主机端中转，因此更快。

### 3.4.2.2 点对点内存访问

取决于系统属性（具体来说是 PCIe 和/或 NVLink 拓扑），各设备能够寻址彼此的内存（即一个设备上执行的核函数可以解引用指向另一个设备内存的指针）。如果 `cudaDeviceCanAccessPeer()` 对指定的设备返回 true，则这两个设备之间支持点对点内存访问。

必须调用 `cudaDeviceEnablePeerAccess()` 在两个设备之间启用点对点内存访问，如以下代码示例所示。在非 NVSwitch 系统上，每个设备最多支持系统范围内 8 个对端连接。

两个设备使用统一虚拟地址空间（见"统一虚拟地址空间"），因此同一指针可以用于寻址两个设备的内存，如以下代码示例所示。

```c
cudaSetDevice(0);                   // 将设备 0 设为当前设备
float* p0;
size_t size = 1024 * sizeof(float);
cudaMalloc(&p0, size);              // 在设备 0 上分配内存
MyKernel<<<1000, 128>>>(p0);        // 在设备 0 上启动核函数

cudaSetDevice(1);                               // 将设备 1 设为当前设备
cudaDeviceEnablePeerAccess(0, 0);               // 启用与设备 0 的点对点访问

// 在设备 1 上启动核函数
// 该核函数启动可以访问地址 p0 处的设备 0 内存
MyKernel<<<1000, 128>>>(p0);
```

> **Note**
>
> 使用 `cudaDeviceEnablePeerAccess()` 启用对端内存访问是全局生效的，作用于对端设备上所有此前的和此后的 GPU 内存分配。通过 `cudaDeviceEnablePeerAccess()` 启用对某设备的对端访问，会给该对端设备上的设备内存分配操作带来运行时开销：必须让这些分配立刻可被当前设备以及同样具有访问权限的其他对端访问，开销会乘法放大，随对端设备数量增长。
>
> 更具扩展性的替代方案是：使用 CUDA 虚拟内存管理 API，仅在需要时、在分配时显式分配可对端访问的内存区域。通过在内存分配期间显式请求对端可访问性，不会被对端访问的分配其运行时分配开销不受影响，而且可对端访问的数据结构得到了正确的作用域限定，有利于软件调试和可靠性（见"虚拟内存管理"）。

### 3.4.2.3 点对点内存一致性

必须使用同步操作来保证跨多设备分布的网格中并发执行线程的内存访问的顺序性和正确性。跨设备同步的线程运行在 `thread_scope_system` 同步作用域；类似地，内存操作属于 `thread_scope_system` 内存同步域。

当只有一个 GPU 访问对端设备内存中的对象时，CUDA 原子函数可以对该对象执行读-修改-写操作。对端原子性的要求与限制在 CUDA 内存模型原子性要求的讨论中描述。

### 3.4.2.4 多设备托管内存

在具有点对点支持的多 GPU 系统上可以使用托管内存。对并发多设备托管内存访问的详细要求，以及 GPU 独占访问托管内存的 API，在"多 GPU"一节中描述。

### 3.4.2.5 主机端 IOMMU 硬件、PCI 访问控制服务与虚拟机

在 Linux 上具体而言，CUDA 和显示驱动不支持启用 IOMMU 的裸机 PCIe 点对点内存传输。但 CUDA 和显示驱动支持经由虚拟机直通的 IOMMU。在裸机系统上运行 Linux 时必须禁用 IOMMU，以防止发生静默的设备内存损坏。相反地，对于虚拟机，应启用 IOMMU 并使用 VFIO 驱动进行 PCIe 直通。

在 Windows 上上述 IOMMU 限制不存在。

另见"在 64 位平台上分配 DMA 缓冲区"。

此外，在支持 IOMMU 的系统上可以启用 PCI 访问控制服务（ACS）。PCI ACS 特性会把所有 PCI 点对点流量重定向经过 CPU 根复合体，由于整体对分带宽降低，可能造成显著的性能损失。

### 3.4.2.6 计算结构传输

点对点内存访问通过发出进程已保留并映射的虚拟地址到达对端分配。计算结构传输为大型 NVLink 结构提供了另一种方式：用逻辑端点 ID 命名对端、用偏移量命名访问的资源，而不是用映射地址。它面向通信库和高级应用程序，详见"计算结构传输"。
