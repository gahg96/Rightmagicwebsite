# 4.1 统一内存

本节详细讲解统一内存（unified memory）各种编程范式各自的行为与用法。前面的章节已经说明了如何判断适用哪种统一内存范式，并简要介绍了每一种。

如前所述，统一内存编程共有四种范式：

- 对显式托管内存（managed memory）分配的完整支持
- 对所有分配加软件一致性的完整支持
- 对所有分配加硬件一致性的完整支持
- 有限的统一内存支持

前三种范式都涉及完整的统一内存支持，其行为和编程模型非常相似，在「具备完整 CUDA 统一内存支持的设备上的统一内存」一节中统一讲解，并标出差异。

最后一种范式——统一内存支持受限的情况——在「Windows、WSL 与 Tegra 上的统一内存」一节中详细讨论。

## 4.1.1 具备完整 CUDA 统一内存支持的设备上的统一内存

这类系统包括具备硬件一致性的内存系统，例如 NVIDIA Grace Hopper，以及启用了异构内存管理（Heterogeneous Memory Management，HMM）的现代 Linux 系统。HMM 是一种基于软件的内存管理系统，提供与具备硬件一致性的内存系统相同的编程模型。

Linux HMM 要求：Linux 内核版本 6.1.24+、6.2.11+ 或 6.3+，计算能力（Compute Capability）7.5 及以上的设备，以及安装了开放内核模块（Open Kernel Modules）的 535+ 版 CUDA 驱动。

> 注
>
> 我们把 CPU 和 GPU 共用一张组合页表的系统称为具备硬件一致性的系统（hardware-coherent system）；CPU 和 GPU 各自使用独立页表的系统称为具备软件一致性的系统（software-coherent system）。

具备硬件一致性的系统（例如 NVIDIA Grace Hopper）为 CPU 和 GPU 提供逻辑上合二为一的页表（参见「CPU 与 GPU 页表：硬件一致性与软件一致性」）。以下小节仅适用于具备硬件一致性的系统：

- 访问计数器迁移

### 4.1.1.1 统一内存：深入示例

具备完整 CUDA 统一内存支持的系统（参见表《统一内存范式概览》）允许设备端访问与之交互的主机进程所拥有的任何内存。本节用一个简单核函数展示几个高级用例，该核函数把输入字符数组的前 8 个字符打印到标准输出：

```cuda
__global__ void kernel(const char* type, const char* data) {
  static const int n_char = 8;
  printf("%s - first %d characters: '", type, n_char);
  for (int i = 0; i < n_char; ++i) printf("%c", data[i]);
  printf("'\n");
}
```

下面的代码展示了用系统分配的内存调用该核函数的多种方式：

**Malloc**

```cuda
void test_malloc() {
  const char test_string[] = "Hello World";
  char* heap_data = (char*)malloc(sizeof(test_string));
  strncpy(heap_data, test_string, sizeof(test_string));
  kernel<<<1, 1>>>("malloc", heap_data);
  ASSERT(cudaDeviceSynchronize() == cudaSuccess,
    "CUDA failed with '%s'", cudaGetErrorString(cudaGetLastError()));
  free(heap_data);
}
```

**Managed**

```cuda
void test_managed() {
  const char test_string[] = "Hello World";
  char* data;
  cudaMallocManaged(&data, sizeof(test_string));
  strncpy(data, test_string, sizeof(test_string));
  kernel<<<1, 1>>>("managed", data);
  ASSERT(cudaDeviceSynchronize() == cudaSuccess,
    "CUDA failed with '%s'", cudaGetErrorString(cudaGetLastError()));
  cudaFree(data);
}
```

**Stack variable（栈变量）**

```cuda
void test_stack() {
  const char test_string[] = "Hello World";
  kernel<<<1, 1>>>("stack", test_string);
  ASSERT(cudaDeviceSynchronize() == cudaSuccess,
    "CUDA failed with '%s'", cudaGetErrorString(cudaGetLastError()));
}
```

**File-scope static variable（文件作用域静态变量）**

```cuda
void test_static() {
  static const char test_string[] = "Hello World";
  kernel<<<1, 1>>>("static", test_string);
  ASSERT(cudaDeviceSynchronize() == cudaSuccess,
    "CUDA failed with '%s'", cudaGetErrorString(cudaGetLastError()));
}
```

**Global-scope variable（全局作用域变量）**

```cuda
const char global_string[] = "Hello World";

void test_global() {
  kernel<<<1, 1>>>("global", global_string);
  ASSERT(cudaDeviceSynchronize() == cudaSuccess,
    "CUDA failed with '%s'", cudaGetErrorString(cudaGetLastError()));
}
```

**Global-scope extern variable（全局作用域 extern 变量）**

```cuda
// 在另一个文件中声明，见下方
extern char* ext_data;

void test_extern() {
  kernel<<<1, 1>>>("extern", ext_data);
  ASSERT(cudaDeviceSynchronize() == cudaSuccess,
    "CUDA failed with '%s'", cudaGetErrorString(cudaGetLastError()));
}
```

```cuda
/** 这可能是非 CUDA 文件 */
char* ext_data;
static const char global_string[] = "Hello World";

void __attribute__ ((constructor)) setup(void) {
  ext_data = (char*)malloc(sizeof(global_string));
  strncpy(ext_data, global_string, sizeof(global_string));
}

void __attribute__ ((destructor)) tear_down(void) {
  free(ext_data);
}
```

注意，对于 extern 变量，它可以由完全不与 CUDA 交互的第三方库声明并拥有、管理。

还要注意，栈变量以及文件作用域和全局作用域变量只能由 GPU 通过指针访问。在这个具体例子中很方便，因为字符数组本身就声明为指针：`const char*`。但请看下面这个全局作用域整数的例子：

```cuda
// 该变量声明在全局作用域
int global_variable;

__global__ void kernel_uncompilable() {
  // 这会导致编译错误：全局（__host__）变量不得
  // 从 __device__ / __global__ 代码中访问
  printf("%d\n", global_variable);
}

// 在 pageableMemoryAccess 设为 1 的系统上，可以取
// 全局变量的地址。下面的核函数把该地址作为参数
__global__ void kernel(int* global_variable_addr) {
  printf("%d\n", *global_variable_addr);
}
int main() {
  kernel<<<1, 1>>>(&global_variable);
  ...
  return 0;
}
```

在上面的例子中，必须把全局变量的指针传给核函数，而不是在核函数中直接访问全局变量。这是因为，没有 `__managed__` 修饰符的全局变量默认声明为仅 `__host__` 可见，因此目前大多数编译器不允许在设备端代码中直接使用这些变量。

#### 4.1.1.1.1 文件映射的统一内存

由于具备完整 CUDA 统一内存支持的系统允许设备端访问主机进程拥有的任何内存，它们可以直接访问文件映射内存（file-backed memory）。

这里展示上一节初始示例的修改版，用文件映射内存把直接从输入文件读取的字符串打印出来。下面的例子中内存由物理文件支撑，但该示例同样适用于内存文件。

```cuda
__global__ void kernel(const char* type, const char* data) {
  static const int n_char = 8;
  printf("%s - first %d characters: '", type, n_char);
  for (int i = 0; i < n_char; ++i) printf("%c", data[i]);
  printf("'\n");
}

void test_file_backed() {
   int fd = open(INPUT_FILE_NAME, O_RDONLY);
   ASSERT(fd >= 0, "Invalid file handle");
   struct stat file_stat;
   int status = fstat(fd, &file_stat);
   ASSERT(status >= 0, "Invalid file stats");
   char* mapped = (char*)mmap(0, file_stat.st_size, PROT_READ, MAP_PRIVATE, fd, 0);

   ASSERT(mapped != MAP_FAILED, "Cannot map file into memory");
   kernel<<<1, 1>>>("file-backed", mapped);
   ASSERT(cudaDeviceSynchronize() == cudaSuccess,
     "CUDA failed with '%s'", cudaGetErrorString(cudaGetLastError()));
   ASSERT(munmap(mapped, file_stat.st_size) == 0, "Cannot unmap file");
   ASSERT(close(fd) == 0, "Cannot close file");
}
```

注意，在不具备 hostNativeAtomicSupported 属性的系统上（参见「主机端原生原子操作」），包括启用了 Linux HMM 的系统，不支持对文件映射内存的原子访问。

#### 4.1.1.1.2 统一内存的进程间通信（IPC）

> 注
>
> 目前，在统一内存上使用 IPC 可能带来明显的性能影响。

许多应用更倾向于每个进程管理一个 GPU，但仍需要使用统一内存（例如为了实现超额订阅（oversubscription）），并从多个 GPU 访问它。

CUDA IPC（参见「进程间通信」）不支持托管内存：这种内存的句柄不能通过本节讨论的任何机制共享。在具备完整 CUDA 统一内存支持的系统上，系统分配的内存具备 IPC 能力。一旦把系统分配内存的访问权限共享给其他进程，就适用相同的编程模型，类似于「文件映射的统一内存」。

关于在 Linux 下创建具备 IPC 能力的系统分配内存的各种方法，参见以下文档：

- 带 `MAP_SHARED` 的 `mmap`
- POSIX IPC API
- Linux 的 `memfd_create`

注意，用这种技术无法在不同主机及其设备之间共享内存。


### 4.1.1.2 性能调优

要在统一内存上获得良好的性能，重要的是：

- 理解系统上的分页机制如何工作，以及如何避免不必要的缺页（page fault）
- 理解各种机制，以便让数据保持在访问它的处理器附近
- 考虑针对系统的内存传输粒度来调优应用

作为一般建议，性能提示（参见「性能提示」）可能带来更好的性能，但使用不当反而可能比默认行为更差。还要注意，任何提示在主机端都有相应的性能开销，因此有用的提示至少要带来足够大的性能提升来抵消这个开销。

#### 4.1.1.2.1 内存分页与页面大小

要更好地理解统一内存对性能的影响，重要的是先理解虚拟寻址、内存页和页面大小。本小节尝试定义所有必要的术语，并解释分页为什么影响性能。

目前统一内存支持的所有系统都使用虚拟地址空间：也就是说，应用程序使用的内存地址代表一个虚拟位置，它可能映射到内存实际驻留的物理位置。

目前所有支持的处理器（包括 CPU 和 GPU）都使用内存分页。因为所有系统都使用虚拟地址空间，所以有两种内存页：

- 虚拟页：代表每个进程固定大小的连续虚拟内存块，由操作系统跟踪，可以映射到物理内存。注意虚拟页与映射相关联：例如，同一个虚拟地址可能用不同的页面大小映射到物理内存。
- 物理页：代表处理器主内存管理单元（Memory Management Unit，MMU）支持的固定大小的连续内存块，虚拟页可以映射到其中。

目前所有 x86_64 CPU 的默认物理页面大小为 4KiB。Arm CPU 支持多种物理页面大小——4KiB、16KiB、32KiB 和 64KiB，取决于具体的 CPU。最后，NVIDIA GPU 支持多种物理页面大小，但偏好 2MiB 或更大的物理页。注意这些大小在未来的硬件中可能发生变化。

虚拟页的默认页面大小通常与物理页面大小对应，但只要操作系统和硬件支持，应用也可以使用不同的页面大小。通常，受支持的虚拟页面大小必须是 2 的幂，且是物理页面大小的倍数。

跟踪虚拟页到物理页映射关系的逻辑实体称为页表（page table），每个给定虚拟页以给定虚拟大小到物理页的映射称为页表项（Page Table Entry，PTE）。所有受支持的处理器都为页表提供专用的缓存，以加速虚拟地址到物理地址的转换。这些缓存称为转换旁路缓冲（Translation Lookaside Buffer，TLB）。

对应用的性能调优有两个重要方面：

- 虚拟页面大小的选择
- 系统是提供 CPU 和 GPU 共用的组合页表，还是 CPU 和每个 GPU 各自独立的页表

##### 4.1.1.2.1.1 选择合适的页面大小

一般来说，小页面会导致（虚拟）内存碎片更少，但 TLB 未命中更多；而大页面会导致内存碎片更多，但 TLB 未命中更少。此外，大页面的内存迁移通常比小页面更昂贵，因为我们通常按整页迁移。这可能导致使用大页面的应用出现更大的延迟尖峰。关于缺页的更多细节，参见下一节。

对性能调优的一个重要方面是：GPU 上的 TLB 未命中通常比 CPU 上昂贵得多。这意味着，如果 GPU 线程频繁随机访问用足够小的页面大小映射的统一内存，它可能比访问用足够大的页面大小映射的同一块统一内存慢得多。虽然 CPU 线程随机访问用小页面大小映射的大片内存时也可能出现类似的效应，但减速没那么明显，也就是说应用可能愿意用这种减速来换取更少的内存碎片。

注意，一般来说，应用不应该针对某个处理器的物理页面大小调优性能，因为物理页面大小会随硬件变化。上面的建议只适用于虚拟页面大小。

##### 4.1.1.2.1.2 CPU 与 GPU 页表：硬件一致性与软件一致性

具备硬件一致性的系统（例如 NVIDIA Grace Hopper）为 CPU 和 GPU 提供逻辑上合二为一的页表。这一点很重要，因为 GPU 要从设备端访问系统分配的内存时，使用的是 CPU 为请求的内存创建的那个页表项。如果该页表项使用默认的 CPU 页面大小（4KiB 或 64KiB），访问大片虚拟内存区域会导致大量 TLB 未命中，从而显著减速。

另一方面，在 CPU 和 GPU 各自拥有逻辑上独立页表的具备软件一致性的系统上，应该考虑不同的性能调优方面：为了保证一致性，这类系统通常在某个处理器访问映射到另一个处理器物理内存中的内存地址时使用缺页。这样的缺页意味着：

- 必须保证当前拥有该物理页的处理器（物理页当前驻留的处理器）不能再访问该页，具体做法是删除页表项或更新它。
- 必须保证请求访问的处理器能够访问该页，具体做法是创建新的页表项或更新已有页表项，使其有效/激活。
- 支撑该虚拟页的物理页必须移动/迁移到请求访问的处理器：这可能是个昂贵的操作，工作量与页面大小成正比。

总的来说，在 CPU 和 GPU 线程频繁并发访问同一内存页的场景下，具备硬件一致性的系统相比具备软件一致性的系统有显著的性能优势：

- 缺页更少：这些系统不需要用缺页来模拟一致性或迁移内存
- 竞争更少：这些系统以缓存行粒度而非页面粒度保持一致，也就是说，当多个处理器的竞争发生在同一缓存行内时，只交换该缓存行（远小于最小的页面大小）；当不同处理器访问同一页内的不同缓存行时，则不存在竞争。

这影响以下场景的性能：

- CPU 和 GPU 对同一地址的并发原子更新
- CPU 线程向 GPU 线程发信号，或反之

##### 4.1.1.2.1.3 混合硬件与软件一致性

某些具备硬件一致性的系统（例如 NVIDIA DGX Station）也支持安装离散的、非一致性的 GPU 硬件。来自具备硬件一致性的 GPU 的访问继续使用「CPU 与 GPU 页表：硬件一致性与软件一致性」中描述的基于硬件的一致性，而来自离散 GPU 的访问使用基于软件的一致性。

这两类 GPU 之间允许共享统一地址空间。这导致性能和迁移行为因访问的 GPU 而异：具体来说，来自具备软件一致性的 GPU 的访问会有更多缺页和内存迁移，而来自具备硬件一致性的 GPU 的访问缺页更少，并尽可能远程映射。

为了获得最佳性能，两个 GPU 之间的数据共享应该尽量少，或者通过显式拷贝完成。或者可以采取一些措施，例如调用 `cudaMemAdviseSetPreferredLocation`，确保频繁共享的数据物理上驻留在 CPU 或具备一致性的 GPU 内存中，因为默认情况下访问具备软件一致性的内存需要缺页并迁移数据。

在混合一致性系统上，`cudaHostRegister` 和其他主机内存访问 API 对具备软件一致性的 GPU 的行为也会变化。不再使用固定映射（pinned mapping），混合一致性系统上的具备软件一致性的 GPU 使用 CPU 页表的软件镜像。这意味着某些 GPU 访问可能发生缺页，而在非混合一致性系统上不会，不过这种缺页很少见，只会在内存压力下发生。

#### 4.1.1.2.2 主机端对统一内存的直接访问

某些设备具备硬件支持，允许主机端对驻留在 GPU 上的统一内存进行一致的读、写和原子访问。这些设备的属性 `cudaDevAttrDirectManagedMemAccessFromHost` 设为 1。注意，所有具备硬件一致性的系统上，通过 NVLink 连接的设备都设置了该属性。在这些系统上，主机无需缺页和数据迁移就能直接访问驻留在 GPU 上的内存。注意，对于 CUDA 托管内存，需要用位置类型为 `cudaMemLocationTypeHost` 的 `cudaMemAdviseSetAccessedBy` 提示来启用这种无缺页的直接访问，见下面的例子。

**System Allocator（系统分配器）**

```cuda
__global__ void write(int *ret, int a, int b) {
  ret[threadIdx.x] = a + b + threadIdx.x;
}

__global__ void append(int *ret, int a, int b) {
  ret[threadIdx.x] += a + b + threadIdx.x;
}

void test_malloc() {
   int *ret = (int*)malloc(1000 * sizeof(int));
   // 对于共享页表系统，以下提示不是必需的
   cudaMemLocation location = {.type = cudaMemLocationTypeHost};
   cudaMemAdvise(ret, 1000 * sizeof(int), cudaMemAdviseSetAccessedBy, location);

   write<<< 1, 1000 >>>(ret, 10, 100);             // 页面在 GPU 内存中填充
   cudaDeviceSynchronize();
   for(int i = 0; i < 1000; i++)
       printf("%d: A+B = %d\n", i, ret[i]);         // directManagedMemAccessFromHost=1：CPU 直接访问 GPU 内存，无迁移
                                                    // directManagedMemAccessFromHost=0：CPU 缺页并触发设备到主机的迁移

   append<<< 1, 1000 >>>(ret, 10, 100);             // directManagedMemAccessFromHost=1：GPU 访问 GPU 内存，无迁移
   cudaDeviceSynchronize();                         // directManagedMemAccessFromHost=0：GPU 缺页并触发主机到设备的迁移

   free(ret);
}
```

**Managed**

```cuda
__global__ void write(int *ret, int a, int b) {
  ret[threadIdx.x] = a + b + threadIdx.x;
}

__global__ void append(int *ret, int a, int b) {
  ret[threadIdx.x] += a + b + threadIdx.x;
}

void test_managed() {
   int *ret;
   cudaMallocManaged(&ret, 1000 * sizeof(int));
   cudaMemLocation location = {.type = cudaMemLocationTypeHost};
   cudaMemAdvise(ret, 1000 * sizeof(int), cudaMemAdviseSetAccessedBy, location);  // 设置直接访问提示

  write<<< 1, 1000 >>>(ret, 10, 100);             // 页面在 GPU 内存中填充
  cudaDeviceSynchronize();
  for(int i = 0; i < 1000; i++)
      printf("%d: A+B = %d\n", i, ret[i]);         // directManagedMemAccessFromHost=1：CPU 直接访问 GPU 内存，无迁移
                                                   // directManagedMemAccessFromHost=0：CPU 缺页并触发设备到主机的迁移

  append<<< 1, 1000 >>>(ret, 10, 100);             // directManagedMemAccessFromHost=1：GPU 访问 GPU 内存，无迁移
  cudaDeviceSynchronize();                         // directManagedMemAccessFromHost=0：GPU 缺页并触发主机到设备的迁移

  cudaFree(ret);
}
```

write 核函数完成后，`ret` 会在 GPU 内存中创建并初始化。接着 CPU 访问 `ret`，然后 append 核函数再次使用同一块 `ret` 内存。这段代码的行为取决于系统架构和对硬件一致性的支持：

- 在 `directManagedMemAccessFromHost=1` 的设备上：CPU 对托管缓冲区的访问不会触发任何迁移；数据继续驻留在 GPU 内存中，后续 GPU 核函数可以直接访问，不会造成缺页或迁移
- 在 `directManagedMemAccessFromHost=0` 的设备上：CPU 对托管缓冲区的访问会缺页并启动数据迁移；任何 GPU 核函数首次访问同一数据时也会缺页，把页面迁回 GPU 内存

#### 4.1.1.2.3 主机端原生原子操作

某些设备（包括具备硬件一致性的系统上通过 NVLink 连接的设备）支持对驻留在 CPU 上的内存的硬件加速原子访问。这意味着对主机内存的原子访问不需要用缺页来模拟。对于这些设备，属性 `cudaDevAttrHostNativeAtomicSupported` 设为 1。

#### 4.1.1.2.4 原子访问与同步原语

CUDA 统一内存支持主机和设备线程可用的所有原子操作，让所有线程可以通过并发访问同一块共享内存位置来协作。libcu++ 库提供了许多为在主机和设备线程之间并发使用而调优的异构同步原语，包括 `cuda::atomic`、`cuda::atomic_ref`、`cuda::barrier`、`cuda::semaphore` 等。

在具备软件一致性的系统上，不支持设备端对文件映射主机内存的原子访问。下面的示例代码在具备硬件一致性的系统上合法，但在其他系统上是未定义行为：

```cuda
#include <cuda/atomic>

#include <cstdio>
#include <fcntl.h>
#include <sys/mman.h>

#define ERR(msg, ...) { fprintf(stderr, msg, ##__VA_ARGS__); return EXIT_FAILURE; }


__global__ void kernel(int* ptr) {
  cuda::atomic_ref{*ptr}.store(2);
}

int main() {
   // 退出时默认关闭/删除
   FILE* tmp_file = tmpfile64();
   // 需要在文件中分配空间，这里用 posix_fallocate
   int status = posix_fallocate(fileno(tmp_file), 0, 4096);
   if (status != 0) ERR("Failed to allocate space in temp file\n");
   int* ptr = (int*)mmap(NULL, 4096, PROT_READ | PROT_WRITE, MAP_PRIVATE, fileno(tmp_file), 0);

   if (ptr == MAP_FAILED) ERR("Failed to map temp file\n");

    // 初始化文件映射内存中的值
    *ptr = 1;
    printf("Atom value: %d\n", *ptr);

    // 设备和主机线程并发访问 ptr，使用 cuda::atomic_ref
    kernel<<<1, 1>>>(ptr);
    while (cuda::atomic_ref{*ptr}.load() != 2);
    // 这里一定是 2
    printf("Atom value: %d\n", *ptr);

    return EXIT_SUCCESS;
}
```

在具备软件一致性的系统上，对统一内存的原子访问可能引发缺页，导致明显的延迟。注意，这些系统上 GPU 对 CPU 内存的原子操作并非全都如此：`nvidia-smi -q | grep "Atomic Caps Outbound"` 列出的操作可能避免缺页。

在具备硬件一致性的系统上，主机和设备之间的原子操作不需要缺页，但仍可能因其他原因缺页——任何内存访问都可能因这些原因缺页。

#### 4.1.1.2.5 Memcpy()/Memset() 在统一内存上的行为

`cudaMemcpy*()` 和 `cudaMemset*()` 接受任何统一内存指针作为参数。

对于 `cudaMemcpy*()`，指定为 `cudaMemcpyKind` 的方向是一个性能提示；如果任何参数是统一内存指针，这个提示对性能的影响可能更大。

因此建议遵循以下性能建议：

- 当统一内存的物理位置已知时，使用准确的 `cudaMemcpyKind` 提示
- 宁愿用 `cudaMemcpyDefault`，也不要用不准确的 `cudaMemcpyKind` 提示
- 始终使用已填充（初始化）过的缓冲区：避免用这些 API 来初始化内存
- 如果两个指针都指向系统分配的内存，避免使用 `cudaMemcpy*()`：启动核函数，或用 `std::memcpy` 这样的 CPU 内存拷贝算法代替

在具备完整 CUDA 统一内存支持的系统上，可以用多种不同的分配器来分配统一内存。下表概览了几种分配器及其各自的特性。注意本节的所有信息在未来的 CUDA 版本中可能发生变化。

5. GPU 驻留内存的页面大小在未来的 CUDA 版本中可能变化。
6. 目前，迁移到 GPU 的内存或通过 GPU 上的首次触及放置的内存，大页面大小可能无法保持。

在具备硬件一致性的系统上，如果设备内存作为 NUMA 域暴露给系统，可以使用 `numa_alloc_on_node` 等专用分配器把内存固定到给定的 NUMA 节点上（主机或设备）。这种内存可以被主机和设备同时访问，且不会迁移。类似地，`mbind` 可以把内存固定到给定的 NUMA 节点上，并能让文件映射内存在首次被访问前就放在给定的 NUMA 节点上。

以下适用于共享内存的分配器：

- 系统分配器（如 `mmap`）允许用 `MAP_SHARED` 标志在进程间共享内存。CUDA 支持这种做法，可用于在连接到同一主机的不同设备之间共享内存。但目前不支持用它在多个主机之间以及多个设备之间共享内存。详见「统一内存的进程间通信（IPC）」。
- 要在多主机上通过网络访问统一内存或其他 CUDA 内存，请查阅所用通信库的文档，例如 NCCL、NVSHMEM、OpenMPI、UCX 等。

#### 4.1.1.2.7 局部性域与统一内存

不支持对托管内存分配做局部化（localizing）。局部性域（locality domain）不是统一内存迁移的目的地；`cudaMemAllocationTypeManaged` 不能与局部化分配组合使用。需要局部性域放置的应用应该改用局部化的固定内存池或局部化的 VMM 分配。

整体编程模型参见「局部性域」。

#### 4.1.1.2.8 访问计数器迁移

在具备硬件一致性的系统上，访问计数器（access counter）特性跟踪 GPU 访问位于其他处理器上的内存的频率。这是确保内存页移动到最频繁访问这些页面的处理器的物理内存所必需的。它可以指导 CPU 与 GPU 之间以及对等 GPU 之间的迁移，这个过程称为访问计数器迁移。

从 CUDA 12.4 开始，访问计数器支持系统分配内存。注意，文件映射内存不会基于访问迁移。对于系统分配内存，可以用 `cudaMemAdviseSetAccessedBy` 提示（指向对应设备 ID 的设备）来开启访问计数器迁移。如果访问计数器开启，可以用设为 host 的 `cudaMemAdviseSetPreferredLocation` 来阻止迁移。默认情况下 `cudaMallocManaged` 基于缺页并迁移（fault-and-migrate）机制迁移⁷。

驱动也可能用访问计数器来更有效地缓解抖动（thrashing）或内存超额订阅（oversubscription）场景。

⁷ 目前的系统允许在设置了 accessed-by 设备提示时，对托管内存使用访问计数器迁移。这是实现细节，不应依赖它来保证未来的兼容性。

#### 4.1.1.2.9 避免 CPU 频繁写驻留在 GPU 上的内存

如果主机访问统一内存，缓存未命中可能在主机和设备之间引入比预期更多的流量。许多 CPU 架构要求所有内存操作（包括写）都经过缓存层次。如果系统内存驻留在 GPU 上，这意味着 CPU 对这块内存的频繁写可能导致缓存未命中，从而先把数据从 GPU 传到 CPU，再把实际值写入请求的内存范围。在具备软件一致性的系统上，这可能引入额外的缺页；在具备硬件一致性的系统上，可能导致 CPU 操作之间更高的延迟。因此，要与设备共享主机产生的数据，考虑写到驻留在 CPU 上的内存，让设备直接读取这些值。下面的代码展示了如何用统一内存实现这一点。

**System Allocator（系统分配器）**

```cuda
     size_t data_size = sizeof(int);
     int* data = (int*)malloc(data_size);
     // 确保数据保持在主机本地，避免缺页
     cudaMemLocation location = {.type = cudaMemLocationTypeHost};
     cudaMemAdvise(data, data_size, cudaMemAdviseSetPreferredLocation, location);
     cudaMemAdvise(data, data_size, cudaMemAdviseSetAccessedBy, location);

  // 频繁交换小数据：如果 CPU 写驻留在 CPU 的内存，
  // 而 GPU 直接访问该数据，可以避免 CPU 缓存
  // 在写之间数据被逐出时重新加载数据
  for (int i = 0; i < 10; ++i) {
    *data = 42 + i;
    kernel<<<1, 1>>>(data);
    cudaDeviceSynchronize();
    // CPU 缓存可能在这里逐出了数据
  }
  free(data);
```

**Managed**

```cuda
     int* data;
     size_t data_size = sizeof(int);
     cudaMallocManaged(&data, data_size);
     // 确保数据保持在主机本地，避免缺页
     cudaMemLocation location = {.type = cudaMemLocationTypeHost};
     cudaMemAdvise(data, data_size, cudaMemAdviseSetPreferredLocation, location);
     cudaMemAdvise(data, data_size, cudaMemAdviseSetAccessedBy, location);

  // 频繁交换小数据：如果 CPU 写驻留在 CPU 的内存，
  // 而 GPU 直接访问该数据，可以避免 CPU 缓存
  // 在写之间数据被逐出时重新加载数据
  for (int i = 0; i < 10; ++i) {
    *data = 42 + i;
    kernel<<<1, 1>>>(data);
      cudaDeviceSynchronize();
      // CPU 缓存可能在这里逐出了数据
  }
  cudaFree(data);
```


#### 4.1.1.2.10 利用对系统内存的异步访问

如果应用需要把设备端的工作成果与主机共享，有几种可行的选择：

1. 设备把结果写到驻留在 GPU 的内存，用 `cudaMemcpy*` 传输结果，主机读取传输后的数据。
2. 设备把结果直接写到驻留在 CPU 的内存，主机读取该数据。
3. 设备写到驻留在 GPU 的内存，主机直接访问该数据。

如果结果被主机传输/访问的同时能在设备上调度独立的工作，优先选择 1 或 3。如果在主机访问结果之前设备一直处于饥饿状态，可能优先选择 2。这是因为设备通常能以比主机读取更高的带宽写入，除非用很多主机线程来读取数据。

**1. 显式拷贝**

```cuda
void exchange_explicit_copy(cudaStream_t stream) {
  int* data, *host_data;
  size_t n_bytes = sizeof(int) * 16;
  // 分配接收缓冲区
  host_data = (int*)malloc(n_bytes);
  // 分配，因为先在设备端触及，所以会驻留在 GPU
  cudaMallocManaged(&data, n_bytes);
  kernel<<<1, 16, 0, stream>>>(data);
  // 在设备上启动独立工作
  // other_kernel<<<1024, 256, 0, stream>>>(other_data, ...);
  // 传输到主机
  cudaMemcpyAsync(host_data, data, n_bytes, cudaMemcpyDeviceToHost, stream);
  // 同步流，确保数据已传输
  cudaStreamSynchronize(stream);
  // 读取传输后的数据
  printf("Got values %d - %d from GPU\n", host_data[0], host_data[15]);
  cudaFree(data);
  free(host_data);
}
```

**2. 设备直接写**

```cuda
void exchange_device_direct_write(cudaStream_t stream) {
  int* data;
  size_t n_bytes = sizeof(int) * 16;
  // 分配接收缓冲区
  cudaMallocManaged(&data, n_bytes);
  // 确保数据已映射并驻留在主机上
    cudaMemLocation location = {.type = cudaMemLocationTypeHost};
    cudaMemAdvise(data, n_bytes, cudaMemAdviseSetPreferredLocation, location);
    cudaMemAdvise(data, n_bytes, cudaMemAdviseSetAccessedBy, location);
    kernel<<<1, 16, 0, stream>>>(data);
    // 同步流，确保数据已传输
    cudaStreamSynchronize(stream);
    // 读取传输后的数据
    printf("Got values %d - %d from GPU\n", data[0], data[15]);
    cudaFree(data);
}
```

**3. 主机直接读**

```cuda
void exchange_host_direct_read(cudaStream_t stream) {
  int* data;
  size_t n_bytes = sizeof(int) * 16;
  // 分配接收缓冲区
  cudaMallocManaged(&data, n_bytes);
  // 确保数据已映射并驻留在设备上
  cudaMemLocation device_loc = {};
  cudaGetDevice(&device_loc.id);
  device_loc.type = cudaMemLocationTypeDevice;
  cudaMemAdvise(data, n_bytes, cudaMemAdviseSetPreferredLocation, device_loc);
  cudaMemAdvise(data, n_bytes, cudaMemAdviseSetAccessedBy, device_loc);
  kernel<<<1, 16, 0, stream>>>(data);
  // 在 GPU 上启动独立工作
  // other_kernel<<<1024, 256, 0, stream>>>(other_data, ...);
  // 同步流，确保数据可被访问（已由设备写入）
  cudaStreamSynchronize(stream);
  // 直接从主机读取数据
  printf("Got values %d - %d from GPU\n", data[0], data[15]);
  cudaFree(data);
}
```

最后，在上面的「显式拷贝」例子中，可以用主机或设备核函数来显式执行这次传输，代替 `cudaMemcpy*`。对于连续数据，优先用 CUDA 拷贝引擎，因为拷贝引擎执行的操作可以与主机和设备上的工作重叠。`cudaMemcpy*` 和 `cudaMemPrefetchAsync` API 可能使用拷贝引擎，但不能保证 `cudaMemcpy*` API 调用一定使用拷贝引擎。出于同样的原因，数据足够大时显式拷贝优先于主机直接读：如果主机和设备执行的工作都没有让各自的内存系统饱和，传输可以由拷贝引擎与主机和设备的工作并发执行。

拷贝引擎通常既用于主机和设备之间的传输，也用于 NVLink 连接系统内对等设备之间的传输。由于拷贝引擎总数有限，某些系统的 `cudaMemcpy*` 带宽可能低于用设备显式执行传输。在这种情况下，如果传输处在应用的关键路径上，可能优先用基于设备的显式传输。

## 4.1.3 Windows、WSL 与 Tegra 上的统一内存

> 注
>
> 本节只讨论计算能力低于 6.0 的设备或 Windows 平台，即 concurrentManagedAccess 属性为 0 的设备。

计算能力低于 6.0 的设备或 Windows 平台（即 concurrentManagedAccess 属性为 0 的设备，参见《统一内存范式概览》）支持 CUDA 托管内存，但有以下限制：

- 数据迁移与一致性：不支持按需把托管数据细粒度地移动到 GPU。每当启动 GPU 核函数时，一般必须把所有托管内存都传输到 GPU 内存，以避免访问内存时缺页。缺页只支持从 CPU 一侧发起。
- GPU 内存超额订阅：不能分配超过 GPU 物理内存大小的托管内存。
- 一致性与并发：无法同时访问托管内存，因为如果 CPU 在 GPU 核函数活动期间访问统一内存分配，由于缺少 GPU 缺页机制，一致性就无法保证。

### 4.1.3.1 多 GPU

在计算能力低于 6.0 的设备或 Windows 平台上，托管分配通过 GPU 的点对点（P2P）能力自动对系统中的所有 GPU 可见。

托管内存分配的行为类似于用 `cudaMalloc()` 分配的非托管内存：当前活动设备是物理分配的归属设备，但系统中的其他 GPU 会通过 PCIe 总线以较低的带宽访问该内存。

在 Linux 上，只要程序实际使用的所有 GPU 都具备点对点支持，托管内存就分配在 GPU 内存中。如果应用在任何时候开始使用一个 GPU，而它与有托管分配的其他 GPU 之间没有点对点支持，驱动会把所有托管分配迁移到系统内存。这种情况下，所有 GPU 都受 PCIe 带宽限制。

在 Windows 上，如果对等映射不可用（例如架构不同的 GPU 之间），系统会自动回退到使用映射内存，无论程序实际是否使用了两个 GPU。如果实际只用一个 GPU，必须在启动程序前设置 `CUDA_VISIBLE_DEVICES` 环境变量。这会限制可见的 GPU，让托管内存可以分配在 GPU 内存中。

或者，在 Windows 上用户也可以把 `CUDA_MANAGED_FORCE_DEVICE_ALLOC` 设为非零值，强制驱动始终用设备内存做物理存储。当该环境变量设为非零值时，该进程中使用的所有支持托管内存的设备必须彼此点对点兼容。如果使用了支持托管内存的设备，而它与该进程中之前用过的任何其他支持托管内存的设备不点对点兼容，即使对那些设备调用过 `::cudaDeviceReset`，也会返回 `::cudaErrorInvalidDevice` 错误。这些环境变量在「CUDA 环境变量」中有说明。

### 4.1.3.2 一致性与并发

为保证一致性，统一内存编程模型对 CPU 和 GPU 并发执行期间的数据访问加以约束。实际上，GPU 独占所有托管数据，任何核函数操作执行期间 CPU 不允许访问它，无论具体的核函数是否实际使用该数据。并发的 CPU/GPU 访问（即使是访问不同的托管内存分配）会导致段错误，因为该页面被认为对 CPU 不可访问。

例如下面的代码在计算能力 6.x 的设备上运行成功——因为 GPU 缺页能力解除了对同时访问的所有限制——但在 pre-6.x 架构和 Windows 平台上会失败，因为 CPU 触及 `y` 时 GPU 程序核函数仍在活动：

```cuda
__device__ __managed__ int x, y=2;
__global__ void kernel() {
    x = 10;
}
int main() {
    kernel<<< 1, 1 >>>();
    y = 20;            // 在不支持并发访问的 GPU 上报错

     cudaDeviceSynchronize();
     return 0;
}
```

程序必须在访问 `y` 之前显式与 GPU 同步（无论 GPU 核函数实际是否触及 `y`，或任何托管数据）：

```cuda
__device__ __managed__ int x, y=2;
__global__ void kernel() {
    x = 10;
}
int main() {
    kernel<<< 1, 1 >>>();
    cudaDeviceSynchronize();
      y = 20;                  // 在不支持并发访问的 GPU 上成功
      return 0;
}
```

注意，任何逻辑上保证 GPU 完成其工作的函数调用，都可以有效保证 GPU 工作在逻辑上已完成，参见「显式同步」。

注意，如果在 GPU 活动期间用 `cudaMallocManaged()` 或 `cuMemAllocManaged()` 动态分配内存，在启动更多工作或 GPU 同步之前，该内存的行为是未指定的。在此期间尝试在 CPU 上访问该内存可能导致段错误，也可能不会。这不适用于用 `cudaMemAttachHost` 或 `CU_MEM_ATTACH_HOST` 标志分配的内存。

### 4.1.3.3 与流关联的统一内存

CUDA 编程模型提供流（stream）作为机制，让程序表明核函数启动之间的依赖与独立关系。启动到同一流的核函数保证连续执行，而启动到不同流的核函数允许并发执行。参见「CUDA 流」一节。

#### 4.1.3.3.1 流回调

只要 GPU 上没有其他可能访问托管数据的流处于活动状态，CPU 从流回调内部访问托管数据是合法的。此外，后面没有设备工作的回调可用于同步：例如从回调内部给条件变量发信号；否则，CPU 访问只在回调持续期间有效。

有几个重要的注意事项：

1. GPU 活动时，CPU 访问非托管的映射内存数据始终是允许的。
2. 只要 GPU 在运行任何核函数（即使该核函数不使用托管数据），GPU 就被视为活动。如果某个核函数可能使用数据，那么访问是被禁止的。
3. 托管内存的并发 GPU 间访问没有约束，除了适用于非托管内存多 GPU 访问的那些约束。
4. 并发的 GPU 核函数访问托管数据没有约束。

注意最后一点允许 GPU 核函数之间存在竞态，这与目前非托管 GPU 内存的情况一样。从 GPU 的角度看，托管内存函数与非托管内存完全相同。下面的代码示例说明了这些要点：

```cuda
int main() {
    cudaStream_t stream1, stream2;
    cudaStreamCreate(&stream1);
    cudaStreamCreate(&stream2);
    int *non_managed, *managed, *also_managed;
    cudaMallocHost(&non_managed, 4);     // 非托管的、CPU 可访问的内存
    cudaMallocManaged(&managed, 4);
    cudaMallocManaged(&also_managed, 4);
    // 要点 1：CPU 可以访问非托管数据。
    kernel<<< 1, 1, 0, stream1 >>>(managed);
    *non_managed = 1;
    // 要点 2：GPU 忙时 CPU 不能访问任何托管数据，
       //          除非 concurrentManagedAccess = 1
       // 注意我们还没有同步，所以 "kernel" 仍在活动。
       *also_managed = 2;       // 会触发段错误
       // 要点 3：并发的 GPU 核函数可以访问相同的数据。
       kernel<<< 1, 1, 0, stream2 >>>(managed);
       // 要点 4：多 GPU 并发访问也是允许的。
       cudaSetDevice(1);
       kernel<<< 1, 1 >>>(managed);
       return 0;
}
```

#### 4.1.3.3.2 与流关联的托管内存允许更细粒度的控制

统一内存建立在流独立模型之上，允许 CUDA 程序把托管分配显式关联到 CUDA 流。这样，程序员可以根据核函数是否启动到指定的流来表明核函数对数据的使用。这基于程序特定的数据访问模式带来了并发机会。控制该行为的函数是：

```cuda
cudaError_t cudaStreamAttachMemAsync(cudaStream_t stream,
                                     void *ptr,
                                     size_t length=0,
                                     unsigned int flags=0);
```

`cudaStreamAttachMemAsync()` 函数把从 `ptr` 开始的 `length` 字节内存与指定的流关联。这允许 CPU 访问该内存区域，只要流中的所有操作都已完成，无论其他流是否活动。实际上，这把活动 GPU 对托管内存区域的独占所有权约束从整个 GPU 活动收窄为按流活动。最重要的是，如果一个分配没有关联到特定流，它对所有运行中的核函数都可见，无论它们的流是什么。这是 `cudaMallocManaged()` 分配或 `__managed__` 变量的默认可见性；因此有了简单情况的规则：任何核函数运行时 CPU 不得触及数据。

> 注
>
> 把分配关联到特定流，程序就保证了只有启动到该流的核函数会触及该数据。统一内存系统不做错误检查。

> 注
>
> 除了带来更大的并发，`cudaStreamAttachMemAsync()` 的使用还能在统一内存系统内启用数据传输优化，可能影响延迟和其他开销。

下面的例子展示了如何把 `y` 显式关联为对主机可访问，从而让 CPU 始终可以访问。（注意核函数调用后没有 `cudaDeviceSynchronize()`。）运行中的核函数访问 `y` 将产生未定义的结果。

```cuda
__device__ __managed__ int x, y=2;
__global__ void kernel() {
    x = 10;
}
int main() {
    cudaStream_t stream1;
    cudaStreamCreate(&stream1);
    cudaStreamAttachMemAsync(stream1, &y, 0, cudaMemAttachHost);
    cudaDeviceSynchronize();          // 等待主机关联生效。
    kernel<<< 1, 1, 0, stream1 >>>(); // 注意：启动到 stream1。
    y = 20;                           // 成功——有核函数在运行，但 "y"
                                      // 没有关联到任何流。
    return 0;
}
```

#### 4.1.3.3.3 多线程主机程序的更详细示例

`cudaStreamAttachMemAsync()` 的主要用途是用 CPU 线程实现独立的任务并行。通常在这样的程序中，CPU 线程为它生成的所有工作创建自己的流，因为用 CUDA 的 NULL 流会在线程之间产生依赖。托管数据对任何 GPU 流的默认全局可见性，可能让多线程程序中 CPU 线程之间的干扰难以避免。因此用 `cudaStreamAttachMemAsync()` 把线程的托管分配关联到线程自己的流，关联通常在线程的生命周期内不再改变。这样的程序只需加一次 `cudaStreamAttachMemAsync()` 调用，就能用统一内存做数据访问：

```cuda
// 此函数在自己的私有流中执行某个任务，可并行运行

void run_task(int *in, int *out, int length) {
     // 创建一个供我们使用的流。
     cudaStream_t stream;
     cudaStreamCreate(&stream);
     // 分配一些托管数据，并关联到我们的流。
     // 注意对 cudaMallocManaged() 使用了 host-attach 标志；
     // 然后我们把该分配关联到我们的流，
     // 这样我们的 GPU 核函数启动就能访问它。
     int *data;
     cudaMallocManaged((void **)&data, length, cudaMemAttachHost);
     cudaStreamAttachMemAsync(stream, data);
     cudaStreamSynchronize(stream);
     // 用某种方式迭代数据，同时使用主机和设备。
     for(int i=0; i<N; i++) {
         transform<<< 100, 256, 0, stream >>>(in, data, length);
         cudaStreamSynchronize(stream);
         host_process(data, length);     // CPU 使用托管数据。
         convert<<< 100, 256, 0, stream >>>(out, data, length);
     }
     cudaStreamSynchronize(stream);
     cudaStreamDestroy(stream);
     cudaFree(data);
}
```

在这个例子中，分配与流的关联只建立一次，然后主机和设备反复使用数据。结果是代码比在主机和设备之间显式拷贝数据简单得多，但结果相同。

函数 `cudaMallocManaged()` 指定了 `cudaMemAttachHost` 标志，它创建的分配初始对设备端执行不可见。（默认分配对所有流上的所有 GPU 核函数都可见。）这确保了在数据分配和为特定流获取数据之间的时间窗口内，不会与其他线程的执行发生意外交互。

没有这个标志，如果另一个线程启动的核函数碰巧正在运行，新分配会被认为在 GPU 上处于使用中。这可能影响线程在把新分配的数据显式关联到私有流之前从 CPU 访问它的能力。因此，为了实现线程之间的安全独立，分配时应该指定这个标志。

另一种做法是在分配关联到流之后，在所有线程之间放置一个进程范围的屏障。这会确保所有线程在启动任何核函数之前完成数据/流关联，避免这种冒险。流销毁前还需要第二个屏障，因为流销毁会使分配恢复默认可见性。`cudaMemAttachHost` 标志的存在既是为了简化这个过程，也是因为并不总能把全局屏障插到需要的位置。

#### 4.1.3.3.4 与流关联的统一内存的数据移动

在 `concurrentManagedAccess` 未设置的设备上，用与流关联的统一内存做 `Memcpy()`/`Memset()` 的行为不同，适用以下规则：

如果指定了 `cudaMemcpyHostTo*` 且源数据是统一内存，那么如果它在拷贝流中能被主机一致访问，就从主机访问（1）；否则从设备访问。如果指定了 `cudaMemcpy*ToHost` 且目标是统一内存，对目标适用类似的规则。

如果指定了 `cudaMemcpyDeviceTo*` 且源数据是统一内存，那么从设备访问。源必须在拷贝流中能被设备一致访问（2）；否则返回错误。如果指定了 `cudaMemcpy*ToDevice` 且目标是统一内存，对目标适用类似的规则。

如果指定了 `cudaMemcpyDefault`，那么在以下情况下统一内存从主机访问：它在拷贝流中不能被设备一致访问（2），或者数据的首选位置是 `cudaCpuDeviceId` 且它在拷贝流中能被主机一致访问（1）；否则从设备访问。

对统一内存使用 `cudaMemset*()` 时，数据必须在用于 `cudaMemset()` 操作的流中能被设备一致访问（2）；否则返回错误。

当 `cudaMemcpy*` 或 `cudaMemset*` 从设备访问数据时，操作流被认为在 GPU 上处于活动。在此期间，CPU 访问与该流关联的数据或全局可见的数据，如果 GPU 的 `concurrentManagedAccess` 设备属性值为 0，会导致段错误。程序必须做适当的同步，确保操作完成后再从 CPU 访问任何关联的数据。

1. 在给定流中能被主机一致访问，意味着该内存既没有全局可见性，也没有关联到给定流。
2. 在给定流中能被设备一致访问，意味着该内存要么有全局可见性，要么关联到给定流。


## 4.1.4 性能提示

性能提示（performance hint）让程序员可以向 CUDA 提供关于统一内存用法的更多信息。CUDA 用性能提示更高效地管理托管内存、提升应用性能。性能提示永远不影响应用的正确性，只影响性能。

> 注
>
> 应用只应在性能提示确实提升性能时才使用统一内存性能提示。

性能提示可用于任何统一内存分配，包括 CUDA 托管内存。在具备完整 CUDA 统一内存支持的系统上，性能提示可以应用于所有系统分配的内存。

### 4.1.4.1 数据预取

`cudaMemPrefetchAsync` API 是一个异步的流有序 API，可以把数据迁移到更接近指定处理器的位置。数据在预取过程中仍可被访问。迁移在流中所有先前的操作完成后才开始，并在流中任何后续操作之前完成。

```cuda
cudaError_t cudaMemPrefetchAsync(const void *devPtr,
                                 size_t count,
                                 struct cudaMemLocation location,
                                 unsigned int flags,
                                 cudaStream_t stream=0);
```

当预取任务在给定流中执行时，`[devPtr, devPtr + count)` 范围内的内存区域可能被迁移：如果 `location.type` 为 `cudaMemLocationTypeDevice`，迁移到目标设备 `location.id`；如果 `location.type` 为 `cudaMemLocationTypeHost`，迁移到 CPU。关于 `flags` 的细节，参见当前的 CUDA Runtime API 文档。

考虑下面这个简单的代码示例：

**System Allocator（系统分配器）**

```cuda
void test_prefetch_sam(const cudaStream_t& s) {
   // 在 CPU 上初始化数据
   char *data = (char*)malloc(dataSizeBytes);
   init_data(data, dataSizeBytes);
   cudaMemLocation location = {.type = cudaMemLocationTypeDevice, .id = myGpuId};


  // 鼓励数据在使用前移动到 GPU
  const unsigned int flags = 0;
  cudaMemPrefetchAsync(data, dataSizeBytes, location, flags, s);

  // 在 GPU 上使用数据
  const unsigned num_blocks = (dataSizeBytes + threadsPerBlock - 1) / threadsPerBlock;

  mykernel<<<num_blocks, threadsPerBlock, 0, s>>>(data, dataSizeBytes);

    // 鼓励数据移回 CPU
    location = {.type = cudaMemLocationTypeHost};
    cudaMemPrefetchAsync(data, dataSizeBytes, location, flags, s);

    cudaStreamSynchronize(s);

    // 在 CPU 上使用数据
    use_data(data, dataSizeBytes);
    free(data);
}
```

**Managed**

```cuda
void test_prefetch_managed(const cudaStream_t& s) {
   // 在 CPU 上初始化数据
   char *data;
   cudaMallocManaged(&data, dataSizeBytes);
   init_data(data, dataSizeBytes);
   cudaMemLocation location = {.type = cudaMemLocationTypeDevice, .id = myGpuId};


    // 鼓励数据在使用前移动到 GPU
    const unsigned int flags = 0;
    cudaMemPrefetchAsync(data, dataSizeBytes, location, flags, s);

  // 在 GPU 上使用数据
    const unsigned num_blocks = (dataSizeBytes + threadsPerBlock - 1) / threadsPerBlock;

  mykernel<<<num_blocks, threadsPerBlock, 0, s>>>(data, dataSizeBytes);

    // 鼓励数据移回 CPU
    location = {.type = cudaMemLocationTypeHost};
    cudaMemPrefetchAsync(data, dataSizeBytes, location, flags, s);

    cudaStreamSynchronize(s);

    // 在 CPU 上使用数据
    use_data(data, dataSizeBytes);
    cudaFree(data);
}
```

### 4.1.4.2 数据用法提示

当多个处理器同时访问同一数据时，可以用 `cudaMemAdvise` 提示 `[devPtr, devPtr + count)` 处的数据将被如何访问：

```cuda
cudaError_t cudaMemAdvise(const void *devPtr,
                          size_t count,
                          enum cudaMemoryAdvise advice,
                          struct cudaMemLocation location);
```

`advice` 可取以下值：

- `cudaMemAdviseSetReadMostly`：
  这表示该数据主要会被读、偶尔被写。一般来说，它允许用该区域的写带宽换取读带宽。
- `cudaMemAdviseSetPreferredLocation`：
  该提示把数据的首选位置设为指定设备的物理内存。该提示鼓励系统把数据保留在首选位置，但不保证。把 `cudaMemLocationTypeHost` 传入 `location.type`，则把首选位置设为 CPU 内存。其他提示（如 `cudaMemPrefetchAsync`）可能覆盖该提示，让内存迁离首选位置。
- `cudaMemAdviseSetAccessedBy`：
  在某些系统上，在从给定处理器访问数据之前先建立到内存的映射，可能对性能有益。该提示告诉系统：当 `location.type` 为 `cudaMemLocationTypeDevice` 时，`location.id` 会频繁访问该数据，让系统可以假定创建这些映射是划算的。该提示不表示数据应该驻留在哪里，但可以与 `cudaMemAdviseSetPreferredLocation` 组合来指定。在具备硬件一致性的系统上，该提示会开启访问计数器迁移，参见「访问计数器迁移」。

每种 advice 也可以用以下值取消设置：`cudaMemAdviseUnsetReadMostly`、`cudaMemAdviseUnsetPreferredLocation` 和 `cudaMemAdviseUnsetAccessedBy`。

下面的例子展示了如何使用 `cudaMemAdvise`：

**System Allocator（系统分配器）**

```cuda
void test_advise_sam(cudaStream_t stream) {
  char *dataPtr;
  size_t dataSize = 64 * threadsPerBlock; // 16 KiB

    // 用 malloc 或 cudaMallocManaged 分配内存
    dataPtr = (char*)malloc(dataSize);

    // 在该内存区域上设置建议
    cudaMemLocation loc = {.type = cudaMemLocationTypeDevice, .id = myGpuId};
    cudaMemAdvise(dataPtr, dataSize, cudaMemAdviseSetReadMostly, loc);

    int outerLoopIter = 0;
    while (outerLoopIter < maxOuterLoopIter) {
      // 每个外层循环迭代都由 CPU 写入数据
      init_data(dataPtr, dataSize);

      // 通过预取让所有 GPU 都能访问数据。
      // 这里的预取导致数据的读复制，
      // 而不是数据迁移
      cudaMemLocation location;
      location.type = cudaMemLocationTypeDevice;
      for (int device = 0; device < maxDevices; device++) {
        location.id = device;
        const unsigned int flags = 0;
        cudaMemPrefetchAsync(dataPtr, dataSize, location, flags, stream);
      }

    // 核函数在内层循环中只读该数据
    int innerLoopIter = 0;
    while (innerLoopIter < maxInnerLoopIter) {
      mykernel<<<32, threadsPerBlock, 0, stream>>>((const char *)dataPtr, dataSize);

      innerLoopIter++;
    }
    outerLoopIter++;
  }

    free(dataPtr);
}
```

**Managed**

### 4.1.4.3 内存丢弃

`cudaMemDiscardBatchAsync` API 让应用可以告诉 CUDA 运行时：指定内存范围的内容不再有用。统一内存驱动会因为基于缺页的迁移或内存逐出（以支持设备内存超额订阅）而执行自动内存传输。这些自动内存传输有时是多余的，会严重降低性能。把地址范围标记为「丢弃」会告诉统一内存驱动：应用已经消费了该范围内的内容，在预取或页面逐出（为给其他分配腾出空间）时无需迁移这些数据。读一个被丢弃的页，如果之后没有写访问或预取，会得到不确定的值。而丢弃操作之后的任何新写，保证能被后续的读访问看到。对正在丢弃的地址范围的并发访问或预取会导致未定义行为。

```cuda
cudaError_t cudaMemDiscardBatchAsync(void **dptrs,
                                    size_t *sizes,
                                    size_t count,
                                    unsigned long long flags,
                                    cudaStream_t stream);
```

该函数对 `dptrs` 和 `sizes` 数组指定的地址范围执行一批内存丢弃。两个数组的长度必须都等于 `count`。每个内存范围必须引用通过 `cudaMallocManaged` 分配或用 `__managed__` 变量声明的托管内存。

`cudaMemDiscardAndPrefetchBatchAsync` API 把丢弃和预取操作合二为一。调用 `cudaMemDiscardAndPrefetchBatchAsync` 在语义上等价于先调用 `cudaMemDiscardBatchAsync` 再调用 `cudaMemPrefetchBatchAsync`，但更优。当应用需要内存位于目标位置但不需要内存的内容时，这很有用。

```cuda
cudaError_t cudaMemDiscardAndPrefetchBatchAsync(void **dptrs,
                                               size_t *sizes,
                                               size_t count,
                                               struct cudaMemLocation *prefetchLocs,
                                               size_t *prefetchLocIdxs,
                                               size_t numPrefetchLocs,
                                               unsigned long long flags,
                                               cudaStream_t stream);
```

`prefetchLocs` 数组指定预取的目的地，`prefetchLocIdxs` 表示每个预取位置适用于哪些操作。例如，如果一批有 10 个操作，前 6 个要预取到一个位置、后 4 个预取到另一个位置，那么 `numPrefetchLocs` 为 2，`prefetchLocIdxs` 为 {0, 6}，`prefetchLocs` 包含两个目标位置。

重要注意事项：

- 读一个被丢弃的范围，如果之后没有写或预取，会返回不确定的值
- 丢弃操作可以通过向该范围写或用 `cudaMemPrefetchAsync` 预取它来撤销
- 与丢弃操作同时发生的任何读、写或预取都会导致未定义行为
- 所有设备的 `cudaDevAttrConcurrentManagedAccess` 必须为非零值

### 4.1.4.4 查询托管内存上的数据用法属性

程序可以用以下 API 查询通过 `cudaMemAdvise` 或 `cudaMemPrefetchAsync` 赋给 CUDA 托管内存的内存范围属性：

```cuda
cudaMemRangeGetAttribute(void *data,
                         size_t dataSize,
                         enum cudaMemRangeAttribute attribute,
                         const void *devPtr,
                         size_t count);
```

该函数查询从 `devPtr` 开始、大小为 `count` 字节的内存范围的属性。该内存范围必须引用通过 `cudaMallocManaged` 分配或用 `__managed__` 变量声明的托管内存。可以查询以下属性：

- `cudaMemRangeAttributeReadMostly`：如果整个内存范围设置了 `cudaMemAdviseSetReadMostly` 属性，返回 1，否则返回 0。
- `cudaMemRangeAttributePreferredLocation`：如果整个内存范围以相应的处理器为首选位置，返回的结果是 GPU 设备 ID 或 `cudaCpuDeviceId`，否则返回 `cudaInvalidDeviceId`。应用可以用这个查询 API 根据托管指针的首选位置属性，决定经由 CPU 还是 GPU 做数据中转。注意，查询时内存范围的实际位置可能与首选位置不同。
- `cudaMemRangeAttributeAccessedBy`：返回对该内存范围设置了该建议的设备列表。
- `cudaMemRangeAttributeLastPrefetchLocation`：返回用 `cudaMemPrefetchAsync` 显式预取该内存范围的最后一个位置。注意，这只是返回应用请求把该内存范围预取到的最后一个位置，不表示到该位置的预取操作已完成甚至已开始。
- `cudaMemRangeAttributePreferredLocationType`：返回首选位置的位置类型，取值如下：
  - `cudaMemLocationTypeDevice`：如果内存范围内的所有页面以同一个 GPU 为首选位置
  - `cudaMemLocationTypeHost`：如果内存范围内的所有页面以 CPU 为首选位置
  - `cudaMemLocationTypeHostNuma`：如果内存范围内的所有页面以同一个主机 NUMA 节点 ID 为首选位置
  - `cudaMemLocationTypeInvalid`：如果所有页面没有相同的首选位置，或者某些页面根本没有首选位置
- `cudaMemRangeAttributePreferredLocationId`：如果对同一地址范围的 `cudaMemRangeAttributePreferredLocationType` 查询返回 `cudaMemLocationTypeDevice`，返回设备序号；如果首选位置类型是主机 NUMA 节点，返回主机 NUMA 节点 ID；否则忽略该 ID。
- `cudaMemRangeAttributeLastPrefetchLocationType`：返回内存范围内所有页面用 `cudaMemPrefetchAsync` 显式预取的最后一个位置类型，取值如下：
  - `cudaMemLocationTypeDevice`：如果内存范围内的所有页面都被预取到同一个 GPU
  - `cudaMemLocationTypeHost`：如果内存范围内的所有页面都被预取到 CPU
  - `cudaMemLocationTypeHostNuma`：如果内存范围内的所有页面都被预取到同一个主机 NUMA 节点 ID
  - `cudaMemLocationTypeInvalid`：如果所有页面没有被预取到同一位置，或者某些页面从未被预取过
- `cudaMemRangeAttributeLastPrefetchLocationId`：如果对同一地址范围的 `cudaMemRangeAttributeLastPrefetchLocationType` 查询返回 `cudaMemLocationTypeDevice`，返回有效的设备序号；如果返回 `cudaMemLocationTypeHostNuma`，返回有效的主机 NUMA 节点 ID；否则忽略该 ID。

此外，可以用相应的 `cudaMemRangeGetAttributes` 函数查询多个属性。

### 4.1.4.5 GPU 内存超额订阅

统一内存让应用可以超额订阅（oversubscription）任何单个处理器的内存：换句话说，它们可以分配和共享比系统中任何单个处理器的内存容量都大的数组，从而实现（包括但不限于）不适配单个 GPU 的数据集的核外（out-of-core）处理，而无需给编程模型增加太多复杂性。
