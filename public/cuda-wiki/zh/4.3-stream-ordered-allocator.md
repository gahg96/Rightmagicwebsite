# 4.3 流式内存分配器

## 4.3.1 简介

使用 `cudaMalloc` 和 `cudaFree` 管理内存分配会导致 GPU 在所有正在执行的 CUDA 流之间同步。流式内存分配器（stream-ordered memory allocator）允许应用程序将内存分配和释放与其他启动到 CUDA 流中的工作（如核函数启动和异步拷贝）进行排序。这种做法利用流排序语义重用内存分配，从而改善应用程序的内存使用。该分配器还允许应用程序控制分配器的内存缓存行为。当设置了合适的释放阈值（release threshold）时，缓存行为可以让分配器避免在应用程序愿意接受更大内存占用时产生昂贵的 OS 调用。该分配器还支持在进程之间轻松、安全地共享分配。

流式内存分配器：

- 减少了对自定义内存管理抽象的需求，也让需要它的应用程序更容易创建高性能的自定义内存管理。
- 使多个库能够共享一个由驱动管理的公共内存池（pool），从而减少多余的内存消耗。
- 让驱动能够基于其对分配器和其他流管理 API 的感知来执行优化。

注意：自 CUDA 11.3 起，Nsight Compute 和新一代 CUDA 调试器已支持该分配器。

## 4.3.2 内存管理

`cudaMallocAsync` 和 `cudaFreeAsync` 是实现流式内存管理的 API。`cudaMallocAsync` 返回一个分配，`cudaFreeAsync` 释放一个分配。两个 API 都接受流参数，以定义分配何时可用、何时停止可用。这些函数允许内存操作绑定到特定的 CUDA 流，使它们无需阻塞主机端或其他流即可执行。通过避免代价高昂的 `cudaMalloc` 与 `cudaFree` 同步，可以提升应用程序性能。

这些 API 还可以通过内存池进一步优化性能：内存池管理和重用大块内存，使分配和释放更高效。内存池有助于减少开销、防止碎片化，在频繁进行内存分配操作的场景中提升性能。

### 4.3.2.1 分配内存

`cudaMallocAsync` 函数在 GPU 上触发与特定 CUDA 流关联的异步内存分配。`cudaMallocAsync` 允许内存分配在不妨碍主机端或其他流的情况下进行，从而消除昂贵的同步需求。

注意：`cudaMallocAsync` 在确定分配驻留位置时忽略当前设备/上下文，而是根据指定的内存池或提供的流来确定合适的设备。

下面的列表展示了一个基本的使用模式：在同一个流中分配内存、使用内存，然后释放回该流。

```cpp
void *ptr;
size_t size = 512;
cudaMallocAsync(&ptr, size, cudaStreamPerThread);
// 使用该分配执行工作
kernel<<<..., cudaStreamPerThread>>>(ptr, ...);
// 可以指定异步释放，无需同步 CPU 与 GPU
cudaFreeAsync(ptr, cudaStreamPerThread);
```

注意：当从分配流之外的流访问分配时，用户必须保证访问发生在分配操作之后，否则行为未定义。

### 4.3.2.2 释放内存

`cudaFreeAsync()` 以流排序的方式异步释放设备内存：内存释放被指派到特定的 CUDA 流，不会阻塞主机端或其他流。

用户必须保证释放操作发生在分配操作和对该分配的所有使用之后。在释放操作开始后对该分配的任何使用都会导致未定义行为。

应当使用事件和/或流同步操作，保证其他流对该分配的所有访问都在释放操作开始前完成，如下例所示。

```cpp
cudaMallocAsync(&ptr, size, stream1);
cudaEventRecord(event1, stream1);
// stream2 必须等待分配就绪后才能访问
cudaStreamWaitEvent(stream2, event1);
kernel<<<..., stream2>>>(ptr, ...);
cudaEventRecord(event2, stream2);
// stream3 必须等待 stream2 完成对该分配的访问后
// 才能释放该分配
cudaStreamWaitEvent(stream3, event2);
cudaFreeAsync(ptr, stream3);
```

用 `cudaMalloc()` 分配的内存可以用 `cudaFreeAsync()` 释放。同上，对该内存的所有访问必须在释放操作开始前完成。

```cpp
cudaMalloc(&ptr, size);
kernel<<<..., stream>>>(ptr, ...);
cudaFreeAsync(ptr, stream);
```

同样，用 `cudaMallocAsync` 分配的内存可以用 `cudaFree()` 释放。当通过 `cudaFree()` API 释放这类分配时，驱动假设对该分配的所有访问都已完成，不再执行额外的同步。用户可以使用 `cudaStreamQuery` / `cudaStreamSynchronize` / `cudaEventQuery` / `cudaEventSynchronize` / `cudaDeviceSynchronize` 来保证相应的异步工作已完成，且 GPU 不会再访问该分配。

```cpp
cudaMallocAsync(&ptr, size, stream);
kernel<<<..., stream>>>(ptr, ...);
// 需要同步以避免过早释放内存
cudaStreamSynchronize(stream);
cudaFree(ptr);
```

## 4.3.3 内存池

内存池封装了虚拟地址和物理内存资源，这些资源根据内存池的属性和特性进行分配和管理。内存池的主要特征是它所管理内存的种类和位置。

所有 `cudaMallocAsync` 调用都使用内存池中的资源。如果未指定内存池，`cudaMallocAsync` 使用所提供流所属设备的当前内存池。设备的当前内存池可以用 `cudaDeviceSetMempool` 设置，用 `cudaDeviceGetMempool` 查询。每个设备都有一个默认内存池，在未调用 `cudaDeviceSetMempool` 时处于活动状态。

`cudaMallocFromPoolAsync` API 和 `cudaMallocAsync` 的 C++ 重载允许用户指定用于分配的内存池，而无需将其设为当前内存池。`cudaDeviceGetDefaultMempool` 和 `cudaMemPoolCreate` API 返回内存池句柄。`cudaMemPoolSetAttribute` 和 `cudaMemPoolGetAttribute` 控制内存池的属性。

注意：设备的当前内存池是该设备本地的。因此，在未指定内存池的情况下分配，得到的分配始终位于该流所属设备本地。

### 4.3.3.1 默认/隐式内存池

调用 `cudaDeviceGetDefaultMempool` 可获取设备的默认内存池。来自设备默认内存池的分配是位于该设备上的不可迁移设备分配，这些分配始终可从该设备访问。默认内存池的可访问性可以用 `cudaMemPoolSetAccess` 修改，用 `cudaMemPoolGetAccess` 查询。由于默认内存池不需要显式创建，它们有时被称为隐式内存池（implicit pools）。设备的默认内存池不支持 IPC。

### 4.3.3.2 显式内存池

`cudaMemPoolCreate` 创建显式内存池。这允许应用程序为其分配请求超出默认/隐式内存池所能提供的属性，例如 IPC 能力、最大内存池大小、在受支持平台上驻留于特定 CPU NUMA 节点的分配等。

```cpp
// 在设备 0 上创建一个类似隐式内存池的内存池
int device = 0;
cudaMemPoolProps poolProps = { };
poolProps.allocType = cudaMemAllocationTypePinned;
poolProps.location.id = device;
poolProps.location.type = cudaMemLocationTypeDevice;

cudaMemPoolCreate(&memPool, &poolProps));
```

下面的代码片段展示了在一个有效的 CPU NUMA 节点上创建支持 IPC 的内存池的示例。

```cpp
// 创建一个驻留在 CPU NUMA 节点上、支持 IPC 共享（通过文件描述符）的内存池
int cpu_numa_id = 0;
cudaMemPoolProps poolProps = { };
poolProps.allocType = cudaMemAllocationTypePinned;
poolProps.location.id = cpu_numa_id;
poolProps.location.type = cudaMemLocationTypeHostNuma;
poolProps.handleType = cudaMemHandleTypePosixFileDescriptor;

cudaMemPoolCreate(&ipcMemPool, &poolProps));
```

### 4.3.3.3 多 GPU 支持的设备可访问性

与通过虚拟内存管理 API 控制的分配可访问性一样，内存池分配的可访问性不遵循 `cudaDeviceEnablePeerAccess` 或 `cuCtxEnablePeerAccess`。对于内存池，`cudaMemPoolSetAccess` API 修改哪些设备可以访问来自该内存池的分配。默认情况下，分配只能从其所在的设备访问，该访问权限不可撤销。要允许其他设备访问，访问设备必须与内存池所在设备具备点对点（P2P）能力。可以用 `cudaDeviceCanAccessPeer` 验证这一点。

如果未检查点对点能力，设置访问权限可能会失败并返回 `cudaErrorInvalidDevice`。但是，如果尚未从该内存池进行过任何分配，即使设备不具备点对点能力，`cudaMemPoolSetAccess` 调用也可能成功。在这种情况下，下一次从该内存池的分配将会失败。

值得注意的是，`cudaMemPoolSetAccess` 会影响来自该内存池的所有分配，而不仅仅是未来的分配。同样，`cudaMemPoolGetAccess` 报告的可访问性适用于该内存池的所有分配，而不仅仅是未来的分配。不建议频繁更改给定 GPU 的内存池可访问性设置。也就是说，一旦某个内存池可从某个 GPU 访问，在该内存池的整个生命周期内都应保持可访问。

```cpp
// 展示 cudaMemPoolSetAccess 用法的代码片段：
cudaError_t setAccessOnDevice(cudaMemPool_t memPool, int residentDevice,
              int accessingDevice) {
    cudaMemAccessDesc accessDesc = {};
    accessDesc.location.type = cudaMemLocationTypeDevice;
    accessDesc.location.id = accessingDevice;
    accessDesc.flags = cudaMemAccessFlagsProtReadWrite;

      int canAccess = 0;
      cudaError_t error = cudaDeviceCanAccessPeer(&canAccess, accessingDevice,
                residentDevice);
      if (error != cudaSuccess) {
          return error;
      } else if (canAccess == 0) {
          return cudaErrorPeerAccessUnsupported;
      }

      // 使地址可访问
      return cudaMemPoolSetAccess(memPool, &accessDesc, 1);
}
```

### 4.3.3.4 为 IPC 启用内存池

内存池可以启用进程间通信（IPC），以便在进程之间轻松、高效、安全地共享 GPU 内存。CUDA 的 IPC 内存池提供与 CUDA 虚拟内存管理 API 相同的安全保障。

使用内存池在进程之间共享内存分为两步：进程首先共享对内存池的访问，然后共享该内存池中的具体分配。第一步建立并强制执行安全策略；第二步协调每个进程中使用的虚拟地址，以及导入进程中映射何时需要有效。

#### 4.3.3.4.1 创建并共享 IPC 内存池

共享对内存池的访问包括：用 `cudaMemPoolExportToShareableHandle()` 获取内存池的 OS 原生句柄，用 OS 原生的 IPC 机制将句柄传递给导入进程，再用 `cudaMemPoolImportFromShareableHandle()` API 创建导入的内存池。要使 `cudaMemPoolExportToShareableHandle` 成功，内存池必须在创建时于内存池属性结构体中指定了请求的句柄类型。请参考示例中在进程之间传递 OS 原生句柄的合适 IPC 机制。其余步骤见以下代码片段。

```cpp
// 在导出进程中
// 在设备 0 上创建一个可导出的、支持 IPC 的内存池
cudaMemPoolProps poolProps = { };
poolProps.allocType = cudaMemAllocationTypePinned;
poolProps.location.id = 0;
poolProps.location.type = cudaMemLocationTypeDevice;

// 将 handleTypes 设为非零值将使内存池可导出（支持 IPC）
poolProps.handleTypes = CU_MEM_HANDLE_TYPE_POSIX_FILE_DESCRIPTOR;

cudaMemPoolCreate(&memPool, &poolProps));

// 基于 FD 的句柄是整数类型
int fdHandle = 0;

// 获取内存池的 OS 原生句柄。
// 注意这里传递的是指向句柄内存的指针。
cudaMemPoolExportToShareableHandle(&fdHandle,
             memPool,
             CU_MEM_HANDLE_TYPE_POSIX_FILE_DESCRIPTOR,
             0);

// 必须使用合适的 OS 特定 API 将句柄发送到导入进程。

// 在导入进程中
int fdHandle;
// 需要使用合适的 OS 特定 API 从导出进程获取句柄。
// 从可共享句柄创建导入的内存池。
// 注意这里句柄是按值传递的。
cudaMemPoolImportFromShareableHandle(&importedMemPool,
          (void*)fdHandle,
          CU_MEM_HANDLE_TYPE_POSIX_FILE_DESCRIPTOR,
          0);
```

#### 4.3.3.4.2 在导入进程中设置访问权限

导入的内存池初始只能从其驻留设备访问。导入的内存池不会继承导出进程设置的任何可访问性。导入进程需要用 `cudaMemPoolSetAccess` 为计划访问该内存的每个 GPU 启用访问。如果导入的内存池属于导入进程不可见的设备，用户必须使用 `cudaMemPoolSetAccess` API 为将使用这些分配的 GPU 启用访问。（参见"多 GPU 支持的设备可访问性"。）

#### 4.3.3.4.3 从导出的内存池创建并共享分配

内存池共享后，在导出进程中用 `cudaMallocAsync()` 从该内存池进行的分配可以共享给已导入该内存池的进程。由于内存池的安全策略在内存池层面建立并验证，OS 无需额外的簿记来为具体的内存池分配提供安全保障。换句话说，导入内存池分配所需的不透明 `cudaMemPoolPtrExportData` 可以用任意机制发送到导入进程。

虽然导出和导入分配无需以任何方式与分配流同步，但导入进程在访问分配时必须遵循与导出进程相同的规则。具体来说，对分配的访问必须发生在分配流中分配操作执行之后。以下两个代码片段展示了用 `cudaMemPoolExportPointer()` 和 `cudaMemPoolImportPointer()` 共享分配，并使用一个 IPC 事件保证在分配就绪前导入进程不会访问该分配。

```cpp
// 在导出进程中准备分配
cudaMemPoolPtrExportData exportData;
cudaEvent_t readyIpcEvent;
cudaIpcEventHandle_t readyIpcEventHandle;

// 用于进程间协调的 IPC 事件
// cudaEventInterprocess 标志使事件成为 IPC 事件
// 出于性能考虑设置 cudaEventDisableTiming

cudaEventCreate(&readyIpcEvent, cudaEventDisableTiming |
              cudaEventInterprocess)

// 从导出的内存池分配
cudaMallocAsync(&ptr, size, exportMemPool, stream);

// 事件用于通知分配何时就绪
cudaEventRecord(readyIpcEvent, stream);
cudaMemPoolExportPointer(&exportData, ptr);
cudaIpcGetEventHandle(&readyIpcEventHandle, readyIpcEvent);

// 使用任意机制与导入进程共享 IPC 事件和指针导出数据。
// 这里将数据复制到共享内存中
shmem->ptrData = exportData;
shmem->readyIpcEventHandle = readyIpcEventHandle;
// 通知消费者数据已就绪

// 导入分配
cudaMemPoolPtrExportData *importData = &shmem->prtData;
cudaEvent_t readyIpcEvent;
cudaIpcEventHandle_t *readyIpcEventHandle = &shmem->readyIpcEventHandle;

// 需要使用任意机制（这里使用共享内存）从导出进程获取 IPC 事件句柄和导出数据，
// 只需要同步保证共享内存已被填好。

cudaIpcOpenEventHandle(&readyIpcEvent, readyIpcEventHandle);

// 导入分配。该操作不会阻塞等待分配就绪。
cudaMemPoolImportPointer(&ptr, importedMemPool, importData);

// 在导入进程中使用该分配之前，等待分配流中的先前流操作完成。
cudaStreamWaitEvent(stream, readyIpcEvent);
kernel<<<..., stream>>>(ptr, ...);
```

释放分配时，分配必须先在导入进程中释放，然后才能在导出进程中释放。以下代码片段展示了使用 CUDA IPC 事件在两个进程的 `cudaFreeAsync` 操作之间提供所需的同步。显然，导入进程对分配的访问受导入进程侧释放操作的限制。值得注意的是，`cudaFree` 可用于在两个进程中释放分配，也可以用其他流同步 API 代替 CUDA IPC 事件。

```cpp
// 释放必须先在导入进程中发生，然后才能在导出进程中发生
kernel<<<..., stream>>>(ptr, ...);

// 导入进程中的最后一次访问
cudaFreeAsync(ptr, stream);

// 释放后不允许在导入进程中再访问
cudaIpcEventRecord(finishedIpcEvent, stream);

// 导出进程
// 导出进程需要将其释放操作与导入进程释放操作的流顺序协调。
cudaStreamWaitEvent(stream, finishedIpcEvent);
kernel<<<..., stream>>>(ptrInExportingProcess, ...);

// 导入进程中的释放不会阻止导出进程使用该分配。
cudFreeAsync(ptrInExportingProcess, stream);
```

#### 4.3.3.4.4 IPC 导出内存池的限制

IPC 内存池目前不支持将物理块释放回 OS。因此 `cudaMemPoolTrimTo` API 没有效果，`cudaMemPoolAttrReleaseThreshold` 实际上被忽略。该行为由驱动控制，而非运行时，未来驱动更新时可能会改变。

#### 4.3.3.4.5 IPC 导入内存池的限制

不允许从导入内存池分配；具体来说，导入内存池不能设为当前内存池，也不能用于 `cudaMallocFromPoolAsync` API。因此，分配重用策略属性对这些内存池没有意义。

与 IPC 导出内存池一样，IPC 导入内存池目前也不支持将物理块释放回 OS。

资源使用统计属性查询只反映导入到该进程的分配及相关的物理内存。

## 4.3.4 最佳实践与调优

### 4.3.4.1 查询支持情况

应用程序可以调用 `cudaDeviceGetAttribute()`（参见开发者博客），传入设备属性 `cudaDevAttrMemoryPoolsSupported`，来判断设备是否支持流式内存分配器。

IPC 内存池支持可以用设备属性 `cudaDevAttrMemoryPoolSupportedHandleTypes` 查询。该属性在 CUDA 11.3 中加入，旧版驱动在查询该属性时会返回 `cudaErrorInvalidValue`。

```cpp
int driverVersion = 0;
int deviceSupportsMemoryPools = 0;
int poolSupportedHandleTypes = 0;
cudaDriverGetVersion(&driverVersion);
if (driverVersion >= 11020) {
    cudaDeviceGetAttribute(&deviceSupportsMemoryPools,
                            cudaDevAttrMemoryPoolsSupported, device);
}
if (deviceSupportsMemoryPools != 0) {
    // `device` 支持流式内存分配器
}

if (driverVersion >= 11030) {
     cudaDeviceGetAttribute(&poolSupportedHandleTypes,
               cudaDevAttrMemoryPoolSupportedHandleTypes, device);
}
if (poolSupportedHandleTypes & cudaMemHandleTypePosixFileDescriptor) {
    // 指定设备上的内存池可以用基于 POSIX 文件描述符的 IPC 创建
}
```

在查询前先检查驱动版本，可以避免在尚无该属性定义的驱动上触发 `cudaErrorInvalidValue` 错误。也可以用 `cudaGetLastError` 清除该错误，而不去避免它。

### 4.3.4.2 物理页缓存行为

默认情况下，分配器会尽量减少内存池拥有的物理内存。要尽量减少向 OS 分配和释放物理内存的调用，应用程序必须为每个内存池配置一个内存占用（memory footprint）。应用程序可以用释放阈值属性（`cudaMemPoolAttrReleaseThreshold`）来做到这一点。

释放阈值是内存池在尝试向 OS 释放内存之前应持有的内存量（以字节为单位）。当内存池持有的内存超过释放阈值字节数时，分配器将在下一次调用流、事件或设备同步时尝试向 OS 释放内存。将释放阈值设为 `UINT64_MAX` 将阻止驱动在每次同步后尝试收缩内存池。

```cpp
Cuuint64_t setVal = UINT64_MAX;
cudaMemPoolSetAttribute(memPool, cudaMemPoolAttrReleaseThreshold, &setVal);
```

将 `cudaMemPoolAttrReleaseThreshold` 设得足够高以有效禁用内存池收缩的应用程序，可能希望显式收缩内存池的内存占用。`cudaMemPoolTrimTo` 允许应用程序这样做。在裁剪内存池占用时，`minBytesToKeep` 参数允许应用程序持有指定数量的内存，例如在后续执行阶段预计需要的量。

```cpp
Cuuint64_t setVal = UINT64_MAX;
cudaMemPoolSetAttribute(memPool, cudaMemPoolAttrReleaseThreshold, &setVal);

// 需要从流式分配器使用大量内存的应用程序阶段
for (i=0; i<10; i++) {
    for (j=0; j<10; j++) {
        cudaMallocAsync(&ptrs[j],size[j], stream);
    }
    kernel<<<...,stream>>>(ptrs,...);
    for (j=0; j<10; j++) {
        cudaFreeAsync(ptrs[j], stream);
    }
}

// 下一个阶段进程不再需要那么多内存。
// 先同步，使裁剪操作知道这些分配不再被使用。
cudaStreamSynchronize(stream);
cudaMemPoolTrimTo(mempool, 0);

// 裁剪操作释放的物理内存现在可供其他进程/分配机制使用。
```

### 4.3.4.3 资源使用统计

查询内存池的 `cudaMemPoolAttrReservedMemCurrent` 属性会报告该内存池当前消耗的物理 GPU 内存总量。查询内存池的 `cudaMemPoolAttrUsedMemCurrent` 返回从该内存池分配且不可重用的所有内存的总大小。`cudaMemPoolAttr*MemHigh` 属性是水位线，记录自上次重置以来相应 `cudaMemPoolAttr*MemCurrent` 属性达到的最大值。可以用 `cudaMemPoolSetAttribute` API 将它们重置为当前值。

```cpp
// 批量获取使用统计的示例辅助函数
struct usageStatistics {
    cuuint64_t reserved;
    cuuint64_t reservedHigh;
    cuuint64_t used;
    cuuint64_t usedHigh;
};

void getUsageStatistics(cudaMemoryPool_t memPool, struct usageStatistics *statistics)
{
     cudaMemPoolGetAttribute(memPool, cudaMemPoolAttrReservedMemCurrent, statistics->reserved);

     cudaMemPoolGetAttribute(memPool, cudaMemPoolAttrReservedMemHigh, statistics->reservedHigh);

     cudaMemPoolGetAttribute(memPool, cudaMemPoolAttrUsedMemCurrent, statistics->used);

     cudaMemPoolGetAttribute(memPool, cudaMemPoolAttrUsedMemHigh, statistics->usedHigh);
}

// 重置水位线将使它们取当前值。
void resetStatistics(cudaMemoryPool_t memPool)
{
    cuuint64_t value = 0;
    cudaMemPoolSetAttribute(memPool, cudaMemPoolAttrReservedMemHigh, &value);
    cudaMemPoolSetAttribute(memPool, cudaMemPoolAttrUsedMemHigh, &value);
}
```

### 4.3.4.4 内存重用策略

为了服务分配请求，驱动在尝试从 OS 分配更多内存之前，会先尝试重用之前经 `cudaFreeAsync()` 释放的内存。例如，在流中释放的内存可以在同一流上的后续分配请求中立即重用。当流与 CPU 同步时，该流中之前释放的内存变为可用于任何流中分配的重用对象。重用策略可以应用于默认内存池和显式内存池。

流式分配器有几个可控的分配策略。内存池属性 `cudaMemPoolReuseFollowEventDependencies`、`cudaMemPoolReuseAllowOpportunistic` 和 `cudaMemPoolReuseAllowInternalDependencies` 控制这些策略，详情如下。这些策略可以通过调用 `cudaMemPoolSetAttribute` 启用或禁用。升级到更新的 CUDA 驱动可能会更改、增强、增补和/或重新排序重用策略的枚举。

#### 4.3.4.4.1 cudaMemPoolReuseFollowEventDependencies

在分配更多物理 GPU 内存之前，分配器会检查由 CUDA 事件建立的依赖信息，并尝试从在另一个流中释放的内存中分配。

```cpp
cudaMallocAsync(&ptr, size, originalStream);
kernel<<<..., originalStream>>>(ptr, ...);
cudaFreeAsync(ptr, originalStream);
cudaEventRecord(event, originalStream);

// 等待捕获释放操作的事件，使分配器能够在
// cudaMemPoolReuseFollowEventDependencies 启用时，
// 用该内存满足另一个流中的新分配请求。
cudaStreamWaitEvent(otherStream, event);
cudaMallocAsync(&ptr2, size, otherStream);
```

#### 4.3.4.4.2 cudaMemPoolReuseAllowOpportunistic

当 `cudaMemPoolReuseAllowOpportunistic` 策略启用时，分配器会检查已释放的分配，看其释放操作的流排序语义是否已满足，例如流已越过释放操作所指示的执行点。当该策略禁用时，分配器仍会重用在流与 CPU 同步时变为可用的内存。禁用该策略不会阻止 `cudaMemPoolReuseFollowEventDependencies` 生效。

```cpp
cudaMallocAsync(&ptr, size, originalStream);
kernel<<<..., originalStream>>>(ptr, ...);
cudaFreeAsync(ptr, originalStream);

// 一段时间后，核函数运行结束
wait(10);

// 当 cudaMemPoolReuseAllowOpportunistic 启用时，此分配请求
// 可以根据 originalStream 的进度用先前的分配来满足。

cudaMallocAsync(&ptr2, size, otherStream);
```

#### 4.3.4.4.3 cudaMemPoolReuseAllowInternalDependencies

当无法从 OS 分配和映射更多物理内存时，驱动会查找其可用性依赖于另一个流待定进度的内存。如果找到这样的内存，驱动将在分配流中插入所需的依赖，并重用该内存。

```cpp
cudaMallocAsync(&ptr, size, originalStream);
kernel<<<..., originalStream>>>(ptr, ...);
cudaFreeAsync(ptr, originalStream);

// 当 cudaMemPoolReuseAllowInternalDependencies 启用
// 且驱动无法分配更多物理内存时，驱动可能会
// 实际在分配流中执行一次 cudaStreamWaitEvent，
// 以保证 'otherStream' 中的后续工作发生在
// 原始流中允许访问原始分配的工作之后。

cudaMallocAsync(&ptr2, size, otherStream);
```

#### 4.3.4.4.4 禁用重用策略

可控的重用策略虽然改善了内存重用，但用户可能希望禁用它们。允许机会性重用（如 `cudaMemPoolReuseAllowOpportunistic`）会基于 CPU 与 GPU 执行的交错，在分配模式上引入逐次运行的差异。内部依赖插入（如 `cudaMemPoolReuseAllowInternalDependencies`）可能会在用户更希望在分配失败时显式同步事件或流的情况下，以意外且可能非确定的方式串行化工作。

### 4.3.4.5 同步 API 行为

分配器作为 CUDA 驱动的一部分所带来的优化之一是与同步 API 的集成。当用户请求 CUDA 驱动同步时，驱动等待异步工作完成。在返回之前，驱动会确定同步保证已完成的释放。这些分配变得可用于分配，而不受指定流或禁用的分配策略限制。驱动还会在此处检查 `cudaMemPoolAttrReleaseThreshold`，并释放它能释放的多余物理内存。

## 4.3.5 补充说明

### 4.3.5.1 cudaMemcpyAsync 的当前上下文/设备敏感性

在当前 CUDA 驱动中，任何涉及来自 `cudaMallocAsync` 的内存的异步 memcpy 都应当使用指定流的上下文作为调用线程的当前上下文。`cudaMemcpyPeerAsync` 不需要这样做，因为该 API 引用的是其中指定的设备主上下文，而非当前上下文。

### 4.3.5.2 cudaPointerGetAttributes 查询

在对分配调用 `cudaFreeAsync` 之后再调用 `cudaPointerGetAttributes` 查询该分配，会导致未定义行为。具体来说，无论从给定流是否仍可访问该分配，行为都是未定义的。

### 4.3.5.3 cudaGraphAddMemsetNode

`cudaGraphAddMemsetNode` 不适用于经流式分配器分配的内存。但对这些分配的 memset 操作可以被流捕获。

### 4.3.5.4 指针属性

`cudaPointerGetAttributes` 查询适用于流式分配。由于流式分配不与上下文关联，查询 `CU_POINTER_ATTRIBUTE_CONTEXT` 会成功，但在 `*data` 中返回 NULL。`CU_POINTER_ATTRIBUTE_DEVICE_ORDINAL` 属性可用于确定分配的位置：在使用 `cudaMemcpyPeerAsync` 进行 p2h2p 拷贝时选择上下文很有用。`CU_POINTER_ATTRIBUTE_MEMPOOL_HANDLE` 属性在 CUDA 11.3 中加入，可用于调试，以及在进行 IPC 之前确认分配来自哪个内存池。

### 4.3.5.5 CPU 虚拟内存

使用 CUDA 流式内存分配器 API 时，避免用 `ulimit -v` 设置 VRAM 限制，因为不受支持。
