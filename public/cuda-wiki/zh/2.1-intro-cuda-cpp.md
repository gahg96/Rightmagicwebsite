# 2.1 CUDA C++ 入门

本章通过展示 CUDA 编程模型的基本概念在 C++ 中的表现形式，来介绍这些概念。

本编程指南主要聚焦 CUDA 运行时 API。CUDA 运行时 API 是在 C++ 中使用 CUDA 最常用的方式，它构建在更底层的 CUDA 驱动 API 之上。《CUDA Runtime API and CUDA Driver API》一节讨论了两种 API 的区别，《CUDA driver API》一节讨论了混用两种 API 编写代码的方式。

本指南假定已安装 CUDA Toolkit 和 NVIDIA 驱动，且存在受支持的 NVIDIA GPU。关于安装所需 CUDA 组件的说明，请参阅《CUDA Quickstart Guide》。

## 2.1.1 使用 NVCC 编译

用 C++ 编写的 GPU 代码使用 NVIDIA CUDA 编译器 nvcc 编译。nvcc 是一个编译器驱动程序，简化了 C++ 或 PTX 代码的编译过程：它提供简单且熟悉的命令行选项，并通过调用实现各个编译阶段的一系列工具来执行它们。

本指南将展示 nvcc 命令行，可在任何安装了 CUDA Toolkit 的 Linux 系统、Windows 命令行或 PowerShell，或安装了 CUDA Toolkit 的 Windows Subsystem for Linux 上使用。nvcc 的常见用例见本指南的 nvcc 章节，完整文档请参阅 nvcc 用户手册。

## 2.1.2 核函数

如 CUDA 编程模型介绍所述，在 GPU 上执行、可从主机端调用的函数称为核函数（kernel）。核函数被编写为可由大量并行线程同时运行。

### 2.1.2.1 指定核函数

核函数的代码使用 `__global__` 声明说明符来指定。这告诉编译器：该函数将为 GPU 编译，以便能通过一次核函数启动来调用。核函数启动是一种开始运行核函数的操作，通常从 CPU 发起。核函数的返回类型为 void。

```c++
// 核函数定义
__global__ void vecAdd(float* A, float* B, float* C)
{

}
```

### 2.1.2.2 启动核函数

将并行执行核函数的线程数量作为核函数启动的一部分指定。这称为执行配置（execution configuration）。同一个核函数的不同调用可以使用不同的执行配置，例如不同的线程数或线程块数。

从 CPU 代码启动核函数有两种方式：三尖括号记号和 cudaLaunchKernelEx。三尖括号记号是最常见的启动核函数的方式，本节先做介绍。使用 cudaLaunchKernelEx 启动核函数的示例见第 3.1.1 节，有详细讨论。

#### 2.1.2.2.1 三尖括号记号

三尖括号记号是一种用于启动核函数的 CUDA C++ 语言扩展。之所以叫三尖括号，是因为它用三个尖括号字符将核函数启动的执行配置括起来，即 `<<< >>>`。执行配置参数以逗号分隔的列表形式写在尖括号内，类似于函数调用的参数。下面展示了启动 vecAdd 核函数的语法。

```c++
    __global__ void vecAdd(float* A, float* B, float* C)
    {

    }

int main()
{
    ...
    // 核函数调用
    vecAdd<<<1, 256>>>(A, B, C);
    ...
}
```

三尖括号记号的前两个参数分别是网格（grid）维度和线程块维度。当使用一维线程块或网格时，可以用整数来指定维度。

上面的代码启动了单个线程块，其中包含 256 个线程。每个线程都将执行完全相同的核函数代码。在《线程与网格索引内建变量》一节中，我们将展示每个线程如何利用自己在线程块和网格中的索引来改变其处理的数据。

每个块的线程数量是有限制的，因为一个块的所有线程都驻留在同一个流多处理器（Streaming Multiprocessor，SM）上，必须共享 SM 的资源。在当前的 GPU 上，一个线程块最多可包含 1024 个线程。如果资源允许，一个 SM 上可以同时调度多个线程块。

核函数启动相对于主机线程是异步的。也就是说，核函数会被安排好在 GPU 上执行，但主机代码不会等待核函数在 GPU 上完成（甚至开始）执行就继续往下走。必须使用某种 GPU 与 CPU 之间的同步（synchronization）手段来确认核函数已执行完毕。最基础的一种是完全同步整个 GPU，见《同步 CPU 与 GPU》一节。更精细的同步手段见《异步执行》一节。

当使用二维或三维网格或线程块时，CUDA 类型 dim3 用作网格和线程块维度参数。下面的代码片段展示了用 16×16 的线程块网格启动 MatAdd 核函数，每个线程块为 8×8。

```c++
int main()
{
    ...
    dim3 grid(16,16);
    dim3 block(8,8);
    MatAdd<<<grid, block>>>(A, B, C);
    ...
}
```

### 2.1.2.3 线程与网格索引内建变量

在核函数代码中，CUDA 提供内建变量（intrinsics），用于访问执行配置的参数以及线程或线程块的索引。

- threadIdx 给出线程在其线程块内的索引。一个线程块中的每个线程都有不同的索引。
- blockDim 给出线程块的维度，即核函数启动时执行配置中指定的维度。
- blockIdx 给出线程块在网格内的索引。每个线程块都有不同的索引。
- gridDim 给出网格的维度，即启动核函数时执行配置中指定的维度。

这些内建变量都是三元向量，带有 `.x`、`.y`、`.z` 成员。启动配置中未指定的维度默认为 1。threadIdx 和 blockIdx 采用零基索引，即 threadIdx.x 的取值范围为 0 到 blockDim.x-1（含两端）。.y 和 .z 在各自维度上同理。

类似地，blockIdx.x 的取值范围为 0 到 gridDim.x-1（含两端），.y 和 .z 维度同理。

这些变量让单个线程能够确定自己应该执行哪部分工作。回到 vecAdd 核函数，该核函数有三个参数，每个都是 float 向量。核函数对 A 和 B 做逐元素加法，结果存入 C。核函数按每个线程执行一次加法的方式并行化。具体计算哪个元素，由其线程和网格索引决定。

```c++
__global__ void vecAdd(float* A, float* B, float* C)
{
   // 计算该线程负责计算哪个元素
   int workIndex = threadIdx.x + blockDim.x * blockIdx.x;

     // 执行计算
     C[workIndex] = A[workIndex] + B[workIndex];
}
```

```c++
int main()
{
     ...
     // A、B、C 是包含 1024 个元素的向量
     vecAdd<<<4, 256>>>(A, B, C);
     ...
}
```

在这个例子中，使用 4 个 256 线程的线程块来对 1024 个元素的向量做加法。在第一个线程块中，blockIdx.x 为零，因此每个线程的 workIndex 就是其 threadIdx.x。在第二个线程块中，blockIdx.x 为 1，于是 blockDim.x * blockIdx.x 等于 blockDim.x，这里即 256。第二个线程块中每个线程的 workIndex 为其 threadIdx.x + 256。第三个线程块中 workIndex 为 threadIdx.x + 512。这种 workIndex 计算在一维并行化中非常常见。扩展到二维或三维时，通常在每个维度上遵循相同的模式。

#### 2.1.2.3.1 边界检查

上面的例子假定向量长度是线程块大小（此处为 256 线程）的整数倍。为了让核函数处理任意长度的向量，可以如下所示添加检查，确保内存访问不越出数组边界，然后启动一个线程块，其中会有一些空闲线程。

```c++
__global__ void vecAdd(float* A, float* B, float* C, int vectorLength)
{
     // 计算该线程负责计算哪个元素
     int workIndex = threadIdx.x + blockDim.x * blockIdx.x;

      if(workIndex < vectorLength)
      {
          // 执行计算
          C[workIndex] = A[workIndex] + B[workIndex];
      }
}
```

有了上述核函数代码，可以启动比需要更多的线程，而不会造成数组越界访问。当 workIndex 超过 vectorLength 时，线程退出，不做任何工作。在线程块中启动不做工作的多余线程不会带来大的开销，但应避免启动没有任何线程做工作的线程块。这个核函数现在可以处理向量长度不是块大小整数倍的情况。

所需的线程块数可以计算为：所需线程数（此处为向量长度）除以每块线程数，结果向上取整。即所需线程数除以每块线程数的整数除法，向上舍入。常用的一种写法是把除法表达为一次整数除法：在整数除法之前先加上 threads - 1，这就等价于向上取整——只有当向量长度不能被每块线程数整除时，才会多出一个线程块。

```c++
// vectorLength 是存储向量元素个数的整数
int threads = 256;
int blocks = (vectorLength + threads-1)/threads;
vecAdd<<<blocks, threads>>>(devA, devB, devC, vectorLength);
```

CUDA Core Compute Library（CCCL）提供了一个方便的工具 cuda::ceil_div，用于做这种向上取整除法，以计算核函数启动所需的块数。使用时需要包含头文件 `<cuda/cmath>`。

```c++
// vectorLength 是存储向量元素个数的整数
int threads = 256;
int blocks = cuda::ceil_div(vectorLength, threads);
vecAdd<<<blocks, threads>>>(devA, devB, devC, vectorLength);
```

这里选择每块 256 线程是任意的，但这个值通常是一个不错的起点。

## 2.1.3 GPU 计算中的内存

要使用上面展示的 vecAdd 核函数，数组 A、B、C 必须位于 GPU 可访问的内存中。实现这一点有多种方式，本节展示其中两种，其他方式将在后文统一内存相关章节中介绍。GPU 上运行代码可用的内存空间在《GPU Memory》一节中介绍过，《GPU Device Memory Spaces》一节有更详细的说明。

### 2.1.3.1 统一内存

统一内存（unified memory）是 CUDA 运行时的一项特性，让 NVIDIA 驱动来管理主机与设备之间的数据迁移。使用 cudaMallocManaged API 分配内存，或用 `__managed__` 说明符声明变量。无论 CPU 还是 GPU 尝试访问该内存，NVIDIA 驱动都会保证它可被访问。

下面的代码展示了一个完整的函数：启动 vecAdd 核函数，并使用统一内存为 GPU 上使用的输入输出向量分配空间。cudaMallocManaged 分配的缓冲区可同时被 CPU 和 GPU 访问。这些缓冲区使用 cudaFree 释放。

```c++
void unifiedMemExample(int vectorLength)
{
    // 指向内存向量的指针
    float* A = nullptr;
    float* B = nullptr;
    float* C = nullptr;
    float* comparisonResult = (float*)malloc(vectorLength*sizeof(float));

     // 使用统一内存分配缓冲区
     cudaMallocManaged(&A, vectorLength*sizeof(float));
     cudaMallocManaged(&B, vectorLength*sizeof(float));
     cudaMallocManaged(&C, vectorLength*sizeof(float));

     // 在主机端初始化向量
     initArray(A, vectorLength);
     initArray(B, vectorLength);

     // 启动核函数。统一内存会保证 A、B、C 可被 GPU 访问
     int threads = 256;
     int blocks = cuda::ceil_div(vectorLength, threads);
     vecAdd<<<blocks, threads>>>(A, B, C, vectorLength);
     // 等待核函数执行完成
     cudaDeviceSynchronize();

     // 在 CPU 上串行执行计算以作对比
     serialVecAdd(A, B, comparisonResult, vectorLength);

     // 确认 CPU 和 GPU 得到相同的结果
     if(vectorApproximatelyEqual(C, comparisonResult, vectorLength))
     {
          printf("Unified Memory: CPU and GPU answers match\n");
     }
     else
     {
          printf("Unified Memory: Error - CPU and GPU answers do not match\n");
     }

     // 清理
     cudaFree(A);
     cudaFree(B);
     cudaFree(C);
     free(comparisonResult);

}
```

所有 CUDA 支持的操作系统和 GPU 都支持统一内存，但底层机制和性能可能因系统架构而异。详见《Unified Memory》一节。在某些 Linux 系统上（例如具有地址转换服务或异构内存管理的系统），所有系统内存都自动是统一内存，无需使用 cudaMallocManaged 或 `__managed__` 说明符。

### 2.1.3.2 显式内存管理

显式地管理内存分配和各内存空间之间的数据迁移有助于提升应用性能，但代码会更冗长。下面的代码使用 cudaMalloc 在 GPU 上显式分配内存。GPU 上的内存使用与前例中统一内存相同的 cudaFree API 释放。

```c++
void explicitMemExample(int vectorLength)
{
    // 主机内存指针
    float* A = nullptr;
    float* B = nullptr;
    float* C = nullptr;
    float* comparisonResult = (float*)malloc(vectorLength*sizeof(float));

     // 设备内存指针
     float* devA = nullptr;
     float* devB = nullptr;
     float* devC = nullptr;

     // 使用 cudaMallocHost API 分配主机内存。当缓冲区用于
     // CPU 与 GPU 内存之间的拷贝时，这是最佳实践
     cudaMallocHost(&A, vectorLength*sizeof(float));
     cudaMallocHost(&B, vectorLength*sizeof(float));
     cudaMallocHost(&C, vectorLength*sizeof(float));

     // 在主机端初始化向量
     initArray(A, vectorLength);
     initArray(B, vectorLength);

     // 在 GPU 上分配内存
     cudaMalloc(&devA, vectorLength*sizeof(float));
     cudaMalloc(&devB, vectorLength*sizeof(float));
     cudaMalloc(&devC, vectorLength*sizeof(float));

     // 把数据拷贝到 GPU
     cudaMemcpy(devA, A, vectorLength*sizeof(float), cudaMemcpyDefault);
     cudaMemcpy(devB, B, vectorLength*sizeof(float), cudaMemcpyDefault);
     cudaMemset(devC, 0, vectorLength*sizeof(float));

     // 启动核函数
     int threads = 256;
     int blocks = cuda::ceil_div(vectorLength, threads);
     vecAdd<<<blocks, threads>>>(devA, devB, devC, vectorLength);
     // 等待核函数执行完成
     cudaDeviceSynchronize();

     // 把结果拷回主机
     cudaMemcpy(C, devC, vectorLength*sizeof(float), cudaMemcpyDefault);

     // 在 CPU 上串行执行计算以作对比
     serialVecAdd(A, B, comparisonResult, vectorLength);

     // 确认 CPU 和 GPU 得到相同的结果
     if(vectorApproximatelyEqual(C, comparisonResult, vectorLength))
     {
          printf("Explicit Memory: CPU and GPU answers match\n");
     }
     else
     {
          printf("Explicit Memory: Error - CPU and GPU answers to not match\n");
     }

     // 清理
     cudaFree(devA);
     cudaFree(devB);
     cudaFree(devC);
     cudaFreeHost(A);
     cudaFreeHost(B);
     cudaFreeHost(C);
     free(comparisonResult);
}
```

CUDA API cudaMemcpy 用于把数据从 CPU 上的缓冲区拷贝到 GPU 上的缓冲区。除了目标指针、源指针和字节数，cudaMemcpy 的最后一个参数是一个 cudaMemcpyKind_t，可取如下值：

- cudaMemcpyHostToDevice：从 CPU 拷贝到 GPU
- cudaMemcpyDeviceToHost：从 GPU 拷贝到 CPU
- cudaMemcpyDeviceToDevice：在 GPU 内部或 GPU 之间拷贝

在这个例子中，传给 cudaMemcpy 的最后一个参数是 cudaMemcpyDefault。这会让 CUDA 根据源指针和目标指针的值来判断执行哪种拷贝。cudaMemcpy API 是同步的，也就是说，它在拷贝完成之前不会返回。异步拷贝见《Launching Memory Transfers in CUDA Streams》一节。

这段代码使用 cudaMallocHost 在 CPU 上分配内存。它分配的是主机端的页锁定（page-locked）内存，可以提升拷贝性能，并且是异步内存传输所必需的。一般来说，用于与 GPU 之间数据传输的 CPU 缓冲区，使用页锁定内存是良好的做法。如果主机内存被页锁定得太多，某些系统的性能会下降。最佳实践是只对用于向 GPU 发送或从 GPU 接收数据的缓冲区使用页锁定。

### 2.1.3.3 内存管理与应用性能

从上面的例子可以看出，显式内存管理更冗长，需要程序员指定主机与设备之间的拷贝。这是显式内存管理的优点也是缺点：它让程序员对数据何时在主机与设备之间拷贝、内存驻留在哪里、具体哪块内存分配在何处有更多控制权。显式内存管理在控制内存传输、并将其与其他计算重叠方面提供了性能优化的机会。

使用统一内存时，也有一些 CUDA API（见《Memory Advise and Prefetch》一节）可以向管理内存的 NVIDIA 驱动提供提示，使用统一内存时也能获得显式内存管理的部分性能优势。

## 2.1.4 同步 CPU 与 GPU

如《启动核函数》所述，核函数启动相对于调用它的 CPU 线程是异步的。这意味着 CPU 线程的控制流会在核函数完成之前继续执行，甚至可能在核函数启动之前就继续了。要保证主机代码继续执行前核函数已执行完毕，需要某种同步机制。

同步 GPU 与主机线程最简单的方法是使用 cudaDeviceSynchronize，它会阻塞主机线程，直到 GPU 上此前发起的所有工作都完成。本章的例子中这种做法足够了，因为 GPU 上一次只执行单个操作。在更大的应用中，GPU 上可能有多个流在执行工作，cudaDeviceSynchronize 会等待所有流中的工作完成。在这些应用中，建议使用流同步 API 只与特定流同步，或使用 CUDA 事件。《异步执行》一章将详细介绍这些内容。

## 2.1.5 综合示例

以下清单展示了本章介绍的简单向量加法核函数的完整代码，包括所有主机代码和用于校验结果正确的工具函数。这些示例默认使用长度为 1024 的向量，但可通过可执行文件的命令行参数指定不同的向量长度。

**统一内存版本**

```c++
#include <cuda_runtime_api.h>
#include <memory.h>
#include <cstdlib>
#include <ctime>
#include <stdio.h>
#include <cuda/cmath>

__global__ void vecAdd(float* A, float* B, float* C, int vectorLength)
{
    int workIndex = threadIdx.x + blockIdx.x*blockDim.x;
    if(workIndex < vectorLength)
    {
        C[workIndex] = A[workIndex] + B[workIndex];
    }
}

void initArray(float* A, int length)
{
      std::srand(std::time({}));
    for(int i=0; i<length; i++)
    {
         A[i] = rand() / (float)RAND_MAX;
    }
}

void serialVecAdd(float* A, float* B, float* C,   int length)
{
    for(int i=0; i<length; i++)
    {
        C[i] = A[i] + B[i];
    }
}

bool vectorApproximatelyEqual(float* A, float* B, int length, float epsilon=0.00001)
{
     for(int i=0; i<length; i++)
     {
          if(fabs(A[i] -B[i]) > epsilon)
          {
              printf("Index %d mismatch: %f != %f", i, A[i], B[i]);
              return false;
          }
     }
     return true;
}
```

**显式内存管理版本**

```c++
#include <cuda_runtime_api.h>
#include <memory.h>
#include <cstdlib>
#include <ctime>
#include <stdio.h>
#include <cuda/cmath>

__global__ void vecAdd(float* A, float* B, float* C, int vectorLength)
{
    int workIndex = threadIdx.x + blockIdx.x*blockDim.x;
    if(workIndex < vectorLength)
    {
        C[workIndex] = A[workIndex] + B[workIndex];
    }
}

void initArray(float* A, int length)
{
      std::srand(std::time({}));
    for(int i=0; i<length; i++)
    {
         A[i] = rand() / (float)RAND_MAX;
    }
}

void serialVecAdd(float* A, float* B, float* C,   int length)
{
    for(int i=0; i<length; i++)
    {
        C[i] = A[i] + B[i];
    }
}

bool vectorApproximatelyEqual(float* A, float* B, int length, float epsilon=0.00001)
{
     for(int i=0; i<length; i++)
     {
          if(fabs(A[i] -B[i]) > epsilon)
          {
              printf("Index %d mismatch: %f != %f", i, A[i], B[i]);
              return false;
          }
     }
     return true;
}

void explicitMemExample(int vectorLength)
{
    // 主机内存指针
    float* A = nullptr;
    float* B = nullptr;
    float* C = nullptr;
    float* comparisonResult = (float*)malloc(vectorLength*sizeof(float));

     // 设备内存指针
     float* devA = nullptr;
     float* devB = nullptr;
     float* devC = nullptr;

     // 使用 cudaMallocHost API 分配主机内存。当缓冲区用于
     // CPU 与 GPU 内存之间的拷贝时，这是最佳实践
     cudaMallocHost(&A, vectorLength*sizeof(float));
     cudaMallocHost(&B, vectorLength*sizeof(float));
     cudaMallocHost(&C, vectorLength*sizeof(float));

     // 在主机端初始化向量
     initArray(A, vectorLength);
     initArray(B, vectorLength);

     // 在 GPU 上分配内存
     cudaMalloc(&devA, vectorLength*sizeof(float));
     cudaMalloc(&devB, vectorLength*sizeof(float));
     cudaMalloc(&devC, vectorLength*sizeof(float));

     // 把数据拷贝到 GPU
     cudaMemcpy(devA, A, vectorLength*sizeof(float), cudaMemcpyDefault);
     cudaMemcpy(devB, B, vectorLength*sizeof(float), cudaMemcpyDefault);
     cudaMemset(devC, 0, vectorLength*sizeof(float));

     // 启动核函数
     int threads = 256;
     int blocks = cuda::ceil_div(vectorLength, threads);
     vecAdd<<<blocks, threads>>>(devA, devB, devC, vectorLength);
     // 等待核函数执行完成
     cudaDeviceSynchronize();

     // 把结果拷回主机
     cudaMemcpy(C, devC, vectorLength*sizeof(float), cudaMemcpyDefault);

     // 在 CPU 上串行执行计算以作对比
     serialVecAdd(A, B, comparisonResult, vectorLength);

     // 确认 CPU 和 GPU 得到相同的结果
     if(vectorApproximatelyEqual(C, comparisonResult, vectorLength))
     {
          printf("Explicit Memory: CPU and GPU answers match\n");
     }
     else
     {
          printf("Explicit Memory: Error - CPU and GPU answers to not match\n");
     }

     // 清理
     cudaFree(devA);
     cudaFree(devB);
     cudaFree(devC);
     cudaFreeHost(A);
     cudaFreeHost(B);
     cudaFreeHost(C);
     free(comparisonResult);
}

int main(int argc, char** argv)
{
    int vectorLength = 1024;
    if(argc >=2)
    {
        vectorLength = std::atoi(argv[1]);
    }
    explicitMemExample(vectorLength);
    return 0;
}
```

在这些例子中，所有线程都做相互独立的工作，不需要相互协调或同步。通常，线程需要与其他线程协作和通信来完成工作。线程块内的线程可以通过共享内存（shared memory）共享数据，并进行同步以协调内存访问。

块级同步最基础的机制是 `__syncthreads()` 内建函数，它充当一个屏障：块内所有线程必须到达此处等待，之后任何线程才能继续执行。《Shared Memory》一节给出了使用共享内存的示例。

为了高效协作，共享内存应当是靠近每个处理器核心的低延迟内存（很像 L1 缓存），而 `__syncthreads()` 应当是轻量级的。`__syncthreads()` 只同步单个线程块内的线程。

线程块之间的同步仅在特定情况下受支持。例如，线程块簇允许簇内的块进行同步，而协作组（cooperative groups）API 提供了创建跨块同步域的机制。

通常，当同步保持在线程块内时性能最佳。线程块仍可以使用原子内存函数在共同的结果上协作，后续章节将介绍原子函数。

第 3.2.4 节介绍的 CUDA 同步原语提供了非常细粒度的控制，用于最大化性能和资源利用率。

## 2.1.6 运行时初始化

CUDA 运行时为系统中的每个设备创建一个 CUDA 上下文（context）。该上下文是该设备的主上下文（primary context），在首次调用需要该设备上存在活动上下文的运行时函数时初始化。上下文在应用的所有主机线程之间共享。作为上下文创建的一部分，如有必要，设备代码会被即时编译并加载到设备内存中。这些都透明地完成。CUDA 运行时创建的主上下文可以按《Interoperability between Runtime and Driver APIs》所述从驱动 API 访问，以实现互操作。

自 CUDA 12.0 起，cudaInitDevice 和 cudaSetDevice 调用会初始化运行时以及与指定设备关联的主上下文。如果运行时 API 请求在这些调用之前发生，运行时会隐式使用设备 0 并按需自初始化。在为运行时函数调用计时以及解释首次调用运行时的错误码时，这一点很重要。在 CUDA 12.0 之前，cudaSetDevice 不会初始化运行时。

cudaDeviceReset 会销毁当前设备的主上下文。如果在主上下文被销毁后调用 CUDA 运行时 API，会为该设备创建新的主上下文。

> **注意**
>
> CUDA 接口使用全局状态，该状态在主机程序启动时初始化，在主机程序终止时销毁。在 main 之后程序启动或终止期间（隐式或显式）使用这些接口中的任何一个都会导致未定义行为。
>
> 自 CUDA 12.0 起，如果运行时尚未初始化，cudaSetDevice 在为主机线程切换当前设备后会显式初始化运行时。旧版本 CUDA 会延迟新设备上的运行时初始化，直到 cudaSetDevice 之后的首次运行时调用。因此，务必检查 cudaSetDevice 的返回值以发现初始化错误。
>
> 参考手册中错误处理和版本管理章节的运行时函数不会初始化运行时。

## 2.1.7 CUDA 中的错误检查

每个 CUDA API 都返回一个枚举类型 cudaError_t 的值。示例代码中这些错误往往不做检查。在生产应用中，最佳实践是始终检查并处理每个 CUDA API 调用的返回值。没有错误时，返回值为 cudaSuccess。许多应用会实现如下所示的工具宏：

```c++
#define CUDA_CHECK(expr_to_check) do {            \
    cudaError_t result = expr_to_check;           \
    if(result != cudaSuccess)                     \
    {                                             \
        fprintf(stderr,                           \
                "CUDA Runtime Error: %s:%i:%d = %s\n", \
                __FILE__,                         \
                __LINE__,                         \
                result,\
                cudaGetErrorString(result));      \
    }                                             \
} while(0)
```

该宏使用 cudaGetErrorString API，它返回描述特定 cudaError_t 值含义的可读字符串。使用上述宏后，应用会把 CUDA 运行时 API 调用放在 CUDA_CHECK(expression) 宏中，如下所示：

```c++
     CUDA_CHECK(cudaMalloc(&devA, vectorLength*sizeof(float)));
     CUDA_CHECK(cudaMalloc(&devB, vectorLength*sizeof(float)));
     CUDA_CHECK(cudaMalloc(&devC, vectorLength*sizeof(float)));
```

如果这些调用中有任何一个检测到错误，宏会将其打印到 stderr。这个宏在小型项目中很常见，在大型应用中可以适配为日志系统或其他错误处理机制。

> **注意**
>
> 需要注意的是，任何 CUDA API 调用返回的错误状态也可能表示此前发出的异步操作发生了错误。《异步错误处理》一节有更详细的介绍。

### 2.1.7.1 错误状态

CUDA 运行时为每个主机线程维护一个 cudaError_t 状态。该值默认为 cudaSuccess，每当发生错误时被改写。cudaGetLastError 返回当前错误状态，然后将其重置为 cudaSuccess。或者，cudaPeekAtLastError 返回错误状态但不重置。

使用三尖括号记号的核函数启动不返回 cudaError_t。良好的做法是紧随核函数启动后立即检查错误状态，以发现核函数启动中的即时错误或核函数启动前的异步错误。紧随核函数启动后检查错误状态得到 cudaSuccess，并不意味着核函数已成功执行甚至已开始执行。它只验证了传给运行时的核函数启动参数和执行配置没有触发任何错误，以及在核函数开始之前错误状态不是此前或异步的错误。

### 2.1.7.2 异步错误

CUDA 核函数启动和许多运行时 API 是异步的。异步 CUDA 运行时 API 将在《异步执行》一节中详细介绍。只要发生错误，CUDA 错误状态就会被设置和改写。这意味着异步操作执行期间发生的错误，只有在下次检查错误状态时才会被报告。如前所述，这可能是调用 cudaGetLastError、cudaPeekAtLastError，也可能是任何返回 cudaError_t 的 CUDA API。

当 CUDA 运行时 API 函数返回错误时，错误状态不会被清除。这意味着异步错误（如核函数的非法内存访问）产生的错误码，会被每个 CUDA 运行时 API 返回，直到通过调用 cudaGetLastError 清除错误状态。

```c++
    vecAdd<<<blocks, threads>>>(devA, devB, devC);
    // 在核函数启动后检查错误状态
    CUDA_CHECK(cudaGetLastError());
    // 等待核函数执行完成
    // CUDA_CHECK 会报告核函数执行期间发生的错误
    CUDA_CHECK(cudaDeviceSynchronize());
```

> **注意**
>
> cudaStreamQuery 和 cudaEventQuery 可能返回的 cudaError_t 值 cudaErrorNotReady 不被视为错误，也不会被 cudaPeekAtLastError 或 cudaGetLastError 报告。

### 2.1.7.3 CUDA_LOG_FILE

识别 CUDA 错误的另一个好方法是使用 CUDA_LOG_FILE 环境变量。当设置了该环境变量时，CUDA 驱动会把遇到的错误信息写入该环境变量指定的文件。例如，下面的 CUDA 代码是错误的：它试图启动的线程块大于任何架构支持的最大值。

```c++

{ }

int main()
{
        k<<<8192, 4096>>>(); // 非法块大小
        CUDA_CHECK(cudaGetLastError());
        return 0;
}
```

编译并运行后，核函数启动后的检查用 2.1.7 节展示的宏检测并报告错误：

```bash

$ ./errlog

```

但如果在设置了 CUDA_LOG_FILE 为某个文本文件的情况下运行该应用，该文件会包含关于该错误的更多信息：

```bash

$ cat cudaLog.txt

[12:46:23.854][137216133754880][CUDA][E] Returning 1 (CUDA_ERROR_INVALID_VALUE) from cuLaunchKernel
```

将 CUDA_LOG_FILE 设为 stdout 或 stderr 会分别打印到标准输出和标准错误。使用 CUDA_LOG_FILE 环境变量，即使应用没有对 CUDA 返回值做恰当的错误检查，也能捕获并识别 CUDA 错误。这种方法对调试极其强大，但仅靠该环境变量不能让应用在运行时处理和恢复 CUDA 错误。CUDA 的错误日志管理功能还允许向驱动注册一个回调函数，每当检测到错误时调用该回调。这可用于在运行时捕获和处理错误，也可以将 CUDA 错误日志无缝集成到应用现有的日志系统中。

第 4.9 节展示了 CUDA 错误日志管理功能的更多示例。错误日志管理和 CUDA_LOG_FILE 需要 NVIDIA 驱动 r570 及以上版本。

## 2.1.9 变量说明符

CUDA 说明符可用于静态变量声明，以控制其存放位置。

- `__device__` 指定变量存放在全局内存（Global Memory）中
- `__constant__` 指定变量存放在常量内存（Constant Memory）中
- `__managed__` 指定变量存放在统一内存（Unified Memory）中
- `__shared__` 指定变量存放在共享内存（Shared Memory）中

在 `__device__` 或 `__global__` 函数内部声明的无说明符变量，尽可能分配到寄存器，必要时分配到本地内存（local memory）。在 `__device__` 或 `__global__` 函数外部声明的无说明符变量，分配在系统内存中。

## 2.1.10 线程块簇

从计算能力（Compute Capability）9.0 起，CUDA 编程模型包含一个可选的层级，称为线程块簇（thread block cluster），由线程块组成。就像线程块中的线程保证被协同调度到一个流多处理器上一样，簇中的线程块也保证被协同调度到 GPU 的一个 GPU 处理簇（GPU Processing Cluster，GPC）上。与线程块类似，簇也组织成一维、二维或三维的线程块簇网格，如图 5 所示。

簇中的线程块数量可由用户定义，CUDA 中作为可移植簇大小最多支持 8 个线程块。注意，在 GPU 硬件或 MIG 配置太小、无法支持 8 个多处理器时，最大簇大小会相应减小。这些较小配置的识别，以及支持超过 8 的线程块簇大小的更大配置的识别，都与架构相关，可使用 cudaOccupancyMaxPotentialClusterSize API 查询。

簇中的所有线程块保证被协同调度到单个 GPU 处理簇（GPC）上同时执行，并允许簇中的线程块使用协作组 API 的 cluster.sync() 进行硬件支持的同步。簇组（cluster group）还提供成员函数，用于查询簇组大小（以线程数或
线程数或线程块数查询簇组大小，分别用 num_threads() 和 num_blocks() API。簇组中线程或块的秩（rank）可分别用 dim_threads() 和 dim_blocks() API 查询。

属于一个簇的线程块可以访问分布式共享内存（distributed shared memory），即簇中所有线程块的共享内存之和。簇中的线程块可以读取、写入分布式共享内存中的任意地址，并对其执行原子操作。《Distributed Shared Memory》一节给出了在分布式共享内存中做直方图的示例。

> **注意**
>
> 在使用簇支持启动的核函数中，gridDim 变量出于兼容性考虑仍然表示以线程块数量计的网格大小。簇中块的秩可以用协作组 API 查到。

### 2.1.10.1 用三尖括号记号启动簇

可以用编译时核属性 `__cluster_dims__(X,Y,Z)` 或 CUDA 核函数启动 API cudaLaunchKernelEx 在核函数中启用线程块簇。下面的例子展示了如何用编译时核属性启动簇。用核属性指定的簇大小在编译时固定，然后可以用经典的 `<<< >>>` 启动核函数。如果核函数使用编译时簇大小，启动核函数时不能修改簇大小。

```c++
// 编译时簇大小：X 维度为 2，Y 和 Z 维度为 1
__global__ void __cluster_dims__(2, 1, 1) cluster_kernel(float *input, float *output)

{

}

int main()
{
       float *input, *output;
       // 用编译时簇大小调用核函数
       dim3 threadsPerBlock(16, 16);
       dim3 numBlocks(N / threadsPerBlock.x, N / threadsPerBlock.y);

       // 网格维度必须是簇大小的整数倍。
```
