# 4.15 内存同步域

## 4.15.1 内存栅栏干扰

有些 CUDA 应用程序可能因内存栅栏/刷出（flush）操作等待了超出 CUDA 内存一致性模型所需的事务，而出现性能下降。

```cpp
__managed__ int x = 0;
__device__ cuda::atomic<int, cuda::thread_scope_device> a(0);
__managed__ cuda::atomic<int, cuda::thread_scope_system> b(0);
```

| 线程 1（SM） | 线程 2（SM） | 线程 3（CPU） |
|---|---|---|
| `x = 1;` | `while (a != 1) ;` | `while (b != 1) ;` |
| `a = 1;` | `assert(x == 1);` | `assert(x == 1);` |
| | `b = 1;` | |

看上面的例子。CUDA 内存一致性模型保证断言的条件为真，因此线程 1 对 `x` 的写入必须在线程 2 对 `b` 的写入之前，对线程 3 可见。

`a` 的释放（release）与获取（acquire）提供的内存顺序只足以让 `x` 对线程 2 可见，不足以让线程 3 可见，因为它是设备作用域的操作。因此，`b` 的释放与获取提供的系统作用域顺序，不仅要保证线程 2 自己发出的写入对线程 3 可见，还要保证线程 2 可见的其他线程的写入对线程 3 可见。这称为**累积性**（cumulativity）。

由于 GPU 在执行时无法知道哪些写入在源码层面保证可见、哪些只是因时机巧合而可见，它必须对在途的内存操作撒一张保守的大网。

这有时会导致干扰：因为 GPU 在等待源码层面并不要求的内存操作，栅栏/刷出可能比必要的时间更长。

注意栅栏可能显式出现在代码中（如本例中的内联函数或原子操作），也可能隐式出现，用于在任务边界实现同步（synchronizes-with）关系。

一个常见的例子是：一个核函数在本地 GPU 内存中做计算，同时一个并行核函数（例如来自 NCCL）与对端做通信。完成后，本地核函数会隐式刷出其写入，以满足与下游工作的同步关系。这可能不必要地等待了通信核函数较慢的 NVLink 或 PCIe 写入，全部或部分。

## 4.15.2 用域隔离流量

从计算能力（Compute Capability）9.0（Hopper 架构）GPU 和 CUDA 12.0 起，**内存同步域**（memory synchronization domains）功能提供了一种缓解这种干扰的办法。以代码显式协助为代价，GPU 可以缩小栅栏操作撒网的范围。每次核函数启动被赋予一个域 ID。写入和栅栏都带上该 ID 的标签，栅栏只对与栅栏同域的写入排序。在上面的并发计算 vs 通信例子中，通信核函数可以放入另一个域。

使用域时，代码必须遵守一条规则：同一 GPU 上不同域之间的顺序或同步需要系统作用域栅栏。域内仍是设备作用域栅栏就够了。这是为了累积性：一个域中核函数的写入不会被另一个域中核函数发出的栅栏涵盖。本质上，累积性是通过提前把跨域流量刷出到系统作用域来保证的。

注意这修改了 `thread_scope_device` 的定义。不过如下文所述，核函数默认在域 0，因此向后兼容得以保持。

## 4.15.3 在 CUDA 中使用域

域通过新的启动属性 `cudaLaunchAttributeMemSyncDomain` 和 `cudaLaunchAttributeMemSyncDomainMap` 访问。前者在逻辑域 `cudaLaunchMemSyncDomainDefault` 和 `cudaLaunchMemSyncDomainRemote` 之间选择；后者提供从逻辑域到物理域的映射。远程域（remote domain）用于执行远程内存访问的核函数，以把它们的内存流量与本地核函数隔离开。但要注意，选择某个域不影响核函数可以合法执行何种内存访问。

域数量可通过设备属性 `cudaDevAttrMemSyncDomainCount` 查询。计算能力 9.0（Hopper）的设备有 4 个域。为了代码可移植，域功能在所有设备上都可用；计算能力 9.0 之前的设备上 CUDA 报告数量为 1。

逻辑域便于应用程序组合。软件栈底层的一次核函数启动（例如来自 NCCL）可以选择语义上的逻辑域，而不必关心周围的应用程序架构。上层可以用映射来引导逻辑域。如果未设置，逻辑域的默认值是默认域；默认映射是把默认域映射到 0、远程域映射到 1（在多于 1 个域的 GPU 上）。特定库可能在 CUDA 12.0 及以后用远程域标记启动；例如 NCCL 2.16 会这样做。这样一来，开箱即用的常见应用程序就能形成有益的使用模式，框架或应用层的其他组件无需改动。另一种使用模式，例如在使用 NVSHMEM 或核函数类型没有明确区分的应用程序中，可以按并行流划分：流 A 把两个逻辑域都映射到物理域 0，流 B 映射到 1，依此类推。

```cpp
// 用远程逻辑域启动核函数的示例
cudaLaunchAttribute domainAttr;
domainAttr.id = cudaLaunchAttrMemSyncDomain;
domainAttr.val = cudaLaunchMemSyncDomainRemote;
cudaLaunchConfig_t config;
// 填写其他配置字段
config.attrs = &domainAttr;
config.numAttrs = 1;
cudaLaunchKernelEx(&config, myKernel, kernelArg1, kernelArg2...);
```

```cpp
// 为流设置映射的示例
// （在计算能力 9.0（Hopper）及以后的流上，如果未显式设置，
// 这就是默认映射，这里仅作说明）
cudaLaunchAttributeValue mapAttr;
mapAttr.memSyncDomainMap.default_ = 0;
mapAttr.memSyncDomainMap.remote = 1;
cudaStreamSetAttribute(stream, cudaLaunchAttributeMemSyncDomainMap, &mapAttr);
```

```cpp
// 把不同流映射到不同物理域、忽略逻辑域设置的示例
cudaLaunchAttributeValue mapAttr;
mapAttr.memSyncDomainMap.default_ = 0;
mapAttr.memSyncDomainMap.remote = 0;
cudaStreamSetAttribute(streamA, cudaLaunchAttributeMemSyncDomainMap, &mapAttr);

mapAttr.memSyncDomainMap.default_ = 1;
mapAttr.memSyncDomainMap.remote = 1;
cudaStreamSetAttribute(streamB, cudaLaunchAttributeMemSyncDomainMap, &mapAttr);
```

与其他启动属性一样，这些属性在 CUDA 流、用 `cudaLaunchKernelEx` 的单次启动、CUDA 图中的核函数节点上统一暴露。典型用法是在流层面设置映射、在启动层面（或一段流使用期间）设置逻辑域，如上所述。

流捕获期间这两个属性都会拷贝到图节点。图从节点自身获取这两个属性，本质上是间接指定物理域的一种方式。图启动到的流上设置的域相关属性在图执行时不使用。
