# 5.6 设备端可调用 API 与内联函数

本章包含参考资料与 API 文档，介绍可以从 CUDA 核函数和设备端代码中调用的 API 与内联函数（intrinsics）。

## 5.6.1 内存屏障原语接口

原语 API 是 `cuda::barrier` 功能的一套类 C 接口。包含头文件 `<cuda_awbarrier_primitives.h>` 即可使用这些原语。

### 5.6.1.1 数据类型

```c
typedef /* implementation defined */ __mbarrier_t;
typedef /* implementation defined */ __mbarrier_token_t;
```

### 5.6.1.2 内存屏障原语 API

```c
uint32_t __mbarrier_maximum_count();
```

```c
void __mbarrier_init(__mbarrier_t* bar, uint32_t expected_count);
```

- `bar` 必须是指向 `__shared__` 内存的指针。
- `expected_count <= __mbarrier_maximum_count()`。
- 将 `*bar` 在当前及下一阶段的预期到达计数初始化为 `expected_count`。

```c
void __mbarrier_inval(__mbarrier_t* bar);
```

- `bar` 必须是指向驻留在共享内存中的屏障对象的指针。
- 在将相应共享内存挪作他用之前，必须先使 `*bar` 失效。

```c
__mbarrier_token_t __mbarrier_arrive(__mbarrier_t* bar);
```

- 调用前必须先完成 `*bar` 的初始化。
- 待处理计数（pending count）不得为零。
- 以原子方式将屏障当前阶段的待处理计数减一。
- 返回与递减紧前一刻屏障状态相关联的到达令牌（token）。

```c
__mbarrier_token_t __mbarrier_arrive_and_drop(__mbarrier_t* bar);
```

- 调用前必须先完成 `*bar` 的初始化。
- 待处理计数不得为零。
- 以原子方式将当前阶段的待处理计数减一，并将屏障下一阶段的预期计数减一。
- 返回与递减紧前一刻屏障状态相关联的到达令牌。

```c
bool __mbarrier_test_wait(__mbarrier_t* bar, __mbarrier_token_t token);
```

- `token` 必须与 `*bar` 紧前一阶段或当前阶段相关联。
- 若 `token` 与 `*bar` 的紧前一阶段相关联，返回 true，否则返回 false。

```c
bool __mbarrier_test_wait_parity(__mbarrier_t* bar, bool phase_parity);
```

- `phase_parity` 必须指示 `*bar` 当前阶段或紧前一阶段的奇偶性。`true` 对应奇数阶段，`false` 对应偶数阶段。
- 若 `phase_parity` 指示的整数奇偶性对应 `*bar` 的紧前一阶段，返回 true，否则返回 false。

```c
bool __mbarrier_try_wait(__mbarrier_t* bar, __mbarrier_token_t token, uint32_t max_sleep_nanosec);
```

- `token` 必须与 `*bar` 紧前一阶段或当前阶段相关联。
- 若 `token` 与 `*bar` 的紧前一阶段相关联，返回 true。否则，执行线程可能被挂起。被挂起的线程在指定阶段完成时恢复执行（返回 true），或在系统相关时间限制到达前（阶段尚未完成）恢复执行（返回 false）。
- `max_sleep_nanosec` 指定可用的时间限制（纳秒），用于替代系统相关的时间限制。

```c
bool __mbarrier_try_wait_parity(__mbarrier_t* bar, bool phase_parity, uint32_t max_sleep_nanosec);
```

- `phase_parity` 必须指示 `*bar` 当前阶段或紧前一阶段的奇偶性。`true` 对应奇数阶段，`false` 对应偶数阶段。
- 若 `phase_parity` 指示的整数奇偶性对应 `*bar` 的紧前一阶段，返回 true。否则，执行线程可能被挂起。被挂起的线程在指定阶段完成时恢复执行（返回 true），或在系统相关时间限制到达前（阶段尚未完成）恢复执行（返回 false）。
- `max_sleep_nanosec` 指定可用的时间限制（纳秒），用于替代系统相关的时间限制。

## 5.6.2 流水线原语接口

流水线原语为 `<cuda/pipeline>` 提供的功能提供了一套类 C 接口。包含头文件 `<cuda_pipeline.h>` 即可使用流水线原语接口；在不兼容 ISO C++ 2011 的情况下编译时，应包含 `<cuda_pipeline_primitives.h>` 头文件。

> **注**
>
> 流水线原语 API 仅支持跟踪从全局内存到共享内存的异步拷贝，且对拷贝的大小和对齐有特定要求。它提供与采用 `cuda::thread_scope_thread` 的 `cuda::pipeline` 对象等价的功能。

### 5.6.2.1 memcpy_async 原语

```c
void __pipeline_memcpy_async(void* __restrict__ dst_shared,
                             const void* __restrict__ src_global,
                             size_t size_and_align,
                             size_t zfill=0);
```

- 请求将以下操作提交为异步执行：

```c
size_t i = 0;
for (; i < size_and_align - zfill; ++i) ((char*)dst_shared)[i] = ((char*)src_global)[i]; /* copy */
for (; i < size_and_align; ++i) ((char*)dst_shared)[i] = 0; /* zero-fill */
```

- 要求：
  - `dst_shared` 必须是指向 `memcpy_async` 共享内存目标的指针。
  - `src_global` 必须是指向 `memcpy_async` 全局内存源的指针。
  - `size_and_align` 必须为 4、8 或 16。
  - `zfill <= size_and_align`。
  - `size_and_align` 必须同时是 `dst_shared` 和 `src_global` 的对齐值。
- 在等待 `memcpy_async` 操作完成之前，任何线程修改源内存或观察目标内存都构成竞态条件。在提交 `memcpy_async` 操作与等待其完成之间，以下任一行为都会引入竞态条件：
  - 从 `dst_shared` 读取。
  - 向 `dst_shared` 或 `src_global` 写入。
  - 对 `dst_shared` 或 `src_global` 应用原子更新。

### 5.6.2.2 提交原语

```c
void __pipeline_commit();
```

- 将已提交的 `memcpy_async` 作为当前批次提交到流水线。

### 5.6.2.3 等待原语

```c
void __pipeline_wait_prior(size_t N);
```

- 设 `{0, 1, 2, ..., L}` 为某线程调用 `__pipeline_commit()` 所对应索引的序列。
- 等待批次完成，至少等到（包含）第 `L-N` 批次。

### 5.6.2.4 屏障到达原语

```c
void __pipeline_arrive_on(__mbarrier_t* bar);
```

- `bar` 指向共享内存中的屏障。
- 将屏障到达计数加一；当在本调用之前已排序的所有 `memcpy_async` 操作完成后，到达计数减一，因此对到达计数的净效应为零。用户有责任确保到达计数的增量不超过 `__mbarrier_maximum_count()`。

## 5.6.3 协作组 API

### 5.6.3.1 cooperative_groups.h

#### 5.6.3.1.1 class thread_block

任何 CUDA 程序员都熟悉一组特定的线程：线程块。协作组（Cooperative Groups）扩展引入了一种新数据类型 `thread_block`，用于在核函数中显式表示这个概念。

```cpp
class thread_block;
```

通过以下方式构造：

```cpp
thread_block g = this_thread_block();
```

公有成员函数：

- `static void sync()`：同步组中指定的线程，等价于 `g.barrier_wait(g.barrier_arrive())`。
- `thread_block::arrival_token barrier_arrive()`：到达线程块屏障，返回一个令牌，该令牌需要传入 `barrier_wait()`。
- `void barrier_wait(thread_block::arrival_token&& t)`：在线程块屏障上等待，接受 `barrier_arrive()` 返回的到达令牌作为右值引用。
- `static unsigned int thread_rank()`：调用线程在 `[0, num_threads)` 范围内的编号。
- `static dim3 group_index()`：线程块在启动网格中的三维索引。
- `static dim3 thread_index()`：线程在启动线程块中的三维索引。
- `static dim3 dim_threads()`：启动线程块的维度（以线程为单位）。
- `static unsigned int num_threads()`：组中线程的总数。
- 历史成员函数（别名）：
  - `static unsigned int size()`：组中线程的总数（`num_threads()` 的别名）。
  - `static dim3 group_dim()`：启动线程块的维度（`dim_threads()` 的别名）。

示例：

```cpp
/// Loading an integer from global into shared memory
__global__ void kernel(int *globalInput) {
    __shared__ int x;
    thread_block g = this_thread_block();
    // Choose a leader in the thread block
    if (g.thread_rank() == 0) {
        // load from global into shared for all threads to work with
        x = (*globalInput);
    }
    // After loading data into shared memory, you want to synchronize
    // if all threads in your thread block need to see it
    g.sync(); // equivalent to __syncthreads();
}
```

注：组中所有线程都必须参与集合操作，否则行为未定义。

相关：`thread_block` 数据类型派生自更通用的 `thread_group` 数据类型，后者可用于表示更广泛的组。
#### 5.6.3.1.2 class cluster_group

该组对象表示在单个集群（cluster）中启动的所有线程。这些 API 在计算能力 9.0+ 的所有硬件上均可用。若启动的是非集群网格，这些 API 将假定为 1×1×1 的集群。

#### 5.6.3.1.4 class thread_block_tile

平铺组的模板版本，模板参数用于指定平铺的大小——由于大小在编译期已知，有可能获得更优的执行性能。

```cpp
template <unsigned int Size, typename ParentT = void>
class thread_block_tile;
```

通过以下方式构造：

```cpp
template <unsigned int Size, typename ParentT>
_CG_QUALIFIER thread_block_tile<Size, ParentT> tiled_partition(const ParentT& g)
```

`Size` 必须为 2 的幂且小于等于 1024。在计算能力 7.5 或更低的硬件上创建大于 32 的平铺时，需要执行额外步骤，见注释（Notes）部分的说明。`ParentT` 是该组划分自的父组类型，自动推导；取值为 `void` 时，将该信息存储在组句柄而非类型中。

公有成员函数：

- `void sync() const`：同步组中指定的线程。
- `unsigned long long num_threads() const`：组中线程的总数。
- `unsigned long long thread_rank() const`：调用线程在 `[0, num_threads)` 范围内的编号。
- `unsigned long long meta_group_size() const`：返回对父组进行划分时创建的组数。
- `unsigned long long meta_group_rank() const`：该组在从父组划分出的平铺集合中的线性编号（以 `meta_group_size` 为界）。
- `T shfl(T var, unsigned int src_rank) const`：参见线程束洗牌函数（Warp Shuffle Functions）。注：对于大于 32 的尺寸，组中所有线程必须指定相同的 `src_rank`，否则行为未定义。
- `T shfl_up(T var, int delta) const`：参见线程束洗牌函数，仅适用于小于等于 32 的尺寸。
- `T shfl_down(T var, int delta) const`：参见线程束洗牌函数，仅适用于小于等于 32 的尺寸。
- `T shfl_xor(T var, int delta) const`：参见线程束洗牌函数，仅适用于小于等于 32 的尺寸。
- `int any(int predicate) const`：参见线程束投票函数（Warp Vote Functions）。
- `int all(int predicate) const`：参见线程束投票函数。
- `unsigned int ballot(int predicate) const`：参见线程束投票函数，仅适用于小于等于 32 的尺寸。
- `unsigned int match_any(T val) const`：参见线程束匹配函数（Warp Match Functions），仅适用于小于等于 32 的尺寸。
- `unsigned int match_all(T val, int &pred) const`：参见线程束匹配函数，仅适用于小于等于 32 的尺寸。
- 历史成员函数（别名）：
  - `unsigned long long size() const`：组中线程的总数（`num_threads()` 的别名）。

注：

- 这里使用的是模板化数据结构 `thread_block_tile`，组的大小作为模板参数（而非函数参数）传入 `tiled_partition` 调用。
- `shfl`、`shfl_up`、`shfl_down` 和 `shfl_xor` 函数在 C++11 或更高版本下编译时接受任意类型的对象。也就是说，只要满足以下约束，非整数类型也可以参与洗牌：
  - 是可平凡拷贝的，即 `is_trivially_copyable<T>::value == true`。
  - 对于小于等于 32 的平铺尺寸，`sizeof(T) <= 32`；对于更大的平铺，`sizeof(T) <= 8`。
- 在计算能力 7.5 或更低的硬件上，大于 32 的平铺需要预留少量内存。可使用 `cooperative_groups::block_tile_memory` 结构体模板完成，该结构必须驻留在共享内存或全局内存中。

```cpp
template <unsigned int MaxBlockSize = 1024>
struct block_tile_memory;
```

`MaxBlockSize` 指定当前线程块中的最大线程数。该参数可用于最小化 `block_tile_memory` 在仅以较小线程数启动的核函数中的共享内存占用。

`block_tile_memory` 需传入 `cooperative_groups::this_thread_block`，以便将生成的 `thread_block` 划分为大于 32 的平铺。接受 `block_tile_memory` 参数的 `this_thread_block` 重载是集合操作，必须由线程块中所有线程调用。`block_tile_memory` 也可用于计算能力 8.0 或更高的硬件，以编写一份源码兼容多种计算能力；当无需预留内存时，将其实例化在共享内存中不应消耗内存。

示例：

```cpp
/// The following code will create two sets of tiled groups, of size 32 and 4 respectively:

/// The latter has the provenance encoded in the type, while the first stores it in the handle

thread_block block = this_thread_block();
thread_block_tile<32> tile32 = tiled_partition<32>(block);
thread_block_tile<4, thread_block> tile4 = tiled_partition<4>(block);

/// The following code will create tiles of size 128 on all Compute Capabilities.

/// block_tile_memory can be omitted on Compute Capability 8.0 or higher.
__global__ void kernel(...) {
     // reserve shared memory for thread_block_tile usage,
     //   specify that block size will be at most 256 threads.
     __shared__ block_tile_memory<256> shared;
     thread_block thb = this_thread_block(shared);

     // Create tiles with 128 threads.
     auto tile = tiled_partition<128>(thb);

     // ...
}
```

#### 5.6.3.1.5 class coalesced_group

在 CUDA 的 SIMT 架构中，硬件层面多处理器以 32 个线程为一组（称为线程束，warp）执行线程。若应用程序代码中存在数据相关的条件分支，使得线程束内的线程产生分支分化，则线程束会串行执行每个分支，禁用不在该路径上的线程。保留在路径上保持活跃的线程称为合并（coalesced）线程。协作组提供了发现并创建一个包含所有合并线程的组的功能。

通过 `coalesced_threads()` 构造组句柄是机会性的：它返回该时刻活跃的线程集合，不保证返回哪些线程（只要是活跃的即可），也不保证这些线程在整个执行期间保持合并状态（它们会为执行集合操作而重新汇合，但之后仍可能再次分化）。

```cpp
class coalesced_group;
```

通过以下方式构造：

```cpp
coalesced_group active = coalesced_threads();
```

公有成员函数：

- `void sync() const`：同步组中指定的线程。
- `unsigned long long num_threads() const`：组中线程的总数。
- `unsigned long long thread_rank() const`：调用线程在 `[0, num_threads)` 范围内的编号。
- `unsigned long long meta_group_size() const`：返回对父组进行划分时创建的组数。若该组是通过查询活跃线程集合创建的（例如 `coalesced_threads()`），`meta_group_size()` 的值为 1。
- `unsigned long long meta_group_rank() const`：该组在从父组划分出的平铺集合中的线性编号（以 `meta_group_size` 为界）。若该组是通过查询活跃线程集合创建的（例如 `coalesced_threads()`），`meta_group_rank()` 的值恒为 0。
- `T shfl(T var, unsigned int src_rank) const`：参见线程束洗牌函数。
- `T shfl_up(T var, int delta) const`：参见线程束洗牌函数。
- `T shfl_down(T var, int delta) const`：参见线程束洗牌函数。
- `int any(int predicate) const`：参见线程束投票函数。
- `int all(int predicate) const`：参见线程束投票函数。
- `unsigned int ballot(int predicate) const`：参见线程束投票函数。
- `unsigned int match_any(T val) const`：参见线程束匹配函数。
- `unsigned int match_all(T val, int &pred) const`：参见线程束匹配函数。
- 历史成员函数（别名）：
  - `unsigned long long size() const`：组中线程的总数（`num_threads()` 的别名）。

注：`shfl`、`shfl_up` 和 `shfl_down` 函数在 C++11 或更高版本下编译时接受任意类型的对象。也就是说，只要满足以下约束，非整数类型也可以参与洗牌：

- 是可平凡拷贝的，即 `is_trivially_copyable<T>::value == true`。
- `sizeof(T) <= 32`。

示例：

```cpp
/// Consider a situation whereby there is a branch in the
/// code in which only the 2nd, 4th and 8th threads in each warp are
/// active. The coalesced_threads() call, placed in that branch, will create (for each
/// warp) a group, active, that has three threads (with
/// ranks 0-2 inclusive).
__global__ void kernel(int *globalInput) {
     // Lets say globalInput says that threads 2, 4, 8 should handle the data
     if (threadIdx.x == *globalInput) {
         coalesced_group active = coalesced_threads();
         // active contains 0-2 inclusive
         active.sync();
     }
}
```

### 5.6.3.2 cooperative_groups/async.h

#### 5.6.3.2.1 memcpy_async

`memcpy_async` 是组范围的集合拷贝（collective memcpy），利用硬件加速支持从全局内存到共享内存的非阻塞内存事务。给定组中指定的线程集合，`memcpy_async` 会通过单个流水线阶段移动指定数量的字节，或指定输入类型指定数量的元素。此外，要通过 `memcpy_async` API 获得最佳性能，要求共享内存和全局内存的对齐均为 16 字节。需要注意的是，虽然一般情况下这是一个 memcpy，但只有当源是全局内存、目标是共享内存，且二者均可按 16、8 或 4 字节对齐寻址时，它才是异步的。异步拷贝的数据只能在调用 `wait` 或 `wait_prior`（表示相应阶段已完成向共享内存的数据搬运）之后读取。

必须等待所有未完成请求的做法会丧失一些灵活性（但换来了简单性）。为了高效地重叠数据传输与执行，重要的是能够在等待并处理请求 N 的同时发起第 N+1 个 `memcpy_async` 请求。为此，请使用 `memcpy_async` 并通过基于阶段的集合式 `wait_prior` API 等待。详见 `wait` 和 `wait_prior`。

用法 1

```cpp
template <typename TyGroup, typename TyElem, typename TyShape>
void memcpy_async(
   const TyGroup &group,
   TyElem *__restrict__ _dst,
   const TyElem *__restrict__ _src,
   const TyShape &shape
);
```

拷贝 `shape` 个字节。

用法 2

```cpp
template <typename TyGroup, typename TyElem, typename TyDstLayout, typename TySrcLayout>
void memcpy_async(
   const TyGroup &group,
   TyElem *__restrict__ dst,
   const TyDstLayout &dstLayout,
   const TyElem *__restrict__ src,
   const TySrcLayout &srcLayout
);
```

拷贝 `min(dstLayout, srcLayout)` 个元素。若布局类型为 `cuda::aligned_size_t<N>`，二者必须指定相同的对齐。

勘误：CUDA 11.1 引入的 `memcpy_async` API（同时带 src 和 dst 输入布局）要求布局以元素而非字节为单位提供。元素类型由 `TyElem` 推导，大小为 `sizeof(TyElem)`。若布局使用 `cuda::aligned_size_t<N>` 类型，则元素个数乘以 `sizeof(TyElem)` 必须为 N 的整数倍，且建议使用 `std::byte` 或 `char` 作为元素类型。

若拷贝的指定形状或布局类型为 `cuda::aligned_size_t<N>`，对齐将保证至少为 `min(16, N)`。此时 `dst` 和 `src` 指针都必须按 N 字节对齐，拷贝的字节数必须为 N 的整数倍。

代码生成要求：最低计算能力 5.0，异步功能需要计算能力 8.0；C++11。

需要包含 `cooperative_groups/memcpy_async.h` 头文件。

示例：

```cpp
/// This example streams elementsPerThreadBlock worth of data from global memory
/// into a limited sized shared memory (elementsInShared) block to operate on.
#include <cooperative_groups.h>
#include <cooperative_groups/memcpy_async.h>

namespace cg = cooperative_groups;

__global__ void kernel(int* global_data) {
    cg::thread_block tb = cg::this_thread_block();
    const size_t elementsPerThreadBlock = 16 * 1024;
    const size_t elementsInShared = 128;
    __shared__ int local_smem[elementsInShared];

     size_t copy_count;
     size_t index = 0;
     while (index < elementsPerThreadBlock) {
         cg::memcpy_async(tb, local_smem, elementsInShared, global_data + index, elementsPerThreadBlock - index);

         copy_count = min(elementsInShared, elementsPerThreadBlock - index);
         cg::wait(tb);
         // Work with local_smem
         index += copy_count;
     }
}
```

#### 5.6.3.2.2 wait 和 wait_prior

```cpp
template <typename TyGroup>
void wait(TyGroup & group);

template <unsigned int NumStages, typename TyGroup>
void wait_prior(TyGroup & group);
```

`wait` 和 `wait_prior` 集合函数用于等待 `memcpy_async` 拷贝完成。`wait` 会阻塞调用线程，直到之前所有拷贝完成。`wait_prior` 允许最后 `NumStages` 个拷贝尚未完成，只等待之前的请求。因此，若共请求了 N 次拷贝，它会等待直到前 N−NumStages 次完成，最后 NumStages 次可能仍在进行。`wait` 和 `wait_prior` 都会同步指定的组。

代码生成要求：最低计算能力 5.0，异步功能需要计算能力 8.0；C++11。

需要包含 `cooperative_groups/memcpy_async.h` 头文件。

示例：

```cpp
/// This example streams elementsPerThreadBlock worth of data from global memory
/// into a limited sized shared memory (elementsInShared) block to operate on in
/// multiple (two) stages. As stage N is kicked off, we can wait on and operate on stage N-1.

#include <cooperative_groups.h>
#include <cooperative_groups/memcpy_async.h>

namespace cg = cooperative_groups;

__global__ void kernel(int* global_data) {
     cg::thread_block tb = cg::this_thread_block();
     const size_t elementsPerThreadBlock = 16 * 1024 + 64;
     const size_t elementsInShared = 128;
     __align__(16) __shared__ int local_smem[2][elementsInShared];
     int stage = 0;
     // First kick off an extra request
     size_t copy_count = elementsInShared;
     size_t index = copy_count;
     cg::memcpy_async(tb, local_smem[stage], elementsInShared, global_data, elementsPerThreadBlock - index);

     while (index < elementsPerThreadBlock) {
         // Now we kick off the next request...
         cg::memcpy_async(tb, local_smem[stage ^ 1], elementsInShared, global_data + index, elementsPerThreadBlock - index);

         // ... but we wait on the one before it
         cg::wait_prior<1>(tb);

           // Its now available and we can work with local_smem[stage] here
           // (...)
           //

           // Calculate the amount of data that was actually copied, for the next iteration.
           copy_count = min(elementsInShared, elementsPerThreadBlock - index);
           index += copy_count;

         // A cg::sync(tb) might be needed here depending on whether
         // the work done with local_smem[stage] can release threads to race ahead or not

         // Wrap to the next stage
         stage ^= 1;
     }
     cg::wait(tb);
     // The last local_smem[stage] can be handled here
}
```
### 5.6.3.3 cooperative_groups/partition.h

#### 5.6.3.3.1 tiled_partition

```cpp
template <unsigned int Size, typename ParentT>
thread_block_tile<Size, ParentT> tiled_partition(const ParentT& g);

```

`tiled_partition` 方法是集合操作，将父组按行主序一维平铺划分为子组。共创建 `(size(parent)/tilesz)` 个子组，因此父组大小必须能被 `Size` 整除。允许的父组为 `thread_block` 或 `thread_block_tile`。

实现可能导致调用线程等待，直到父组所有成员都调用了该操作才恢复执行。功能限制在原生硬件尺寸 1/2/4/8/16/32 上，`cg::size(parent)` 必须大于 `Size` 参数。`tiled_partition` 的模板版本还支持 64/128/256/512 尺寸，但在计算能力 7.5 或更低的硬件上需要额外步骤，详见 `class thread_block_tile`。

代码生成要求：最低计算能力 5.0；大于 32 的尺寸需要 C++11。

### 5.6.3.4 cooperative_groups/reduce.h

#### 5.6.3.4.1 归约算子（Reduce Operators）

以下是对可与 `reduce` 配合使用的一些基本操作的函数对象原型。

```cpp
namespace cooperative_groups {
  template <typename Ty>
  struct cg::plus;

    template <typename Ty>
    struct cg::less;

    template <typename Ty>
    struct cg::greater;

    template <typename Ty>
    struct cg::bit_and;

    template <typename Ty>
    struct cg::bit_xor;

    template <typename Ty>
    struct cg::bit_or;
}
```

归约受限于编译期实现可知的信息。因此，为了利用计算能力 8.0 引入的内联函数（intrinsics），`cg::` 命名空间暴露了若干镜像硬件的函数对象。这些对象与 C++ STL 中呈现的类似，`less`/`greater` 除外。与 STL 有差异的原因是，这些函数对象被设计为实际镜像硬件内联函数的操作。

功能说明：

- `cg::plus`：接受两个值，用 `operator+` 返回二者之和。
- `cg::less`：接受两个值，用 `operator<` 返回较小值。差异在于返回较小的值而非布尔值。
- `cg::greater`：接受两个值，用 `operator<` 返回较大值。差异在于返回较大的值而非布尔值。
- `cg::bit_and`：接受两个值，返回 `operator&` 的结果。
- `cg::bit_xor`：接受两个值，返回 `operator^` 的结果。
- `cg::bit_or`：接受两个值，返回 `operator|` 的结果。

示例：

```cpp
{
       // cg::plus<int> is specialized within cg::reduce and calls __reduce_add_sync(...) on CC 8.0+
       cg::reduce(tile, (int)val, cg::plus<int>());

       // cg::plus<float> fails to match with an accelerator and instead performs a standard shuffle based reduction
       cg::reduce(tile, (float)val, cg::plus<float>());

    // While individual components of a vector are supported, reduce will not use hardware intrinsics for the following
    // It will also be necessary to define a corresponding operator for vector and any custom types that may be used

    int4 vec = {...};
    cg::reduce(tile, vec, cg::plus<int4>())

     // Finally lambdas and other function objects cannot be inspected for dispatch
     // and will instead perform shuffle based reductions using the provided function object.

     cg::reduce(tile, (int)val, [](int l, int r) -> int {return l + r;});
}
```

#### 5.6.3.4.2 reduce

```cpp
template <typename TyGroup, typename TyArg, typename TyOp>
auto reduce(const TyGroup& group, TyArg&& val, TyOp&& op) -> decltype(op(val, val));
```

`reduce` 对传入组中每个指定线程提供的数据执行归约操作。在算术加、min、max 操作以及逻辑 AND、OR、XOR 方面，利用硬件加速（在计算能力 8.0 及更高设备上），在旧代硬件上提供软件回退。只有 4 字节类型由硬件加速。

- `group`：有效组类型为 `coalesced_group` 和 `thread_block_tile`。
- `val`：满足以下要求的任意类型：
  - 是可平凡拷贝的，即 `is_trivially_copyable<TyArg>::value == true`。
  - 对于 `coalesced_group` 和小于等于 32 的平铺，`sizeof(T) <= 32`；对于更大的平铺，`sizeof(T) <= 8`。
  - 针对给定的函数对象，具有合适的算术或比较算子。
- 注：组中不同线程可为该参数传入不同的值。
- `op`：与整数类型配合可提供硬件加速的有效函数对象有 `plus()`、`less()`、`greater()`、`bit_and()`、`bit_xor()`、`bit_or()`。这些必须已构造，因此需要 `TyVal` 模板参数，例如 `plus<int>()`。`reduce` 也支持可用 `operator()` 调用的 lambda 和其他函数对象。

异步归约（Asynchronous reduce）：

```cpp
template <typename TyGroup, typename TyArg, typename TyAtomic, typename TyOp>
void reduce_update_async(const TyGroup& group, TyAtomic& atomic, TyArg&& val, TyOp&& op);

template <typename TyGroup, typename TyArg, typename TyAtomic, typename TyOp>
void reduce_store_async(const TyGroup& group, TyAtomic& atomic, TyArg&& val, TyOp&& op);

template <typename TyGroup, typename TyArg, typename TyOp>
void reduce_store_async(const TyGroup& group, TyArg* ptr, TyArg&& val, TyOp&& op);
```

该 API 的 `*_async` 变体异步计算结果，并由参与线程之一存储到或更新到指定目标，而不是由每个线程返回。要观察这些异步调用的效果，调用线程所在的组或包含该组的更大组需要同步。

- 对于原子存储或更新变体，`atomic` 参数可以是 CUDA C++ 标准库提供的 `cuda::atomic` 或 `cuda::atomic_ref`。该 API 变体仅在 CUDA C++ 标准库支持这些类型的平台和设备上可用。归约结果按指定的 `op` 原子地更新原子变量，例如在 `cg::plus()` 的情况下将结果原子地加到原子变量上。原子变量持有类型必须与 `TyArg` 类型匹配。原子变量的作用域必须包含组中所有线程；若多个组并发使用同一原子变量，作用域必须包含所有使用该原子变量的组中的全部线程。原子更新采用宽松（relaxed）内存序。
- 对于指针存储变体，归约结果将被弱（weakly）存储到 `dst` 指针。

### 5.6.3.5 cooperative_groups/scan.h

#### 5.6.3.5.1 inclusive_scan 和 exclusive_scan

```cpp
template <typename TyGroup, typename TyVal, typename TyFn>
auto inclusive_scan(const TyGroup& group, TyVal&& val, TyFn&& op) -> decltype(op(val, val));

template <typename TyGroup, typename TyVal>
TyVal inclusive_scan(const TyGroup& group, TyVal&& val);

template <typename TyGroup, typename TyVal, typename TyFn>
auto exclusive_scan(const TyGroup& group, TyVal&& val, TyFn&& op) -> decltype(op(val, val));

template <typename TyGroup, typename TyVal>
TyVal exclusive_scan(const TyGroup& group, TyVal&& val);
```

`inclusive_scan` 和 `exclusive_scan` 对传入组中每个指定线程提供的数据执行扫描操作。对每个线程，其结果是该线程在 `exclusive_scan` 情况下对 `thread_rank` 更低的线程数据的归约；`inclusive_scan` 的结果还将调用线程自身的数据纳入归约。

- `group`：有效组类型为 `coalesced_group` 和 `thread_block_tile`。
- `val`：满足以下要求的任意类型：
  - 是可平凡拷贝的，即 `is_trivially_copyable<TyArg>::value == true`。
  - 对于 `coalesced_group` 和小于等于 32 的平铺，`sizeof(T) <= 32`；对于更大的平铺，`sizeof(T) <= 8`。
  - 针对给定的函数对象，具有合适的算术或比较算子。
- 注：组中不同线程可为该参数传入不同的值。
- `op`：为方便定义的函数对象有 `plus()`、`less()`、`greater()`、`bit_and()`、`bit_xor()`、`bit_or()`，见 cooperative_groups/reduce.h。这些必须已构造，因此需要 `TyVal` 模板参数，例如 `plus<int>()`。`inclusive_scan` 和 `exclusive_scan` 也支持可用 `operator()` 调用的 lambda 和其他函数对象。不带该参数的重载使用 `cg::plus<TyVal>()`。

扫描更新（Scan update）：

```cpp
template <typename TyGroup, typename TyAtomic, typename TyVal, typename TyFn>
auto inclusive_scan_update(const TyGroup& group, TyAtomic& atomic, TyVal&& val, TyFn&& op) -> decltype(op(val, val));

template <typename TyGroup, typename TyAtomic, typename TyVal>
TyVal inclusive_scan_update(const TyGroup& group, TyAtomic& atomic, TyVal&& val);

template <typename TyGroup, typename TyAtomic, typename TyVal, typename TyFn>
auto exclusive_scan_update(const TyGroup& group, TyAtomic& atomic, TyVal&& val, TyFn&& op) -> decltype(op(val, val));

template <typename TyGroup, typename TyAtomic, typename TyVal>
TyVal exclusive_scan_update(const TyGroup& group, TyAtomic& atomic, TyVal&& val);
```

`*_scan_update` 集合函数接受一个额外参数 `atomic`，可以是 CUDA C++ 标准库提供的 `cuda::atomic` 或 `cuda::atomic_ref`。这些 API 变体仅在 CUDA C++ 标准库支持这些类型的平台和设备上可用。这些变体将按 `op` 用组中所有线程输入值之和更新原子变量。原子变量的原有值将与每个线程的扫描结果合并后返回。原子变量持有类型必须与 `TyVal` 类型匹配。原子变量的作用域必须包含组中所有线程；若多个组并发使用同一原子变量，作用域必须包含所有使用该原子变量的组中的全部线程。原子更新采用宽松内存序。

以下伪代码说明扫描的 update 变体如何工作：

```cpp
/*
 inclusive_scan_update behaves as the following block,
 except both reduce and inclusive_scan is calculated simultaneously.
auto total = reduce(group, val, op);
TyVal old;
if (group.thread_rank() == selected_thread) {
    atomically {
        old = atomic.load();
        atomic.store(op(old, total));
    }
}
old = group.shfl(old, selected_thread);
return op(inclusive_scan(group, val, op), old);
*/
```

需要包含 `cooperative_groups/scan.h` 头文件。

使用 `exclusive_scan` 进行流压缩（stream compaction）的示例：

```cpp
#include <cooperative_groups.h>
#include <cooperative_groups/scan.h>
namespace cg = cooperative_groups;

// put data from input into output only if it passes test_fn predicate
template<typename Group, typename Data, typename TyFn>
__device__ int stream_compaction(Group &g, Data *input, int count, TyFn&& test_fn, Data *output) {

     int per_thread = count / g.num_threads();
     int thread_start = min(g.thread_rank() * per_thread, count);
     int my_count = min(per_thread, count - thread_start);

     // get all passing items from my part of the input
     // into a contagious part of the array and count them.
     int i = thread_start;
     while (i < my_count + thread_start) {
         if (test_fn(input[i])) {
             i++;
         }
         else {
             my_count--;
             input[i] = input[my_count + thread_start];
         }
     }

     // scan over counts from each thread to calculate my starting
     // index in the output
     int my_idx = cg::exclusive_scan(g, my_count);

     for (i = 0; i < my_count; ++i) {
         output[my_idx + i] = input[thread_start + i];
     }
     // return the total number of items in the output
     return g.shfl(my_idx + my_count, g.num_threads() - 1);
}
```

使用 `exclusive_scan_update` 进行动态缓冲空间分配的示例：

```cpp
#include <cooperative_groups.h>
#include <cooperative_groups/scan.h>
namespace cg = cooperative_groups;

// Buffer partitioning is static to make the example easier to follow,
// but any arbitrary dynamic allocation scheme can be implemented by replacing this function.

__device__ int calculate_buffer_space_needed(cg::thread_block_tile<32>& tile) {

     return tile.thread_rank() % 2 + 1;
}

__device__ int my_thread_data(int i) {
    return i;
}

__global__ void kernel() {
    __shared__ extern int buffer[];
    __shared__ cuda::atomic<int, cuda::thread_scope_block> buffer_used;

      auto block = cg::this_thread_block();
      auto tile = cg::tiled_partition<32>(block);
      buffer_used = 0;
      block.sync();

      // each thread calculates buffer size it needs
      int buf_needed = calculate_buffer_space_needed(tile);

    // scan over the needs of each thread, result for each thread is an offset
    // of that thread’s part of the buffer. buffer_used is atomically updated with

    // the sum of all thread's inputs, to correctly offset other tile’s allocations

    int buf_offset =
        cg::exclusive_scan_update(tile, buffer_used, buf_needed);

      // each thread fills its own part of the buffer with thread specific data
      for (int i = 0 ; i < buf_needed ; ++i) {
          buffer[buf_offset + i] = my_thread_data(i);
      }

      block.sync();
      // buffer_used now holds total amount of memory allocated
      // buffer is {0, 0, 1, 0, 0, 1 ...};
}
```

### 5.6.3.6 cooperative_groups/sync.h

#### 5.6.3.6.1 barrier_arrive 和 barrier_wait

```cpp
T::arrival_token T::barrier_arrive();
void T::barrier_wait(T::arrival_token&&);
```

`barrier_arrive` 和 `barrier_wait` 成员函数提供了一个类似 `cuda::barrier` 的同步 API（详见相关文档）。协作组自动初始化组屏障，但由于这些操作具有集合性质，arrive 和 wait 操作还有一条额外限制：每个阶段，组中所有线程必须在屏障上到达一次并等待一次。当用某个组调用 `barrier_arrive` 后，在通过 `barrier_wait` 调用观察到屏障阶段完成之前，调用任何集合操作或用该组再次进行屏障到达的结果都是未定义的。阻塞在 `barrier_wait` 上的线程可能在其他线程调用 `barrier_wait` 之前就被释放，但前提是组中所有线程都已调用 `barrier_arrive`。组类型 `T` 可以是任意隐式组。这允许线程在到达后、等待同步完成前做独立的工作，从而隐藏部分同步延迟。`barrier_arrive` 返回一个 `arrival_token` 对象，该对象必须传入对应的 `barrier_wait`。令牌以此方式被消费，不能再次用于另一次 `barrier_wait` 调用。

用 `barrier_arrive` 和 `barrier_wait` 同步集群间共享内存初始化的示例：

```cpp
#include <cooperative_groups.h>

using namespace cooperative_groups;

void __device__ init_shared_data(const thread_block& block, int *data);
void __device__ local_processing(const thread_block& block);
void __device__ process_shared_data(const thread_block& block, int *data);

__global__ void cluster_kernel() {
    extern __shared__ int array[];
    auto cluster = this_cluster();
    auto block   = this_thread_block();

       // Use this thread block to initialize some shared state
       init_shared_data(block, &array[0]);

       auto token = cluster.barrier_arrive(); // Let other blocks know this block is running and data was initialized

       // Do some local processing to hide the synchronization latency
       local_processing(block);
```
```cpp
    // Map data in shared memory from the next block in the cluster
    int *dsmem = cluster.map_shared_rank(&array[0], (cluster.block_rank() + 1) % cluster.num_blocks());



       // Make sure all other blocks in the cluster are running and initialized shared data before accessing dsmem
       cluster.barrier_wait(std::move(token));

       // Consume data in distributed shared memory
       process_shared_data(block, dsmem);
       cluster.sync();
}
```

#### 5.6.3.6.2 sync

```cpp
static void T::sync();

template <typename T>
void sync(T& group);
```

`sync` 同步组中指定的线程。组类型 `T` 可以是任意现有组类型，因为它们都支持同步。它既可作为每个组类型的成员函数使用，也可以作为接受组参数的自由函数使用。

##### 5.6.3.6.2.1 网格同步

在协作组引入之前，CUDA 编程模型只允许在核函数完成边界处进行线程块之间的同步。核函数边界隐含地带有状态失效，并可能带来性能影响。

例如，在某些用例中，应用程序有大量小核函数，每个核函数代表处理流水线中的一个阶段。当前 CUDA 编程模型要求这些核函数存在，以确保在一个流水线阶段上操作的线程块在生产数据后，操作下一流水线阶段的线程块才能消费数据。在这种情况下，若能提供全局的线程块间同步，应用程序就可以重构为具有持久线程块的形式，当某阶段完成时在设备上同步。

要在核函数内部跨网格同步，只需使用 `grid.sync()` 函数：

```cpp
grid_group grid = this_grid();
grid.sync();
```

而在启动核函数时，不能使用 `<<<...>>>` 执行配置语法，而必须使用 CUDA 运行时启动 API `cudaLaunchCooperativeKernel` 或 CUDA 驱动的等价接口。

示例：为保证 GPU 上线程块的共驻（co-residency），需要仔细考虑启动的线程块数量。例如，可按如下方式启动与 SM 数量相等的线程块：

```cpp
int dev = 0;
cudaDeviceProp deviceProp;
cudaGetDeviceProperties(&deviceProp, dev);
// initialize, then launch
cudaLaunchCooperativeKernel((void*)my_kernel, deviceProp.multiProcessorCount, numThreads, args);
```

或者，可以使用占用率计算器计算每个 SM 可同时容纳多少个线程块，从而最大化暴露的并行度，方法如下：

```cpp
/// This will launch a grid that can maximally fill the GPU, on the default stream with kernel arguments

int numBlocksPerSm = 0;
  // Number of threads my_kernel will be launched with
int numThreads = 128;
cudaDeviceProp deviceProp;
cudaGetDeviceProperties(&deviceProp, dev);
cudaOccupancyMaxActiveBlocksPerMultiprocessor(&numBlocksPerSm, my_kernel, numThreads, 0);

// launch
void *kernelArgs[] = { /* add kernel args */ };
dim3 dimBlock(numThreads, 1, 1);
dim3 dimGrid(deviceProp.multiProcessorCount*numBlocksPerSm, 1, 1);
cudaLaunchCooperativeKernel((void*)my_kernel, dimGrid, dimBlock, kernelArgs);
```

建议先通过查询设备属性 `cudaDevAttrCooperativeLaunch` 确认设备支持协作启动：

```cpp
int dev = 0;
int supportsCoopLaunch = 0;
cudaDeviceGetAttribute(&supportsCoopLaunch, cudaDevAttrCooperativeLaunch, dev);
```

若设备 0 支持该属性，`supportsCoopLaunch` 将被置为 1。只有计算能力 6.0 及更高的设备受支持。此外，还需要运行在以下任一环境：

- 无 MPS 的 Linux 平台；
- 带 MPS 且设备计算能力 7.0 或更高的 Linux 平台；
- 最新的 Windows 平台。

## 5.6.4 CUDA 设备运行时（CUDA Device Runtime）

CUDA 设备运行时是一套可在核函数代码内使用的 API，提供与主机端 CUDA 运行时 API 相同的许多功能。这些 API 最常用于 CUDA 动态并行（CUDA Dynamic Parallelism）或设备端图启动（Device Graph Launch）的场景。

### 5.6.4.1 在 CUDA 代码中包含设备运行时 API

与主机端运行时 API 类似，CUDA 设备运行时 API 的原型在程序编译期间自动包含，无需显式包含 `cuda_device_runtime_api.h`。

### 5.6.4.2 CUDA 设备运行时的内存

#### 5.6.4.2.1 配置选项

设备运行时系统软件的资源分配通过主机端程序中的 `cudaDeviceSetLimit()` API 控制。限制必须在启动任何核函数之前设置，且在 GPU 正在积极运行程序时不得更改。

可设置以下命名限制：

| 限制 | 行为 |
|---|---|
| cudaLimitDevRuntimePendingLaunchCount | 控制为缓冲核函数启动和尚未开始执行的事件而预留的内存量，原因可能是未解决的依赖或执行资源不足。缓冲满时，在设备端核函数启动期间尝试分配启动槽将失败并返回 `cudaErrorLaunchOutOfResources`，而尝试分配事件槽将失败并返回 `cudaErrorMemoryAllocation`。启动槽的默认数量为 2048。应用程序可通过设置 `cudaLimitDevRuntimePendingLaunchCount` 增加启动和/或事件槽的数量。分配的事件槽数量是该限制值的两倍。 |
| cudaLimitStackSize | 控制每个 GPU 线程的栈大小（字节）。CUDA 驱动会在每次核函数启动时根据需要自动增大每线程栈大小；此大小在每次启动后不会重置回原值。要将每线程栈大小设为不同的值，可调用 `cudaDeviceSetLimit()` 设置该限制。栈将被立即调整大小；如有必要，设备将阻塞，直到所有先前请求的任务完成。可调用 `cudaDeviceGetLimit()` 获取当前每线程栈大小。 |

#### 5.6.4.2.2 分配与生命周期

`cudaMalloc()` 和 `cudaFree()` 在主机端环境与设备端环境中的语义不同。从主机端调用时，`cudaMalloc()` 从未使用的设备内存中分配新区域。从设备运行时调用时，这些函数映射到设备端的 `malloc()` 和 `free()`。这意味着，在设备端环境中，可分配内存总量受限于设备 `malloc()` 堆大小，该堆可能小于可用未使用设备内存。此外，对由设备端 `cudaMalloc()` 分配的指针从主机端程序调用 `cudaFree()` 是错误的，反之亦然。

| | 主机端 cudaMalloc() | 设备端 cudaMalloc() |
|---|---|---|
| 主机端 cudaFree() | 支持 | 不支持 |
| 设备端 cudaFree() | 不支持 | 支持 |
| 分配上限 | 可用设备内存 | cudaLimitMallocHeapSize |

##### 5.6.4.2.2.1 内存声明

##### 5.6.4.2.2.2 设备端与常量内存

在文件作用域用 `__device__` 或 `__constant__` 内存空间限定符声明的内存，在使用设备运行时时行为相同。所有核函数都可读写设备端变量，无论该核函数最初是由主机端还是设备运行时启动的。同样，所有核函数在模块作用域声明的 `__constant__` 上具有相同视图。

##### 5.6.4.2.2.3 纹理与表面

设备运行时不允许在设备端代码内创建或销毁纹理或表面对象。从主机端创建的纹理和表面对象可在设备端自由使用和传递。无论在哪里创建，动态创建的纹理对象始终有效，并可从父核函数传递给子核函数。

> **注**
>
> 设备运行时不支持在设备端启动的核函数内使用旧式模块作用域（即计算能力 2.0 或 Fermi 风格）纹理和表面。模块作用域（旧式）纹理可从主机端创建，并在设备端代码中像任何核函数一样使用，但只能由顶层核函数（即从主机端启动的核函数）使用。

##### 5.6.4.2.2.4 共享内存变量声明

在 CUDA C++ 中，共享内存可声明为静态尺寸的文件作用域或函数作用域变量，也可声明为 `extern` 变量，其大小在运行时由核函数调用方通过启动配置参数确定。两种声明在设备运行时下均有效。

```cpp
__global__ void permute(int n, int *data) {
   extern __shared__ int smem[];
   if (n <= 1)
       return;

      smem[threadIdx.x] = data[threadIdx.x];
      __syncthreads();

      permute_data(smem, n);
      __syncthreads();

      // Write back to GMEM since we can't pass SMEM to children.
      data[threadIdx.x] = smem[threadIdx.x];
      __syncthreads();

      if (threadIdx.x == 0) {
          permute<<< 1, 256, n/2*sizeof(int) >>>(n/2, data);
          permute<<< 1, 256, n/2*sizeof(int) >>>(n/2, data+n/2);
      }
}
```
```cpp
void host_launch(int *data) {
    permute<<< 1, 256, 256*sizeof(int) >>>(256, data);
}
```

##### 5.6.4.2.2.5 常量内存

常量不能从设备端修改。只能从主机端修改；但在有并发网格于其生命周期的任意时刻访问该常量的情况下从主机端修改常量，行为未定义。

##### 5.6.4.2.2.6 符号地址

设备端符号（即标记为 `__device__` 的符号）在核函数内只需通过 `&` 运算符即可引用，因为所有全局作用域设备端变量都在核函数可见地址空间内。这同样适用于 `__constant__` 符号，但此时指针将引用只读数据。由于设备端符号可以直接引用，那些引用符号的 CUDA 运行时 API（例如 `cudaMemcpyToSymbol()` 或 `cudaGetSymbolAddress()`）没有必要，且设备运行时不支持它们。这意味着即使在子核函数启动之前，也无法在运行的核函数内更改常量数据，因为对 `__constant__` 空间的引用是只读的。

### 5.6.4.3 SM 编号与线程束编号

注意，在 PTX 中 `%smid` 和 `%warpid` 被定义为易变（volatile）值。设备运行时可能为了更高效地管理资源，将线程块重新调度到不同的 SM 上执行。因此，不能依赖 `%smid` 或 `%warpid` 在线程或线程块的整个生命周期内保持不变，这是不安全的。

### 5.6.4.4 启动配置 API

《设备端核函数启动（Device-Side Kernel Launch）》介绍了从设备端代码启动核函数的语法，采用与主机端 CUDA 运行时 API 相同的三尖括号启动记法。

核函数启动是通过设备运行时库暴露的系统级机制。它也可直接从 PTX 通过 `cudaGetParameterBuffer()` 和 `cudaLaunchDevice()` API 使用。CUDA 应用程序可以自行调用这些 API，要求与 PTX 相同。在这两种情况下，用户负责按规范以正确格式正确填充所有必要的数据结构。这些数据结构的向后兼容性有保证。

### 5.6.4.7 API 错误与启动失败

与 CUDA 运行时通常情况一样，任何函数都可能返回错误码。返回的最后一个错误码会被记录，可通过 `cudaGetLastError()` 调用获取。错误按线程记录，因此每个线程可以识别其生成的最近错误。错误码的类型为 `cudaError_t`。

与主机端启动类似，设备端启动可能因多种原因失败（参数无效等）。用户必须调用 `cudaGetLastError()` 来判断启动是否产生错误，但启动后无错误并不意味着子核函数成功完成。

对于设备端异常，例如访问无效地址，子网格中的错误将被返回给主机端。

### 5.6.4.8 设备运行时流

CUDA 设备运行时暴露了特殊的命名流，为从设备端启动的核函数和图提供特定行为。与设备端图启动相关的命名流见《设备启动（Device Launch）》文档。另外两个可用于 CUDA 设备运行时中核函数和 memcpy 操作的命名流是 `cudaStreamTailLaunch` 和 `cudaStreamFireAndForget`。这些命名流的具体行为见本节。

设备运行时同时提供命名流和未命名（NULL）流。流句柄不得传递给父网格或子网格。换句话说，流应被视为创建它的网格私有的。

主机端 NULL 流的跨流屏障语义在设备端不受支持（详见下文）。为保持与主机端运行时的语义兼容，所有设备端流必须使用 `cudaStreamCreateWithFlags()` API 创建，并传入 `cudaStreamNonBlocking` 标志。CUDA 设备运行时中不提供 `cudaStreamCreate()` API。

设备运行时不支持 `cudaStreamSynchronize()` 和 `cudaStreamQuery()`。当应用程序需要知道流中启动的子核函数已完成时，应改用向 `cudaStreamTailLaunch` 流中启动核函数。

#### 5.6.4.8.1 隐式（NULL）流

在主机端程序中，未命名（NULL）流与其他流之间具有额外的屏障同步语义（详见《阻塞与非阻塞流及默认流》）。设备运行时提供单个隐式的未命名流，由线程块中所有线程共享，但由于所有命名流都必须以 `cudaStreamNonBlocking` 标志创建，向 NULL 流中启动的工作不会对任何其他流中待处理的工作（包括其他线程块的 NULL 流）插入隐式依赖。

#### 5.6.4.8.2 即发即弃流（Fire-and-Forget Stream）

即发即弃命名流（`cudaStreamFireAndForget`）允许用户以更少的样板代码、零流跟踪开销启动即发即弃工作。它在功能上等同于每次启动都新建一个流并向该流启动，但速度更快。

即发即弃启动会立即调度执行，不依赖于先前启动的网格的完成情况。除了父网格结束时的隐式同步外，其他网格启动不能依赖即发即弃启动的完成。因此，尾启动或父网格流中的下一个网格不会在父网格的即发即弃工作完成前启动。

```cpp
// In this example, C2's launch will not wait for C1's completion
__global__ void P( ... ) {
   C1<<< ... , cudaStreamFireAndForget >>>( ... );
   C2<<< ... , cudaStreamFireAndForget >>>( ... );
}
```

即发即弃流不能用于记录或等待事件。尝试这样做会返回 `cudaErrorInvalidValue`。当编译时定义了 `CUDA_FORCE_CDP1_IF_SUPPORTED` 时不支持即发即弃流。使用即发即弃流要求以 64 位模式编译。

#### 5.6.4.8.3 尾启动流（Tail Launch Stream）

尾启动命名流（`cudaStreamTailLaunch`）允许网格在自身完成后调度一个新网格启动。在大多数情况下，尾启动可实现与 `cudaDeviceSynchronize()` 相同的功能。

每个网格有自己的尾启动流。尾流启动前，一个网格的所有非尾启动工作都会被隐式同步。即：父网格的尾启动在其父网格，以及父网格向普通流、每线程流或即发即弃流启动的所有工作全部完成之前不会启动。若两个网格启动到同一网格的尾启动流中，后一个网格在前一个网格及其所有后代工作完成后才启动。

```cpp
// In this example, C2 will only launch after C1 completes.
__global__ void P( ... ) {
   C1<<< ... , cudaStreamTailLaunch >>>( ... );
   C2<<< ... , cudaStreamTailLaunch >>>( ... );
}
```

启动到尾启动流中的网格，在父网格的所有工作完成前不会启动，包括父网格在所有非尾启动流中启动的所有其他网格（及其后代），包括在尾启动之后执行或启动的工作。

```cpp
// In this example, C will only launch after all X, F and P complete.
__global__ void P( ... ) {
   C<<< ... , cudaStreamTailLaunch >>>( ... );
   X<<< ... , cudaStreamPerThread >>>( ... );
   F<<< ... , cudaStreamFireAndForget >>>( ... )
}
```

父网格流中的下一个网格，不会在父网格的尾启动工作完成前启动。换句话说，尾启动流的行为如同被插入在父网格与其父网格流中的下一个网格之间。

```cpp
// In this example, P2 will only launch after C completes.
__global__ void P1( ... ) {
   C<<< ... , cudaStreamTailLaunch >>>( ... );
}

__global__ void P2( ... ) {
}

int main ( ... ) {
   ...
    P1<<< ... >>>( ... );
    P2<<< ... >>>( ... );
    ...
}
```

每个网格只有一个尾启动流。要并发地尾启动多个网格，可如下例操作：

```cpp
// In this example, C1 and C2 will launch concurrently after P's completion
__global__ void T( ... ) {
   C1<<< ... , cudaStreamFireAndForget >>>( ... );
   C2<<< ... , cudaStreamFireAndForget >>>( ... );
}

__global__ void P( ... ) {
   ...
   T<<< ... , cudaStreamTailLaunch >>>( ... );
}
```

尾启动流不能用于记录或等待事件。尝试这样做会返回 `cudaErrorInvalidValue`。当编译时定义了 `CUDA_FORCE_CDP1_IF_SUPPORTED` 时不支持尾启动流。使用尾启动流要求以 64 位模式编译。

### 5.6.4.9 ECC 错误

CUDA 核函数内的代码无法收到 ECC 错误的通知。ECC 错误在整个启动树完成后于主机端报告。嵌套程序执行期间出现的任何 ECC 错误将根据错误类型和配置产生异常或继续执行。
