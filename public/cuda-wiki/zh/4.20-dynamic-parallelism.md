# 4.20 CUDA 动态并行

## 4.20.1 介绍

### 4.20.1.1 概述

CUDA 动态并行（常缩写为 CDP）是 CUDA 编程模型的一项特性，允许在 GPU 上运行的代码创建新的 GPU 工作。也就是说，已在 GPU 上运行的设备代码可以通过额外的核函数启动，把新的工作加入到 GPU 中。这项特性减少了在主机端与设备端之间传递执行控制权和数据的需求，因为启动配置的决策可以在运行时由设备端运行的线程做出。

依赖数据的并行工作可以在核函数运行时动态生成。在 CUDA 加入 CDP 之前，有些算法和编程模式需要修改，以消除递归、不规则循环结构，或其他不适合扁平单层并行的结构。采用 CUDA 动态并行后，这些程序结构可以更自然地表达。

> **注：** 本节记录的是更新版的 CUDA 动态并行，有时称为 CDP2，自 CUDA 12.0 起是默认版本。CDP2 是计算能力 9.0 及以上设备上唯一可用的 CUDA 动态并行版本。开发者仍可通过编译参数 `-DCUDA_FORCE_CDP1_IF_SUPPORTED` 为计算能力低于 9.0 的设备选择旧版 CUDA 动态并行（CDP1）。CDP1 的文档见旧版《CUDA 编程指南》（Legacy versions of the CUDA Programming Guide）。CDP1 计划在未来的 CUDA 版本中移除。

## 4.20.2 执行环境

CUDA 动态并行允许 GPU 线程配置、启动新的网格，并对其隐式同步。网格是核函数启动的一次实例，包含线程块的具体形状和线程块网格。在后续章节中，需要注意区分核函数本身与该核函数的一次具体调用（即网格）。

### 4.20.2.1 父网格与子网格

配置并启动新网格的设备线程属于父网格。被这次调用创建的新网格称为子网格。

子网格的调用与完成是恰当嵌套的：父网格在其线程创建的所有子网格全部完成之前，不被视为完成；运行时保证父网格与子网格之间存在隐式同步。

### 4.20.2.2 CUDA 原语的作用域

CUDA 动态并行依赖 CUDA 设备运行时（CUDA Device Runtime），它提供了一组有限的 API，其语法与 CUDA 运行时 API 相似，但可用于设备代码。设备运行时 API 的行为与其主机端对应版本相似，但存在一些差异。这些差异记录在 API 参考章节的表格中。

在主机端和设备端，CUDA 运行时都提供启动核函数的 API，以及通过流和事件跟踪启动之间依赖关系的机制。在设备端，启动的核函数与 CUDA 对象对调用网格中的所有线程都可见。例如，一个流可以由一个线程创建，再由同一网格中的任意其他线程使用。但是，通过设备端 API 调用创建的流、事件等 CUDA 对象，仅在创建它们的网格内有效。

### 4.20.2.3 流与事件

CUDA 流与事件用于控制核函数启动之间的依赖关系：启动到同一个流中的核函数按顺序执行，事件可用于在流之间创建依赖关系。在设备端创建的流与事件也起到完全相同的作用。

在一个网格内创建的流和事件存在于网格作用域内，但在创建它们的网格之外使用它们是未定义行为。如前所述，网格退出时，它启动的所有工作会被隐式同步；启动到流中的工作也包含在内，所有依赖关系都会得到恰当的解决。对在网格作用域之外被修改过的流执行操作，其行为是未定义的。

在主机端创建的流和事件，在任何核函数内使用都是未定义行为；同样，父网格创建的流和事件，若在子网格内使用，也是未定义行为。

### 4.20.2.4 顺序与并发

设备运行时的核函数启动顺序遵循 CUDA 流的顺序语义。在一个网格内，所有启动到同一流中的核函数（即发即弃流除外，见后文）都按顺序执行。当同一网格中的多个线程向同一个流发起启动时，流内的顺序取决于网格内的线程调度顺序，可以用 `__syncthreads()` 等同步原语来控制。

注意，虽然具名流由网格内的所有线程共享，但隐式 NULL 流仅由一个线程块内的所有线程共享。如果一个线程块内的多个线程向隐式流发起启动，这些启动将按顺序执行。如果不同线程块中的线程向隐式流发起启动，这些启动可能并发执行。如果希望同一线程块内多个线程的启动能够并发，应当使用显式的具名流。

设备运行时没有为 CUDA 执行模型引入新的并发保证。也就是说，设备上任意数量的不同线程块之间，不保证并发执行。

并发保证的缺失也延伸到父网格与子网格之间。当父网格启动子网格后，只要流依赖关系得到满足且硬件资源可用，子网格就可以开始执行；但在父网格到达隐式同步点之前，不保证子网格开始执行。

并发程度会随设备配置、应用负载和运行时调度而变化。因此，依赖不同线程块之间的任何并发都是不安全的。
## 4.20.3 内存连贯性与一致性

父网格与子网格共享相同的全局内存和常量内存存储，但各自拥有独立的本地内存和共享内存。下表列出了哪些内存空间允许父子双方通过相同的指针访问。子网格永远不能访问父网格的本地内存或共享内存，父网格也不能访问子网格的本地内存或共享内存。

表 26：动态并行——父网格与子网格之间的内存空间可访问性

| 内存空间 | 父子双方是否使用相同指针？ |
|---|---|
| 全局内存 | 是 |
| 映射内存 | 是 |
| 本地内存 | 否 |
| 共享内存 | 否 |
| 纹理内存 | 是（只读） |

### 4.20.3.1 全局内存

父网格与子网格对全局内存的访问是连贯的，但子网格与父网格之间只有弱一致性保证。在子网格执行过程中，其内存视图与父线程完全一致的时间点只有一个：父线程调用子网格的那一刻。

子网格调用之前，父线程对全局内存的所有操作对子网格都可见。随着 `cudaDeviceSynchronize()` 被移除，父网格已无法再访问子网格中线程的修改。要在父网格退出之前访问子网格中线程的修改，唯一的办法是通过启动到 `cudaStreamTailLaunch` 流中的核函数。

在下面的示例中，执行 `child_launch` 的子网格只保证能看到子网格启动之前对 `data` 的修改。由于执行启动的是父网格的线程 0，子网格的内存视图将与父线程 0 看到的内存一致。由于第一个 `__syncthreads()` 调用，子网格将看到 `data[0]=0, data[1]=1, …, data[255]=255`（如果没有这个 `__syncthreads()` 调用，只能保证子网格看到 `data[0]=0`）。子网格只保证在隐式同步时返回。这意味着，子网格中线程的修改永远不保证能被父网格看到。要访问 `child_launch` 的修改，需要把 `tail_launch` 核函数启动到 `cudaStreamTailLaunch` 流中。

```cuda
__global__ void tail_launch(int *data) {
   data[threadIdx.x] = data[threadIdx.x]+1;
}

__global__ void child_launch(int *data) {
    data[threadIdx.x] = data[threadIdx.x]+1;
}

__global__ void parent_launch(int *data) {
   data[threadIdx.x] = threadIdx.x;

    __syncthreads();

    if (threadIdx.x == 0) {
        child_launch<<< 1, 256 >>>(data);
        tail_launch<<< 1, 256, 0, cudaStreamTailLaunch >>>(data);
    }
}

void host_launch(int *data) {
    parent_launch<<< 1, 256 >>>(data);
}
```

### 4.20.3.2 映射内存

映射系统内存的连贯性和一致性保证与全局内存完全相同，遵循上述语义。核函数不能分配或释放映射内存，但可以使用主机端程序传入的指向映射内存的指针。

### 4.20.3.3 共享内存与本地内存

共享内存和本地内存分别是一个线程块或一个线程的私有内存，在父网格与子网格之间不可见，也不连贯。在其所属作用域之外引用其中任一位置上的对象，其行为是未定义的，并可能导致错误。

如果编译器能检测到作为核函数启动参数传递的是指向本地内存或共享内存的指针，NVIDIA 编译器会尝试发出警告。在运行时，程序员可以使用 `__isGlobal()` 内建函数判断一个指针是否引用全局内存，从而确认它能否安全地传递给子网格启动。

调用 `cudaMemcpy*Async()` 或 `cudaMemset*Async()` 时，为了保持流语义，可能会在设备端启动新的子核函数。因此，向这些 API 传递共享内存或本地内存指针是非法的，会返回错误。

### 4.20.3.4 本地内存

本地内存是执行线程的私有存储，在该线程之外不可见。启动子核函数时，把指向本地内存的指针作为启动参数传递是非法的。子网格对这类本地内存指针解引用的结果是未定义的。

例如，以下代码是非法的：如果 `child_launch` 访问 `x_array`，其行为是未定义的：

```cuda
int x_array[10];       // 在父网格的本地内存中创建 x_array
child_launch<<< 1, 1 >>>(x_array);
```

程序员有时很难察觉编译器何时会把一个变量放入本地内存。一般原则是：传递给子核函数的所有存储都应从全局内存堆中显式分配，要么用 `cudaMalloc()`、`new()`，要么在全局作用域声明 `__device__` 存储。例如：

```cuda
// 正确 —— "value" 是全局存储
__device__ int value;
__device__ void x() {
    value = 5;
    child<<< 1, 1 >>>(&value);
}

// 非法 —— "value" 是本地存储
__device__ void y() {
    int value = 5;
    child<<< 1, 1 >>>(&value);
}
```

#### 4.20.3.4.1 纹理内存

对纹理所映射的全局内存区域的写入，相对于纹理访问是不连贯的。纹理内存的连贯性在子网格调用时和子网格完成时得到保证。也就是说，子核函数启动之前的内存写入会反映在子网格的纹理内存访问中。与上面的全局内存类似，子网格的内存写入永远不保证能反映到父网格的纹理内存访问中。要在父网格退出之前访问子网格中线程的修改，唯一的办法是通过启动到 `cudaStreamTailLaunch` 流中的核函数。父网格与子网格的并发访问可能导致数据不一致。
## 4.20.4 编程接口

### 4.20.4.1 基础

下面的示例展示了一个包含动态并行的简单 Hello World 程序：

```cuda
#include <stdio.h>

__global__ void childKernel()
{
    printf("Hello ");
}

__global__ void tailKernel()
{
    printf("World!\n");
}

__global__ void parentKernel()
{
    // 启动子核函数
    childKernel<<<1,1>>>();
    if (cudaSuccess != cudaGetLastError()) {
        return;
    }

    // 启动尾核函数到 cudaStreamTailLaunch 流
    // 隐式同步：等待子核函数完成
    tailKernel<<<1,1,0,cudaStreamTailLaunch>>>();

}

int main(int argc, char *argv[])
{
    // 启动父核函数
    parentKernel<<<1,1>>>();
    if (cudaSuccess != cudaGetLastError()) {
        return 1;
    }

    // 等待父核函数完成
    if (cudaSuccess != cudaDeviceSynchronize()) {
        return 2;
    }

    return 0;
}
```

该程序可以按如下方式在命令行一步构建：

```bash
$ nvcc -arch=sm_75 -rdc=true hello_world.cu -o hello -lcudadevrt
```

### 4.20.4.2 CDP 的 C++ 语言接口

CUDA 核函数使用 CUDA C++ 实现动态并行时可用的语言接口和 API，称为 CUDA 设备运行时（CUDA Device Runtime）。

在可能的情况下，设备运行时的 CUDA 运行时 API 保留了原有的语法和语义，以便在主机端或设备端环境中都能运行的例程可以复用代码。

与所有 CUDA C++ 代码一样，这里描述的 API 和代码都是按线程执行的代码。这使每个线程都能做出独特的动态决策，决定接下来执行哪个核函数或操作。执行所提供的任何设备运行时 API 时，线程块内的线程之间都不需要同步；因此，设备运行时 API 函数可以在任意分支分化（divergent）的核函数代码中调用而不会死锁。

#### 4.20.4.2.1 设备端核函数启动

可以在设备端使用标准的 CUDA `<<< >>>` 语法启动核函数：

```cuda
kernel_name<<< Dg, Db, Ns, S >>>([kernel arguments]);
```

- `Dg` 的类型为 `dim3`，指定网格的维度和大小；
- `Db` 的类型为 `dim3`，指定每个线程块的维度和大小；
- `Ns` 的类型为 `size_t`，指定本次调用为每个线程块动态分配的共享内存字节数，在静态分配内存之外另行分配。`Ns` 是可选参数，默认值为 0；
- `S` 的类型为 `cudaStream_t`，指定与本次调用关联的流。该流必须是在发起调用的同一个网格内分配的。`S` 是可选参数，默认为 NULL 流。

##### 4.20.4.2.1.1 启动是异步的

与主机端启动相同，所有设备端核函数启动对启动线程都是异步的。也就是说，`<<<>>>` 启动命令会立即返回，启动线程继续执行，直到遇到隐式启动同步点，例如启动到 `cudaStreamTailLaunch` 流中的核函数（尾启动流，见后文）。子网格可以在启动后的任意时刻开始执行，但不保证在启动线程到达隐式启动同步点之前开始执行。

与主机端启动类似，启动到不同流中的工作可以并发运行，但实际并发并不保证。依赖子核函数之间并发的程序不被 CUDA 编程模型支持，其行为是未定义的。

##### 4.20.4.2.1.2 启动环境配置

所有全局设备配置设置（例如 `cudaDeviceGetCacheConfig()` 返回的共享内存和 L1 缓存大小、`cudaDeviceGetLimit()` 返回的设备限制）都从父网格继承。同样，诸如栈大小之类的设备限制保持原有配置。

对于主机端启动的核函数，主机端设置的按核函数配置优先于全局设置。这些配置在从设备端启动该核函数时同样适用。无法从设备端重新配置核函数的环境。

#### 4.20.4.2.2 事件

只支持 CUDA 事件的流间同步能力。也就是说，支持 `cudaStreamWaitEvent()`，但不支持 `cudaEventSynchronize()`、`cudaEventElapsedTime()` 和 `cudaEventQuery()`。由于不支持 `cudaEventElapsedTime()`，必须通过 `cudaEventCreateWithFlags()` 并传入 `cudaEventDisableTiming` 标志来创建 CUDA 事件。

与流一样，事件对象可以在创建它的网格内的所有线程之间共享，但它属于该网格的本地对象，不能传递给其他核函数。不同网格之间不保证事件句柄唯一，因此在未创建该事件的网格内使用事件句柄会导致未定义行为。

#### 4.20.4.2.3 同步

如果调用线程需要与其它线程调用的子网格同步，程序要自己负责执行足够的线程间同步，例如通过 CUDA 事件。由于无法从父线程显式同步子网格的工作，因此无法保证子网格中发生的修改对父网格内的线程可见。

#### 4.20.4.2.4 设备管理

只能从核函数控制该核函数正在运行的设备。也就是说，设备运行时不支持 `cudaSetDevice()` 等设备 API。从 GPU 上看到的活动设备（`cudaGetDevice()` 返回的值）与主机端系统看到的设备编号相同。`cudaDeviceGetAttribute()` 调用可以请求其它设备的信息，因为该 API 允许在参数中指定设备 ID。注意，设备运行时不提供包罗万象的 `cudaGetDeviceProperties()` API——属性必须逐个查询。
## 4.20.5 编程指南

### 4.20.5.1 性能

#### 4.20.5.1.1 启用动态并行的核函数开销

在控制动态启动时处于活动状态的系统软件，可能会给当时运行的任何核函数带来开销，无论该核函数自身是否发起核函数启动。该开销源自设备运行时的执行跟踪与管理软件，可能导致性能下降。一般而言，链接了设备运行时库的应用程序都会承担这一开销。

### 4.20.5.2 实现约束与限制

动态并行保证本节文档所述的所有语义，但某些硬件和软件资源是与实现相关的，会限制使用设备运行时的程序的规模、性能等属性。

#### 4.20.5.2.1 运行时

##### 4.20.5.2.1.1 内存占用

设备运行时系统软件会为各种管理目的保留内存，特别是为跟踪待处理的网格启动保留内存。提供了配置控制，可用一定的启动限制换取缩小这部分预留内存。详见下文的“配置选项”。

##### 4.20.5.2.1.2 待处理的核函数启动

启动核函数时，所有相关的配置和参数数据都会被跟踪，直到核函数完成。这些数据存储在系统管理的启动池中。

固定大小的启动池的大小是可配置的：在主机端调用 `cudaDeviceSetLimit()` 并指定 `cudaLimitDevRuntimePendingLaunchCount` 即可。

### 4.20.5.3 兼容性与互操作性

CDP2 是默认版本。可以用 `-DCUDA_FORCE_CDP1_IF_SUPPORTED` 编译函数，在计算能力低于 9.0 的设备上不使用 CDP2。

| | 用 CUDA 12.0 及更新版本编译的函数（默认） | 用 CUDA 12.0 之前的版本编译的函数，或用 CUDA 12.0 及更新版本编译但指定了 `-DCUDA_FORCE_CDP1_IF_SUPPORTED` 的函数 |
|---|---|---|
| 编译 | 如果设备代码引用 `cudaDeviceSynchronize`，编译报错。 | 如果代码引用 `cudaStreamTailLaunch` 或 `cudaStreamFireAndForget`，编译报错。如果设备代码引用 `cudaDeviceSynchronize` 且为 sm_90 或更新架构编译，编译报错。 |
| 计算能力 < 9.0 | 使用新接口。 | 使用旧接口。 |
| 计算能力 9.0 及以上 | 使用新接口。 | 使用新接口。如果函数在设备代码中引用了 `cudaDeviceSynchronize`，函数加载返回 `cudaErrorSymbolNotFound`（如果代码为计算能力低于 9.0 的设备编译，但通过 JIT 运行在计算能力 9.0 及以上的设备上，可能发生这种情况）。 |

使用 CDP1 和 CDP2 的函数可以在同一上下文中同时加载和运行。CDP1 函数可以使用 CDP1 特有的功能（例如 `cudaDeviceSynchronize`），CDP2 函数可以使用 CDP2 特有的功能（例如尾启动和即发即弃启动）。

使用 CDP1 的函数不能启动使用 CDP2 的函数，反之亦然。如果一个将使用 CDP1 的函数的调用图中包含一个将使用 CDP2 的函数，或反之，函数加载时会返回 `cudaErrorCdpVersionMismatch` 错误。

本文档不包含旧版 CDP1 的行为。关于 CDP1 的信息，请参阅旧版《CUDA 编程指南》。

## 4.20.6 从 PTX 进行设备端启动

前面的章节讨论了如何用 CUDA 设备运行时实现动态并行。也可以从 PTX 实现动态并行。对于以并行线程执行（PTX）为目标、并计划在其语言中支持动态并行的编程语言和编译器实现者，本节提供在 PTX 层面支持核函数启动的底层细节。

### 4.20.6.1 核函数启动 API

设备端核函数启动可以用 PTX 可访问的以下两个 API 实现：`cudaLaunchDevice()` 和 `cudaGetParameterBuffer()`。`cudaLaunchDevice()` 用通过调用 `cudaGetParameterBuffer()` 获得并填入启动核函数参数的参数缓冲区，来启动指定的核函数。如果被启动的核函数不带参数，参数缓冲区可以为 NULL，即无需调用 `cudaGetParameterBuffer()`。

#### 4.20.6.1.1 cudaLaunchDevice

在 PTX 层面，使用 `cudaLaunchDevice()` 之前，必须按下面两种形式之一声明它：

```ptx
// PTX 层面声明 cudaLaunchDevice()，.address_size 为 64 时
.extern .func(.param .b32 func_retval0) cudaLaunchDevice
(
  .param .b64 func,
  .param .b64 parameterBuffer,
  .param .align 4 .b8 gridDimension[12],
  .param .align 4 .b8 blockDimension[12],
  .param .b32 sharedMemSize,
  .param .b64 stream
)
;
```

下面的 CUDA 层面声明映射到上述某一种 PTX 层面声明，位于系统头文件 `cuda_device_runtime_api.h` 中。该函数在 `cudadevrt` 系统库中定义，使用设备端核函数启动功能时，程序必须链接该库。

```cuda
// CUDA 层面声明 cudaLaunchDevice()
extern "C" __device__
cudaError_t cudaLaunchDevice(void *func, void *parameterBuffer,
                              dim3 gridDimension, dim3 blockDimension,
                              unsigned int sharedMemSize,
                              cudaStream_t stream);
```

第一个参数是指向要启动的核函数的指针，第二个参数是保存被启动核函数实际参数的参数缓冲区。参数缓冲区的布局在下文的“参数缓冲区布局”中说明。其它参数指定启动配置，即网格维度、线程块维度、共享内存大小，以及与启动关联的流（启动配置的详细说明请参阅核函数配置章节）。

#### 4.20.6.1.2 cudaGetParameterBuffer

使用 `cudaGetParameterBuffer()` 之前，必须在 PTX 层面声明它。PTX 层面声明必须采用下面两种形式之一，具体取决于地址大小：

```ptx
// PTX 层面声明 cudaGetParameterBuffer()，.address_size 为 64 时
.extern .func(.param .b64 func_retval0) cudaGetParameterBuffer
(
  .param .b64 alignment,
  .param .b64 size
)
;
```

下面的 CUDA 层面声明 `cudaGetParameterBuffer()` 映射到上述 PTX 层面声明：

```cuda
// CUDA 层面声明 cudaGetParameterBuffer()
extern "C" __device__
void *cudaGetParameterBuffer(size_t alignment, size_t size);
```

第一个参数指定参数缓冲区的对齐要求，第二个参数以字节为单位指定大小要求。在当前实现中，`cudaGetParameterBuffer()` 返回的参数缓冲区总是保证 64 字节对齐，对齐要求参数被忽略。但建议传入正确的对齐要求值——即待放入参数缓冲区的各参数中最大的对齐值——以保证未来的可移植性。

### 4.20.6.2 参数缓冲区布局

参数缓冲区中的参数不允许重排，且放入参数缓冲区的每个参数都要求对齐。也就是说，每个参数必须放在参数缓冲区的第 n 个字节处，其中 n 是大于前一个参数所占最后一个字节偏移量的、参数大小的最小倍数。参数缓冲区的最大大小为 4KB。

关于 CUDA 编译器生成的 PTX 代码的更详细说明，请参阅 PTX 3.5 规范。
