# 4.18 计算 Fabric 传输

计算 fabric 传输（compute fabric transport）通过 NVLink fabric 为 NCCL 和 NVSHMEM 等通信库提供大规模 GPU 到 GPU 通信，接口是 NCCL 设备 API 和 NVSHMEM。大多数开发者应当优先选用这些库，前提是它们能匹配所需的通信模式。计算 fabric 传输主要面向编写这类通信库的开发者，以及通信模式无法被这些库很好覆盖、需要细粒度控制的应用。编写自定义通信核函数的作者也可以把 fabric 操作与 NCCL 和 NVSHMEM 的设备 API 结合使用，在仅用这些设备 API 还不够直接时获得更直接的访问能力。

单播和多播内存共享 API 让应用通过把远端物理内存映射到本地虚拟地址空间，经 NVLink fabric 访问 GPU 内存。一旦对端分配被映射并赋予访问权限，核函数就像访问本地内存一样用加载和存储指令访问它（多播映射还可以用 multimem 指令）。这种模型既是地址中心型，也是内存中心型：共享的单位是虚拟到物理的映射，核函数在对端触及的每个字节都必须通过发出进程已保留并映射的地址可达。

在大规模 NVLink fabric 上，这种模型有两个局限性，两者都会影响应用的编写方式。虚拟地址不提供错误传播通道。当核函数向对端地址发出加载或存储时，硬件要么交付数据，要么产生内存错误——不存在发出线程可以检查、从而以编程方式检测和处理失败的中间结果。在大规模 fabric 系统上，丢包或链路重置等瞬时错误是有可能的，规模足够大时它们会成为弹性应用设计必须考虑的因素。在远端访问期间遇到 fabric 错误通常会导致该访问出错或终止进程，而 GPU 核函数没有任何办法响应这种失败：没有重试或重路由的路径。

虚拟地址也只能命名内存。映射是按物理内存定义的，因此 fabric 上非内存的资源根本无法通过映射到达。

计算 fabric 传输为通过 NVLink fabric 连接的 GPU 提供了一个互补的资源中心型模型。应用不再把对端的内存导入本地地址空间，而是创建一个逻辑端点（logical endpoint）：一个命名的传输对象，代表 fabric 上可达的资源。逻辑端点用 32 位整数标识，即逻辑端点 id；其内部的目标则由该 id 加 64 位偏移量命名，而不是用虚拟地址。由于 id 命名的是资源本身，该模型不绑定于内存，尽管目前逻辑端点暴露的资源只有内存一种。

导入的端点在所有者更换其后备内存时仍然有效。对端导入端点，把它关联到自己保留的某个端点 id 上，而不导入所有者的分配。因此，所有者可以通过本地重新绑定来增长、缩小或替换端点背后的缓冲区，而对端无需重新导入就能继续使用本地的端点 id。所有者及其对端仍需跨重新绑定同步，以免对端在所有者重新绑定到新内存期间访问该端点。此外，发出落到当前已绑定范围之外的操作是未定义行为。相比之下，VMM 的 IPC 导入映射的是特定的分配，因此如果所有者侧调整了该分配的大小，对端必须导入并映射新的分配。

一旦端点被创建、共享给需要的对端并绑定了资源，就可以对对端的逻辑端点 id 和偏移量发出异步 fabric 操作——put、get、原子操作和归约。与向映射的对端地址做加载/存储不同，fabric 操作会报告发出代码可以检查的显式完成状态。失败时，应用可以重试、重路由或采取其他恢复动作，而不是让进程出错。

## 4.18.1 前置条件与范围

使用逻辑端点有以下要求：

- CUDA 驱动 API。逻辑端点 API 是低层级 CUDA 驱动 API 的一部分。
- NVLink fabric 连接和设备支持。参与的 GPU 必须能通过 NVLink fabric 互相到达。设备是否支持逻辑端点取决于其架构、驱动和系统配置，因此应用应当通过查询 4.18.2.2 节描述的设备属性来确定支持情况，而不是根据硬件推测。
- IMEX 守护进程和通道。在进程之间共享端点使用 fabric IPC 句柄，需要 NVIDIA IMEX 守护进程正在运行，且 IMEX 通道已配置。

端点可以共享给同一节点内或同一 NVLink fabric 内不同节点上的进程。fabric IPC 句柄机制与 VMM API 使用的类似。关于 fabric 句柄和 IMEX 通道的细节，见“虚拟内存管理”一节。

## 4.18.2 预备知识

以下定义确立了本节其余部分使用的关键对象和操作。

### 4.18.2.1 定义

**逻辑端点 id**：逻辑端点 id（`CUlogicalEndpointId`）是一个 32 位值，在进程内命名一个逻辑端点。端点 id 是进程局部的：每个进程用 `cuLogicalEndpointIdReserve` 保留自己的范围，并选择把保留的 id 与哪个端点关联。fabric 操作用该 id 加偏移量寻址端点。一个端点 id 只命名一个端点，但多个 id 可以命名同一个端点。端点 id 通过 `cuLogicalEndpointCreate` 或 `cuLogicalEndpointImport` 与端点关联。在用 `cuLogicalEndpointIdRelease` 释放端点 id 之前，必须先用 `cuLogicalEndpointDestroy` 解除这种关联。在仍与端点关联的情况下释放端点 id 是未定义行为。稍后再次保留时可能会重用已释放的 id。4.18.6 节描述了逻辑端点 id 的生命周期。

**逻辑端点**：逻辑端点是一个传输对象，代表 NVLink fabric 上可达的资源，暴露为有界的偏移量空间。创建端点会分配用于路由发往它的 fabric 操作的资源。应用随后必须显式把目标资源绑定到端点偏移量空间的一个或多个范围。fabric 操作用关联的端点 id 加该空间内的偏移量命名其目标。当进程用 `cuLogicalEndpointCreate` 创建端点，或用 `cuLogicalEndpointImport` 导入对端端点时，端点与保留的 id 关联。在显式解绑其资源之前销毁端点关联会解绑这些资源，但不会销毁资源本身。在从端点解绑之前销毁资源是未定义行为。4.18.3 节概述了端点的生命周期。

**单播逻辑端点**：单播逻辑端点代表点对点的传输目标。它只有一个所有者设备，在创建端点时指定，端点绑定的内存就驻留在该设备上。对端设备对端点 id 发出 put 或 get 操作，把数据移入或移出所有者的绑定内存。

**多播逻辑端点**：多播逻辑端点代表一个传输目标，在每个偏移量处暴露多个资源。绑定其资源之前，每个参与的进程必须先把该资源加入多播端点，然后把资源绑定到端点。这些绑定一起为团队中的每个成员创建一个副本。对多播端点发出的 fabric 操作访问每个副本中的对应偏移量。多播逻辑端点是“多播内存共享”一节描述的 VMM 多播对象在计算 fabric 传输中的对应物。

**计算 fabric 传输句柄**：计算 fabric 传输句柄是传统指针的资源中心型替代物。它是逻辑端点 id 与偏移量的组合：逻辑端点 id 选择 NVLink fabric 上的目标——单播端点的所有者设备或多播团队——偏移量选择该目标的绑定内存中的位置。fabric 操作用这个句柄代替对端虚拟地址。

**逻辑端点团（clique）**：逻辑端点团是在所需能力级别上通过计算 fabric 传输操作互相可达的 GPU 的动态分组。团类型（clique type）描述所需的能力级别。有两种逻辑端点团类型：`CU_CLIQUE_TYPE_UNICAST_LOGICAL_ENDPOINT` 和 `CU_CLIQUE_TYPE_MULTICAST_LOGICAL_ENDPOINT`。团 id 是命名该 GPU 动态分组的 32 位值。试图把逻辑端点导入到与导出方设备不在同一团的设备上会失败。试图用不属于同一团的设备创建多播逻辑端点会失败。单个设备可以是多个团的成员。程序可以用 `cuDeviceGetCliqueCount` 和 `cuDeviceGetCliqueInfo` 查询设备所属的团。

**端点绑定**：端点绑定是逻辑端点偏移量空间中的一段范围与应用提供的物理内存分配之间的关联。应用可以用映射的虚拟地址通过 `cuLogicalEndpointBindAddr` 绑定内存，或用分配句柄通过 `cuLogicalEndpointBindMem` 绑定。fabric 操作仅对已绑定的端点范围有效，绑定必须满足端点的对齐和大小限制。见 4.18.8 节和 4.18.6.1 节。

所有 fabric 操作都是异步的：发出操作只是启动传输。它们的完成和状态通过每种操作提供的完成机制显式报告（见 4.18.10 节）。

**Put 和 Get 操作**：put 和 get 是计算 fabric 传输提供的数据移动原语。put 操作把数据从发出 GPU 移动到目标逻辑端点。多播变体 `cuda::ptx::fabric_try_put_multimem` 执行向多播逻辑端点的广播，把源数据写入每个副本中的对应偏移量。get 操作把数据从目标逻辑端点移动到发出 GPU。在两个方向上，远端都用逻辑端点 id 和偏移量标识，而不是用对端虚拟地址；远端的分配不需要映射到发出进程的虚拟地址空间。

**归约和拉归约操作**：归约操作（red）用归约算子把发出 GPU 的数据合并到目标逻辑端点。拉归约操作（pull_red）从目标多播逻辑端点读取，用归约算子合并多播团队各副本的值，并把结果返回给发出 GPU。它是 `multimem.ld_reduce` 在 fabric 上的对应物。

**原子操作**：原子操作（atom）对目标逻辑端点执行原子读-改-写。它读取原始值，用新值覆盖，并返回原始值。相比之下，归约操作不返回原始值。计算新值的算子包括加、最小值、最大值、按位与、或、异或。交换操作存储用户提供的值；比较并交换仅当目标持有预期的比较值时才存储新值。

**计数操作**：计数操作是一种 fabric 操作，当数据到达时，按写入目标的字节数递增目标计数器。接收方等待计数器达到预期的字节数后再消费数据。在达到预期字节数之前，接收方不知道哪些字节已被写入。一旦计数器达到预期字节数，接收方就可以安全地消费数据。计数器必须在端点内存中按 256 字节边界对齐。端点必须用启用计数操作支持（`CU_LOGICAL_ENDPOINT_FLAG_COUNTED_OPS`）创建，应用在使用该能力前必须查询设备支持情况（`CU_DEVICE_ATTRIBUTE_LOGICAL_ENDPOINT_COUNTED_OPS_SUPPORTED`）。

**完成状态与错误报告**：fabric 操作由完成对象跟踪，完成对象在操作完成时发出信号并记录操作的状态。等待该对象可以判断被跟踪的操作是成功完成还是发生了 fabric 错误。当报告失败时，应用可以查询详细的逐操作错误状态，然后重试、重路由或以其他方式恢复，而不是让进程出错。

因为 fabric 操作的更新是乱序交付的，观察到某个目标位置已被写入——例如目标区域的最后一个字节——并不意味着传输的其余部分已经落地。观察到每个目标位置都已被写入，也不表示操作成功完成、目标资源可以重用。例如，如果响应被丢弃，生产者可能会收到错误状态，从而重试该操作。因此，应用必须等待完成并检查报告的状态，才能把操作视为完成。见 4.18.10 节。
### 4.18.2.2 查询支持情况

应用应当在使用逻辑端点 API 之前先查询支持情况，因为可用性取决于 GPU 架构、驱动和系统配置。以下设备属性描述了相关的能力。这些特性是相互独立的，应用应当只查询它打算使用的那几个。

**单播逻辑端点支持**。查询设备是否支持单播逻辑端点：

```c
int unicastSupported = 0;
cuDeviceGetAttribute(&unicastSupported,
                     CU_DEVICE_ATTRIBUTE_LOGICAL_ENDPOINT_UNICAST_SUPPORTED,
                     device);
if (unicastSupported != 0) {
    ∕∕ `device` 支持单播逻辑端点
}
```

**多播逻辑端点支持**。查询设备是否支持多播逻辑端点：

```c
int multicastSupported = 0;
cuDeviceGetAttribute(&multicastSupported,
                     CU_DEVICE_ATTRIBUTE_LOGICAL_ENDPOINT_MULTICAST_SUPPORTED,
                     device);
if (multicastSupported != 0) {
      ∕∕ `device` 支持多播逻辑端点
}
```

**逻辑端点 IPC 句柄支持**。在导出或导入端点之前，查询设备支持的逻辑端点 IPC 句柄类型。该属性返回 `CUlogicalEndpointIpcHandleType` 值的位掩码。以下代码检查设备是否支持逻辑端点的 fabric IPC 句柄类型：

```c
int supportedHandleTypes = 0;
cuDeviceGetAttribute(
    &supportedHandleTypes,
    CU_DEVICE_ATTRIBUTE_LOGICAL_ENDPOINT_SUPPORTED_HANDLE_TYPES,
    device);
if ((supportedHandleTypes &
     CU_LOGICAL_ENDPOINT_IPC_HANDLE_TYPE_FABRIC) != 0) {
    ∕∕ `device` 支持逻辑端点的 fabric IPC 句柄
}
```

**计数操作支持**。计数操作是可选能力。在端点上请求 `CU_LOGICAL_ENDPOINT_FLAG_COUNTED_OPS` 之前，先查询设备是否支持：

```c
int countedOpsSupported = 0;
cuDeviceGetAttribute(&countedOpsSupported,
                      CU_DEVICE_ATTRIBUTE_LOGICAL_ENDPOINT_COUNTED_OPS_
 ,→SUPPORTED,

                      device);
if (countedOpsSupported != 0) {
     ∕∕ `device` 通过逻辑端点支持计数操作
}
```

**从所有者设备访问单播**。单播端点的所有者设备在传给 `cuLogicalEndpointCreate` 的端点属性中指定。设备属性 `CU_DEVICE_ATTRIBUTE_LOGICAL_ENDPOINT_UNICAST_ACCESS_ON_OWNER_DEVICE_SUPPORTED` 表示该设备能否访问它拥有的单播逻辑端点。如果不支持这种访问，设备可以通过指针访问绑定内存，目前这是所有者设备性能最好的方式。所有者之外的设备可以通过与该端点关联的逻辑端点 id 访问单播端点。

```c
int ownerAccessSupported = 0;
cuDeviceGetAttribute(&ownerAccessSupported,
                      CU_DEVICE_ATTRIBUTE_LOGICAL_ENDPOINT_UNICAST_ACCESS_ON_
 ,→OWNER_DEVICE_SUPPORTED,

                      device);
if (ownerAccessSupported != 0) {
     ∕∕ `device` 支持在所有者设备上访问单播逻辑端点
}
```

## 4.18.3 API 概览

逻辑端点 API 是低层级 CUDA 驱动 API 的一部分，使用逻辑端点遵循定义明确的生命周期。下面的步骤概述了工作流程，后续各节逐一详细介绍。分为以下阶段：

- 设置阶段（步骤 1–11）：验证参与设备属于同一团，保留 id，描述并创建端点，与对端共享，确认其就绪，然后在数据移动开始前分配并绑定其后备内存。
- 使用阶段（步骤 12）：从设备对端点发出 fabric 操作。
- 清理阶段（步骤 13）：在所有使用完成后解绑并销毁端点，释放其 id，释放后备内存。

1. 验证团成员关系。用 4.18.4 节描述的 `cuDeviceGetCliqueCount` 和 `cuDeviceGetCliqueInfo` 验证参与设备属于同一团。
2. 保留 id。用 `cuLogicalEndpointIdReserve` 保留一段逻辑端点 id。保留是按进程的。id 生命周期以及重用与释放的规则见 4.18.6 节。
3. 描述端点。用 `CUlogicalEndpointProp` 填充端点类型（单播或多播）、单播的所有者设备或多播的组大小、大小、请求的 IPC 句柄类型（`ipcHandleTypes`），以及任何标志——例如 `CU_LOGICAL_ENDPOINT_FLAG_COUNTED_OPS` 表示请求支持计数操作（见“计数操作”）。
4. 检查对齐和大小限制。对提议的属性调用 `cuLogicalEndpointGetLimits`，获得所需的 `bindAlignment` 和 `maxSize`。`maxSize` 是该配置允许的最大端点大小。端点大小和所有绑定都必须满足这些限制。
5. 创建端点。调用 `cuLogicalEndpointCreate` 把一个保留的 id 与按上面填充的 `CUlogicalEndpointProp` 描述的新建端点关联。
6. 共享端点。用 `cuLogicalEndpointExport` 把端点导出为 fabric IPC 句柄，通过任意 IPC 机制传输给需要的对端进程，每个对端进程用 `cuLogicalEndpointImport` 导入。导出和导入端点不需要先绑定内存。
7. 添加设备（仅多播）。对于多播端点，每个参与的设备必须用 `cuLogicalEndpointAddDevice` 加入组。每个进程在本地持有端点之后再添加自己的设备，因此对于多播，端点先被共享，设备后添加。
8. 确认就绪。`cuLogicalEndpointCreate` 和 `cuLogicalEndpointImport` 都是非阻塞的。使用前用 `cuLogicalEndpointQuery` 确认就绪。在绑定其内存之前确认本地创建的端点，在核函数对它发出操作之前确认导入的端点。
9. 分配后备内存。用虚拟内存管理 API（`cuMemCreate`）或 `cudaMallocAsync` 分配后备内存。如果端点会共享给另一个进程，绑定的内存必须可跨进程共享。当内存通过导入的多播端点绑定时同样适用。创建时请求 fabric 句柄类型（`CU_MEM_HANDLE_TYPE_FABRIC`）来把分配配置为可跨进程共享，并让分配大小同时满足 `bindAlignment` 和分配粒度。此步骤与端点创建相互独立，但两者都必须在绑定之前完成。
10. 绑定内存。用 `cuLogicalEndpointBindMem`（按分配句柄）或 `cuLogicalEndpointBindAddr`（按映射地址）把物理内存与端点关联。内存不能绑定到导入的单播端点，但可以绑定到导入的多播端点。fabric 操作仅对已绑定的范围有效。
11. 绑定后同步。在任何进程发出 fabric 操作之前，参与进程必须在绑定后同步，见 4.18.8 节。
12. 使用端点。启动核函数，对对端端点 id 发出 fabric 操作。
13. 清理。解绑内存，销毁端点，释放 id 范围，释放后备内存。

## 4.18.4 验证团成员关系

在发出任何计算 fabric 传输操作之前，需要确保所有参与设备都是支持所需计算 fabric 传输操作集合的团的成员，并且对于特定的团类型，它们都是同一团的成员。否则，这些设备无法用该类型的操作通过网络互相到达。

首先，查询该设备是几个团的成员：

```c
  size_t cliqueCount = 0; ∕∕ 出错时不修改
  cuDeviceGetCliqueCount(&cliqueCount, cuDevice);
```

然后，查询该设备所属的所有团的团信息，找到将要使用的团的团 id。本例中使用类型为 `CU_CLIQUE_TYPE_UNICAST_LOGICAL_ENDPOINT` 的团：

```c
  std::vector<CUcliqueInfo> cliqueInfos(cliqueCount);
  cuDeviceGetCliqueInfo(cliqueInfos.data(), &cliqueCount, cuDevice);
  unsigned int localCliqueId = 0;
  bool found = false;
  for (size_t idx = 0; idx < cliqueCount; ++idx) {
    if (cliqueInfos[idx].type == CU_CLIQUE_TYPE_UNICAST_LOGICAL_ENDPOINT) {
      localCliqueId = cliqueInfos[idx].id;
      found = true;
      break;
    }
  }
```

验证所有参与设备对该团类型具有相同的团 id：

```c
  std::vector<unsigned int> allCliqueIds(numRanks);
  MPI_Allgather(&localCliqueId, sizeof(unsigned int), MPI_BYTE,
                           allCliqueIds.data(), sizeof(unsigned int), MPI_BYTE,
,→ MPI_COMM_WORLD);

  for (int i = 0; i < numRanks; i++) {
    if (allCliqueIds[i] != localCliqueId) {
      fprintf(stderr, "Rank %d: Clique id %u does not match expected %u\n",
,→myRank, allCliqueIds[i], localCliqueId);

      return EXIT_FAILURE;
    }
  }
```

## 4.18.5 创建端点

创建和导入端点首先要确定进程需要多少个逻辑端点 id。然后用 `cuLogicalEndpointIdReserve` 保留一段 id，返回该范围的基 id。预留的数量要足够容纳进程将创建或导入的每个端点。该范围关联的端点可以具有不同的属性。例如，应用可以为每个 GPU 保留一个 id，再为多播端点保留一个 id。下面的例子为每个 rank 保留一个 id：

```c
  CUlogicalEndpointId leId = 0;
  cuLogicalEndpointIdReserve(&leId, (uint32_t)numRanks);
```

保留范围之后，在创建或导入端点时把其 id 关联进去。本地创建的端点用 `cuLogicalEndpointCreate`，远端端点的句柄可用时用 `cuLogicalEndpointImport`。对于进程创建的每个端点，用 `CUlogicalEndpointProp` 描述其属性。单播端点命名将持有其绑定内存的单个所有者设备。设置端点类型、请求的 IPC 句柄类型（`ipcHandleTypes`）以及任何标志，仅在需要时选择加入计数操作：

```c
  CUlogicalEndpointProp endpointProp {};
  endpointProp.type = CU_LOGICAL_ENDPOINT_TYPE_UNICAST;
  endpointProp.unicast = {.device = cuDevice};
  endpointProp.ipcHandleTypes = CU_LOGICAL_ENDPOINT_IPC_HANDLE_TYPE_FABRIC;
  endpointProp.flags = useCounted ? CU_LOGICAL_ENDPOINT_FLAG_COUNTED_OPS : CU_
,→LOGICAL_ENDPOINT_FLAG_NONE;
```

端点大小单独设置，在其对齐和最大大小限制已知之后。4.18.6.1 节介绍了如何查询这些限制以及如何选择大小。

调用 `cuLogicalEndpointCreate` 把保留的 id 与上述属性关联。创建本地端点并导入对端端点的进程通常为每个参与者保留一个 id，这样对端就按“基 id 加 rank”来寻址。每个 rank 在 `leId + myRank` 处创建自己的端点：

```c
  cuLogicalEndpointCreate(leId + myRank, &endpointProp);
```

`cuLogicalEndpointCreate` 是非阻塞的，因此返回时端点尚不可用。在把内存绑定到它之前，先按 4.18.7.1 节所述用 `cuLogicalEndpointQuery` 确认它已完全构建。

**多播端点**。多播端点遵循相同的步骤，区别在于描述方式，以及需要加入一组设备。用 `type = CU_LOGICAL_ENDPOINT_TYPE_MULTICAST` 描述，并把 `multicast.numDevices` 设置为多播组的设备数量。创建并共享之后，每个参与的设备必须用 `cuLogicalEndpointAddDevice` 加入组。进程只在本地持有端点之后才添加自己的设备——创建者在 `cuLogicalEndpointCreate` 之后添加，每个对端在 `cuLogicalEndpointImport` 之后添加。多播组完整之前，端点尚未就绪。成员关系在端点存续期间是永久的。
## 4.18.6 逻辑端点 id

逻辑端点 id 是进程局部的名称，其生命周期与它标识的端点相互独立。端点 id 始终处于以下状态之一：

1. 未保留。该 id 不属于进程，不能与端点关联。`cuLogicalEndpointIdReserve` 保留它。
2. 已保留。该 id 属于进程，但尚不命名任何东西。用已保留的 id 调用 `cuLogicalEndpointCreate` 或 `cuLogicalEndpointImport` 会把它与端点关联，并进入已关联状态。`cuLogicalEndpointIdRelease` 把它返回到未保留状态。
3. 已关联。该 id 命名一个端点，使用该 id 的 fabric 操作以该端点为目标。`cuLogicalEndpointDestroy` 解除关联，把 id 返回到已保留状态。

`cuLogicalEndpointIdReserve` 保留一段数量为 `count` 的端点 id，并返回其基 id `baseLeId`，因此保留的范围是 `[baseLeId, baseLeId + count)`。基 id 是输出：调用者不能选择收到哪些 id；如果没有数量为 `count` 的可用范围，保留会失败，例如因为进程中的另一个库持有保留。

一个端点可以同时与多个 id 关联。例如，它可以通过 `cuLogicalEndpointCreate` 与所有者的 id 关联，也可以通过 `cuLogicalEndpointImport` 与额外的 id 关联。这些 id 是同一端点的别名，对其中任何一个发出的操作都到达同一目标。

`cuLogicalEndpointDestroy` 解除一个 id 的关联。该 id 随后可以被后续的 create 或 import 与不同的端点关联，无需重新保留。Destroy 还会解绑本进程通过该 id 绑定的内存。端点本身仅在它的最后一个别名被销毁时才释放。

`cuLogicalEndpointIdRelease(baseLeId, count)` 释放 `[baseLeId, baseLeId + count)` 范围内最多 `count` 个 id。该范围内的每个 id 都必须已被保留，且与该范围内 id 关联的每个端点都必须先被销毁。

因为保留是按进程的，端点在每个导入进程中不一定要用相同的 id 导入。一个方便的约定是：每个进程保留同样大小的范围（每个参与者一个 id），本地按 `baseLeId + 对端` 寻址某个对端的端点。每个进程有自己的保留基 id `baseLeId`，各进程之间不必相同。如果同一对端端点在不同进程中以不同 id 导入，CUDA 不会检测或报告不匹配。维护正确的本地“对端到端点 id”映射是应用的责任。

### 4.18.6.1 限制与对齐

端点的对齐和最大大小要求取决于其属性，因此必须针对要创建的具体配置查询，而不能想当然。`cuLogicalEndpointGetLimits` 为给定的 `CUlogicalEndpointProp` 返回这两个值：

```c
cuuint64_t bindAlignment = 0;
cuuint64_t maxSize = 0;
cuLogicalEndpointGetLimits(&bindAlignment, &maxSize, &prop);
```

端点大小和每个绑定偏移都必须是返回的 `bindAlignment` 的整数倍。`maxSize` 是逻辑端点的最大大小。如果 `maxSize` 小于 `CUlogicalEndpointProp::size`，应用必须把请求调整到这个更小的值。要暴露整个请求范围，应用可以把它划分到多个端点上，每个不超过 `maxSize`。用单个分配覆盖整个端点是最简单的安排，但不是强制要求。端点的偏移量空间同样可以由多个绑定支持，这些绑定映射不同、可能不连续的物理分配，只要每个已绑定范围都是 `bindAlignment` 的整数倍。

## 4.18.7 共享端点

与对端共享端点遵循“导出—传输—导入”交换流程：所有者把端点导出为 fabric IPC 句柄，把该句柄传输给需要的对端，每个对端导入该端点并把它与自己保留的、尚未关联任何端点的逻辑端点 id 关联。共享使用 fabric IPC 句柄，因此端点必须绑定可跨进程共享的内存，且环境必须满足 4.18.1 节描述的 fabric IPC 要求。

用 `cuLogicalEndpointExport` 导出端点，请求的 IPC 句柄类型要与描述端点时使用的（`ipcHandleTypes`）相同。这会产生 `CUlogicalEndpointFabricHandle`——代表逻辑端点的 fabric IPC 句柄。用应用选择的进程间通信机制把它传输给对端，然后每个对端用 `cuLogicalEndpointImport` 导入。导入时选择本地的 id：导入方可以选择在哪个逻辑端点 id 处导入该端点。该 id 必须已成功保留，且不能已关联任何其他逻辑端点，但不必与所有者创建端点时用的 id 相同。每个设备可以在不同的 id 处导入同一端点，甚至在多个不同的 id 处导入（即允许多次导入同一端点）。

下面的单播点对点例子在环形拓扑上共享端点。每个 rank 导出自己的端点，用一次 `MPI_Sendrecv` 把句柄发给接收邻居，同时收集发送邻居的句柄。它把该句柄导入为 `leId + sendRank`——这正是它之后对导入端点的绑定内存发出 fabric 操作时使用的 id：

```c
  ∕∕ 把我们自己的端点导出为 fabric IPC 句柄，交给需要的对端，
  ∕∕ 并把每个对端的句柄导入到本地保留的 id。
  CUlogicalEndpointFabricHandle localHandle;
  CUlogicalEndpointFabricHandle sendRankHandle;
  cuLogicalEndpointExport(&localHandle, leId + myRank, CU_LOGICAL_ENDPOINT_
,→IPC_HANDLE_TYPE_FABRIC);

  MPI_Sendrecv(
      &localHandle, sizeof(CUlogicalEndpointFabricHandle), MPI_BYTE, recvRank,
,→ 0,

      &sendRankHandle, sizeof(CUlogicalEndpointFabricHandle), MPI_BYTE,
,→sendRank, 0,

      MPI_COMM_WORLD, MPI_STATUS_IGNORE);
  cuLogicalEndpointImport(leId + sendRank, &sendRankHandle, CU_LOGICAL_
,→ENDPOINT_IPC_HANDLE_TYPE_FABRIC);
```

### 4.18.7.1 确认就绪

`cuLogicalEndpointCreate` 和 `cuLogicalEndpointImport` 在请求被接受后立即返回。在 `cuLogicalEndpointQuery` 报告就绪之前，对逻辑端点 id 使用要求端点已完全构建的 API 是未定义行为。`cuLogicalEndpointQuery` 本身是非阻塞的：如果查询范围内的任何 id 尚未就绪，它返回 0；当给定范围内的所有 id 都就绪时返回非零值，因此通常在轮询循环中调用。

在查询就绪之前，先保留逻辑端点 id，并通过 `cuLogicalEndpointCreate` 或 `cuLogicalEndpointImport` 把它与端点关联。多播端点在所有设备都用 `cuLogicalEndpointAddDevice` 加入之前不会就绪，因此多进程程序在阻塞等待其就绪之前必须先导出（`cuLogicalEndpointExport`）并共享它。

在对逻辑端点执行以下任一操作之前，先调用 `cuLogicalEndpointQuery` 并等待它报告逻辑端点已完全构建：

- 用 `cuLogicalEndpointBindAddr` 或 `cuLogicalEndpointBindMem` 绑定内存。
- 用 `cuLogicalEndpointUnbind` 解绑内存。
- 发出任何 `cuda::ptx::fabric_try_*` 操作。

以下 API 不要求 `cuLogicalEndpointQuery` 已报告就绪：

- `cuLogicalEndpointExport`
- `cuLogicalEndpointDestroy`
- `cuLogicalEndpointIdRelease`

这些 API 不要求就绪，但它们的其余生命周期前置条件仍然适用。

## 4.18.8 绑定内存

端点不拥有任何内存。绑定把端点偏移量空间中的一段范围与物理分配关联起来，fabric 操作仅对已绑定的范围有效。绑定是按设备建立的：单播绑定作用于所有者设备，多播绑定作用于多播团队中的单个设备。

根据应用持有分配的方式，内存有两种绑定方法：

- `cuLogicalEndpointBindMem` 按分配句柄绑定，使用 `cuMemCreate` 返回的 `CUmemGenericAllocationHandle`。
- `cuLogicalEndpointBindAddr` 按映射的虚拟地址绑定。例子包括 `cudaMallocAsync` 返回的指针，以及用 `cuMemMap` 映射的范围中的地址。当前支持的分配类型见 CUDA 内存管理 API。

> 注意：并非所有 CUDA 可访问的分配都能绑定到逻辑端点。绑定 API 当前支持的分配类型见 CUDA 驱动 API 文档。

两者都接受端点 id、绑定适用的设备、端点偏移量空间中的偏移量、要绑定的分配，以及绑定的大小。`cuLogicalEndpointBindMem` 还额外接受分配内的 `memOffset`，允许绑定句柄的子范围。端点偏移量、大小以及（对于 `cuLogicalEndpointBindMem`）`memOffset` 都必须是 `bindAlignment` 的整数倍，且已绑定范围必须落在端点大小之内（见 4.18.6.1 节）。

```c
  ∕∕ 在端点偏移量 0 处绑定整个后备分配，按分配句柄绑定。
  cuLogicalEndpointBindMem(leId + myRank, cuDevice, 0, exportHandle, 0,
,→exportSize, 0);

  ∕∕ 在每个目标都已绑定之前，任何 rank 都不得发出操作。
  MPI_CHECK(MPI_Barrier(MPI_COMM_WORLD));
```

建立初始绑定后，所有参与进程必须在任何进程发出 fabric 操作之前同步。对于单播端点，每个导入方必须在所有者绑定其后备内存后与导出进程同步。对于多播端点，所有参与进程必须等到每个参与者都绑定了其后备内存。应用可以使用任何能建立这种顺序的进程间同步机制。

因为对端导入的是端点而不是所有者的分配，所有者无需对端重新导入就能替换端点背后的内存。用 `cuLogicalEndpointUnbind` 解绑当前范围，再通过同一端点 id 把新的分配绑定到端点偏移量空间的同一范围。所有者与其对端必须跨重新绑定同步，确保在端点未绑定期间没有对端对它发出操作。发出落到当前已绑定范围之外的操作是未定义行为。
## 4.18.9 Fabric 操作

线程通过执行接受计算 fabric 传输句柄——逻辑端点 id 与偏移量的组合——的 fabric 操作来访问端点资源。fabric 操作是异步的，即程序必须显式等待其完成才能观察到效果。fabric 操作以 `try_` 为前缀，表示它们可能失败。也就是说，等待完成之后，线程必须检查操作的完成机制（见 4.18.10 节）来判断操作是否成功。这把 fabric 操作与普通的指针操作区分开来：基于指针的访问失败是通过销毁上下文或整个应用向应用报告的。希望处理这些错误（例如从指针失败中恢复）的应用只能在上下文或进程级别处理。fabric 操作让应用能够在程序线程级别处理错误。

设备代码通过以下 `cuda::ptx` 指令发出 fabric 操作：

| 指令 | 操作 |
|------|------|
| `cuda::ptx::fabric_try_put` | 向计算 fabric 传输句柄写入。 |
| `cuda::ptx::fabric_try_get` | 从计算 fabric 传输句柄读取。 |
| `cuda::ptx::fabric_try_red` | 向计算 fabric 传输句柄做归约。 |
| `cuda::ptx::fabric_try_pullred` | 从计算 fabric 传输句柄做拉归约。 |
| `cuda::ptx::fabric_try_atom` | 对计算 fabric 传输句柄做原子读-改-写。 |

上述操作（`try_atom` 除外）以 16 字节为单位移动数据，因此传输的两端都必须 16 字节对齐：源指针和端点中的目标偏移量都必须是 16 字节的整数倍。

下面的例子发出 fabric put。put 从共享内存缓冲区读取数据，写入目标句柄。多个线程把输入数据写入共享内存，然后用 `__syncthreads` 与发出 put 的线程同步。put 通过 async-proxy 读取共享内存，因此发出线程调用 `cuda::ptx::fence_proxy_async(cuda::ptx::space_shared)` 把 generic-proxy 的共享内存写入同步到 async proxy。put 接受目标句柄、源缓冲区基地址、字节数，以及将跟踪完成的 mbarrier：

```c
       ∕∕ 在 put 读取之前，先让暂存的共享内存源对 async proxy 可见。
       cuda::ptx::fence_proxy_async(cuda::ptx::space_shared);
       cuda::ptx::fabric_try_put(cuda::ptx::space_shared, cuda::ptx::sem_relaxed,
                                  cuda::ptx::scope_sys, putLeId, offset, smemBuf,
                                  FABRIC_CHUNK_SIZE, &putBar);
```

该调用设置了若干指令修饰符，其完整的集合——每条指令接受的访问大小、内存顺序模式和作用域——由 PTX ISA 指定（见“Fabric 指令”）。这里值得指出该操作的两个方面，因为它们把它与程序的其余部分联系起来：如何跟踪其完成，以及如何指定内存顺序。

**事务计数**。使用 mbarrier 跟踪完成的 fabric 操作遵循与指针寻址的 `cuda::ptx::cp_async_bulk` 拷贝（见“使用 TMA 传输数据”）相同的 mbarrier 事务记账模型。put 完成时，每交付 16 字节就把其 mbarrier 的事务计数减 1。当所有预期的到达都发生且事务计数归零时，barrier 阶段完成。put 不设置预期的事务计数。单独的 `cuda::ptx::mbarrier_arrive_expect_tx` 在操作提交后发出，记录一次到达，并按字节数除以 16 增加事务计数——因为 put 将按这个量递减它。取回类操作使用按字节的事务记账。`cuda::ptx::fabric_try_get` 和 `cuda::ptx::fabric_try_pullred` 每交付一字节就把事务计数减 1，因此 `cuda::ptx::mbarrier_arrive_expect_tx` 增加完整的字节数。4.18.10 节涵盖 mbarrier 布局要求以及如何读回 fabric 状态。

计数 put 还会在其数据到达时递增目标侧的字节计数器，这样接收方可以在访问本地数据之前轮询该计数器，而不用交换单独的完成消息。下面的代码用 `cuda::ptx::fabric_try_put_counted` 实现这一点——即普通 put 的 `.counted::bytes` 变体——传入第二个目标偏移量，即计数器在端点中的偏移量：

```c
    ∕∕ 在 put 读取之前，先让暂存的共享内存源对 async proxy 可见。
    cuda::ptx::fence_proxy_async(cuda::ptx::space_shared);
    cuda::ptx::fabric_try_put_counted(cuda::ptx::space_shared, cuda::ptx::sem_
,→relaxed,

                                       cuda::ptx::scope_sys, putLeId, offset,
,→counterOffset,

                                       smemBuf, FABRIC_CHUNK_SIZE, &putBar);
```

计数操作要求端点用计数操作支持（`CU_LOGICAL_ENDPOINT_FLAG_COUNTED_OPS`，见 4.18.2.2 节）创建，且目标计数器必须在端点内存中按 256 字节边界对齐。应用在布局端点的后备内存时满足这一点：在适当对齐的区域中预留计数器。

虽然例子只发出 put，但 get、归约和拉归约操作使用 4.18.10 节描述的相同提交、状态报告和等待序列。它们的事务计数单位是操作特定的，如上所述。

**内存顺序**。例子中的 fabric put 以 relaxed 顺序在 sys 作用域发出。一个 fabric put 横跨多个代理：它通过 fabric-proxy 访问远端数据（计数 put 还访问计数器），通过 async-proxy 读取 `.shared::cta` 源，通过 generic-proxy 更新完成 mbarrier。因为 mbarrier 通过 generic-proxy 更新，只需用块作用域操作在 barrier 处等待就能观察到完成。然而，与 `cuda::ptx::cp_async_bulk` 操作不同，观察到 fabric 操作完成并不会把 fabric-proxy 访问顺序排到 generic-proxy 之前。在用指针通过 generic-proxy 访问数据之前，必须使用 `cuda::ptx::fence_proxy_generic_fabric_alias` 把 fabric-proxy 与 generic-proxy 同步。

仅有端点 id 并不提供对远端目标的指针访问。导入端点不会把其绑定的资源映射到导入方的虚拟地址空间。因此下面的例子使用发出线程的设备拥有的单播端点。`leId` 是端点 id，在 `dataOffset` 处绑定的内存也映射到了该设备的虚拟地址空间中。`dataPtr` 指向同一位置。

发出 put 之后，线程等待完成。在用 `dataPtr` 通过 generic-proxy 读取目标之前，线程必须先用 `cuda::ptx::sem_release` 再用 `cuda::ptx::sem_acquire` 发出 `cuda::ptx::fence_proxy_generic_fabric_alias`。仅靠完成等待并不能把 fabric-proxy 写入排到 generic-proxy 指针加载之前。`waitForSuccessfulCompletion` 代表 4.18.10 节描述的 mbarrier 等待与状态检查。初始时目标为 0，`smemSrcData` 是 16 字节的共享内存源，其第一个 `uint32_t` 元素的值为 42。

同一线程发出并加载（线程 0）：

```c
 namespace ptx = cuda::ptx;

 ptx::fabric_try_put(
     ptx::space_shared,
     ptx::sem_relaxed,
     ptx::scope_sys,
     leId, dataOffset,
     smemSrcData, 16, &mBar);
 ptx::fabric_submit();
 ptx::mbarrier_arrive_expect_tx(
     ptx::sem_acquire,
     ptx::scope_cta,
     ptx::space_shared,
     &mBar, 1);
 waitForSuccessfulCompletion(&mBar);

 ∕∕ 把后续的 generic-proxy 加载排到 fabric put 之后。
```

### 4.18.9.1 逐线程与线程束集体操作

每条 fabric 指令定义了自己的执行粒度。`fabric.try_get`、`fabric.try_get.tensor`、`fabric.try_put`、`fabric.try_put.tensor` 和 `fabric.try_red` 是逐线程的：每次执行都为发出线程发起一个独立的操作。`fabric.try_pullred` 是线程束集体的：线程束的 32 个通道必须一起执行该指令。每条指令所需的参与方式由 PTX ISA 指定。

执行粒度只描述线程如何发出 fabric 操作。完成跟踪与该粒度无关，见 4.18.10.1 节。
## 4.18.10 完成状态与错误报告

fabric 操作通过其完成对象报告状态。这里描述的操作使用共享内存 mbarrier 作为完成对象，因此同一个 mbarrier 既发出完成信号，又记录状态。用 `cuda::ptx::mbarrier_init` 并传入 `cuda::ptx::layout_v1` 初始化这个 mbarrier。该布局用保存 fabric 操作状态的字段扩展了对象。默认的 `cuda::ptx::layout_v0` 只跟踪到达和事务计数，无法携带该状态，因此不能用于该报告机制：

```c
     cuda::ptx::mbarrier_init(cuda::ptx::layout_v1, &putBar, 1);
```

`cuda::ptx::fabric_try_put` 接受跟踪该操作的 mbarrier。当操作的数据被交付时，fabric 引擎在 barrier 上完成相应的事务并记录操作的状态。因此，“传输已落地”的信号来自 put 本身，而不是发出线程。

put 交付它的字节，但不告诉 barrier 期望多少。以上面展示的逐线程 put 为例，发出线程在单独的步骤中提供这个计数。它先用 `fabric_submit` 提交操作，让 fabric 引擎最终开始消费它，然后调用 `cuda::ptx::mbarrier_arrive_expect_tx` 记录一次到达，并增加预期的事务计数——即操作将交付的字节数，以 16 字节为单位计数。每条 fabric 操作都必须在跟踪其完成的 barrier 阶段推进之前提交。提交操作之后，发出线程要么执行该阶段推进所需的 barrier 操作（例如 `cuda::ptx::mbarrier_arrive_expect_tx` 或 `cuda::ptx::mbarrier_expect_tx`），要么与执行该操作的另一个线程同步。发出线程不必自己等待该 barrier，其他线程可以执行等待。当所有预期的到达都发生且事务计数归零时，barrier 阶段推进，等待返回。程序必须在网格退出前等待每条 fabric 操作完成。网格退出时仍有未完成的操作是未定义行为。

### 4.18.10.1 配置 Barrier 到达与事务计数

上面的完成序列从发出 put 的线程记录到达和预期事务贡献。哪个线程可以记录它们取决于操作的执行粒度。对于逐线程操作，发出线程必须为自己的操作记录它们。对于线程束集体的 `fabric.try_pullred`，参与线程束的单个通道代表整个线程束记录，或每个通道记录自己的到达。`cuda::ptx::mbarrier_arrive_expect_tx` 是单个融合操作：它在同一步中计数一次到达并增加预期事务计数，因此必须由一个线程执行。它必须在操作用 `fabric.submit` 提交之后、等待观察到完成之前运行。记录到达和预期事务计数的线程不必是等待该 barrier 的线程。

多个独立操作可以共享一个 barrier。当线程束集体的 `fabric.try_pullred` 使用单次到达时，任一通道增加的预期事务计数等于该线程束交付的字节数。如果改为每个通道都记录一次到达，其他 31 个通道贡献零事务，因此 barrier 初始化的到达计数必须是完整的线程束宽度。

当许多操作共享 barrier 时，每个线程记录一次到达会膨胀 barrier 的到达计数。`layout::v1` mbarrier 把到达计数放在 9 位字段中，因此上限是 511；超过会溢出 barrier。512 个线程的块若每个线程都在一个共享 barrier 上到达一次，就会超过这个上限。在粒度允许时优先每个组一次到达：同步线程束并选举单个通道，或同步整个块并在块范围的共享 barrier 上记录一次到达。

## 4.18.11 清理

清理要求在可能对端点发出操作的任何进程与已向端点绑定资源的任何进程之间同步。对于单播端点，这意味着在导入方仍可能对端点发出操作时，所有者不得解绑或销毁端点，也不得释放其后备资源。对于多播端点，每个参与进程拥有自己绑定的副本，因此在另一进程仍可能对端点发出操作时，任何参与者都不得解绑或释放其副本。重要的是顺序，而不是强制顺序的机制：任何在移除绑定之前建立这种顺序的进程间同步都足够。

```c
  ∕∕ ---- 清理端点并释放后备分配。----
  ∕∕ 每个 rank 的流都同步之后，所有 fabric put 都已完成，
  ∕∕ 不会再有 rank 发出操作。用一个 barrier 把这点全局化，

  ∕∕ 确保没有对端仍以我们下面清理的端点为目标。

  MPI_Barrier(MPI_COMM_WORLD);

  ∕∕ 销毁导入的端点（我们的 put 所寻址的对端目标）。导入
  ∕∕ 只是对对端端点 id 的本地引用，不映射任何对端内存，
  ∕∕ 因此我们的 put 排空之后，这一步只是丢弃该引用。
  cuLogicalEndpointDestroy(leId + sendRank);

     ∕∕ 解绑并销毁我们拥有的端点，然后释放保留的 id 范围。
     cuLogicalEndpointUnbind(leId + myRank, cuDevice, 0, exportSize);
     cuLogicalEndpointDestroy(leId + myRank);
     cuLogicalEndpointIdRelease(leId, numRanks);

     ∕∕ 按 VMM 清理顺序释放后备分配：解除范围映射，释放
     ∕∕ 物理句柄，然后释放保留的虚拟地址范围。
     cuMemUnmap(exportPtr, exportSize);
     cuMemRelease(exportHandle);
     cuMemAddressFree(exportPtr, exportSize);
```

等待 fabric 操作和所有发出者停下来。跟踪 fabric 操作的完成对象在释放之前必须先等待。对于网格发出的 fabric 操作，网格中的线程必须在网格退出前等待完成。不执行该等待就退出是未定义行为。例子中，每个核函数在返回前都等待完成，流同步确认这些核函数及其等待都已完成。

由其他进程发出、以同一逻辑端点绑定的资源为目标的 fabric 操作可能仍在飞行中。因此，在移除单播绑定之前，所有者必须等到每个导入方都停止发出。在移除任何多播绑定之前，拥有绑定副本的每个参与者都必须知道所有进程都已停止发出。例子在所有 rank 同步其 CUDA 流之后用一个 barrier 做到这一点。当能保持所需顺序时，应用可以使用更窄的同步方案。

**销毁导入的端点 id**。每个导入进程调用 `cuLogicalEndpointDestroy` 销毁与其导入端点关联的逻辑端点 id。这只丢弃该本地别名，不在所有者侧解绑任何东西，因此 destroy 本身不需要跨进程协调。

**销毁所有者的端点 id**。销毁所有者的逻辑端点 id 还会解绑本进程通过该 id 绑定的内存，因此先调用 `cuLogicalEndpointUnbind` 是可选的，但推荐这么做。端点的资源在每个别名——所有者的 id 和所有导入——都被销毁后释放。

单播和多播端点走同一条路径。因为多播成员关系是永久的，更改多播组需要销毁端点并创建新的。在端点存续期间，设备不能离开组。

**重用或释放端点 id**。端点关联被 `cuLogicalEndpointDestroy` 销毁后，其 id 仍处于保留但未关联状态，可以立即重用。要把 id 归还给系统，对先前用 `cuLogicalEndpointIdReserve` 保留的范围调用 `cuLogicalEndpointIdRelease`。

**释放后备分配**。端点不拥有其后备内存，因此该分配单独释放。使用与分配方式对应的释放机制。对于 VMM 分配，常规顺序是：`cuMemUnmap` 解除映射，`cuMemRelease` 释放物理句柄，`cuMemAddressFree` 归还保留的虚拟地址范围。程序不得在分配仍绑定到端点时释放它。
