# 1.2 编程模型

本章从较高的层面介绍 CUDA 编程模型，与具体语言无关。这里引入的术语与概念适用于任何支持的编程语言中的 CUDA。后面的章节将以 C++ 为例说明这些概念。

## 1.2.1 异构系统

CUDA 编程模型假设运行在一个异构计算系统上，即同时包含 GPU 与 CPU 的系统。CPU 及其直连的内存分别称为主机端（host）和主机端内存；GPU 及其直连的内存分别称为设备端（device）和设备端内存。在某些片上系统（SoC）中，它们可能是同一封装的一部分；在更大的系统中，可能有多个 CPU 或 GPU。

CUDA 应用程序有一部分代码在 GPU 上执行，但应用程序总是从 CPU 开始执行。主机端代码（即在 CPU 上运行的代码）可以使用 CUDA API 在主机端内存与设备端内存之间复制数据、启动 GPU 上的代码执行，并等待数据复制或 GPU 代码执行完成。CPU 与 GPU 可以同时执行代码，通常让 CPU 和 GPU 都达到最大利用率，才能获得最佳性能。

应用程序在 GPU 上执行的代码称为设备端代码；出于历史原因，一个在 GPU 上被调用执行的函数称为核函数（kernel）。启动一个核函数开始运行的操作称为启动（launch）核函数。可以把核函数的启动理解为：启动大量线程，在 GPU 上并行执行核函数代码。GPU 线程的运行方式与 CPU 线程类似，但存在一些对正确性与性能都很重要的差异，后面的小节会介绍（参见 3.2.2.1.1 节）。

## 1.2.2 GPU 硬件模型

与其他编程模型一样，CUDA 也依赖于一个底层硬件的概念模型。就 CUDA 编程而言，GPU 可以看作流多处理器（Streaming Multiprocessor，SM）的集合，这些 SM 被组织成称为图形处理簇（Graphics Processing Cluster，GPC）的分组。每个 SM 包含一个本地寄存器文件（register file）、一个统一数据缓存（unified data cache）以及若干执行计算的功能单元。统一数据缓存为共享内存（shared memory）与 L1 缓存提供物理资源。统一数据缓存在 L1 与共享内存之间的分配可以在运行时配置。不同 GPU 架构的 SM 中，各类内存的大小与功能单元的数量可能有所不同。

> **注意**
>
> GPU 的实际硬件布局，或其物理上执行编程模型的方式，可能有所不同。这些差异不影响用 CUDA 编程模型编写的软件的正确性。

### 1.2.2.1 线程块与网格

应用程序启动核函数时，会同时启动大量线程，通常达到数百万。这些线程被组织成块。一个线程的块称为线程块（thread block）。线程块又被组织成网格（grid）。网格中的所有线程块大小与维度都相同。图 3 展示了线程块网格的示意图。

线程块与网格可以是一维、二维或三维的。这些维度可以方便地把各个线程映射到工作单元或数据项上。

启动核函数时，需要指定执行配置（execution configuration），其中给出网格与线程块的维度。执行配置还可以包含一些可选参数，如簇大小、流（stream）与 SM 配置设置，后面的小节会介绍。

通过内置变量，执行核函数的每个线程可以确定自己在所属线程块中的位置，以及所属线程块在所属网格中的位置。线程还可以用这些内置变量确定核函数启动时线程块与网格的维度。这样，每个线程在所有运行核函数的线程中都有了唯一的身份。这个身份常用于确定每个线程负责的数据或操作。

线程块的所有线程都在单个 SM 上执行。这样，同一线程块内的线程就可以高效地通信与同步。线程块内的所有线程都能访问片上共享内存，可用于线程块内线程之间交换信息。

一个网格可能包含数百万个线程块，而执行该网格的 GPU 可能只有几十个或几百个 SM。线程块的所有线程由单个 SM 执行，在大多数情况下¹ 会在该 SM 上运行到结束。线程块之间的调度不作任何保证，因此一个线程块不能依赖其他线程块的结果，因为后者可能要等该线程块完成后才能被调度。图 4 展示了网格中的线程块如何分配到 SM 上。

CUDA 编程模型让任意大的网格都能在任何规模的 GPU 上运行，无论是只有一个 SM 还是数千个 SM。要实现这一点，CUDA 编程模型要求不同线程块中的线程之间没有数据依赖（个别例外除外）。也就是说，一个线程不应依赖同一网格中其他线程块的线程的结果，也不应与其同步。线程块内的所有线程在同一 SM 上同时运行；网格中的不同线程块被调度到可用的 SM 上，可以按任意顺序执行。总之，CUDA 编程模型要求线程块必须能以任意顺序、并行或串行地执行。

> ¹ 在使用 CUDA 动态并行等功能的某些情况下，线程块可能被挂起到内存中。即 SM 的状态被保存到系统管理的 GPU 内存区域，SM 被释放出来执行其他线程块。这类似于 CPU 上的上下文切换。这种情况不常见。

### 1.2.2.1.1 线程块簇

除了线程块之外，计算能力 9.0 及更高的 GPU 还有一种可选的分组层级，称为簇（cluster）。簇是一组线程块，与线程块和网格一样，可以是 1 维、2 维或 3 维布局。图 5 展示了一个同时按簇组织的线程块网格。指定簇不会改变网格维度，也不会改变线程块在网格中的索引。

指定簇把相邻的线程块组成簇，为簇层级的同步与通信提供了额外的机会。具体来说，簇中的所有线程块都在单个 GPC 中执行。图 6 展示了指定簇时，线程块如何调度到 GPC 中的 SM 上。由于这些线程块是同时调度且位于同一个 GPC 内，同一簇内不同线程块的线程可以使用 Cooperative Groups 提供的软件接口进行通信与同步。簇中的线程可以访问簇内所有线程块的共享内存，这称为分布式共享内存（distributed shared memory）。簇的最大尺寸取决于硬件，在不同设备上有所不同。

### 1.2.2.2 线程束与 SIMT

在线程块内部，线程被组织成每组 32 个线程的分组，称为线程束（warp）。一个线程束以单指令多线程（SIMT）范式执行核函数代码。在 SIMT 中，线程束中的所有线程执行相同的核函数代码，但每个线程可以走不同的分支。也就是说，虽然程序的所有线程都执行同一份代码，但不要求走相同的执行路径。

当线程束执行线程时，会为它们分配线程束通道（warp lane）。线程束通道编号为 0 到 31，线程块中的线程以可预测的方式分配到各个线程束，详见硬件多线程（Hardware Multithreading）。

线程束中的所有线程同时执行同一条指令。如果线程束中有些线程在执行中走了控制流分支，而另一些没有，那么没有走该分支的线程会被屏蔽（masked off），走分支的线程则继续执行这些指令。例如，如果条件只对线程束中一半的线程为真，另一半线程束会被屏蔽，直到活动线程执行完这些指令。这种情况如图 7 所示。当线程束中的不同线程走不同的代码路径时，有时称为线程束分支分化（warp divergence）。因此，线程束内的线程走相同的控制流路径时，GPU 的利用率最高。

在 SIMT 模型中，线程束中的所有线程以锁步（lock step）方式推进核函数。硬件实际执行可能有所不同。关于这种区别在何处重要，参见独立线程执行（Independent Thread Execution）的相关章节。不要试图利用线程束执行如何映射到真实硬件的知识，CUDA 编程模型与 SIMT 规定：线程束中的所有线程一起推进代码。只要遵循编程模型，硬件可以以对程序透明的方式优化被屏蔽的通道。如果程序违反了这个模型，可能导致未定义行为，且在不同 GPU 硬件上表现不同。

编写 CUDA 代码时不需要考虑线程束，但理解线程束执行模型有助于理解全局内存合并访存（coalescing）、共享内存 bank 访问模式等概念。一些高级编程技巧会让线程块内的线程束分工协作，以减少线程分支分化、提高利用率。这些优化都利用了“线程在执行时按线程束分组”这一知识。

线程束执行的一个含义是：线程块的线程总数最好是 32 的倍数。使用任意数量的线程都是合法的，但总数不是 32 的倍数时，线程块的最后一个线程束会有一些通道在整个执行期间空闲。这很可能导致该线程束的功能单元利用率和内存访问次优。

> SIMT 常被拿来与单指令多数据（SIMD）并行比较，但两者有重要区别。在 SIMD 中，执行只走一条控制流路径；而在 SIMT 中，每个线程都可以走自己的控制流路径。因此，SIMT 不像 SIMD 那样有固定的数据宽度。关于 SIMT 的更详细讨论，参见 SIMT 执行模型。

### 1.2.2.3 CUDA 中的分块（Tile）编程

除上述 SIMT 模型外，CUDA 还支持分块（tile）编程模型。在分块编程中，程序员以整个线程块为粒度编写代码，描述对称为分块（tile）的多维数据集合的操作。编译器把这些操作映射到线程块的各个线程上。

分块核函数按线程块与网格小节描述的方式，在由线程块组成的网格上启动。每个线程块执行分块核函数，并通过查询自己在网格中的位置，确定自己负责哪部分数据。程序员只需指定网格维度；每个线程块的线程数由编译器根据核函数中的分块操作决定（图 8）。

（图 8：SIMT 与分块编程模型下的程序员视角。在 SIMT 中，程序员编写逐线程代码，控制每个线程如何访问数据；在分块编程中，程序员编写逐线程块代码，对分块进行操作，编译器把操作映射到线程块的线程上。）

在一个分块核函数中，线程块执行单一的控制流。程序员指定对分块的操作，编译器把工作分配到线程块的各个线程上。条件语句、循环等标准控制流结构都支持，但由于线程块只有一条控制流，不存在线程束分支分化的概念。计算索引或循环界限等标量操作由线程块中的单个线程执行；把两个分块逐元素相加等分块操作则由线程块的所有线程共同并行执行。

不要把线程块（执行单元）与分块（数据单元）混淆。一个线程块可以创建多个形状和数据类型各不相同的分块，并对其进行操作。

#### 1.2.2.3.1 数组与分块

分块核函数处理两种数据：数组（array）与分块（tile）。数组（或全局数组）是存储在设备端内存中的多维元素容器。数组是可变的：核函数中的存储操作可以修改其内容。数组有形状和数据类型。

分块是只存在于分块代码中、属于单个线程块的多维值集合。分块是不可变的：对分块的每个操作都会产生一个新的分块，而不是修改已有的分块。与数组不同，分块不一定有内存表示——编译器决定分块数据的存储方式，可能使用寄存器、共享内存或 SM 的其他资源。分块的每一维都必须是 2 的幂，且在编译时已知（即值必须在核函数执行前确定，而不是在执行中计算）。分块不能作为核函数参数传递；它们完全在分块代码内部创建和消费。

#### 1.2.2.3.2 分块空间与数据移动

数据通过加载与存储操作在数组与分块之间移动。这些操作使用一个称为分块空间（tile space）的概念：把数组在概念上划分成大小相等、互不重叠的分块。例如，一个形状为 (M, N) 的二维数组，若加载操作指定分块形状为 (tm, tn)，则数组被概念上划分为 ⌈M /tm ⌉ 行、⌈N /tn ⌉ 列的分块。分块空间中的一个索引（如 (i, j)）标识要加载哪个分块。加载返回形状为 (tm, tn) 的分块，其中包含数组中对应的元素。当分块超出数组边界时——例如数组维度不是分块维度的整数倍时，分块在边缘处超出边界——加载操作会指定越界元素的处理方式，例如用零填充（图 9）。

（图 9：分块空间与数据移动。形状为 (M, N) 的二维数组在概念上被划分为形状为 (tm, tn) 的分块网格。分块空间索引 (i, j) 处的加载返回对应的分块。在数组边界，超出数组的元素可以用零填充。存储操作把分块写回分块空间索引处的数组。）

存储操作是其逆操作：给定一个分块和分块空间中的一个索引，把分块的元素写到数组的对应区域。落在数组边界之外的写操作会被静默丢弃。分块程序还支持聚集（gather）与分散（scatter）操作，可以从数组的任意位置加载或向任意位置存储。

#### 1.2.2.3.3 分块操作

分块程序提供了一组作用于分块的内置操作，包括逐元素算术、矩阵乘法、沿一个或多个轴的归约（如求和与最大值）、形状变换（如重塑与转置）以及类型转换。当两个形状不同的分块参与运算时，较小的分块会在运算前自动扩展到与较大分块相同的形状。

#### 1.2.2.3.4 与 SIMT 编程的关系

分块编程与 SIMT 编程在 CUDA 中共存。一个应用程序可以同时包含 SIMT 核函数与分块核函数，两种核函数都可以操作设备端内存中的同一数据。编程模型的选择是按核函数决定的。分块编程不会取代 SIMT 编程。SIMT 提供对单个线程的细粒度控制，这对某些算法和优化技术仍然必要。分块编程提供更高层的抽象，可以简化核函数开发。由于线程层面的决策交给了编译器，同一个分块核函数无需修改源码即可运行在不同的 GPU 架构上。两种模型都建立在前面小节描述的同一底层硬件上——SM、线程块与网格——也使用相同的设备端内存空间，下一小节将介绍这些内存空间。

## 1.2.3 GPU 内存

在现代计算系统中，高效利用内存与充分利用执行计算的功能单元同等重要。异构系统有多个内存空间，GPU 除了高速缓存外，还有多种可编程的片上内存。下面几小节详细介绍这些内存空间。

### 1.2.3.1 异构系统中的 DRAM 内存

GPU 与 CPU 都有直连的 DRAM 芯片。在有多块 GPU 的系统中，每块 GPU 都有自己的内存。从设备端代码的视角看，GPU 直连的 DRAM 称为全局内存（global memory），因为它对 GPU 中的所有 SM 都可访问。这个术语并不意味着它在整个系统中处处可访问。CPU 直连的 DRAM 称为系统内存或主机端内存。

与 CPU 一样，GPU 也使用虚拟内存寻址。在所有当前支持的系统上，CPU 与 GPU 使用统一的虚拟内存空间。也就是说，系统中每块 GPU 的虚拟内存地址范围都是唯一且互不重叠的，与 CPU 和其他 GPU 都不重复。对一个给定的虚拟内存地址，可以判断该地址是在 GPU 内存还是系统内存中；在多 GPU 系统中，还可以判断是哪块 GPU 的内存。

CUDA 提供了分配 GPU 内存、CPU 内存的 API，以及在 CPU 与 GPU 之间、在 GPU 内部、或多 GPU 系统的 GPU 之间复制数据的 API。需要时可以显式控制数据的局部性。下面讨论的统一内存（Unified Memory）则允许由 CUDA 运行时或系统硬件自动处理内存的放置。

### 1.2.3.2 局部域

局部域（locality domain）是 GPU 内存与流多处理器（SM）的一个子集。每块 GPU 至少有一个局部域。更大的 GPU 可能有多个局部域。在有多个局部域的 GPU 上，使用局部化的内存与计算可以提升某些核函数的性能。局部化内存是指完全包含在单个局部域内的内存分配。使用这种内存的核函数可以被调度到同一局部域内的 SM 上。当内存与计算在多个局部域之间划分，且工作可以并行地提交到每个局部域时，应用程序能从局部化中受益。

未指定局部域分配的 GPU 内存称为非局部化内存。非局部化内存分配会横跨多个局部域，但极小的分配除外。

在只有一个局部域的 GPU 上，该 GPU 的所有 SM 与内存都属于这一个局部域。4.7 节介绍了在指定局部域内局部化 GPU 内存与计算的机制。局部域是一个性能特性：不做内存或计算局部化的 CUDA 代码仍然可以正确执行。

### 1.2.3.3 GPU 片上内存

除全局内存外，每块 GPU 还有一些片上内存。每个 SM 都有自己的寄存器文件和共享内存。这些内存是 SM 的一部分，SM 内执行的线程可以极快地访问。

寄存器文件存储线程局部变量，通常由编译器分配。共享内存可被线程块或簇内的所有线程访问。共享内存可用于线程块或簇的线程之间交换数据。

SM 中的寄存器文件与统一数据缓存的大小有限。SM 的寄存器文件、统一数据缓存的大小，以及统一数据缓存如何在 L1 与共享内存之间配置平衡，可查计算能力相关的内存信息（Memory Information per Compute Capability）。寄存器文件、共享内存空间与 L1 缓存在线程块的所有线程之间共享。

要把一个线程块调度到 SM 上，每个线程所需的寄存器总数乘以线程块中的线程数，必须小于或等于 SM 中可用的寄存器数。如果线程块所需的寄存器数超过寄存器文件的大小，该核函数无法启动，必须减少线程块中的线程数才能启动。

共享内存分配是按线程块进行的。也就是说，与按线程分配的寄存器不同，共享内存的分配是整个线程块共用的。

#### 1.2.3.3.1 高速缓存

除可编程内存外，GPU 还有 L1 与 L2 缓存。每个 SM 都有一个 L1 缓存，它是统一数据缓存的一部分。更大的 L2 缓存由 GPU 内的所有 SM 共享，如图 2 的 GPU 框图所示。每个 SM 还有一个独立的常量缓存（constant cache），用于缓存已声明在核函数生命周期内保持不变的全局内存值。编译器也可能把核函数参数放入常量内存（constant memory）中。这样可以把核函数参数缓存到 SM 中、与 L1 数据缓存分开，从而提升核函数性能。

### 1.2.3.4 统一内存

应用程序在 GPU 或 CPU 上显式分配的内存，只能被运行在该设备上的代码访问。也就是说，CPU 内存只能被 CPU 代码访问，GPU 内存只能被运行在 GPU 上的核函数访问²。CPU 与 GPU 之间的内存复制用 CUDA API 显式完成，以便在正确的时机把数据复制到正确的位置。

CUDA 的一项特性称为统一内存（unified memory），允许应用程序分配 CPU 或 GPU 都能访问的内存。CUDA 运行时或底层硬件在需要时启用访问或把数据搬迁到正确的位置。即使使用统一内存，也要尽量减少内存迁移、尽量让处理器访问直连该内存所在位置的数据，才能获得最佳性能。

系统硬件特性决定了内存空间之间的数据访问与交换如何实现。统一内存（Unified Memory）一节介绍了不同类别的统一内存系统。统一内存（Unified Memory）一节包含更多关于统一内存在各种情况下使用与行为的细节。

> ² 例外是映射内存（mapped memory），它是分配了特殊属性、能被 GPU 直接访问的 CPU 内存。但映射访问要经过 PCIe 或 NVLINK 连接。GPU 无法用并行掩盖其较高的延迟和较低的带宽，因此映射内存不是统一内存或把数据放在合适的内存空间的性能替代品。
