# 3.1 高级 CUDA API 与特性

本节将介绍一些更高级的 CUDA API 和特性。这些内容主要涉及那些通常不需要修改 CUDA 核函数的技巧或特性，但它们仍能从主机端影响应用层行为——既影响 GPU 工作的执行与性能，也影响 CPU 端的性能。

## 3.1.1 cudaLaunchKernelEx

当三重尖括号（triple chevron）记法在 CUDA 早期版本中引入时，核函数的启动配置（Kernel Configuration）只有四个可编程参数：

- 线程块维度
- 网格维度
- 动态共享内存（可选，未指定则为 0）
- 流（未指定则使用默认流）

有些 CUDA 特性可以从随核函数启动一起提供的额外属性和提示中受益。`cudaLaunchKernelEx` 允许程序通过 `cudaLaunchConfig_t` 结构体设置上述执行配置参数。此外，`cudaLaunchConfig_t` 结构体还允许程序传入零个或多个 `cudaLaunchAttribute`，以控制或建议核函数启动的其他参数。例如，本章后面讨论的 `cudaLaunchAttributePreferredSharedMemoryCarveout`（见"配置 L1/共享内存配比"）就是通过 `cudaLaunchKernelEx` 指定的；本章后面讨论的 `cudaLaunchAttributeClusterDimension` 属性用于指定核函数启动所需的集群（cluster）尺寸。

支持的属性完整列表及其含义见 CUDA 运行时 API 参考文档。

## 3.1.2 启动集群（Launching Clusters）

前文介绍的线程块集群（thread block cluster）是计算能力（Compute Capability）9.0 及以上版本提供的可选的线程块组织层级。它能保证一个集群内的线程块同时在单个 GPC 上执行，使线程数量超过单个流多处理器（Streaming Multiprocessor，SM）容量的更大线程组能够彼此交换数据并同步。

第 2.1.10.1 节展示了如何用三重尖括号记法指定并启动使用集群的核函数。其中使用了 `__cluster_dims__` 注解来指定启动核函数时必须使用的集群维度。用三重尖括号记法启动时，集群尺寸是隐式确定的。

### 3.1.2.1 使用 cudaLaunchKernelEx 启动集群

与用三重尖括号记法启动集群核函数不同，线程块集群的尺寸可以按每次启动单独配置。下面的代码示例展示了如何用 `cudaLaunchKernelEx` 启动集群核函数。

```cuda
// 核函数定义
// 核函数未附带编译时属性
__global__ void cluster_kernel(float *input, float* output)
{

}

int main()
{
    float *input, *output;
    dim3 threadsPerBlock(16, 16);
    dim3 numBlocks(N / threadsPerBlock.x, N / threadsPerBlock.y);

    // 使用运行时集群尺寸调用核函数
    {
        cudaLaunchConfig_t config = {0};
        // 网格维度不受集群启动影响，仍按
        // 线程块数量枚举。
        // 网格维度应为集群尺寸的整数倍。
        config.gridDim = numBlocks;
        config.blockDim = threadsPerBlock;

          cudaLaunchAttribute attribute[1];
          attribute[0].id = cudaLaunchAttributeClusterDimension;
          attribute[0].val.clusterDim.x = 2; // X 维度的集群尺寸
          attribute[0].val.clusterDim.y = 1;
          attribute[0].val.clusterDim.z = 1;
          config.attrs = attribute;
          config.numAttrs = 1;

          cudaLaunchKernelEx(&config, cluster_kernel, input, output);
      }
}
```

与线程块集群相关的 `cudaLaunchAttribute` 有两种：`cudaLaunchAttributeClusterDimension` 和 `cudaLaunchAttributePreferredClusterDimension`。

属性 ID `cudaLaunchAttributeClusterDimension` 指定执行集群所需的维度。该属性的值 `clusterDim` 是一个三维值；网格的对应维度（x、y、z）必须能被所指定集群维度的对应维度整除。其作用类似于在核函数定义上使用 `__cluster_dims__` 编译时属性（如"用三重尖括号记法启动集群"所示），但可以在运行时为同一核函数的不同启动更改。

在计算能力 10.0 及以上的 GPU 上，另一个属性 ID `cudaLaunchAttributePreferredClusterDimension` 允许应用程序再指定一个首选的集群维度。首选维度必须是核函数上 `__cluster_dims__` 属性或传给 `cudaLaunchKernelEx` 的 `cudaLaunchAttributeClusterDimension` 属性所指定的最小集群维度的整数倍。也就是说，除首选集群维度外，还必须指定一个最小集群维度。网格的对应维度（x、y、z）必须能被所指定首选集群维度的对应维度整除。

所有线程块都将以不小于最小集群维度的集群执行；在条件允许时将使用首选维度的集群，但并非所有集群都保证以首选维度执行。所有线程块都将以最小或首选集群维度之一的集群执行。使用首选集群维度的核函数必须编写为在最小或首选集群维度下都能正确运行。

### 3.1.2.2 块即集群（Blocks as Clusters）

当核函数用 `__cluster_dims__` 注解定义时，网格中的集群数量是隐式的，可由网格尺寸除以指定的集群尺寸计算得出。

```cuda
__cluster_dims__((2, 2, 2)) __global__ void foo();

// 8x8x8 个集群，每个集群含 2x2x2 个线程块。
foo<<<dim3(16, 16, 16), dim3(1024, 1, 1)>>>();
```

在上面的例子中，核函数以 16x16x16 个线程块的网格启动，也就是说使用了 8x8x8 个集群的网格。

核函数也可以使用 `__block_size__` 注解，它在定义核函数时同时指定所需的块尺寸和集群尺寸。使用该注解时，三重尖括号启动中的第一个参数变为以集群而非线程块为单位的网格维度，如下所示。

```cuda
// 每个线程块多少线程、每个集群多少块等实现细节
// 作为核函数的属性处理。
__block_size__((1024, 1, 1), (2, 2, 2)) __global__ void foo();

// 8x8x8 个集群。
foo<<<dim3(8, 8, 8)>>>();
```

`__block_size__` 需要两个字段，每个字段都是含 3 个元素的元组。第一个元组表示块维度，第二个表示集群尺寸。第二个元组若未传入，默认为 (1,1,1)。在核函数启动时指定动态共享内存尺寸和/或流时，`<<<>>>` 中的第二个参数必须使用占位符 1；任何其他值都会导致未定义行为。

注意，`__block_size__` 的第二个元组与 `__cluster_dims__` 不能同时指定。`__block_size__` 也不能与空的 `__cluster_dims__` 一起使用。当 `__block_size__` 的第二个元组被指定时，就意味着启用了"块即集群"（Blocks as Clusters），编译器会把 `<<<>>>` 中的第一个参数识别为集群数量而非线程块数量。

## 3.1.3 关于流与事件的更多内容

前文"CUDA 流"介绍了 CUDA 流的基础知识。默认情况下，提交到给定 CUDA 流（stream）上的操作是串行化的：一个操作必须等前一个完成后才能开始执行。唯一的例外是最近加入的编程式依赖启动与同步（Programmatic Dependent Launch and Synchronization）特性。多流是一种实现并发执行的方法，另一种方法是使用 CUDA 图（CUDA Graphs）。两种方法也可以结合使用。

提交到不同 CUDA 流上的工作在特定条件下可能并发执行，例如：没有事件依赖、没有隐式同步、有充足的资源，等等。

如果在两个来自不同 CUDA 流的独立操作之间提交了 NULL 流上的任何 CUDA 操作，则它们无法并发运行——除非使用的是非阻塞 CUDA 流。非阻塞流是指用运行时 API `cudaStreamCreateWithFlags()` 并带 `cudaStreamNonBlocking` 标志创建的流。为了提高 GPU 工作并发执行的可能性，建议用户创建非阻塞 CUDA 流。

还建议用户选择能满足需求的粒度最粗的同步方式。例如，若需求是让 CPU 等待（阻塞）某个特定 CUDA 流上的所有工作完成，对该流使用 `cudaStreamSynchronize()` 就比 `cudaDeviceSynchronize()` 更合适，因为后者会无谓地等待该设备所有 CUDA 流上的 GPU 工作完成。如果需求是让 CPU 以非阻塞方式等待，那么在轮询循环中用 `cudaStreamQuery()` 并检查其返回值可能更合适。

类似的同步效果也可以用 CUDA 事件（CUDA Events）实现，例如在该流上记录一个事件，然后调用 `cudaEventSynchronize()` 以阻塞方式等待该事件捕获的工作完成。这同样比 `cudaDeviceSynchronize()` 更合适、更有针对性。以非阻塞方式在轮询循环中调用 `cudaEventQuery()` 并检查其返回值则是非阻塞的替代方案。

如果这一操作发生在应用的关键路径上，显式同步方法的选择尤为重要。表 4 概括了与主机同步的各种选项。

**表 4：与主机显式同步选项汇总**

| | 等待特定流 | 等待特定事件 | 等待设备上的一切 |
|---|---|---|---|
| 非阻塞（需轮询循环） | cudaStreamQuery() | cudaEventQuery() | 不适用 |
| 阻塞 | cudaStreamSynchronize() | cudaEventSynchronize() | cudaDeviceSynchronize() |

对于流之间的同步（即表达依赖关系），推荐使用非计时 CUDA 事件，详见"CUDA 事件"。用户可以调用 `cudaStreamWaitEvent()`，强制之后提交到特定流上的操作等待先前记录的事件（例如在另一流上记录的事件）完成。注意，对于任何等待或查询事件的 CUDA API，用户有责任确保此前已调用过 `cudaEventRecord` API——未被记录的事件总会返回成功。

CUDA 事件默认携带计时信息，因为它们可用于 `cudaEventElapsedTime()` API 调用。但仅用于表达流间依赖关系的 CUDA 事件不需要计时信息。对这类情况，建议用 `cudaEventCreateWithFlags()` API 并带 `cudaEventDisableTiming` 标志创建禁用计时的事件，以获得更好的性能。

### 3.1.3.1 流优先级

流的相对优先级可以在创建流时用 `cudaStreamCreateWithPriority()` 指定。可用优先级的范围（按[最高优先级，最低优先级]排序）可通过 `cudaDeviceGetStreamPriorityRange()` 函数获取。运行时 GPU 调度器利用流优先级决定任务执行顺序，但这些优先级只是提示而非保证。在选择要启动的工作时，高优先级流中的待处理任务优先于低优先级流中的任务。高优先级任务不会抢占已在运行的低优先级任务。GPU 在任务执行期间不会重新评估工作队列，提高流的优先级也不会中断正在进行的工作。流优先级会影响任务执行，但不强制严格的顺序——用户可以利用流优先级影响任务执行，而不依赖严格的顺序保证。

下面的代码示例获取当前设备的可用优先级范围，并创建两个分别具有最高和最低可用优先级的非阻塞 CUDA 流。

```cuda
// 获取该设备的流优先级范围
int leastPriority, greatestPriority;
cudaDeviceGetStreamPriorityRange(&leastPriority, &greatestPriority);

// 创建具有最高和最低可用优先级的流
cudaStream_t st_high, st_low;
cudaStreamCreateWithPriority(&st_high, cudaStreamNonBlocking, greatestPriority);

cudaStreamCreateWithPriority(&st_low, cudaStreamNonBlocking, leastPriority);
```

### 3.1.3.2 显式同步

如前所述，流之间同步有多种方式。以下按粒度列举常用方法：

- `cudaDeviceSynchronize()`：等待所有主机线程的所有流中所有前置命令完成。
- `cudaStreamSynchronize()`：以流为参数，等待给定流中所有前置命令完成。可用于主机与特定流同步，同时允许其他流继续在设备端执行。
- `cudaStreamWaitEvent()`：以流和事件为参数（事件的说明见"CUDA 事件"），使在调用 `cudaStreamWaitEvent()` 之后添加到给定流的所有命令延迟执行，直到给定事件完成。
- `cudaStreamQuery()`：为应用提供一种获知流中所有前置命令是否完成的方法。

### 3.1.3.3 隐式同步

如果主机线程在来自不同流的两个命令之间发出了以下任一操作，这两个命令就无法并发运行：

- 页锁定主机内存分配
- 设备内存分配
- 设备内存设置
- 同一设备内存两地址之间的内存拷贝
- 发往 NULL 流的任何 CUDA 命令
- L1/共享内存配置切换

需要依赖检查的操作包括：与被检查启动位于同一流中的其他命令，以及对该流的任何 `cudaStreamQuery()` 调用。因此，应用应遵循以下准则以提高核函数并发执行的可能性：

- 所有独立操作应在依赖操作之前发出；
- 任何形式的同步都应尽量推迟。

## 3.1.4 编程式依赖核函数启动（Programmatic Dependent Kernel Launch）

如前文所述，CUDA 流的语义是核函数按序执行。这样，当有两个连续的核函数、第二个依赖第一个的结果时，程序员可以确信第二个核函数开始执行时，所依赖的数据已经就绪。然而，可能出现这样的情况：第一个核函数已经把第二个核函数所依赖的数据写入全局内存（global memory），但它自己还有更多工作要做；同样，第二个核函数在需要第一个核函数的数据之前，可能有一些独立的工作要做。在这种情况下，如果硬件资源允许，两个核函数的执行可以部分重叠；第二个核函数的启动开销也可以被重叠。除了硬件资源可用性，可达到的重叠程度取决于核函数的具体结构，例如：

- 第一个核函数在执行到什么位置时完成第二个核函数所依赖的工作？
- 第二个核函数在执行到什么位置时开始处理来自第一个核函数的数据？

因为这高度依赖具体的核函数，难以完全自动化，所以 CUDA 提供了一种机制，让应用开发者指定两个核函数之间的同步点，这就是编程式依赖核函数启动（Programmatic Dependent Kernel Launch，PDL）。下图描绘了这一情形。

PDL 有三个主要组成部分：

1. 第一个核函数（称为主核函数，primary kernel）需要调用一个特殊函数，表明它已完成所有后续依赖核函数（也称从核函数，secondary kernel）需要的工作。这通过调用 `cudaTriggerProgrammaticLaunchCompletion()` 实现。
2. 依赖的从核函数需要表明它已执行完与主核函数无关的工作部分，现在等待主核函数完成它所依赖的工作。这通过函数 `cudaGridDependencySynchronize()` 实现。
3. 第二个核函数需要用特殊属性启动：`cudaLaunchAttributeProgrammaticStreamSerialization`，并将其 `programmaticStreamSerializationAllowed` 字段设为 1。

下面的代码片段展示了如何实现。

**示例 3：两个核函数的编程式依赖核函数启动示例**

```cuda
__global__ void primary_kernel() {
    // 应在启动从核函数之前完成的初始工作

       // 触发从核函数
       cudaTriggerProgrammaticLaunchCompletion();

       // 可与从核函数同时执行的工作
}

__global__ void secondary_kernel()
{
    // 初始化、独立工作等

       // 将阻塞，直到从核函数所依赖的所有主核函数
       // 完成并把结果刷新到全局内存
       cudaGridDependencySynchronize();

       // 依赖工作
}

// 用特殊属性启动从核函数

// 设置属性
cudaLaunchAttribute attribute[1];
attribute[0].id = cudaLaunchAttributeProgrammaticStreamSerialization;
attribute[0].val.programmaticStreamSerializationAllowed = 1;

// 在核函数启动配置中设置属性
 cudaLaunchConfig_t config = {0};

// 基本启动配置
config.gridDim = grid_dim;
config.blockDim = block_dim;
config.dynamicSmemBytes= 0;
config.stream = stream;

// 添加 PDL 特殊属性
config.attrs = attribute;
config.numAttrs = 1;

// 启动主核函数
primary_kernel<<<grid_dim, block_dim, 0, stream>>>();

// 用带该属性的配置启动从（依赖）核函数
cudaLaunchKernelEx(&config, secondary_kernel);
```

## 3.1.5 批量内存传输（Batched Memory Transfers）

CUDA 开发中一种常见模式是批处理技术。这里的"批处理"大致指把若干（通常较小的）任务组合成一个（通常较大的）操作。批量中的各任务不一定完全相同，但常常如此。一个例子是 cuBLAS 提供的批量矩阵乘法操作。

与 CUDA 图和 PDL 一样，批处理的目的通常是减少逐个分发批量任务带来的开销。就内存传输而言，启动一次内存传输会产生一些 CPU 和驱动开销。此外，当前形式的常规 `cudaMemcpyAsync()` 函数不一定能给驱动提供足够信息来优化传输，例如关于源和目标的提示。在 Tegra 平台上，传输可以使用 SM 或拷贝引擎（Copy Engine，CE）执行，当前由驱动中的启发式策略决定使用哪一种。这很重要，因为使用 SM 可能传输更快，但会占用一部分可用的算力；而使用 CE 可能传输稍慢，但整体应用性能更高，因为它把 SM 留出来做其他工作。

这些考虑促成了 `cudaMemcpyBatchAsync()` 函数（及其变体 `cudaMemcpyBatch3DAsync()`）的设计。这些函数允许对批量内存传输进行优化。除了源和目标指针列表，API 还用内存拷贝属性指定顺序期望，以及源和目标位置的提示，还有是否希望传输与计算重叠的偏好（目前仅在带 CE 的 Tegra 平台上支持）。

先考虑最简单的情况：从页锁定主机内存到页锁定设备内存的简单批量传输。

**示例 4：从页锁定主机内存到页锁定设备内存的同构批量内存传输示例**

```cuda
std::vector<void *> srcs(batch_size);
std::vector<void *> dsts(batch_size);
std::vector<size_t> sizes(batch_size);

// 分配源和目标缓冲区
// 用流编号初始化
for (size_t i = 0; i < batch_size; i++) {
    cudaMallocHost(&srcs[i], sizes[i]);
    cudaMalloc(&dsts[i], sizes[i]);
    cudaMemsetAsync(srcs[i], sizes[i], stream);
}

// 为这批拷贝设置属性
cudaMemcpyAttributes attrs = {};
attrs.srcAccessOrder = cudaMemcpySrcAccessOrderStream;

// 批量中所有拷贝具有相同的拷贝属性。
size_t attrsIdxs = 0; // 属性的索引

// 启动批量内存传输
cudaMemcpyBatchAsync(&dsts[0], &srcs[0], &sizes[0], batch_size,
    &attrs, &attrsIdxs, 1 /*numAttrs*/, nullptr /*failIdx*/, stream);
```

`cudaMemcpyBatchAsync()` 函数的前几个参数很好理解：包含源和目标指针以及传输尺寸的数组，每个数组必须有 `batch_size` 个元素。新信息来自属性。函数需要一个指向属性数组的指针，以及一个对应的属性索引数组。原则上还可以传入一个 `size_t` 数组，记录失败传输的索引，但传入 `nullptr` 也是安全的，此时失败索引将不被记录。

再看属性：本例中的传输是同构的，所以只用一个属性，它将应用于所有传输。这由 `attrIndex` 参数控制。原则上它可以是一个数组，数组中第 i 个元素包含第 i 个属性所适用的第一次传输的索引。在本例中，`attrIndex` 被视为只有一个元素的数组，值为 0，含义是 `attribute[0]` 将应用于索引为 0 及以上的所有传输，也就是所有传输。

最后注意到我们把 `srcAccessOrder` 属性设为 `cudaMemcpySrcAccessOrderStream`。这意味着源数据将按常规流顺序访问。换句话说，memcpy 会阻塞，直到处理这些源和目标指针数据的前置核函数完成。

下一个例子考虑更复杂的情况：异构批量传输。

**示例 5：使用部分临时主机内存到页锁定设备内存的异构批量内存传输示例**

```cuda
std::vector<void *> srcs(batch_size);
std::vector<void *> dsts(batch_size);
std::vector<size_t> sizes(batch_size);

// 分配源和目标缓冲区
for (size_t i = 0; i < batch_size - 10; i++) {
    cudaMallocHost(&srcs[i], sizes[i]);
    cudaMalloc(&dsts[i], sizes[i]);
}

int buffer[10];

for (size_t i = batch_size - 10; i < batch_size; i++) {
    srcs[i] = &buffer[10 - (batch_size - i];
    cudaMalloc(&dsts[i], sizes[i]);
}

// 为这批拷贝设置属性
cudaMemcpyAttributes attrs[2] = {};
attrs[0].srcAccessOrder = cudaMemcpySrcAccessOrderStream;
attrs[1].srcAccessOrder = cudaMemcpySrcAccessOrderDuringApiCall;

size_t attrsIdxs[2];
attrsIdxs[0] = 0;
attrsIdxs[1] = batch_size - 10;

// 启动批量内存传输
cudaMemcpyBatchAsync(&dsts[0], &srcs[0], &sizes[0], batch_size,
    &attrs, &attrsIdxs, 2 /*numAttrs*/, nullptr /*failIdx*/, stream);
```

这里有两种传输：`batch_size - 10` 次从页锁定主机内存到页锁定设备内存的传输，以及 10 次从主机数组到页锁定设备内存的传输。此外，`buffer` 数组不仅在主机端，而且只在当前作用域内存在——它的地址就是所谓的临时指针（ephemeral pointer）。该指针在 API 调用完成后可能不再有效（它是异步的）。要执行这类临时指针的拷贝，属性中的 `srcAccessOrder` 必须设为 `cudaMemcpySrcAccessOrderDuringApiCall`。

现在我们有两个属性：第一个适用于索引从 0 开始、小于 `batch_size - 10` 的所有传输；第二个适用于索引从 `batch_size - 10` 开始、小于 `batch_size` 的所有传输。

如果 `buffer` 数组不是从栈上分配，而是用 `malloc` 从堆上分配的，数据就不再是临时的，在指针被显式释放之前一直有效。这种情况下如何组织拷贝最好，取决于系统是否有硬件托管内存（hardware managed memory），或 GPU 是否能通过地址转换一致地访问主机内存——如果有，用流顺序最好；如果没有，立即组织传输最合理。在这种情况下，属性的 `srcAccessOrder` 应使用值 `cudaMemcpyAccessOrderAny`。

`cudaMemcpyBatchAsync` 函数还允许程序员给出源和目标位置的提示。这通过设置 `cudaMemcpyAttributes` 结构体的 `srcLocation` 和 `dstLocation` 字段实现。`srcLocation` 和 `dstLocation` 字段均为 `cudaMemLocation` 类型，该结构体包含位置类型和位置 ID。这与用 `cudaMemPrefetchAsync()` 给运行时提供预取提示时用的 `cudaMemLocation` 结构体相同。下面代码示例展示了如何为从设备到主机特定 NUMA 节点的传输设置提示：

**示例 6：设置源和目标位置提示示例**

```cuda
// 分配源和目标缓冲区
std::vector<void *> srcs(batch_size);
std::vector<void *> dsts(batch_size);
std::vector<size_t> sizes(batch_size);

// 将用于提供位置提示的 cudaMemLocation 结构体
// 设备 device_id
cudaMemLocation srcLoc = {cudaMemLocationTypeDevice, dev_id};

// NUMA 节点 numa_id 的主机
cudaMemLocation dstLoc = {cudaMemLocationTypeHostNuma, numa_id};

// 分配源和目标缓冲区
for (size_t i = 0; i < batch_size; i++) {
    cudaMallocManaged(&srcs[i], sizes[i]);
    cudaMallocManaged(&dsts[i], sizes[i]);

      cudaMemPrefetchAsync(srcs[i], sizes[i], srcLoc, 0, stream);
      cudaMemPrefetchAsync(dsts[i], sizes[i], dstLoc, 0, stream);
      cudaMemsetAsync(srcs[i], sizes[i], stream);
}

// 为这批拷贝设置属性
cudaMemcpyAttributes attrs = {};

// 这是托管内存（managed memory）指针，流顺序是合适的
attrs.srcAccessOrder = cudaMemcpySrcAccessOrderStream;

// 在这里指定位置提示。
attrs.srcLocHint = srcLoc;
attrs.dstlocHint = dstLoc;

// 批量中所有拷贝具有相同的拷贝属性。
size_t attrsIdxs = 0;

// 启动批量内存传输
cudaMemcpyBatchAsync(&dsts[0], &srcs[0], &sizes[0], batch_size,
    &attrs, &attrsIdxs, 1 /*numAttrs*/, nullptr /*failIdx*/, stream);
```

最后要介绍的是提示是否希望用 SM 还是 CE 执行传输的标志。对应字段是 `cudaMemcpyAttributes` 的 `flags`，可能的值有：

- `cudaMemcpyFlagDefault`：默认行为
- `cudaMemcpyFlagPreferOverlapWithCompute`：提示系统优先用 CE 执行传输，使传输与计算重叠。

总之，关于 `cudaMemcpyBatchAsync` 的要点如下：

- `cudaMemcpyBatchAsync` 函数（及其 3D 变体）允许程序员指定一批内存传输，从而摊销传输的启动开销。
- 除源和目标指针以及传输尺寸外，函数还可以接受一个或多个内存拷贝属性，提供关于被传输内存种类的信息、源指针相应的流顺序行为、源和目标位置的提示，以及是否希望传输与计算重叠（如可能）或使用 SM 执行传输的偏好。
- 有了上述信息，运行时可以尽可能优化传输。

## 3.1.6 环境变量

CUDA 提供多种环境变量（见 5.2 节），它们会影响执行和性能。如果没有显式设置，CUDA 会为它们使用合理的默认值，但某些情况下可能需要特殊处理，例如调试目的或获得更好的性能。

例如，可能需要增大 `CUDA_DEVICE_MAX_CONNECTIONS` 环境变量的值，以降低因虚假依赖导致不同 CUDA 流的独立工作被串行化的可能性。当使用相同的底层资源时，可能引入这种虚假依赖。建议先用默认值，只在出现性能问题（例如不同 CUDA 流上的独立工作出现无法用 SM 资源不足等其他因素解释的意外串行化）时再研究该环境变量的影响。值得注意的是，在 MPS 情况下该环境变量的默认值更低。

同样，对延迟敏感的应用，把 `CUDA_MODULE_LOADING` 环境变量设为 `EAGER` 可能更合适，以便把模块加载带来的所有开销移到应用初始化阶段，移出其关键阶段。当前默认模式是延迟模块加载。在该默认模式下，可以通过在应用初始化阶段对各种核函数做"预热"调用，强制模块加载提前发生，从而达到类似急切模块加载的效果。

关于各种 CUDA 环境变量的更多信息，请参阅"CUDA 环境变量"。建议在启动应用之前把环境变量设为新值；在应用内部设置可能没有效果。
