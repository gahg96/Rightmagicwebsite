# 4.7 局部性域

局部性域（locality domain）是 GPU 的一部分，包含流多处理器（Streaming Multiprocessor，SM）和设备端内存。应用程序可以在某个局部性域中分配设备端内存，并在同一局部性域中创建拥有 SM 资源的绿色上下文（green context）。在有多个局部性域的设备上，把计算放在其访问的内存附近，有助于提升性能。计算本地化的 API 见"本地化计算资源"（Localizing Compute Resources）一节，内存本地化见"分配本地化设备内存"（Allocating Localized Device Memory）一节。

CUDA 通过从 0 开始编号的局部性域 ID 来标识设备的局部性域。局部性域 ID 只有与设备 ID 结合才有意义。SM 资源和内存本地化使用同一个 ID，应用程序因此可以为两者请求匹配的放置位置。

## 4.7.1 发现局部性域

使用 `cudaDeviceGetAttribute` 并传入以下 `cudaDeviceAttr` 值：

- `cudaDevAttrLocalityDomainCount` 返回设备上的局部性域数量。
- `cudaDevAttrLocalityDomainMultiprocessorCount` 返回每个局部性域中的 SM 数量。

应用程序应查询这些属性，而不应假设特定的拓扑结构。设备上可用的局部性域数量受系统配置影响；同一型号的设备在不同场景下（见 4.7.5.3 节）可能呈现不同数量的局部性域。所有设备（包括只有一个可用局部性域的设备）都可以使用局部性域 API。在只有一个局部性域的设备上，这些 API 与针对整个设备等效。

用设备属性以编程方式查询设备的局部性域属性：

```c
int localityDomainCount = 0;
int smsPerLocalityDomain = 0;

cudaDeviceGetAttribute(&localityDomainCount, cudaDevAttrLocalityDomainCount, device);

cudaDeviceGetAttribute(&smsPerLocalityDomain, cudaDevAttrLocalityDomainMultiprocessorCount, device);
```

## 4.7.2 本地化计算资源

要把 SM 资源本地化到指定局部性域，使用 CUDA 绿色上下文 API。SM 的放置通过 4.6 节所述的绿色上下文资源 API 表达。构建本地化 SM 分区的主要步骤：

1. 用 `cudaDeviceGetDevResource` 获取设备的 `cudaDevResourceTypeSm` 资源。
2. 用 `cudaDevSmResourceGroupParams` 描述本地化 SM 组（详见下文）。
3. 把组参数传给 `cudaDevSmResourceSplit`。
4. 用 `cudaDevResourceGenerateDesc` 生成资源描述符，用 `cudaGreenCtxCreate` 创建绿色上下文，最后用 `cudaExecutionCtxStreamCreate` 创建流。
5. 在该流上启动核函数。

典型的绿色上下文创建流程见 4.6.2 节。下面展示本地化 SM 资源所需的补充部分：

要描述本地化 SM 组，在 `flags` 中设置 `cudaDevSmResourceGroupLocalityDomainId`，并在 `localityDomainId` 中设置 ID。有效 ID 范围是 0 到 `cudaDevAttrLocalityDomainCount` - 1。

```c
cudaDevResource smResource;
cudaDeviceGetDevResource(device, &smResource, cudaDevResourceTypeSm);

{
    cudaDevSmResourceGroupParams params = {};
    // params 的所有字段都必须零初始化
    params.flags = cudaDevSmResourceGroupLocalityDomainId;
    params.localityDomainId = localityDomainId;

    cudaDevResource result;
    cudaDevSmResourceSplit(&result, 1, &smResource, nullptr, 0, &params);
}
```

在请求局部性域的同时，`params` 中还可以组合指定多个约束条件。例如：

`smCount` 约束可以是 0（发现模式）或正数。发现模式下，API 在 `params.smCount` 中返回该局部性域中的 SM 数量。在完整的、未分区的设备资源上，该值与 `cudaDevAttrLocalityDomainMultiprocessorCount` 相同。`smCount` 为正数时，API 至多分配 `cudaDevAttrLocalityDomainMultiprocessorCount` 个 SM；更大的请求会失败。

`coscheduledSmCount` 为 0 时，API 不按协同调度能力限制 SM，可用的本地化 SM 数量最多。分区的集群（cluster）能力可稍后用 `cudaOccupancyMaxPotentialClusterSize` 动态查询。`coscheduledSmCount` 非零时，API 只选择满足所请求协同调度数量的本地化 SM。

默认情况下，结果中的所有 SM 都必须满足局部性域约束和指定的其他约束。要放宽此行为，可在 `params.flags` 中加入 `cudaDevSmResourceGroupBackfill`。启用回填（backfill）后，API 先从请求的局部性域填充，再从未归属到任何局部性域的 SM 填充，最后从其他局部性域的 SM 填充。如果在请求的局部性域中找不到任何 SM，调用失败并返回 `cudaErrorInvalidResourceConfiguration`。

未返回在结果中的剩余 SM 会在 API 的 `remainder` 参数中返回。

结果的 `cudaDevResource.sm.flags` 和 `cudaDevResource.sm.localityDomainId` 报告资源的放置情况。在一个描述符中组合 SM 资源时，各资源的约束必须匹配，包括 `flags` 和 `localityDomainId` 的值。

以下代码查询局部性域数量，并为每个局部性域构造一个流：

```cpp
std::vector<cudaExecutionContext_t> contexts(localityDomainCount);
std::vector<cudaStream_t> streams(localityDomainCount);

{
    std::vector<cudaDevSmResourceGroupParams> params(localityDomainCount);
    std::vector<cudaDevResource> result(localityDomainCount);

    for (int i = 0; i < localityDomainCount; i++) {
        params[i] = {};
        params[i].flags = cudaDevSmResourceGroupLocalityDomainId;
        params[i].localityDomainId = i;
    }

    // 一次拆分即为所有域产出互不重叠的资源。
    cudaDevSmResourceSplit(result.data(), localityDomainCount, &smResource, nullptr, 0, params.data());

    for (int i = 0; i < localityDomainCount; i++) {
        cudaDevResourceDesc_t desc;
        cudaDevResourceGenerateDesc(&desc, &result[i], 1);
        cudaGreenCtxCreate(&contexts[i], desc, device, 0);
        cudaExecutionCtxStreamCreate(&streams[i], contexts[i], cudaStreamDefault, 0);
    }
}
```

`streams` 中的每个流在索引对应的局部性域的 SM 上执行。不再需要时，用 `cudaStreamDestroy` 销毁流，再用 `cudaExecutionCtxDestroy` 销毁其上下文。

## 4.7.3 分配本地化设备内存

CUDA 用类型为 `cudaMemLocationTypeDeviceLocalityDomain` 的 `cudaMemLocation` 表示本地化的内存位置。对于这种位置类型，初始化 `cudaMemLocation.localized` 的两个成员：

- `deviceId` 标识 GPU。
- `localityDomainId` 标识该 GPU 上的一个局部性域。

运行时 API 在流序内存池（4.3 节）中使用该位置。驱动 API 还在虚拟内存管理分配（4.17 节）中使用对应的 `CUmemLocation`。

通过其他机制创建的分配（如 `cudaMalloc` 或统一内存）不能本地化。MLOPart 模式下的 MPS（多进程服务）可用来对依赖 `cudaMalloc` 的应用程序透明地本地化。

### 4.7.3.1 创建本地化内存池

要创建本地化内存池，在 `cudaMemPoolProps` 中设置位置并调用 `cudaMemPoolCreate`：

```c
cudaMemPool_t pool {};
cudaMemPoolProps props {};

props.allocType = cudaMemAllocationTypePinned;
props.location.type = cudaMemLocationTypeDeviceLocalityDomain;
props.location.localized.deviceId = device;
props.location.localized.localityDomainId = localityDomainId;

cudaMemPoolCreate(&pool, &props);
```

用 `cudaMallocFromPoolAsync` 从该池分配，用 `cudaFreeAsync` 释放。当为该局部性域选择默认或当前固定内存池时，该位置也可传给 `cudaMemGetDefaultMemPool`、`cudaMemGetMemPool` 和 `cudaMemSetMemPool`。通用的内存池编程模型见"内存池"（Memory Pools）一节。

### 4.7.3.2 创建本地化 VMM 分配

驱动 API 可以把 `cuMemCreate` 创建的物理内存放入局部性域。把 `CUmemAllocationProp::location.type` 设为 `CU_MEM_LOCATION_TYPE_DEVICE_LOCALITY_DOMAIN`，并初始化 `location.localized.deviceId` 和 `location.localized.localityDomainId`。所得的物理分配与其他 VMM 分配一样被预留、映射并授予访问权限。通过 `cuMemSetAccess` 设置的访问控制作用于整个设备粒度，而非单个局部性域。完整的分配序列和粒度要求见本地化 VMM 分配一节。

托管内存不能本地化：用 `cudaMemLocationTypeDeviceLocalityDomain` 请求 `cudaMemAllocationTypeManaged` 会返回 `CUDA_ERROR_NOT_SUPPORTED`。同样，`cudaMemPrefetchAsync` 和 `cudaMemAdvise` 不接受设备端局部性域作为位置，会返回 `CUDA_ERROR_NOT_SUPPORTED`。

局部性域与统一内存的关系见"局部性域与统一内存"（Locality Domains and Unified Memory）一节。

## 4.7.4 查询内存放置

用 `cudaMemPoolGetAttribute` 并传入 `cudaMemPoolAttrLocalityDomainId` 查询内存池。它返回本地化池的局部性域 ID，非本地化池返回 -1。

用 `cudaPointerGetAttributes` 通过指针查询分配。返回的 `cudaPointerAttributes.localityDomainOrdinal` 字段包含该分配的局部性域序号；未本地化时为 -1：

```c
cudaPointerAttributes attributes {};
cudaPointerGetAttributes(&attributes, ptr);
int localityDomainId = attributes.localityDomainOrdinal;
```

## 4.7.5 编程指导

要本地化工作负载，用与内存分配同一局部性域的计算资源启动核函数。

只本地化计算或只本地化内存资源通常不会提升性能。

如果核函数必须使用多个局部性域的内存，请实测计算本地化是否有益。

### 4.7.5.1 采用 Fork/Join 模式的本地化核函数

fork/join 模式用事件和流等待表达一个并行区域。应用程序用 `cudaExecutionCtxStreamCreate` 为每个本地化绿色上下文创建一个流，另用一个主（main）流协调这些本地化流。用 `cudaEventCreateWithFlags` 为主的流创建一个 fork 事件、为每个本地化流创建一个 join 事件；当事件只用于排序时应禁用计时。

fork 时，在父流上记录一个事件，让每个本地化流等待该事件。于是此前提交到父流的工作排在本地化工作之前。向本地化流提交相互独立的工作，使用各自局部性域的内存。

join 时，在每个本地化流完成工作后记录一个事件，让父流等待所有这些事件。于是之后提交到父流的工作排在本地化工作之后。

```c
produceInputs<<<grid, block, 0, parentStream>>>(...);
cudaEventRecord(forkEvent, parentStream);

// localizedStreams[i] 属于局部性域 i 的绿色上下文。
for (int i = 0; i < localityDomainCount; i++) {
    cudaStreamWaitEvent(localizedStreams[i], forkEvent);
    processPartition<<<grid, block, 0, localizedStreams[i]>>>(...);
    cudaEventRecord(joinEvents[i], localizedStreams[i]);
}

for (int i = 0; i < localityDomainCount; i++) {
    cudaStreamWaitEvent(parentStream, joinEvents[i]);
}
consumeResults<<<grid, block, 0, parentStream>>>(...);
```

### 4.7.5.2 CUDA 图

CUDA 图（4.2 节）通过流捕获和手动图构建支持本地化。对某些应用程序，CUDA 图的性能可能优于基于流的编程。

#### 4.7.5.2.1 流捕获

fork/join 模式可以捕获为 CUDA 图。在父流上开始捕获，记录 fork 事件，并在每个本地化流上等待 fork 事件。在 fork 事件上的等待会把本地化流纳入与父流相同的捕获图。提交到本地化流的操作成为图的并行分支。在本地化流上启动完所有工作后，记录 join 事件，并在父流上等待所有 join 事件。这些等待把所有分支重新汇合到父流。在调用 `cudaStreamEndCapture` 之前，每个参与的流都必须汇合回起始流。

```c
cudaStreamBeginCapture(parentStream, cudaStreamCaptureModeGlobal);

// 记录 forkEvent，向各本地化流提交工作，记录 joinEvents，
// 并如上面的 fork/join 示例一样让 parentStream 等待。

cudaGraph_t graph;
cudaStreamEndCapture(parentStream, &graph);
```

每个子流的局部性限制由捕获的核函数节点保留。图重放使用最初记录的本地化 SM，即使可执行图在不同的流上启动。图启动流只提供排序，不替代节点中记录的执行资源。

#### 4.7.5.2.2 图构建

同样的图拓扑可以显式构建。为每个局部性域添加一个核函数节点，在 `cudaKernelNodeParamsV2.ctx` 中使用对应的本地化执行上下文：

```c
cudaGraph_t graph = nullptr;
cudaGraphCreate(&graph, 0);

std::vector<cudaGraphNode_t> localizedNodes(localityDomainCount);
for (int i = 0; i < localityDomainCount; i++) {
    cudaGraphNodeParams params = { CU_GRAPH_NODE_TYPE_KERNEL };
    params.kernel.kern = kernel;
    params.kernel.gridDim = grid;
    params.kernel.blockDim = block;
    params.kernel.kernelParams = kernelArgs[i];
    params.kernel.ctx = localizedContexts[i];

    cudaGraphAddNode(&localizedNodes[i], graph, nullptr, nullptr, 0, &params);
}
```

### 4.7.5.3 兼容性说明

vGPU 和 MIG 设备不支持本地化，只报告 1 个局部性域。

Windows 上的 CUDA 不支持本地化，只报告 1 个局部性域。

CUDA Checkpoint 不保证本地化绿色上下文在恢复到不同设备上时保留其本地化属性。恢复后应用程序性能可能下降。

MLOPart 模式的 MPS（多进程服务）把每个 MLOPart 设备呈现为具有单个局部性域的 CUDA 设备。MPS 静态分区把整个设备视为单个局部性域。
