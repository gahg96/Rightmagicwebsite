# 3.5 CUDA 特性巡览（A Tour of CUDA Features）

本编程指南第 1–3 章介绍了 CUDA 和 GPU 编程，概念上和简单的代码示例中都覆盖了基础主题。本指南第 4 部分介绍具体 CUDA 特性的章节，默认读者已掌握第 1–3 章的概念。

CUDA 有许多特性，适用于不同的问题。并非每个特性都适用于所有用例。本章介绍这些特性，描述其预期用途和能帮助解决的问题。特性按所要解决的问题类型大致分类。有些特性（如 CUDA 图）可以归入多个类别。第 4 章对这些 CUDA 特性有更完整的详细说明。

## 3.5.1 提升核函数性能（Improving Kernel Performance）

本节概述的特性都旨在帮助核函数开发者最大化其核函数的性能。

### 3.5.1.1 异步屏障（Asynchronous Barriers）

异步屏障在第 3.2.4.2 节介绍过，可以对线程之间的同步做更细致的控制。异步屏障将屏障的到达与等待分开。这样，应用程序可以在等待其他线程到达屏障的同时，执行不依赖该屏障的工作。异步屏障可以指定不同的线程作用域。异步屏障的完整细节见第 4.10 节。

### 3.5.1.2 异步数据拷贝与张量内存加速器（TMA）

CUDA 核函数代码语境下的异步数据拷贝，指的是在进行计算的同时在共享内存和 GPU DRAM 之间搬运数据的能力。这不应与 CPU 和 GPU 之间的异步内存拷贝混淆。该特性使用异步屏障。第 4.12 节详细介绍了异步拷贝的用法。

### 3.5.1.3 流水线（Pipelines）

流水线是一种工作暂存与协调多缓冲生产者–消费者模式的机制，常用于将计算与异步数据拷贝重叠。第 4.11 节有在 CUDA 中使用流水线的细节和示例。

### 3.5.1.4 集群启动控制下的工作窃取（Work Stealing with Cluster Launch Control）

工作窃取是一种在负载不均的工作负载中维持利用率的技术：完成工作的 worker 可以从其他 worker 那里"窃取"任务。集群启动控制是计算能力 10.0（Blackwell）引入的特性，让核函数可以直接控制在飞的线程块调度，从而实时适应负载不均的工作负载。线程块可以取消尚未启动的另一个线程块或集群的启动、认领其索引，并立即开始执行窃取来的工作。这种工作窃取流程让 SM 保持忙碌，减少不规则数据或运行时变化下的空闲时间——实现更细粒度的负载均衡，而不完全依赖硬件调度器。第 4.13 节详细介绍了如何使用该特性。

## 3.5.2 降低延迟（Improving Latencies）

本节概述的特性有一个共同主题：旨在降低某种延迟，不过不同特性针对的延迟类型不同。总体上，它们聚焦于核函数启动级别或更高层级的延迟。核函数内部的 GPU 内存访问延迟不在此列。

### 3.5.2.1 绿色上下文（Green Contexts）

绿色上下文，也叫执行上下文，是一个 CUDA 特性的名称，它允许程序创建只在 GPU 的一部分 SM 上执行工作的 CUDA 上下文。默认情况下，一次核函数启动的线程块会被调度到 GPU 上任何能满足核函数资源需求的 SM 上。影响哪些 SM 可以执行线程块的因素很多，包括但不限于：共享内存使用量、寄存器使用量、是否使用集群，以及线程块中的线程总数。

执行上下文允许将核函数启动到专门创建的上下文中，进一步限制可用于执行该核函数的 SM 数量。重要的是，当程序创建了使用某组 SM 的绿色上下文后，GPU 上的其他上下文不会再将线程块调度到分配给该绿色上下文的 SM 上。这包括 CUDA 运行时使用的默认上下文（主上下文）。这使得这些 SM 可以保留给高优先级或延迟敏感的工作负载。

第 4.6 节有绿色上下文用法的完整细节。

### 3.5.2.2 局部域（Locality Domains）

局部域是 GPU 内存和 SM 的一个子集。在拥有多个局部域的 GPU 上，将内存分配在特定局部域内，然后在只包含同一局部域 SM 的绿色上下文中执行使用该内存的核函数，可以带来好处。

局部域是性能特性：不做内存或计算本地化的 CUDA 代码仍然能正确执行。

第 1.2.3.2 节介绍了局部域背后的概念，第 4.7 节提供更多信息：如何确定 GPU 有多少个局部域、如何将内存分配到特定局部域，以及如何创建只含同一局部域 SM 的绿色上下文。

### 3.5.2.3 流序内存分配（Stream-Ordered Memory Allocation）

流序内存分配器允许程序将 GPU 内存的分配和释放排序进 CUDA 流。与立即执行的 `cudaMalloc` 和 `cudaFree` 不同，`cudaMallocAsync` 和 `cudaFreeAsync` 将内存分配或释放操作插入 CUDA 流。第 4.3 节涵盖这些 API 的所有细节。

### 3.5.2.4 CUDA 图（CUDA Graphs）

CUDA 图让应用程序可以指定一系列 CUDA 操作（如核函数启动或内存拷贝）及其之间的依赖关系，从而在 GPU 上高效执行。用 CUDA 流也能达到类似的效果，实际上创建图的一种机制就叫流捕获，可以把流上的操作记录成 CUDA 图。也可以用 CUDA 图 API 创建图。

图创建后可以实例化并执行多次。这对需要重复的工作负载很有用。图在降低调用 CUDA 操作相关的 CPU 启动开销方面有一些性能收益，还能启用只有在整个工作负载预先指定时才可用的优化。

第 4.2 节介绍并演示了如何使用 CUDA 图。

### 3.5.2.5 编程式依赖启动（Programmatic Dependent Launch）

编程式依赖启动是一个 CUDA 特性，允许依赖核函数（即依赖前一个核函数输出的核函数）在其所依赖的主核函数完成之前就开始执行。依赖核函数可以执行准备代码和不相关的工作，直到需要主核函数的数据时在那里阻塞。主核函数可以在依赖核函数所需的数据就绪时发信号，释放依赖核函数继续执行。这使得两个核函数之间有部分重叠，有助于在保持 GPU 利用率的同时最小化关键数据路径的延迟。第 4.5 节涵盖编程式依赖启动。

### 3.5.2.6 懒加载（Lazy Loading）

懒加载是一个特性，允许控制 JIT 编译器在应用程序启动时的行为。有许多核函数需要从 PTX JIT 编译为 cubin 的应用程序，如果所有核函数都在应用程序启动时编译，启动时间可能很长。默认行为是：模块直到被需要时才编译。可以用环境变量改变这一行为，详见第 4.8 节。

## 3.5.3 功能性特性（Functionality Features）

这里介绍的特性有一个共同点：它们旨在启用额外的能力或功能。

### 3.5.3.1 扩展 GPU 内存（Extended GPU Memory）

扩展 GPU 内存是 NVLink-C2C 互联系统中的一个特性，可以在 GPU 内高效访问系统中的所有内存。扩展 GPU 内存详见第 4.19 节。

### 3.5.3.2 动态并行（Dynamic Parallelism）

CUDA 应用程序最常见的是从 CPU 上运行的代码启动核函数。也可以从 GPU 上运行的核函数创建新的核函数调用。该特性称为 CUDA 动态并行。第 4.20 节详述如何从 GPU 上运行的代码创建新的 GPU 核函数启动。

## 3.5.4 CUDA 互操作性（CUDA Interoperability）

### 3.5.4.1 CUDA 与其他 API 的互操作性

在 GPU 上运行代码的机制不止 CUDA 一种。应用所用的 GPU 最初是为了加速计算机图形学而构建的，图形学有自己的一套 API，如 Direct3D 和 Vulkan。应用程序可能希望用某个图形 API 做 3D 渲染，同时用 CUDA 做计算。CUDA 提供了在 CUDA 上下文与 3D API 使用的 GPU 上下文之间交换 GPU 上存储数据的机制。例如，应用程序可以用 CUDA 做仿真，然后用 3D API 可视化结果。这通过让一些缓冲区同时可被 CUDA 和图形 API 读和/或写来实现。

允许与图形 API 共享缓冲区的同一机制，也被用来与通信机制共享缓冲区，这些通信机制可以在多节点环境中实现快速的直接 GPU 到 GPU 通信。

第 4.21 节介绍 CUDA 如何与其他 GPU API 互操作、如何在 CUDA 与其他 API 之间共享数据，并针对多个不同的 API 给出具体示例。

### 3.5.4.2 进程间通信（Interprocess Communication）

对于非常大的计算，通常把多个 GPU 组合起来使用，以获得更多内存和更多计算资源共同处理一个问题。在单个系统（按集群计算术语即一个节点）内，多个 GPU 可以在单个主机进程中使用。这在第 3.4 节介绍。

也常用跨越单个或多个计算机的多个独立主机进程。当多个进程协同工作时，它们之间的通信称为进程间通信。CUDA 进程间通信（CUDA IPC）提供了在不同进程之间共享 GPU 缓冲区的机制。第 4.16 节解释并演示了如何用 CUDA IPC 在不同主机进程之间协调和通信。

## 3.5.5 细粒度控制（Fine-Grained Control）

### 3.5.5.1 虚拟内存管理（Virtual Memory Management）

如第 2.6.1 节所述，系统中的所有 GPU 连同 CPU 内存共享一个统一虚拟地址空间。大多数应用程序可以直接使用 CUDA 提供的默认内存管理，无需改变其行为。但 CUDA 驱动 API 为有需要的人提供了对该虚拟内存空间布局的高级而细致的控制。这主要用于控制在系统内和跨多个系统共享 GPU 之间的缓冲区的行为。

第 4.17 节涵盖 CUDA 驱动 API 提供的控制选项、其工作原理，以及开发者何时会发现它们有用。

### 3.5.5.2 计算结构传输（Compute Fabric Transport）

第 4.18 节描述了一种面向资源的模型，用于通过 NVLink 结构做 GPU 发起的数据搬运，其中对端由逻辑端点 ID 和偏移量命名，而不是由映射的虚拟地址命名。该特性面向编写通信原语的开发者；如果通信模式匹配，应用程序应优先使用 NCCL Device API 或 NVSHMEM。

### 3.5.5.3 驱动入口点访问（Driver Entry Point Access）

驱动入口点访问指的是从 CUDA 11.3 开始，检索 CUDA 驱动和 CUDA 运行时 API 函数指针的能力。它还允许开发者检索驱动函数的特定变体的函数指针，以及访问比 CUDA Toolkit 自带的驱动更新的驱动中的驱动函数。第 4.22 节涵盖驱动入口点访问。

### 3.5.5.4 错误日志管理（Error Log Management）

错误日志管理提供了处理和记录 CUDA API 错误的工具。设置单个环境变量 `CUDA_LOG_FILE` 即可将 CUDA 错误直接捕获到 stderr、stdout 或文件中。错误日志管理还让应用程序可以注册一个回调，在 CUDA 遇到错误时触发。第 4.9 节有错误日志管理的更多细节。
