# 3.2 高级核函数编程

本章将首先深入剖析 NVIDIA GPU 的硬件模型，然后介绍 CUDA 核函数代码中可用于提升核函数性能的一些更高级的特性。本章还会引入与线程作用域（thread scope）、异步执行及相关同步原语有关的一些概念。这些概念讨论为核函数代码中的高级性能特性提供了必要基础。

其中一些特性的详细说明在本编程指南后半部分各自的专门章节中：

- 本章引入的高级同步原语在 4.10 节和 4.11 节完整讲解。
- 异步数据拷贝（含张量内存加速器 TMA）在本章引入，在 4.12 节完整讲解。

## 3.2.1 使用 PTX

并行线程执行（Parallel Thread Execution，PTX）是 CUDA 用来抽象硬件 ISA 的虚拟机指令集架构（ISA），在 1.3.3 节中已介绍。直接用 PTX 写代码是一种非常高级的优化技术，大多数开发者不需要，应视为最后的手段。尽管如此，在某些场景下，直接写 PTX 带来的细粒度控制确实能在特定应用中提升性能。这些场景通常出现在应用中对性能极度敏感的部分，那里每一丁点的性能提升都有显著收益。所有可用的 PTX 指令都在 PTX ISA 文档中。

**cuda::ptx 命名空间**

在代码中直接使用 PTX 的一种方法是使用 libcu++ 中的 `cuda::ptx` 命名空间。该命名空间提供直接映射到 PTX 指令的 C++ 函数，简化了它们在 C++ 应用中的使用。更多信息请参阅 `cuda::ptx` 命名空间文档。

**内联 PTX**

在代码中加入 PTX 的另一种方法是使用内联 PTX（inline PTX）。该方法在相应文档中有详细介绍。这与在 CPU 上写汇编代码非常相似。

## 3.2.2 硬件实现

流多处理器（Streaming Multiprocessor，SM，见"GPU 硬件模型"）被设计为可并发执行数百个线程。为了管理如此多的线程，它采用一种独特的并行计算模型，称为单指令多线程（Single-Instruction, Multiple-Thread，即 SIMT），在"SIMT 执行模型"中介绍。指令采用流水线执行，在单个线程内利用指令级并行，同时通过大规模的硬件多线程（如"硬件多线程"所述）实现广泛的线程级并行。与 CPU 核心不同，SM 按序发射指令，不做分支预测或推测执行。

"SIMT 执行模型"和"硬件多线程"两节描述所有设备共有的 SM 架构特性；"计算能力"一节给出不同计算能力设备的具体细节。

NVIDIA GPU 架构采用小端表示。

### 3.2.2.1 SIMT 执行模型

每个 SM 以 32 个并行线程为一组创建、管理、调度和执行线程，这样的组称为线程束（warp）。组成一个线程束的各个线程从同一程序地址一起开始，但它们有各自的指令地址计数器和寄存器状态，因此可以自由分支、独立执行。"warp"一词源于纺织中的"经线"（weaving），即第一代并行线程技术。半线程束（half-warp）是指线程束的前半或后半；四分之一线程束（quarter-warp）是指线程束的第一、二、三或四分之一部分。

一个线程束一次执行一条公共指令，因此当线程束中 32 个线程的执行路径完全一致时效率最高。如果线程束的线程因数据相关的条件分支而分化，线程束会逐条执行被走到的各条分支路径，并禁用不在该路径上的线程。分支分化只发生在线程束内部；不同的线程束彼此独立执行，无论它们执行的代码路径相同还是不同。

SIMT 架构类似于 SIMD（单指令多数据）向量组织，因为一条指令控制多个处理单元。关键区别在于：SIMD 向量组织把 SIMD 宽度暴露给软件，而 SIMT 指令只描述单个线程的执行和分支行为。与 SIMD 向量机不同，SIMT 让程序员既可以为相互独立的标量线程编写线程级并行代码，也可以为协作的线程编写数据并行代码。就正确性而言，程序员基本可以忽略 SIMT 行为；但只要注意让代码很少需要线程束内线程分化，就能获得可观的性能提升。实践中，这类似于缓存行的角色：设计正确性时可以安全地忽略缓存行大小，但设计峰值性能时必须在代码结构中考虑它。而向量架构则要求软件把访存合并成向量，并手动管理分化。

#### 3.2.2.1.1 独立线程调度（Independent Thread Scheduling）

在计算能力低于 7.0 的 GPU 上，线程束使用线程束内所有 32 个线程共享的一个程序计数器，以及一个指定线程束活动线程的活动掩码。因此，来自同一线程束的线程在分化区域或处于不同执行状态时，无法相互发信号或交换数据；依赖锁或互斥量保护的细粒度数据共享算法可能导致死锁，具体取决于竞争线程来自哪个线程束。

在计算能力 7.0 及以上的 GPU 上，独立线程调度允许线程之间完全并发，不受线程束限制。在独立线程调度下，GPU 按线程维护执行状态（包括程序计数器和调用栈），并能以每线程粒度让出执行——既为了更好地利用执行资源，也允许一个线程等待另一个线程产生数据。调度优化器决定如何把同一线程束的活动线程组合到 SIMT 单元中。这保留了此前 NVIDIA GPU 的 SIMT 执行高吞吐，同时灵活得多：线程现在可以在子线程束粒度上分化和重新会聚。

独立线程调度会打破依赖此前 GPU 架构隐式线程束同步行为的代码。线程束同步代码假定同一线程束的线程在每条指令上锁步执行，但线程在子线程束粒度上分化与会聚的能力使这种假设失效。这会导致参与执行代码的线程集合与预期不同。为 7.0 之前的 GPU 开发的任何线程束同步代码（如无同步的线程束内归约）都应重新审视以确保兼容。开发者应使用 `__syncwarp()` 显式同步这类代码，以保证在所有代 GPU 上行为正确。

> **注**
>
> 线程束中参与当前指令的线程称为活动线程，而不在当前指令上的线程是非活动的（被禁用）。线程变为非活动有多种原因，包括比同一线程束的其他线程更早退出、走了与线程束当前执行的分支路径不同的分支路径，或是线程块中线程数不是线程束大小的整数倍时的最后几个线程。
>
> 如果线程束执行的非原子指令中，线程束的多个线程向全局内存或共享内存中的同一位置写入，发生到该位置的串行化写入次数可能因设备的计算能力而异。但对所有计算能力而言，最终由哪个线程完成写入是未定义的。
>
> 如果线程束执行的原子指令中，线程束的多个线程对全局内存中的同一位置读、修改、写，则对该位置的每次读/修改/写都会发生且全部串行化，但它们发生的顺序是未定义的。

### 3.2.2.2 硬件多线程

当 SM 被分配一个或多个线程块执行时，它把它们划分成线程束，每个线程束由线程束调度器调度执行。块划分成线程束的方式总是固定的：每个线程束包含 ID 连续递增的线程，第一个线程束包含线程 0。"线程层级"介绍了线程 ID 与块中线程索引的关系。块中的线程束总数定义如下：

```
       ( T )
  ceil ( ------- , 1 )
       ( Wsize )
```

- T 为每块的线程数；
- Wsize 为线程束大小，等于 32；
- ceil(x, y) 等于 x 向上取整到 y 的最近倍数。

SM 处理的每个线程束的执行上下文（程序计数器、寄存器等）在该线程束的整个生命周期内都驻留在片上。因此，线程束之间切换没有开销。在每个指令发射周期，线程束调度器选择一个有线程就绪执行下一条指令的线程束（线程束的活动线程），并把该指令发射给这些线程。

每个 SM 有一组 32 位寄存器在线程束之间划分，还有在线程块之间划分的共享内存。对于给定核函数，能同时驻留和处理于 SM 上的块数和线程束数，取决于核函数使用的寄存器和共享内存数量，以及 SM 上可用的寄存器和共享内存数量。每个 SM 还有驻留块数和线程束数的上限。这些限制以及 SM 上可用的寄存器和共享内存数量取决于设备的计算能力，在"计算能力"中给出。如果每个 SM 上没有足够的资源至少处理一个块，核函数将启动失败。块分配的总寄存器数和共享内存可按"占用率"一节记录的几种方法确定。

### 3.2.2.3 异步执行特性

近几代 NVIDIA GPU 加入了异步执行能力，以在 GPU 内更多地重叠数据搬运、计算和同步。这些能力使从 GPU 代码调用的某些操作能与同一线程块中的其他 GPU 代码异步执行。这种异步执行不应与 2.5 节讨论的异步 CUDA API 混淆——后者使 GPU 核函数启动或内存操作彼此异步、或与 CPU 异步。

计算能力 8.0（NVIDIA Ampere GPU 架构）引入了硬件加速的从全局内存到共享内存的异步数据拷贝和异步屏障（见 NVIDIA A100 Tensor Core GPU 架构）。

计算能力 9.0（NVIDIA Hopper GPU 架构）扩展了异步执行特性，加入了张量内存加速器（Tensor Memory Accelerator，TMA）单元（可在全局内存与共享内存之间双向传输大数据块和多维张量）、异步事务屏障，以及异步矩阵乘加操作（详情见 Hopper 架构深度解析博客文章）。

CUDA 提供可供设备代码中的线程调用的 API 来使用这些特性。异步编程模型定义了异步操作相对于 CUDA 线程的行为。

异步操作是由 CUDA 线程发起、但异步执行的运算，仿佛由另一个线程执行，我们称之为异步线程（async thread）。在一个结构良好的程序中，一个或多个 CUDA 线程与该异步操作同步。发起异步操作的 CUDA 线程不一定是参与同步的线程。异步线程始终与发起该操作的 CUDA 线程关联。

异步操作用一个同步对象（可以是屏障或流水线）来通知完成。这些同步对象在"高级同步原语"中详细讲解，它们在执行异步内存操作中的作用在"异步数据拷贝"中演示。

#### 3.2.2.3.1 异步线程与异步代理（Async Thread and Async Proxy）

异步操作的访存方式可能与常规操作不同。为了区分这些不同的访存方法，CUDA 引入了异步线程、通用代理（generic proxy）和异步代理（async proxy）的概念。常规操作（加载和存储）走通用代理。一些异步指令（如 LDGSTS 和 STAS/REDAS）被建模为在通用代理中运行的异步线程。另一些异步指令，如带 TMA 的批量异步拷贝和部分张量核心操作（tcgen05.*、wgmma.mma_async.*），被建模为在异步代理中运行的异步线程。

**在通用代理中运行的异步线程。** 当发起异步操作时，它与一个异步线程关联，该异步线程不同于发起操作的 CUDA 线程。同一地址上在前的通用代理（常规）加载和存储保证排在异步操作之前。但其后的常规加载和存储到同一地址不保证维持顺序，可能在异步线程完成前产生竞态。

**在异步代理中运行的异步线程。** 当发起异步操作时，它与一个异步线程关联，该异步线程不同于发起操作的 CUDA 线程。同一地址上在前和在后的常规加载和存储都不保证维持顺序。需要代理栅栏（proxy fence）来跨代理同步它们，以保证正确的内存顺序。"使用张量内存加速器（TMA）"一节演示了用代理栅栏保证 TMA 异步拷贝正确性的方法。

这些概念的更多细节见 PTX ISA 文档。

## 3.2.3 线程作用域（Thread Scopes）

CUDA 线程构成线程层级，正确和高效地编写 CUDA 核函数都离不开这个层级。在这个层级内，内存操作的可见性和同步作用域可能不同。为了应对这种非一致性，CUDA 编程模型引入了线程作用域的概念。线程作用域定义了哪些线程能观察到一个线程的加载和存储，并规定哪些线程能用原子操作、屏障等同步原语彼此同步。每个作用域在内存层级中都有一个关联的一致性点。

线程作用域在 CUDA PTX 中暴露，也作为 libcu++ 库的扩展提供。下表定义了可用的线程作用域：

| CUDA 线程作用域 | C++ 线程作用域 | CUDA PTX | 说明 | 内存层级中的一致性点 |
|---|---|---|---|---|
| cuda::thread_scope_thread | | | 内存操作仅对本线程可见。 | – |
| cuda::thread_scope_block | | .cta | 内存操作对同一线程块中的其他线程可见。 | L1 |
| | | .cluster | 内存操作对同一线程块集群中的其他线程可见。 | L2 |
| cuda::thread_scope_device | | .gpu | 内存操作对同一 GPU 设备中的其他线程可见。 | L2 |
| cuda::thread_scope_system | | .sys | 内存操作对同一系统（CPU、其他 GPU）中的其他线程可见。 | L2 + 相连的缓存 |

"高级同步原语"和"异步数据拷贝"两节演示了线程作用域的用法。

## 3.2.4 高级同步原语

本节介绍三类同步原语：

- **作用域原子操作（Scoped Atomics）**，把 C++ 内存顺序与 CUDA 线程作用域配对，在块、集群、设备或系统作用域跨线程安全通信（见"线程作用域"）。
- **异步屏障（Asynchronous Barriers）**，把同步拆分为到达（arrival）和等待（wait）两个阶段，可用于跟踪异步操作的进度。
- **流水线（Pipelines）**，分阶段组织工作，协调多缓冲的生产者–消费者模式，常用于把计算与异步数据拷贝重叠。

### 3.2.4.1 作用域原子操作

5.4.5 节概述了 CUDA 中可用的原子函数。本节聚焦支持 C++ 标准原子内存语义的作用域原子操作，可通过 libcu++ 库或编译器内置函数使用。作用域原子操作为在 CUDA 线程层级的适当层级高效同步提供了工具，让复杂的并行算法兼顾正确性与性能。

#### 3.2.4.1.1 线程作用域与内存顺序

作用域原子操作结合了两个关键概念：

- **线程作用域**：定义哪些线程能观察到原子操作的效果（见"线程作用域"）。
- **内存顺序**：定义相对于其他内存操作的顺序约束（见 C++ 标准原子内存语义）。

**CUDA C++ cuda::atomic**

```cuda
#include <cuda/atomic>

__global__ void block_scoped_counter() {
    // 共享原子计数器，仅在该块内可见
    __shared__ cuda::atomic<int, cuda::thread_scope_block> counter;

      // 初始化计数器（只应由一个线程执行）
      if (threadIdx.x == 0) {
          counter.store(0, cuda::memory_order_relaxed);
      }
      __syncthreads();

      // 块中所有线程原子地递增
      int old_value = counter.fetch_add(1, cuda::memory_order_relaxed);

      // 使用 old_value...
}
```

**内置原子函数**

```cuda
__global__ void block_scoped_counter() {
    // 共享计数器，仅在该块内可见
    __shared__ int counter;

      // 初始化计数器（只应由一个线程执行）
      if (threadIdx.x == 0) {
          __nv_atomic_store_n(&counter, 0,
                               __NV_ATOMIC_RELAXED,
                               __NV_THREAD_SCOPE_BLOCK);
      }
      __syncthreads();

      // 块中所有线程原子地递增
      int old_value = __nv_atomic_fetch_add(&counter, 1,
                                             __NV_ATOMIC_RELAXED,
                                             __NV_THREAD_SCOPE_BLOCK);

      // 使用 old_value...
}
```

这个例子实现了一个块作用域原子计数器，演示了作用域原子操作的基本概念：

- **共享变量**：用 `__shared__` 内存让块中所有线程共享一个计数器。
- **原子类型声明**：`cuda::atomic<int, cuda::thread_scope_block>` 创建块级可见的原子整数。
- **单次初始化**：只有线程 0 初始化计数器，避免设置阶段的竞态。
- **块同步**：`__syncthreads()` 确保所有线程在继续前看到已初始化的计数器。
- **原子递增**：每个线程原子地递增计数器并拿到旧值。

这里选择 `cuda::memory_order_relaxed`，因为我们只需要原子性（不可分割的读-改-写），不需要不同内存位置之间的顺序约束。这是一个简单的计数操作，递增的顺序不影响正确性。

对于生产者–消费者模式，acquire-release 语义保证正确的顺序：

**CUDA C++ cuda::atomic**

```cuda
__global__ void producer_consumer() {
    __shared__ int data;
    __shared__ cuda::atomic<bool, cuda::thread_scope_block> ready;

     if (threadIdx.x == 0) {
         // 生产者：写 data 然后发出 ready 信号
         data = 42;
         ready.store(true, cuda::memory_order_release); // Release 保证 data 的写入可见

     } else {
         // 消费者：等待 ready 信号然后读 data
         while (!ready.load(cuda::memory_order_acquire)) { // Acquire 保证 data 的读能看到写入

              // 自旋等待
         }
         int value = data;
         // 处理 value...
     }
}
```

**内置原子函数**

```cuda
__global__ void producer_consumer() {
    __shared__ int data;
    __shared__ bool ready; // 只有 ready 标志需要原子操作

    if (threadIdx.x == 0) {
        // 生产者：写 data 然后发出 ready 信号
        data = 42;
        __nv_atomic_store_n(&ready, true,
                             __NV_ATOMIC_RELEASE,
                             __NV_THREAD_SCOPE_BLOCK); // Release 保证 data 的写入可见

    } else {
        // 消费者：等待 ready 信号然后读 data
        while (!__nv_atomic_load_n(&ready,
                                    __NV_ATOMIC_ACQUIRE,
                                    __NV_THREAD_SCOPE_BLOCK)) { // Acquire 保证 data 的读能看到写入

             // 自旋等待
        }
        int value = data;
           // 处理 value...
      }
}
```

#### 3.2.4.1.2 性能考虑

- 使用尽可能窄的作用域：块作用域原子操作远快于系统作用域原子操作。
- 优先用更弱的顺序：只在正确性需要时才用更强的顺序。
- 考虑内存位置：共享内存原子操作快于全局内存原子操作。

### 3.2.4.2 异步屏障

异步屏障与典型的单阶段屏障（`__syncthreads()`）不同：线程到达屏障的通知（"到达"）与等待其他线程到达屏障的操作（"等待"）是分离的。这种分离提高了执行效率——线程可以在等待期间执行与屏障无关的其他操作，更充分地利用等待时间。异步屏障可用于实现 CUDA 线程的生产者–消费者模式，或通过让拷贝操作完成时向屏障"到达"发信号，在内存层级内实现异步数据拷贝。

异步屏障在计算能力 7.0 及以上的设备上可用。计算能力 8.0 及以上的设备为共享内存中的异步屏障提供硬件加速，并在同步粒度上有重大进步：允许对块内 CUDA 线程的任意子集做硬件加速同步。此前架构只在整个线程束（`__syncwarp()`）或整个块（`__syncthreads()`）层级加速同步。

CUDA 编程模型通过 `cuda::std::barrier`（libcu++ 库中符合 ISO C++ 的屏障）提供异步屏障。除了实现 `std::barrier`，该库还提供 CUDA 特定扩展：可选择屏障的线程作用域以提升性能，并暴露更底层的 `cuda::ptx` API。`cuda::barrier` 可通过友元函数 `cuda::device::barrier_native_handle()` 取到屏障的原生句柄并传给 `cuda::ptx` 函数，从而与 `cuda::ptx` 互操作。CUDA 还为线程块作用域的共享内存异步屏障提供原语 API。

下表概览了可用于不同线程作用域同步的异步屏障：

| 线程作用域 | 内存位置 | 在屏障到达 | 在屏障等待 | 硬件加速 | CUDA API |
|---|---|---|---|---|---|
| block | 本地共享内存 | 允许 | 允许 | 是（8.0+） | cuda::barrier、cuda::ptx、原语 |
| cluster | 本地共享内存 | 允许 | 允许 | 是（9.0+） | cuda::barrier、cuda::ptx |
| cluster | 远端共享内存 | 允许 | 不允许 | 是（9.0+） | cuda::barrier、cuda::ptx |
| device | 全局内存 | 允许 | 允许 | 否 | cuda::barrier |
| system | 全局/统一内存 | 允许 | 允许 | 否 | cuda::barrier |

**同步的时间拆分**

没有异步到达–等待屏障时，线程块内的同步用 `__syncthreads()` 实现；用 Cooperative Groups 时用 `block.sync()`。

```cuda
#include <cooperative_groups.h>

__global__ void simple_sync(int iteration_count) {
    auto block = cooperative_groups::this_thread_block();

      for (int i = 0; i < iteration_count; ++i) {
          /* 到达前的代码 */

            // 等待所有线程到达此处。
           block.sync();

           /* 等待后的代码 */
      }
}
```

线程在同步点（`block.sync()`）被阻塞，直到所有线程都到达同步点。此外，同步点之前发生的内存更新保证在同步点之后对块中所有线程可见。

这种模式有三个阶段：

- 同步前的代码执行内存更新，同步后会被读取。
- 同步点。
- 同步后的代码，能看到同步前发生的内存更新。

改用异步屏障后，时间拆分的同步模式如下。

**CUDA C++ cuda::barrier**

```cuda
#include <cuda/barrier>
#include <cooperative_groups.h>

__device__ void compute(float *data, int iteration);

__global__ void split_arrive_wait(int iteration_count, float *data)
{
  using barrier_t = cuda::barrier<cuda::thread_scope_block>;
  __shared__ barrier_t bar;
  auto block = cooperative_groups::this_thread_block();

      if (block.thread_rank() == 0)
      {
        // 用期望的到达计数初始化屏障。
        init(&bar, block.size());
      }
      block.sync();

      for (int i = 0; i < iteration_count; ++i)
      {
        /* 到达前的代码 */

          // 本线程到达。到达不会阻塞线程。
          barrier_t::arrival_token token = bar.arrive();

          compute(data, i);

        // 等待参与屏障的所有线程完成 bar.arrive()。
        bar.wait(std::move(token));

          /* 等待后的代码 */
      }
}
```

**CUDA C++ cuda::ptx**

```cuda
#include <cuda/ptx>
#include <cooperative_groups.h>

__device__ void compute(float *data, int iteration);

__global__ void split_arrive_wait(int iteration_count, float *data)
{
  __shared__ uint64_t bar;
  auto block = cooperative_groups::this_thread_block();

      if (block.thread_rank() == 0)
      {
        // 用期望的到达计数初始化屏障。
        cuda::ptx::mbarrier_init(&bar, block.size());
      }
      block.sync();

      for (int i = 0; i < iteration_count; ++i)
      {
        /* 到达前的代码 */

          // 本线程到达。到达不会阻塞线程。
          uint64_t token = cuda::ptx::mbarrier_arrive(&bar);

          compute(data, i);

        // 等待参与屏障的所有线程完成 mbarrier_arrive()。
        while(!cuda::ptx::mbarrier_try_wait(&bar, token)) {}

          /* 等待后的代码 */
      }
}
```

**CUDA C 原语**

```cuda
 #include <cuda_awbarrier_primitives.h>
 #include <cooperative_groups.h>

 __device__ void compute(float *data, int iteration);

 __global__ void split_arrive_wait(int iteration_count, float *data)
 {
   __shared__ __mbarrier_t bar;
   auto block = cooperative_groups::this_thread_block();

       if (block.thread_rank() == 0)
       {
         // 用期望的到达计数初始化屏障。
         __mbarrier_init(&bar, block.size());
       }
       block.sync();

       for (int i = 0; i < iteration_count; ++i)
       {
         /* 到达前的代码 */

           // 本线程到达。到达不会阻塞线程。
           __mbarrier_token_t token = __mbarrier_arrive(&bar);

           compute(data, i);

         // 等待参与屏障的所有线程完成 __mbarrier_arrive()。
         while(!__mbarrier_try_wait(&bar, token, 1000)) {}

           /* 等待后的代码 */
       }
 }
```

在这种模式中，同步点被拆分为到达点（`bar.arrive()`）和等待点（`bar.wait(std::move(token))`）。线程从第一次调用 `bar.arrive()` 起开始参与 `cuda::barrier`。当线程调用 `bar.wait(std::move(token))` 时，它会被阻塞，直到参与的线程完成 `bar.arrive()` 的次数达到期望次数，即传给 `init()` 的期望到达计数参数。参与线程在调用 `bar.arrive()` 之前发生的内存更新，保证在参与线程调用 `bar.wait(std::move(token))` 之后可见。注意调用 `bar.arrive()` 不会阻塞线程，它可以继续做其他工作，只要这些工作不依赖于其他参与线程调用 `bar.arrive()` 之前的内存更新。

到达–等待模式有五个阶段：

- 到达前的代码执行内存更新，等待后会被读取。
- 到达点，带隐式内存栅栏（即等价于 `cuda::atomic_thread_fence(cuda::memory_order_release, cuda::thread_scope_block)`）。
- 到达与等待之间的代码。
- 等待点。
- 等待后的代码，能看到到达前执行的更新。

异步屏障的完整使用指南见"异步屏障"。

### 3.2.4.3 流水线（Pipelines）

CUDA 编程模型提供流水线同步对象作为协调机制，把异步内存拷贝按多个阶段排序，便于实现双缓冲或多缓冲的生产者–消费者模式。流水线是一个带头尾的双端队列，按先进先出（FIFO）顺序处理工作。生产者线程把工作提交到流水线的头部，消费者线程从流水线的尾部取走工作。

流水线通过 libcu++ 库中的 `cuda::pipeline` API 以及原语 API 暴露。下表描述两个 API 的主要功能。

| cuda::pipeline API | 说明 |
|---|---|
| producer_acquire | 在流水线内部队列中获取一个可用阶段。 |
| producer_commit | 把在 producer_acquire 调用之后发出的异步操作提交到流水线当前获取的阶段。 |
| consumer_wait | 等待流水线最旧阶段中的异步操作完成。 |
| consumer_release | 把流水线最旧的阶段释放回流水线对象以复用。释放的阶段可再被生产者获取。 |

| 原语 API | 说明 |
|---|---|
| __pipeline_memcpy_async | 请求一次从全局内存到共享内存的内存拷贝，提交异步执行。 |
| __pipeline_commit | 把该调用之前发出的异步操作提交到流水线的当前阶段。 |
| __pipeline_wait_prior(N) | 等待流水线中除最近 N 次提交外所有提交的异步操作完成。 |

`cuda::pipeline` API 接口更丰富、限制更少，而原语 API 只支持跟踪从全局内存到共享内存、满足特定尺寸和对齐要求的异步拷贝。原语 API 的功能等价于一个 `cuda::thread_scope_thread` 的 `cuda::pipeline` 对象。

详细用法和示例见"流水线"。

## 3.2.5 异步数据拷贝

内存层级内的高效数据搬运是 GPU 计算获得高性能的基础。传统的同步内存操作迫使线程在数据传输期间空闲等待。GPU 天生通过并行隐藏内存延迟：即 SM 在内存操作完成期间切换去执行另一个线程束。即使有这种靠并行的延迟隐藏，内存延迟仍可能成为内存带宽利用率和计算资源效率的瓶颈。为解决这些瓶颈，现代 GPU 架构提供硬件加速的异步数据拷贝机制，让内存传输独立进行，线程同时继续执行其他工作。

异步数据拷贝通过把内存传输的发起与等待其完成解耦，实现计算与数据搬运的重叠。这样，线程可以在内存延迟期间做有用的工作，从而提高整体吞吐和资源利用率。

> **注**
>
> 本节的概念和原理与前文"异步执行"一章讨论的类似，但那一章讲的是核函数和内存传输（如 `cudaMemcpyAsync` 调用的那些）的异步执行，可视为应用不同组件之间的异步。
>
> 本节的异步指的是：在单次核函数启动执行内部，把数据在 GPU 的 DRAM（即全局内存）与片上内存（如共享内存或张量内存）之间搬运，而不阻塞 GPU 线程。

要理解异步拷贝如何提升性能，先看一个常见的 GPU 计算模式。CUDA 应用常用"拷贝–计算"模式：

- 从全局内存取数据；
- 把数据存到共享内存；
- 对共享内存数据做计算，并可能把结果写回全局内存。

该模式的拷贝阶段通常表达为 `shared[local_idx] = global[global_idx]`。这个全局到共享的内存拷贝会被编译器展开为：从全局内存读到寄存器，再从寄存器写到共享内存。当这种模式出现在迭代算法中时，每个线程块需要在 `shared[local_idx] = global[global_idx]` 赋值后同步，确保计算阶段开始前对共享内存的所有写入都完成；计算阶段后还要再同步一次，防止在所有线程完成计算前覆盖共享内存。下面的代码片段演示了这种模式。

```cuda
#include <cooperative_groups.h>

__device__ void compute(int* global_out, int const* shared_in) {
    // 用共享内存中当前批次的所有值计算。
    // 把本线程的结果存回全局内存。
}

__global__ void without_async_copy(int* global_out, int const* global_in, size_t size, size_t batch_sz) {

   auto grid = cooperative_groups::this_grid();
   auto block = cooperative_groups::this_thread_block();
   assert(size == batch_sz * grid.size()); // 说明：输入尺寸恰为 batch_sz * grid_size

    extern __shared__ int shared[]; // block.size() * sizeof(int) 字节

    size_t local_idx = block.thread_rank();

  for (size_t batch = 0; batch < batch_sz; ++batch) {
    // 计算本块当前批次在全局内存中的索引。
    size_t block_batch_idx = block.group_index().x * block.size() + grid.size() * batch;

    size_t global_idx = block_batch_idx + threadIdx.x;
    shared[local_idx] = global_in[global_idx];

        // 等待所有拷贝完成。
        block.sync();

        // 计算并把结果写到全局内存。
        compute(global_out + block_batch_idx, shared);

        // 等待使用共享内存的计算结束。
        block.sync();
    }
}
```

用异步数据拷贝后，从全局内存到共享内存的数据搬运可以异步进行，在等待数据到达时更高效地利用 SM。

```cuda
#include <cooperative_groups.h>
#include <cooperative_groups/memcpy_async.h>

__device__ void compute(int* global_out, int const* shared_in) {
    // 用共享内存中当前批次的所有值计算。
    // 把本线程的结果存回全局内存。
}

__global__ void with_async_copy(int* global_out, int const* global_in, size_t size, size_t batch_sz) {

   auto grid = cooperative_groups::this_grid();
   auto block = cooperative_groups::this_thread_block();
   assert(size == batch_sz * grid.size()); // 说明：输入尺寸恰为 batch_sz * grid_size

    extern __shared__ int shared[]; // block.size() * sizeof(int) 字节

    size_t local_idx = block.thread_rank();

  for (size_t batch = 0; batch < batch_sz; ++batch) {
    // 计算本块当前批次在全局内存中的索引。
    size_t block_batch_idx = block.group_index().x * block.size() + grid.size() * batch;

    // 整个线程组协作把整个批次拷贝到共享内存。
    cooperative_groups::memcpy_async(block, shared, global_in + block_batch_idx, block.size());

        // 等待期间对其他数据做计算。

        // 等待所有拷贝完成。
        cooperative_groups::wait(block);

        // 计算并把结果写到全局内存。
        compute(global_out + block_batch_idx, shared);

        // 等待使用共享内存的计算结束。
        block.sync();
    }
}
```

`cooperative_groups::memcpy_async` 函数把 `block.size()` 个元素从全局内存拷贝到共享数据。该操作仿佛由另一个线程执行，在拷贝完成后与当前线程对 `cooperative_groups::wait` 的调用同步。在拷贝完成之前，修改全局数据或读写共享数据都会引入数据竞态。

这个例子说明了所有异步拷贝操作背后的基本概念：它们把内存传输的发起与完成解耦，让线程在数据于后台搬运时做其他工作。CUDA 编程模型提供多种 API 访问这些能力，包括 Cooperative Groups 和 libcu++ 库中的 `memcpy_async` 函数，以及更底层的 `cuda::ptx` 和原语 API。这些 API 的语义相似：它们把对象从源拷贝到目标，仿佛由另一个线程执行，拷贝完成时可用不同的完成机制同步。

现代 GPU 架构提供多种异步数据搬运的硬件机制：

- LDGSTS（计算能力 8.0+）支持从全局到共享内存的高效小规模异步传输。
- 张量内存加速器（TMA，计算能力 9.0+）扩展了这些能力，提供针对大多维数据传输优化的批量异步拷贝操作。
- STAS 指令（计算能力 9.0+）支持从寄存器到集群内分布式共享内存的小规模异步传输。

这些机制支持不同的数据路径、传输尺寸和对齐要求，开发者可为具体的数据访问模式选择最合适的方法。下表概览 GPU 内异步拷贝支持的数据路径。

**表 5：异步拷贝可能的源和目标内存空间。空单元格表示不支持该源–目标组合。**

| 方向（源 → 目标） | | 拷贝机制 | |
|---|---|---|---|
| 源 | 目标 | 异步拷贝 | 批量异步拷贝 |
| global | global | | |
| shared::cta | global | | 支持（TMA，9.0+） |
| global | shared::cta | 支持（LDGSTS，8.0+） | 支持（TMA，9.0+） |
| global | shared::cluster | | 支持（TMA，9.0+） |
| shared::cluster | shared::cta | | 支持（TMA，9.0+） |
| shared::cta | shared::cta | | |
| registers | shared::cluster | 支持（STAS，9.0+） | |

"使用 LDGSTS"、"使用张量内存加速器（TMA）"和"使用 STAS"三节将详细介绍每种机制。

## 3.2.6 配置 L1/共享内存配比

如"L1 数据缓存"所述，SM 上的 L1 和共享内存使用同一块物理资源，即统一数据缓存。在大多数架构上，如果核函数很少或不使用共享内存，统一数据缓存可以配置为提供架构允许的最大 L1 缓存。

为共享内存保留的统一数据缓存可按核函数配置。应用可在核函数启动前用 `cudaFuncSetAttribute` 函数设置 carveout（即首选的共享内存容量）：

```cuda
cudaFuncSetAttribute(kernel_name,
    cudaFuncAttributePreferredSharedMemoryCarveout, carveout);
```

应用可以把 carveout 设为该架构最大支持共享内存容量的整数百分比。除了整数百分比，还提供三个便捷枚举作为 carveout 值：

- cudaSharedmemCarveoutDefault
- cudaSharedmemCarveoutMaxL1
- cudaSharedmemCarveoutMaxShared

最大支持的共享内存和支持的 carveout 尺寸因架构而异，见"每计算能力的共享内存容量"。

当所选的整数百分比 carveout 不能精确对应某个支持的共享内存容量时，使用下一个更大的容量。例如，计算能力 12.0 的设备最大共享内存容量为 100KB，把 carveout 设为 50% 会得到 64KB 共享内存而非 50KB，因为计算能力 12.0 的设备支持的共享内存尺寸为 0、8、16、32、64、100（KB）。

传给 `cudaFuncSetAttribute` 的函数必须用 `__global__` 说明符声明。`cudaFuncSetAttribute` 被驱动视为提示，驱动可根据需要选择不同的 carveout 尺寸以执行核函数。

> **注**
>
> 另一个 CUDA API `cudaFuncSetCacheConfig` 也允许应用调整核函数的 L1 与共享内存配比。但该 API 对核函数启动的共享/L1 配比是硬性要求，导致交错执行不同共享内存配置的核函数时，会在共享内存重配置后面无谓地串行启动。推荐使用 `cudaFuncSetAttribute`，因为驱动可根据需要选择不同配置以执行函数或避免抖动。

依赖每块超过 48KB 共享内存分配的核函数是架构相关的。因此它们必须用动态共享内存而非静态数组，并用 `cudaFuncSetAttribute` 显式申请，如下所示：

```cuda
// 设备端代码
__global__ void MyKernel(...)
{
  extern __shared__ float buffer[];
  ...
}

// 主机端代码
int maxbytes = 98304; // 96 KB
cudaFuncSetAttribute(MyKernel, cudaFuncAttributeMaxDynamicSharedMemorySize, maxbytes);

MyKernel <<<gridDim, blockDim, maxbytes>>>(...);
```
