# 2.5 异步执行

## 2.5.1 什么是异步并发执行？

CUDA 允许并发（即重叠）执行多个任务，具体包括：

- 主机端计算
- 设备端计算
- 从主机到设备的内存传输
- 从设备到主机的内存传输
- 给定设备内存内部的内存传输
- 多个设备之间的内存传输

这种并发能力通过异步接口来表达：分发函数调用或核函数启动都会立即返回。异步调用通常在已分发的操作完成之前就返回，甚至可能在异步操作尚未开始时就返回。然后，应用程序就可以在最初分发的操作执行的同时，自由地执行其他任务。当需要最初分发的操作的最终结果时，应用程序必须执行某种形式的同步，以确保该操作已经完成。一个典型的并发执行模式示例是：将主机与设备之间的内存传输和计算重叠起来，从而降低甚至消除其开销。

（图 20：用 CUDA 流实现的异步并发执行示意。）

一般来说，异步接口通常提供三种与已分发操作同步的主要方式：

- 阻塞（blocking）方式：应用程序调用一个函数，该函数会阻塞（即等待），直到操作完成；
- 非阻塞（non-blocking）方式（又称轮询方式）：应用程序调用一个函数，该函数立即返回，并提供操作状态的相关信息；
- 回调（callback）方式：在操作完成时执行一个预先注册的函数。

虽然编程接口是异步的，但各种操作实际能否并发执行，取决于 CUDA 版本和所用硬件的计算能力（Compute Capability）——这些细节留待本指南后续章节讨论（见“计算能力（Compute Capabilities）”）。

在“同步 CPU 与 GPU”一节中介绍过 CUDA 运行时函数 `cudaDeviceSynchronize()`，它是一个阻塞调用，会等待所有之前提交的工作完成。之所以需要调用 `cudaDeviceSynchronize()`，是因为核函数启动是异步的，会立即返回。CUDA 为同步提供了阻塞和非阻塞两种方式的 API，甚至还支持使用主机端回调函数。

CUDA 中异步执行的核心 API 组件是 CUDA 流（CUDA Streams）和 CUDA 事件（CUDA Events）。本节其余部分将解释如何使用这些元素在 CUDA 中表达异步执行。

一个相关主题是 CUDA Graphs（CUDA 图）：它允许预先定义好一个异步操作的图，然后以极小的开销反复执行。2.4.9.2 节“使用流捕获的 CUDA 图简介”对 CUDA Graphs 做了非常简要的介绍，4.1 节“CUDA Graphs”则提供了更全面的讨论。

## 2.5.2 CUDA 流

在最基本的层面上，CUDA 流是一种抽象，它让程序员能够表达一个操作序列。流的工作方式类似一个工作队列：程序可以把操作（如内存拷贝或核函数启动）加入队列，按顺序执行。对于给定流的队列，位于队首的操作被执行并出队，随后下一个排队的操作来到队首等待执行。流中操作的执行顺序是顺序的，操作按入队的顺序执行。

应用程序可以同时使用多个流。在这种情况下，运行时会根据 GPU 资源的状态，从有可用工作的流中选择一个任务执行。可以为流指定优先级：优先级是给运行时的一个提示，用于影响调度，但不保证特定的执行顺序。

在流中运行的 API 函数调用和核函数启动，相对于主机线程都是异步的。应用程序可以通过等待流变为空来与流同步，也可以在设备级别进行同步。

CUDA 有一个默认流：没有指定流的操作和核函数启动都会排入这个默认流。不指定流的代码示例都是在隐式地使用这个默认流。默认流有一些特殊的语义，详见“阻塞流与非阻塞流及默认流”小节。

### 2.5.2.1 创建和销毁 CUDA 流

CUDA 流可以通过 `cudaStreamCreate()` 函数创建。该函数调用会初始化一个流句柄，后续函数调用中可用该句柄标识这个流。

```cuda
cudaStream_t stream;                // 流句柄
cudaStreamCreate(&stream);          // 创建一个新流

// 基于流的操作……

cudaStreamDestroy(stream);          // 销毁流
```

如果应用程序调用 `cudaStreamDestroy()` 时设备仍在该流中执行工作，该流会先完成流中的全部工作，然后再被销毁。

### 2.5.2.2 在 CUDA 流中启动核函数

启动核函数常用的三重尖括号语法，也可以用来把核函数启动到特定的流中。流作为核函数启动的一个额外参数来指定。在下面的示例中，名为 `kernel` 的核函数被启动到句柄为 `stream` 的流中，该句柄类型为 `cudaStream_t`，假定之前已创建好：

```cuda
kernel<<<grid, block, shared_mem_size, stream>>>(...);
```

核函数启动是异步的，函数调用会立即返回。假设核函数启动成功，核函数将在流 `stream` 中执行；应用程序可以在核函数执行期间，在 CPU 上或 GPU 的其他流中自由执行其他任务。

### 2.5.2.3 在 CUDA 流中启动内存传输

要把内存传输启动到流中，可以使用 `cudaMemcpyAsync()` 函数。该函数类似于 `cudaMemcpy()`，但多了一个指定用于本次内存传输的流的参数。下面代码块中的函数调用将 `src` 指向的主机内存中的 `size` 个字节，拷贝到 `dst` 指向的设备内存中，拷贝发生在流 `stream` 中：

```cuda
// 在流 stream 中把 size 个字节从 src 拷贝到 dst
cudaMemcpyAsync(dst, src, size, cudaMemcpyHostToDevice, stream);
```

与其他异步函数调用一样，该函数调用会立即返回，而 `cudaMemcpy()` 函数会阻塞，直到内存传输完成。为了安全地访问传输结果，应用程序必须通过某种形式的同步来确定操作已经完成。

其他 CUDA 内存传输函数（如 `cudaMemcpy2D()`）也有异步版本。

> **注意**
>
> 要想异步执行涉及 CPU 内存的内存拷贝，主机缓冲区必须被固定并页锁定（pinned and page-locked）。如果使用未固定、未页锁定的主机内存，`cudaMemcpyAsync()` 也能正确工作，但会回退为同步行为，无法与其他工作重叠。这会抑制使用异步内存传输带来的性能收益。建议程序使用 `cudaMallocHost()` 来分配用于与 GPU 收发数据的缓冲区。

### 2.5.2.4 流同步

与流同步最简单的方法是等待流中没有任务。这可以通过两种方式实现：使用 `cudaStreamSynchronize()` 函数或 `cudaStreamQuery()` 函数。

`cudaStreamSynchronize()` 函数会阻塞，直到流中的全部工作完成。

```cuda
// 等待流中没有任务
cudaStreamSynchronize(stream);

// 此时该流已完成，
// 我们可以安全地访问流操作的结果
```

如果我们不想阻塞，只想快速检查流是否为空，可以使用 `cudaStreamQuery()` 函数：

```cuda
// 看一眼流的状态
// 若流为空，返回 cudaSuccess
// 若流不为空，返回 cudaErrorNotReady
cudaError_t status = cudaStreamQuery(stream);

switch (status) {
    case cudaSuccess:
        // 流为空
        std::cout << "The stream is empty" << std::endl;
        break;
    case cudaErrorNotReady:
        // 流不为空
        std::cout << "The stream is not empty" << std::endl;
        break;
    default:
        // 发生了错误——需要处理
        break;
};
```

## 2.5.3 CUDA 事件

CUDA 事件是一种在 CUDA 流中插入标记的机制。它们本质上像示踪粒子，可用于跟踪流中任务的进度。设想向一个流中启动两个核函数。没有这种跟踪事件，我们只能判断流是否为空。如果第三个操作（无论是 CPU 上的操作，还是另一个流中的操作）依赖第一个核函数的输出，我们必须等到流为空才能安全地启动该操作——此时两个核函数都已完成。

使用 CUDA 事件可以做得更好。在第一个核函数之后、第二个核函数之前向流中排入一个事件，我们可以让 CPU 线程或另一个流等待这个事件来到流的队首。然后，我们就可以安全地启动依赖的操作，因为此时第一个核函数已完成，而第二个核函数尚未开始。以这种方式使用 CUDA 事件，可以在操作与流之间构建依赖关系图。这种图的类比可以直接对应到后面关于 CUDA 图的讨论。

CUDA 事件还记录时间信息，可用于为核函数启动和内存传输计时。

### 2.5.3.1 创建和销毁 CUDA 事件

CUDA 事件可以使用 `cudaEventCreate()` 和 `cudaEventDestroy()` 函数创建和销毁。

```cuda
cudaEvent_t event;

// 创建事件
cudaEventCreate(&event);

// 执行一些涉及该事件的工作……

// 工作完成且不再需要该事件时，
// 我们可以销毁它
cudaEventDestroy(event);
```

应用程序负责在不再需要事件时将其销毁。

### 2.5.3.2 将事件插入 CUDA 流

可以使用 `cudaEventRecord()` 函数将 CUDA 事件插入流中。

```cuda
cudaEvent_t event;
cudaStream_t stream;

// 创建事件
cudaEventCreate(&event);

// 将事件插入流中
cudaEventRecord(event, stream);
```

### 2.5.3.3 在 CUDA 流中为操作计时

CUDA 事件可用于为流中各种操作的执行计时，包括核函数。当一个事件到达流的队首时，它会记录一个时间戳。通过把流中的一个核函数夹在两个事件之间，我们可以精确测量核函数执行的持续时间，如下面的代码片段所示：

```cuda
cudaStream_t stream;
cudaStreamCreate(&stream);

cudaEvent_t start;
cudaEvent_t stop;

// 创建事件
cudaEventCreate(&start);
cudaEventCreate(&stop);

// 记录开始事件
cudaEventRecord(start, stream);

// 启动核函数
kernel<<<grid, block, 0, stream>>>(...);

// 记录结束事件
cudaEventRecord(stop, stream);

// 等待流完成
// 两个事件都将被触发
cudaStreamSynchronize(stream);

// 获取计时结果
float elapsedTime;
cudaEventElapsedTime(&elapsedTime, start, stop);
std::cout << "Kernel execution time: " << elapsedTime << " ms" << std::endl;

// 清理
cudaEventDestroy(start);
cudaEventDestroy(stop);
cudaStreamDestroy(stream);
```

### 2.5.3.4 检查 CUDA 事件的状态

与检查流状态类似，我们可以用阻塞或非阻塞两种方式检查事件状态。

`cudaEventSynchronize()` 函数会阻塞，直到事件完成。在下面的代码片段中，我们向一个流中启动一个核函数，接着插入一个事件，然后启动第二个核函数。我们可以用 `cudaEventSynchronize()` 函数等待第一个核函数之后的事件完成，从而在原则上立即启动依赖任务——甚至可能在 kernel2 结束之前就启动。

```cuda
cudaEvent_t event;
cudaStream_t stream;

// 创建流
cudaStreamCreate(&stream);

// 创建事件
cudaEventCreate(&event);

// 向流中启动一个核函数
kernel<<<grid, block, 0, stream>>>(...);

// 记录事件
cudaEventRecord(event, stream);

// 向流中启动第二个核函数
kernel2<<<grid, block, 0, stream>>>(...);

// 等待事件完成
// 此时可保证 kernel1 已完成，
// 我们可以启动依赖任务
cudaEventSynchronize(event);
dependentCPUtask();

// 等待流变为空
// 此时可保证 kernel2 已完成
cudaStreamSynchronize(stream);

// 销毁事件
cudaEventDestroy(event);

// 销毁流
cudaStreamDestroy(stream);
```

也可以用 `cudaEventQuery()` 函数以非阻塞方式检查 CUDA 事件是否完成。在下面的示例中，我们向一个流中启动两个核函数。第一个核函数 kernel1 生成一些数据，我们想把这些数据拷贝到主机，但同时 CPU 端还有工作要做。在下面的代码中，我们先把 kernel1、接着一个事件（event）、然后 kernel2 排入流 stream1。然后进入 CPU 工作循环，但会时不时看一眼事件是否已完成——这表示 kernel1 已结束。如果完成，我们就向流 stream2 中启动一个从设备到主机的拷贝。这种方法让 CPU 工作与 GPU 核函数执行以及设备到主机的拷贝重叠起来。

```cuda
cudaEvent_t event;
cudaStream_t stream1;
cudaStream_t stream2;

size_t size = LARGE_NUMBER;
float* d_data;
float* h_data;

// 创建一些数据
cudaMalloc(&d_data, size);
cudaMallocHost(&h_data, size);

// 创建流
cudaStreamCreate(&stream1);            // 处理流
cudaStreamCreate(&stream2);            // 拷贝流
bool copyStarted = false;

// 创建事件
cudaEventCreate(&event);

// 把 kernel1 启动到流中
kernel1<<<grid, block, 0, stream1>>>(d_data, size);
// 在 kernel1 之后排入一个事件
cudaEventRecord(event, stream1);

// 把 kernel2 启动到流中
kernel2<<<grid, block, 0, stream1>>>();

// 在核函数运行时，在 CPU 上做一些工作，
// 但要检查 kernel1 是否完成，
// 因为一旦完成，我们就向 stream2 启动
// 从设备到主机的拷贝
while ( not allCPUWorkDone() || not copyStarted ) {
    doNextChunkOfCPUWork();

    // 看一眼 kernel1 是否已完成
    // 如果是，向 stream2 排入一个非阻塞拷贝
    if ( not copyStarted ) {
        if( cudaEventQuery(event) == cudaSuccess ) {
            cudaMemcpyAsync(h_data, d_data, size, cudaMemcpyDeviceToHost, stream2);
            copyStarted = true;
        }
    }
}

// 等待两个流都完成
cudaStreamSynchronize(stream1);
cudaStreamSynchronize(stream2);

// 销毁事件
cudaEventDestroy(event);

// 销毁流并释放数据
cudaStreamDestroy(stream1);
cudaStreamDestroy(stream2);
cudaFree(d_data);
free(h_data);
```

## 2.5.4 流的回调函数

CUDA 提供了一种从流中在主机上启动函数的机制。目前有两个函数可用于此目的：`cudaLaunchHostFunc()` 和 `cudaAddCallback()`。不过，`cudaAddCallback()` 已被列入弃用计划，因此应用程序应使用 `cudaLaunchHostFunc()`。

使用 `cudaLaunchHostFunc()` 时，该函数的签名如下：

```cuda
cudaError_t cudaLaunchHostFunc(cudaStream_t stream, void (*func)(void *), void *data);
```

其中：

- `stream`：要把回调函数启动到的流。
- `func`：要启动的回调函数。
- `data`：指向要传递给回调函数的用户数据的指针。

主机函数本身是一个简单的 C 函数，签名如下：

```cuda
void hostFunction(void *data);
```

`data` 参数指向用户自定义的数据结构，函数可以对其进行解释。

使用这类回调函数时有一些注意事项需要牢记。特别是，主机函数**不能调用任何 CUDA API**。

出于与统一内存配合使用的目的，提供如下执行保证：

- 在函数执行期间，流被视为空闲状态。因此，例如该函数总可以使用附加到其被排入的那个流的内存。
- 函数开始执行的效果，等同于同步了在同一流中紧贴在该函数之前记录的一个事件。因此，它可以同步那些在该函数之前已被“合并（joined）”的流。
- 向任何流中添加设备工作，并不会使流变为活动状态——除非所有排在前面的主机函数和流回调都已执行完毕。因此，例如，如果工作已通过一个事件排在该函数调用之后，即使其他流中有工作，该函数仍可以使用全局附加内存（global attached memory）。
- 除上述情况外，函数完成不会使流变为活动状态。如果函数之后没有设备工作，流将保持空闲；即使有连续多个主机函数或流回调、其间没有设备工作，流也保持空闲。因此，例如可以通过从流末尾的主机函数发出信号来进行流同步。

### 2.5.4.1 使用 cudaStreamAddCallback()

> **注意**
>
> `cudaStreamAddCallback()` 函数已被列入弃用和移除计划，这里讨论它是为了完整性，也因为它可能仍出现在现有代码中。应用程序应使用 `cudaLaunchHostFunc()`，或切换到 `cudaLaunchHostFunc()`。

`cudaStreamAddCallback()` 函数的签名如下：

```cuda
cudaError_t cudaStreamAddCallback(cudaStream_t stream, cudaStreamCallback_t callback, void* userData, unsigned int flags);
```

其中：

- `stream`：要把回调函数启动到的流。
- `callback`：要启动的回调函数。
- `userData`：指向要传递给回调函数的用户数据的指针。
- `flags`：目前该参数必须为 0，以保证未来的兼容性。

回调函数的签名与使用 `cudaLaunchHostFunc()` 时略有不同。此时的回调函数是一个 C 函数，签名如下：

```cuda
void callbackFunction(cudaStream_t stream, cudaError_t status, void* userData);
```

该函数会接收到以下参数：

- `stream`：启动该回调函数的流的句柄。
- `status`：触发该回调的流操作的状态。
- `userData`：指向传递给回调函数的用户数据的指针。

特别是，`status` 参数包含流当前的错误状态，该状态可能由之前的操作设置。与 `cudaLaunchHostFunc()` 情况类似：在主机函数完成之前，流不会变为活动状态并推进到后续任务，并且回调函数内部不能调用任何 CUDA 函数。

### 2.5.4.2 异步错误处理

在一个 CUDA 流中，错误可能源于流中的任何操作，包括核函数启动和内存传输。这些错误在运行时可能不会立即传播回用户，直到流被同步为止，例如通过等待一个事件或调用 `cudaStreamSynchronize()`。

有两种方法可以获知流中可能发生的错误：

- 使用 `cudaGetLastError()` 函数——该函数返回并清除当前上下文中任何流遇到的最后一个错误。如果两次调用之间没有发生其他错误，紧接着的第二次 `cudaGetLastError()` 调用将返回 `cudaSuccess`。
- 使用 `cudaPeekAtLastError()` 函数——该函数返回当前上下文中的最后一个错误，但不清除它。

这两个函数都以 `cudaError_t` 类型的值返回错误。可以使用 `cudaGetErrorName()` 和 `cudaGetErrorString()` 函数生成错误的可打印名称。下面展示了一个使用这些函数的示例：

代码清单 1：使用 `cudaGetLastError()` 和 `cudaPeekAtLastError()` 的示例

```cuda
// 在流中进行了一些工作。
cudaStreamSynchronize(stream);

// 查看最后一个错误，但不清除它
cudaError_t err = cudaPeekAtLastError();
if (err != cudaSuccess) {
    printf("Error with name: %s\n", cudaGetErrorName(err));
    printf("Error description: %s\n", cudaGetErrorString(err));
}

// 查看最后一个错误并清除它
cudaError_t err2 = cudaGetLastError();
if (err2 != cudaSuccess) {
    printf("Error with name: %s\n", cudaGetErrorName(err2));
    printf("Error description: %s\n", cudaGetErrorString(err2));
}

if (err2 != err) {
    printf("As expected, cudaPeekAtLastError() did not clear the error\n");
}

// 再次检查
cudaError_t err3 = cudaGetLastError();
if (err3 == cudaSuccess) {
    printf("As expected, cudaGetLastError() cleared the error\n");
}
```

> **提示**
>
> 当错误出现在同步点（尤其是有很多操作的流中）时，往往难以准确定位错误在流中的哪个位置发生。要调试这种情况，一个有用的技巧是设置环境变量 `CUDA_LAUNCH_BLOCKING=1`，然后运行应用程序。这个环境变量的效果是：在每次核函数启动之后进行同步。这有助于定位是哪个核函数或传输引发了错误。同步开销可能很大；设置此环境变量后，应用程序的运行速度可能明显变慢。

## 2.5.5 CUDA 流的排序

现在我们已经讨论了流、事件和回调函数的基本机制，接下来需要考虑流中异步操作的排序语义。这些语义是为了让应用程序程序员能够安全地思考流中操作的顺序。其中有一些特殊情况会放宽这些语义，以实现性能优化，例如：程序化依赖核函数启动（programmatic dependent kernel launch）的情况——它通过特殊的属性和核函数启动机制允许两个核函数重叠；或者使用异步批量内存拷贝函数批量传输内存的情况——此时运行时可以并发执行不重叠的批量拷贝。

最重要的一点是：CUDA 流是所谓的有序流（in-order stream）。这意味着流中操作的执行顺序与这些操作入队的顺序相同。流中的某个操作不能跳过前面的操作。内存操作（如拷贝）由运行时跟踪，总会在下一个操作之前完成，以便依赖的核函数能安全地访问正在传输的数据。

## 2.5.6 阻塞流与非阻塞流及默认流

CUDA 中有两种流：阻塞流和非阻塞流。名字有点容易误解，因为“阻塞”和“非阻塞”的语义只涉及流与默认流如何同步。用 `cudaStreamCreate()` 创建的流默认为阻塞流。要创建非阻塞流，必须使用 `cudaStreamCreateWithFlags()` 函数，并传入 `cudaStreamNonBlocking` 标志：

```cuda
cudaStream_t stream;
cudaStreamCreateWithFlags(&stream, cudaStreamNonBlocking);
```

非阻塞流同样用 `cudaStreamDestroy()` 销毁。

### 2.5.6.1 传统默认流

阻塞流与非阻塞流的关键区别在于它们与默认流如何同步。CUDA 提供了一个传统默认流（也称为 NULL 流，或流 ID 为 0 的流）：在核函数启动或阻塞式 `cudaMemcpy()` 调用中没有指定流时，就会使用它。这个默认流在所有主机线程之间共享，是一个阻塞流。当一个操作被启动到这个默认流中时，它会与所有其他阻塞流同步——换句话说，它要等所有其他阻塞流完成后才能执行。

```cuda
cudaStream_t stream1, stream2;
cudaStreamCreate(&stream1);
cudaStreamCreate(&stream2);

kernel1<<<grid, block, 0, stream1>>>(...);
kernel2<<<grid, block>>>(...);
kernel3<<<grid, block, 0, stream2>>>(...);

cudaDeviceSynchronize();
```

默认流的行为意味着，在上面的代码片段中，即使原则上三个核函数都可以并发执行，kernel2 也会等待 kernel1 完成，kernel3 会等待 kernel2 完成。通过创建非阻塞流可以避免这种同步行为。

在下面的代码片段中，我们创建了两个非阻塞流。默认流将不再与这些流同步，原则上三个核函数都可以并发执行。因此，我们不能假设核函数的任何执行顺序，必须进行显式同步（如相当“重”的 `cudaDeviceSynchronize()` 调用），以确保核函数都已完成。

```cuda
cudaStream_t stream1, stream2;
cudaStreamCreateWithFlags(&stream1, cudaStreamNonBlocking);
cudaStreamCreateWithFlags(&stream2, cudaStreamNonBlocking);

kernel1<<<grid, block, 0, stream1>>>(...);
kernel2<<<grid, block>>>(...);
kernel3<<<grid, block, 0, stream2>>>(...);

cudaDeviceSynchronize();
```

### 2.5.6.2 每个线程的默认流

从 CUDA 7 开始，CUDA 允许每个主机线程拥有自己独立的默认流，而不是共享的传统默认流。要启用这种行为，必须使用 nvcc 编译器选项 `--default-stream per-thread`，或定义预处理器宏 `CUDA_API_PER_THREAD_DEFAULT_STREAM`。启用后，每个主机线程都将拥有自己独立的默认流，它不会像传统默认流那样与其他流同步。在这种情况下，传统默认流的示例将表现出与非阻塞流示例相同的同步行为。

## 2.5.7 显式同步

有多种方式可以显式地同步流之间的执行：

- `cudaDeviceSynchronize()` 会等待所有主机线程的所有流中先前提交的命令全部完成。
- `cudaStreamSynchronize()` 以一个流为参数，等待给定流中先前提交的命令全部完成。它可用于将主机与特定流同步，同时允许其他流继续在设备上执行。
- `cudaStreamWaitEvent()` 以一个流和一个事件为参数（事件的说明见“CUDA 事件”），使得在调用 `cudaStreamWaitEvent()` 之后加入给定流的所有命令都延迟执行，直到给定事件完成。
- `cudaStreamQuery()` 为应用程序提供了一种了解流中所有先前命令是否已完成的方法。

## 2.5.8 隐式同步

如果两个操作来自不同的流，且在这两个操作之间有任何 CUDA 操作被提交到 NULL 流，那么这两个操作不能并发运行——除非这些流是非阻塞流（用 `cudaStreamNonBlocking` 标志创建）。

为了提高核函数并发执行的潜力，应用程序应遵循以下准则：

- 所有相互独立的操作应在依赖操作之前提交；
- 任何形式的同步都应尽量推迟。

## 2.5.9 杂项和高级主题

### 2.5.9.1 流优先级

如前所述，开发者可以为 CUDA 流指定优先级。优先流必须使用 `cudaStreamCreateWithPriority()` 函数创建。该函数接受两个参数：流句柄和优先级。总的原则是：数字越小，对应的优先级越高。可以用 `cudaDeviceGetStreamPriorityRange()` 函数查询给定设备和上下文的优先级范围。流的默认优先级为 0。

```cuda
int minPriority, maxPriority;

// 查询设备的优先级范围
cudaDeviceGetStreamPriorityRange(&minPriority, &maxPriority);

// 创建两个不同优先级的流
// cudaStreamDefault 表示以默认标志创建流，
// 换句话说，相对于传统默认流，它们将是阻塞流

// 这里也可以使用 cudaStreamNonBlocking 选项来创建非阻塞流

cudaStream_t stream1, stream2;
cudaStreamCreateWithPriority(&stream1, cudaStreamDefault, minPriority);  // 最低优先级

cudaStreamCreateWithPriority(&stream2, cudaStreamDefault, maxPriority);  // 最高优先级
```

需要注意的是，流的优先级只是给运行时的一个提示，一般主要适用于核函数启动，内存传输不一定会遵守。流优先级不会抢占已经在执行的工作，也不会保证任何特定的执行顺序。

### 2.5.9.2 使用流捕获的 CUDA 图简介

CUDA 流允许程序按顺序指定一系列操作（核函数或内存拷贝）。使用多个流，并通过 `cudaStreamWaitEvent` 实现跨流依赖，应用程序可以指定一个完整的操作有向无环图（DAG）。有些应用程序有一系列操作（或 DAG）需要在执行过程中运行很多次。

针对这种情况，CUDA 提供了一个称为 CUDA 图（CUDA graphs）的特性。本节介绍 CUDA 图和一种称为“流捕获（stream capture）”的创建方式。关于 CUDA 图的更详细讨论见“CUDA 图”一节。捕获或创建图有助于降低重复调用主机线程的同一系列 API 链的延迟和 CPU 开销。相反，指定图操作的 API 只需调用一次，然后得到的图可以执行很多次。

CUDA 图的工作方式如下：

i) 应用程序捕获图。这一步在图第一次执行时完成一次。也可以使用 CUDA 图 API 手动组合图。

ii) 图被实例化。这一步在图捕获之后完成一次。这一步可以搭建好执行图所需的各种运行时结构，以便让其组件的启动尽可能快。

iii) 在后续步骤中，预先实例化的图被执行所需的次数。由于执行图操作所需的运行时结构都已就绪，图执行的 CPU 开销被降到最低。

代码清单 2：使用 CUDA 图捕获、实例化和执行一个简单线性图的阶段（摘自 CUDA 开发者技术博客，A. Gray，2019）

```cuda
#define N 500000  // 调整到让核函数耗时几微秒

// 一个非常轻量的核函数
__global__ void shortKernel(float * out_d, float * in_d){
    int idx=blockIdx.x*blockDim.x+threadIdx.x;
    if(idx<N) out_d[idx]=1.23*in_d[idx];
}

bool graphCreated=false;
cudaGraph_t graph;
cudaGraphExec_t instance;

// 该图将被执行 NSTEP 次
for(int istep=0; istep<NSTEP; istep++){
    if(!graphCreated){
        // 捕获图
        cudaStreamBeginCapture(stream, cudaStreamCaptureModeGlobal);

        // 启动 NKERNEL 个核函数
        for(int ikrnl=0; ikrnl<NKERNEL; ikrnl++){
            shortKernel<<<blocks, threads, 0, stream>>>(out_d, in_d);
        }

        // 结束捕获
        cudaStreamEndCapture(stream, &graph);

        // 实例化图
        cudaGraphInstantiate(&instance, graph, NULL, NULL, 0);
        graphCreated=true;
    }

    // 启动图
    cudaGraphLaunch(instance, stream);

    // 同步流
    cudaStreamSynchronize(stream);
}
```

关于 CUDA 图的更多细节见“CUDA 图”。

## 2.5.10 异步执行小结

本节要点：

- 异步 API 让我们能够表达任务的并发执行，提供了重叠各种操作的方式。实际能达到的并发程度取决于可用的硬件资源和计算能力。
- CUDA 中异步执行的关键抽象是流、事件和回调函数。
- 可以在事件、流和设备三个级别进行同步。
- 默认流是阻塞流，它与所有其他阻塞流同步，但不与非阻塞流同步。
- 可以通过 `--default-stream per-thread` 编译器选项或 `CUDA_API_PER_THREAD_DEFAULT_STREAM` 预处理器宏，使用每个线程的默认流来避免默认流的行为。
- 流可以创建为不同优先级，但优先级只是给运行时的提示，内存传输不一定会遵守。
- CUDA 提供了 API 函数，用于降低或重叠核函数启动和内存传输的开销，例如 CUDA 图、批量内存传输（Batched Memory Transfers）和程序化依赖核函数启动（Programmatic Dependent Kernel Launch）。
