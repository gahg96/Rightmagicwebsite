# 4.17 虚拟内存管理

在 CUDA 编程模型中，内存分配调用（如 `cudaMalloc()`）会返回 GPU 内存中的一个内存地址。该地址可用于任何 CUDA API，也可以直接在设备核函数中使用。开发者可以通过 `cudaEnablePeerAccess` 为这些内存分配启用对端设备访问。启用之后，不同设备上的核函数便能访问同一份数据。然而，所有过去和未来的用户分配都会被映射到目标对端设备上。这会导致用户无意中为把所有 `cudaMalloc` 分配映射到对端设备付出运行时开销。在大多数情况下，应用只需要与另一台设备共享少数几个分配。把全部的分配映射到所有设备通常是不必要的。此外，把这种方式扩展到多节点场景本身也非常困难。

CUDA 提供了一套虚拟内存管理（VMM）API，让开发者能够以显式、低层级的方式控制这一过程。

虚拟内存分配是一个复杂的过程，由操作系统和内存管理单元（MMU）管理，它包含两个关键阶段。首先，操作系统为程序保留（reserve）一段连续的虚拟地址范围，但并不分配任何物理内存。然后，当程序第一次尝试使用这段内存时，操作系统再提交（commit）这些虚拟地址，按需把物理存储指派给虚拟页。

CUDA 的 VMM API 把类似的概念引入 GPU 内存管理：允许开发者显式保留一段虚拟地址范围，然后在之后把它映射到物理 GPU 内存。借助 VMM，应用可以精确选择哪些分配要对其他设备可见。

VMM API 让复杂应用能够在多个 GPU（以及 CPU 核心）之间更高效地管理内存。通过对内存保留、映射和访问权限进行手动控制，VMM API 使得细粒度数据共享、零拷贝传输、自定义内存分配器等高级技术成为可能。CUDA VMM API 让用户能以细粒度控制应用中的 GPU 内存管理。

开发者能从 VMM API 中获得以下几方面的好处：

- 对虚拟内存和物理内存进行细粒度控制，可以把不连续的物理内存块分配并映射到连续的虚拟地址空间。这有助于减少 GPU 内存碎片、提高内存利用率，特别是在深度神经网络训练这样的大规模负载中。
- 把虚拟地址空间的保留与物理内存的分配分开，从而高效地分配和释放内存。开发者可以保留较大的虚拟内存区域，按需映射物理内存，而无需代价高昂的内存拷贝或重新分配。这让动态数据结构和变长内存分配的性能得到提升。
- 无需拷贝和重新分配全部数据就能动态增长 GPU 内存分配，类似于 CPU 内存管理中的 `realloc` 或 `std::vector`。这支持更灵活、更高效的 GPU 内存使用模式。
- 提供低层级 API，帮助开发者构建复杂的内存分配器和缓存管理系统（如动态管理大语言模型中的键值缓存），从而提高开发效率和应用性能，改善吞吐和延迟。
- CUDA VMM API 在分布式多 GPU 环境中极具价值，它支持跨多个 GPU 的高效内存共享和访问。通过把虚拟地址与物理内存解耦，该 API 允许开发者创建统一的虚拟地址空间，数据可以动态映射到不同的 GPU 上。这既优化了内存使用，也降低了数据传输开销。例如，NVIDIA 的 NCCL 和 NVSHMEM 库就在积极使用 VMM。

总之，CUDA VMM API 让开发者拥有了超越传统 `malloc` 式抽象的高级工具，能够以精细、高效、灵活、可扩展的方式管理 GPU 内存，这对高性能和大内存应用至关重要。

> 注意：本节描述的这套 API 需要系统支持 UVA。详见“虚拟内存管理 API”一节。

## 4.17.1 预备知识

### 4.17.1.1 定义

**Fabric 内存**：fabric 内存（fabric memory）指通过高速互连 fabric（如 NVIDIA 的 NVLink 和 NVSwitch）可访问的内存。这种 fabric 在多个 GPU 或节点之间提供了内存一致性和高带宽通信层，使它们能够像共享统一 fabric 上的内存一样高效地共享内存，而非各自局限于孤立的设备内存。CUDA 12.4 及以后版本提供了 VMM 分配句柄类型 `CU_MEM_HANDLE_TYPE_FABRIC`。在受支持的平台上，且在 NVIDIA IMEX 守护进程运行的前提下，该分配句柄类型不仅支持通过任意通信机制（如 MPI）在节点内共享分配，也支持跨节点共享。这使得多节点 NVLink 系统中的 GPU 能够映射同一 NVLink fabric 内所有其他 GPU 的内存，即使它们位于不同的节点上。

> 注意：这里描述的 fabric 内存是地址中心型的：对端的物理内存被映射到本地虚拟地址空间，通过普通的加载和存储指令访问。计算 fabric 传输（compute fabric transport）在同一 NVLink fabric 上提供了互补的资源中心型模型：通过异步的 put、get 和归约操作访问命名的逻辑端点，而不是映射地址。它为每次操作报告显式的完成状态，因此适合 fabric 错误恢复值得关注的大规模 fabric。

**内存句柄**：在 VMM 中，句柄是代表物理内存分配的不透明标识符。这些句柄是低层级 CUDA VMM API 中内存管理的核心。它们让用户能够灵活控制可映射到虚拟地址空间的物理内存对象。每个句柄唯一标识一个物理内存分配。句柄是内存资源的抽象引用，不暴露直接指针。句柄支持在进程或设备之间导出和导入内存，便于内存共享与虚拟化。

**IMEX 通道**：IMEX 是“internode memory exchange”（节点间内存交换）的缩写，是 NVIDIA 实现跨节点 GPU 到 GPU 通信的解决方案的一部分。IMEX 通道是一项 GPU 驱动特性，为 IMEX 域内的多用户或多节点环境提供基于用户的内存隔离。IMEX 通道是安全与隔离机制。

IMEX 通道与 fabric 句柄直接相关，在多节点 GPU 通信中必须启用。当某个 GPU 分配了内存并希望让另一个节点上的 GPU 访问它时，首先需要导出该内存的句柄。在导出过程中会使用 IMEX 通道生成安全的 fabric 句柄，只有拥有正确通道访问权限的远端进程才能导入该句柄。

**单播内存访问**：在 VMM API 的语境中，单播内存访问指某个特定设备或进程以受控、直接的方式，把物理内存映射并访问到一段唯一的虚拟地址范围。与向多个设备广播访问不同，单播内存访问意味着被显式授予读写权限的 GPU 设备获得一段预留的虚拟地址范围，该范围映射到一处物理内存分配。

**多播内存访问**：在 VMM API 的语境中，多播内存访问指单块物理内存分配（或内存区域）能够通过多播机制同时映射到多个设备的虚拟地址空间。这使得数据能够以一对多的方式在多个 GPU 间高效共享，减少冗余的数据传输，提高通信效率。NVIDIA 的 CUDA VMM API 支持创建多播对象，把来自多个设备的物理内存分配绑定到一起。
### 4.17.1.2 查询支持情况

应用在尝试使用这些功能之前应当先查询其是否受支持，因为可用性会随 GPU 架构、驱动版本以及所使用的软件库而变化。以下几节介绍如何以编程方式检查所需的支持情况。

**VMM 支持**。在尝试使用 VMM API 之前，应用必须确认要使用的设备支持 CUDA 虚拟内存管理。以下代码示例展示了如何查询 VMM 支持情况：

```c
int deviceSupportsVmm;
CUresult result = cuDeviceGetAttribute(&deviceSupportsVmm, CU_DEVICE_
 ,→ATTRIBUTE_VIRTUAL_MEMORY_MANAGEMENT_SUPPORTED, device);

if (deviceSupportsVmm != 0) {
     ∕∕ `device` 支持虚拟内存管理
}
```

**Fabric 内存支持**：在尝试使用 fabric 内存之前，应用必须确认要使用的设备支持 fabric 内存。以下代码示例展示了如何查询 fabric 内存支持情况：

```c
int deviceSupportsFabricMem;
CUresult result = cuDeviceGetAttribute(&deviceSupportsFabricMem, CU_DEVICE_
 ,→ATTRIBUTE_HANDLE_TYPE_FABRIC_SUPPORTED, device);

if (deviceSupportsFabricMem != 0) {
     ∕∕ `device` 支持 Fabric 内存
}
```

除了使用 `CU_MEM_HANDLE_TYPE_FABRIC` 作为句柄类型、并且不需要操作系统原生机制来进行进程间通信以交换可共享句柄之外，使用 fabric 内存与使用其他分配句柄类型没有任何区别。

**IMEX 通道支持**。在 IMEX 域内，IMEX 通道为多用户环境提供安全的内存共享。NVIDIA 驱动通过创建字符设备 `nvidia-caps-imex-channels` 来实现这一功能。要使用基于 fabric 句柄的共享，用户应当验证两件事：

- 首先，应用必须验证该设备存在于 `/proc/devices` 下：

```bash
# cat ∕proc∕devices | grep nvidia
195 nvidia
195 nvidiactl
234 nvidia-caps-imex-channels
509 nvidia-nvswitch
```

`nvidia-caps-imex-channels` 设备应该有一个主设备号（例如 234）。

- 其次，要让两个 CUDA 进程（导出方和导入方）共享内存，它们必须都能访问同一个 IMEX 通道文件。这些文件（如 `/dev/nvidia-caps-imex-channels/channel0`）是代表单个 IMEX 通道的节点。系统管理员必须创建这些文件，例如使用 `mknod()` 命令。

```bash
# mknod ∕dev∕nvidia-caps-imex-channels∕channelN c <major_number> 0
```

这条命令使用从 `/proc/devices` 获得的主设备号创建 `channelN`。

> 注意：默认情况下，如果指定了模块参数 `NVreg_CreateImexChannel0`，驱动可以创建 `channel0`。

**多播对象支持**：在尝试使用多播对象之前，应用必须确认要使用的设备支持它们。以下代码示例展示了如何查询多播对象支持情况：

```c
int deviceSupportsMultiCast;
CUresult result = cuDeviceGetAttribute(&deviceSupportsMultiCast, CU_DEVICE_
 ,→ATTRIBUTE_MULTICAST_SUPPORTED, device);

if (deviceSupportsMultiCast != 0) {
     ∕∕ `device` 支持多播对象
}
```
## 4.17.2 API 概览

VMM API 让开发者能够对虚拟内存管理进行细粒度控制。VMM 是一个非常低层级的 API，需要直接使用 CUDA 驱动 API。该多用途 API 既可用于单节点环境，也可用于多节点环境。

要有效使用 VMM，开发者必须扎实掌握内存管理中的几个关键概念：

- 了解操作系统的虚拟内存基础知识，包括操作系统如何处理页和地址空间；
- 了解内存层次结构和硬件特性是必要的；
- 熟悉进程间通信（IPC）方法，如套接字或消息传递；
- 了解内存访问权限方面的基本安全知识。

图 55：VMM 使用概览。该图概述了使用 VMM 所需的步骤序列。首先评估环境配置；根据评估结果，用户必须做出一个关键的初始决策：使用 fabric 内存句柄还是 OS 特定句柄。基于最初的句柄选择，后续要采取各自不同的步骤序列。然而，最终的内存管理操作——具体是映射、保留和设置已分配内存的访问权限——无论选择哪种句柄都完全相同。

VMM API 的工作流程包含一系列内存管理步骤，重点在于在不同设备或进程之间共享内存。首先，开发者必须在源设备上分配物理内存。为了便于共享，VMM API 使用句柄把必要信息传递给目标设备或进程。用户必须为共享导出一个句柄，可以是 OS 特定句柄，也可以是 fabric 特定句柄。OS 特定句柄只能用于单节点上的进程间通信，而 fabric 特定句柄更灵活，既可用于单节点环境，也可用于多节点环境。需要注意的是，使用 fabric 特定句柄需要启用 IMEX 通道。

句柄导出后，必须使用进程间通信协议把它共享给接收进程，具体方法由开发者自行选择。接收进程随后使用 VMM API 导入该句柄。在句柄被导出、共享并导入之后，源进程和目标进程都必须保留虚拟地址空间，待分配的物理内存将映射到其中。最后一步是为每个设备设置内存访问权限，确保权限设置正确。整个流程（包括两种句柄方式）在附图中进一步详细说明。

## 4.17.3 单播内存共享

GPU 内存共享可以发生在一台机器的多个 GPU 之间，也可以发生在由多台机器组成的网络中。该过程遵循以下步骤：

- 分配并导出：一个 GPU 上的 CUDA 程序分配内存，并为其获取可共享的句柄。
- 共享并导入：该句柄通过 IPC、MPI 或 NCCL 等方式发送给节点上的其他程序。在接收端的 GPU 上，CUDA 驱动导入该句柄并创建必要的内存对象。
- 保留并映射：驱动建立从程序的虚拟地址（VA）到 GPU 物理地址（PA），再到其网络 Fabric 地址（FA）的映射。
- 访问权限：为该分配设置访问权限。
- 释放内存：程序执行结束时释放所有分配。

### 4.17.3.1 分配并导出

**分配物理内存**。使用虚拟内存管理 API 分配内存的第一步是创建一块物理内存，供后续分配使用。要分配物理内存，应用必须使用 `cuMemCreate` API。该函数创建的分配没有任何设备或主机映射。函数参数 `CUmemGenericAllocationHandle` 描述了要分配内存的属性，例如分配的位置、该分配是否会共享给其他进程（或图形 API）、要分配内存的物理属性等。用户必须确保请求的分配大小与适当的粒度对齐。分配的粒度要求可以通过 `cuMemGetAllocationGranularity` 查询。

OS 特定句柄（Linux）：

```c
CUmemGenericAllocationHandle allocatePhysicalMemory(int device, size_t size) {
     CUmemAllocationHandleType handleType = CU_MEM_HANDLE_TYPE_POSIX_FILE_
 ,→DESCRIPTOR;

     CUmemAllocationProp prop = {};
     prop.type = CU_MEM_ALLOCATION_TYPE_PINNED;
     prop.location.type = CU_MEM_LOCATION_TYPE_DEVICE;
     prop.location.id = device;
     prop.requestedHandleType = handleType;

    size_t granularity = 0;
    cuMemGetAllocationGranularity(&granularity, &prop, CU_MEM_ALLOC_
,→GRANULARITY_MINIMUM);



     ∕∕ 确保大小符合该分配的粒度要求
     size_t padded_size = ROUND_UP(size, granularity);

     ∕∕ 分配物理内存
     CUmemGenericAllocationHandle allocHandle;
     cuMemCreate(&allocHandle, padded_size, &prop, 0);

     return allocHandle;
}
```

Fabric 句柄：

```c
CUmemGenericAllocationHandle allocatePhysicalMemory(int device, size_t size) {
    CUmemAllocationHandleType handleType = CU_MEM_HANDLE_TYPE_FABRIC;
    CUmemAllocationProp prop = {};
    prop.type = CU_MEM_ALLOCATION_TYPE_PINNED;
    prop.location.type = CU_MEM_LOCATION_TYPE_DEVICE;
    prop.location.id = device;
    prop.requestedHandleType = handleType;

    size_t granularity = 0;
    cuMemGetAllocationGranularity(&granularity, &prop, CU_MEM_ALLOC_
,→GRANULARITY_MINIMUM);



     ∕∕ 确保大小符合该分配的粒度要求
     size_t padded_size = ROUND_UP(size, granularity);

     ∕∕ 分配物理内存
     CUmemGenericAllocationHandle allocHandle;
     cuMemCreate(&allocHandle, padded_size, &prop, 0);

     return allocHandle;
}
```

> 注意：`cuMemCreate` 分配的内存由它返回的 `CUmemGenericAllocationHandle` 引用。注意，这个引用不是指针，其内存尚不可访问。

> 注意：分配句柄的属性可以通过 `cuMemGetAllocationPropertiesFromHandle` 查询。

**在局域性域中分配设备内存**。要在特定的局域性域（locality domain）中分配设备内存，请将 `CUmemAllocationProp::location.type` 设置为 `CU_MEM_LOCATION_TYPE_DEVICE_LOCALITY_DOMAIN`。`CUmemAllocationProp::location.localized` 的两个成员都需要设置：`deviceId` 标识 GPU，`localityDomainId` 标识该 GPU 上的有效局域性域。用 `cuDeviceGetAttribute` 和 `CU_DEVICE_ATTRIBUTE_LOCALITY_DOMAIN_COUNT` 查询有效的局域性域数量。分配大小必须是为该局域化分配属性返回的最小粒度的整数倍：

```c
CUmemAllocationProp prop {};
prop.type = CU_MEM_ALLOCATION_TYPE_PINNED;
prop.location.type = CU_MEM_LOCATION_TYPE_DEVICE_LOCALITY_DOMAIN;
prop.location.localized.deviceId = device;
prop.location.localized.localityDomainId = localityDomainId;

size_t granularity = 0;
cuMemGetAllocationGranularity(&granularity, &prop, CU_MEM_ALLOC_GRANULARITY_
 ,→MINIMUM);

size_t alignedSize = ((size + granularity - 1) ∕ granularity) * granularity;

CUmemGenericAllocationHandle allocationHandle {};
cuMemCreate(&allocationHandle, alignedSize, &prop, 0);
```

返回的句柄与 VMM 其他分配一样，使用相同的保留、映射、访问控制和释放 API。

在只有一个局域性域的设备上，请求局域性域 0 等价于用 `CU_MEM_LOCATION_TYPE_DEVICE` 创建的全设备分配；得到的分配会报告其位置类型为 `CU_MEM_LOCATION_TYPE_DEVICE`。总体编程模型见“局域性域”一节。

**导出内存句柄**。CUDA 虚拟内存管理 API 暴露了一种新的进程间通信机制，使用句柄来交换关于分配和物理地址空间的必要信息。可以导出 OS 特定 IPC 句柄或 fabric 特定 IPC 句柄。OS 特定 IPC 句柄只能用于单节点配置，fabric 特定句柄可用于单节点或多节点配置。

OS 特定句柄（Linux）：

```c
CUmemAllocationHandleType handleType = CU_MEM_HANDLE_TYPE_POSIX_FILE_
 ,→DESCRIPTOR;

CUmemGenericAllocationHandle handle = allocatePhysicalMemory(0, 1<<21);
int fd;
cuMemExportToShareableHandle(&fd, handle, handleType, 0);
```

Fabric 句柄：

```c
CUmemAllocationHandleType handleType = CU_MEM_HANDLE_TYPE_FABRIC;
CUmemGenericAllocationHandle handle = allocatePhysicalMemory(0, 1<<21);
CUmemFabricHandle fh;
cuMemExportToShareableHandle(&fh, handle, handleType, 0);
```

> 注意：OS 特定句柄要求所有进程都属于同一个 OS。

> 注意：fabric 特定句柄要求由系统管理员启用 IMEX 通道。

`memMapIpcDrv` 示例可作为在 VMM 分配中使用 IPC 的参考。

### 4.17.3.2 共享并导入

**共享内存句柄**。句柄导出后，必须使用某种进程间通信协议把它共享给接收进程。开发者可以自由选择任何方法共享句柄。具体使用的 IPC 方法取决于应用的设计和环境。常用方法包括 OS 特定的进程间套接字和分布式消息传递。使用 OS 特定 IPC 传输性能高，但仅限于同一台机器上的进程，且不可移植。fabric 特定 IPC 更简单、更具可移植性，但需要系统级支持。所选方法必须安全可靠地把句柄数据传输到目标进程，以便它导入内存并建立有效映射。IPC 方法选择的灵活性让 VMM API 能够集成到从单节点应用到分布式多节点配置的广泛系统架构中。在下面的代码片段中，我们将给出使用套接字编程和 MPI 共享与接收句柄的示例。
发送：OS 特定 IPC（Linux）

```c
int ipcSendShareableHandle(int socket, int fd, pid_t process) {
    struct msghdr msg;
    struct iovec iov[1];

      union {
          struct cmsghdr cm;
          char* control;
      } control_un;

      size_t sizeof_control = CMSG_SPACE(sizeof(int)) * sizeof(char);
      control_un.control = (char*) malloc(sizeof_control);

      struct cmsghdr *cmptr;
      ssize_t readResult;
      struct sockaddr_un cliaddr;
      socklen_t len = sizeof(cliaddr);

      ∕∕ 构造客户端地址，把这个可共享句柄发送给它
      memset(&cliaddr, 0, sizeof(cliaddr));
      cliaddr.sun_family = AF_UNIX;
      char temp[20];
      sprintf(temp, "%s%u", "∕tmp∕", process);
      strcpy(cliaddr.sun_path, temp);
      len = sizeof(cliaddr);

      ∕∕ 把相应的可共享句柄发送给客户端
      int sendfd = fd;

      msg.msg_control = control_un.control;
```

### 4.17.3.3 保留并映射

**保留虚拟地址范围**。由于在 VMM 中地址和内存是两个不同的概念，应用必须划出一个能够容纳 `cuMemCreate` 所做内存分配的地址范围。保留的地址范围必须至少与用户计划放入其中的所有物理内存分配的大小之和一样大。

应用可以通过向 `cuMemAddressReserve` 传递适当的参数来保留一段虚拟地址范围。得到的地址范围不关联任何设备或主机物理内存。保留的虚拟地址范围可以映射到属于系统中任何设备的内存块，从而为应用提供连续的 VA 范围，其背后由属于不同设备的内存映射和支持。应用应该使用 `cuMemAddressFree` 把虚拟地址范围归还给 CUDA。用户必须确保在调用 `cuMemAddressFree` 之前整个 VA 范围都已解除映射。这些函数在概念上类似于 Linux 上的 `mmap` 和 `munmap`，或 Windows 上的 `VirtualAlloc` 和 `VirtualFree`。下面的代码片段展示了该函数的用法：

```c
CUdeviceptr ptr;
∕∕ `ptr` 保存返回的已保留虚拟地址范围的起始地址。
CUresult result = cuMemAddressReserve(&ptr, size, 0, 0, 0); ∕∕ 对齐 = 0 表示使用默认对齐
```

**映射内存**。前两节中的已分配物理内存与划出的虚拟地址空间体现了 VMM API 引入的内存与地址的区分。要让分配的内存可用，用户必须把它映射到地址空间。必须用 `cuMemMap` 把 `cuMemAddressReserve` 返回的地址范围与 `cuMemCreate` 或 `cuMemImportFromShareableHandle` 得到的物理分配关联起来。只要划出的地址空间足够大，用户可以把来自多个设备的分配映射到连续的虚拟地址范围中。要解除物理分配与地址范围的关联，用户必须用 `cuMemUnmap` 解除地址映射的映射。用户可以在同一地址范围上反复映射和解除映射，只要不试图在已经建立映射的 VA 范围保留区上创建映射。下面的代码片段展示了该函数的用法：

```c
CUdeviceptr ptr;
∕∕ `ptr`：先前用 cuMemAddressReserve 保留的地址范围中的地址。

∕∕ `allocHandle`：先前调用 cuMemCreate 得到的 CUmemGenericAllocationHandle。

```

### 4.17.3.4 访问权限

CUDA 的虚拟内存管理 API 让应用能够用访问控制机制显式保护其 VA 范围。用 `cuMemMap` 把分配映射到地址范围的某个区域并不会让该地址可访问，如果被 CUDA 核函数访问会导致程序崩溃。用户必须在源设备和访问设备上用 `cuMemSetAccess` 函数显式选择访问控制。这允许或限制特定设备访问已映射的地址范围。下面的代码片段展示了该函数的用法：

```c
void setAccessOnDevice(int device, CUdeviceptr ptr, size_t size) {
    CUmemAccessDesc accessDesc = {};
    accessDesc.location.type = CU_MEM_LOCATION_TYPE_DEVICE;
    accessDesc.location.id = device;
    accessDesc.flags = CU_MEM_ACCESS_FLAGS_PROT_READWRITE;

       ∕∕ 使该地址可访问
       cuMemSetAccess(ptr, size, &accessDesc, 1);
}
```

VMM 暴露的访问控制机制让用户能够明确指定希望与系统上其他对端设备共享哪些分配。如前所述，`cudaEnablePeerAccess` 会强制所有过去和未来用 `cudaMalloc` 创建的分配都映射到目标对端设备。这种做法在很多情况下很方便，因为用户不用担心跟踪每个分配到每个设备的映射状态。但这种方式有性能方面的影响。有了分配粒度的访问控制，VMM 可以在最小开销下实现对端映射。

`vectorAddMMAP` 示例可作为使用虚拟内存管理 API 的参考。

### 4.17.3.5 释放内存

要释放已分配的内存和地址空间，源进程和目标进程都应按顺序依次使用 `cuMemUnmap`、`cuMemRelease` 和 `cuMemAddressFree` 函数。`cuMemUnmap` 把之前映射的内存区域从地址范围中解除映射，实质上是把物理内存从保留的虚拟地址空间分离。接下来，`cuMemRelease` 释放之前创建的物理内存，把它归还给系统。最后，`cuMemAddressFree` 释放之前保留的虚拟地址范围，供以后使用。这一特定顺序确保了物理内存和虚拟地址空间都能干净、彻底地释放。

```c
cuMemUnmap(ptr, size);
cuMemRelease(handle);
cuMemAddressFree(ptr, size);
```

> 注意：在 OS 特定情况下，导出的句柄必须用 `fclose` 关闭。此步骤不适用于基于 fabric 的情况。

## 4.17.4 多播内存共享

多播对象管理 API 提供了一种创建多播对象的方法，结合上文描述的虚拟内存管理 API，应用可以利用受支持的、通过 NVSwitch 连接的 NVLink GPU 上的 NVLink SHARP。NVLink SHARP 让 CUDA 应用能够利用 fabric 内计算来加速通过 NVSwitch 连接的 GPU 之间的广播和归约等操作。要实现这一点，多个 NVLink 连接的 GPU 组成一个多播团队，团队中的每个 GPU 用物理内存备份一个多播对象。于是，由 N 个 GPU 组成的多播团队就拥有了 N 个多播对象的物理副本，每个副本本地属于一个参与的 GPU。使用多播对象映射的 multimem PTX 指令可以操作该多播对象的所有副本。

要使用多播对象，应用需要：

- 查询多播支持情况。
- 用 `cuMulticastCreate` 创建多播句柄。
- 把多播句柄共享给所有控制应参与多播团队的 GPU 的进程。这可如上文所述用 `cuMemExportToShareableHandle` 实现。
- 用 `cuMulticastAddDevice` 把应参与多播团队的所有 GPU 都加入进来。
- 对每个参与的 GPU，把如上文所述用 `cuMemCreate` 分配的物理内存绑定到多播句柄。在任何设备上绑定内存之前，必须先把所有设备都加入多播团队。
- 如上文常规单播映射所述，保留地址范围、映射多播句柄并设置访问权限。对同一物理内存可以同时存在单播映射和多播映射。参见“虚拟别名支持”一节，了解如何保证同一物理内存的多个映射之间的一致性。
- 对多播映射使用 multimem PTX 指令。

Multi GPU Programming Models GitHub 仓库中的 `multi_node_p2p` 示例是一个完整的例子，它使用包括多播对象在内的 fabric 内存来利用 NVLink SHARP。请注意，这个例子是为 NCCL 或 NVSHMEM 这类库的开发者准备的。它展示了 MPI、NCCL、NVSHMEM 这样的高级编程模型在（多节点）NVLink 域内部的工作方式。应用开发者一般应当使用高级的 MPI、NCCL 或 NVSHMEM 接口，而不是直接使用这个 API。

> 注意：这里描述的多播共享把多播对象映射到每个设备的虚拟地址空间中，并用 multimem 指令操作——这是地址中心型模型。计算 fabric 传输提供了资源中心型的对应物：多播逻辑端点，它为 NVLink fabric 上的多播团队服务，而不需要把对象映射到本地地址空间。它为每次操作报告显式的完成状态，因此适合 fabric 错误恢复值得关注的大规模 fabric。

## 4.17.5 高级配置

### 4.17.5.1 内存类型

VMM 还提供了一种机制，让应用能够分配某些设备可能支持的特殊类型内存。用 `cuMemCreate` 时，应用可以用 `CUmemAllocationProp::allocFlags` 指定内存类型要求，以选择加入特定的内存特性。应用必须确保请求的内存类型被设备支持。

### 4.17.5.2 可压缩内存

可压缩内存可用于加速对具有非结构化稀疏性和其他可压缩数据模式的数据的访问。压缩可以节省 DRAM 带宽、L2 读带宽和 L2 容量，具体取决于数据。希望在支持计算数据压缩的设备上分配可压缩内存的应用，可以通过把 `CUmemAllocationProp::allocFlags::compressionType` 设置为 `CU_MEM_ALLOCATION_COMP_GENERIC` 来实现。用户必须用 `CU_DEVICE_ATTRIBUTE_GENERIC_COMPRESSION_SUPPORTED` 通过 `cuDeviceGetAttribute` 查询设备是否支持计算数据压缩。以下代码片段展示了用 `cuDeviceGetAttribute` 查询可压缩内存支持情况：

```c
int compressionSupported = 0;
cuDeviceGetAttribute(&compressionSupported, CU_DEVICE_ATTRIBUTE_GENERIC_
 ,→COMPRESSION_SUPPORTED, device);
```

在支持计算数据压缩的设备上，用户必须在分配时选择加入，如下所示：

```c
prop.allocFlags.compressionType = CU_MEM_ALLOCATION_COMP_GENERIC;
```

```c

 ,→GENERIC)

```
### 4.17.5.3 虚拟别名支持

虚拟内存管理 API 允许用 `cuMemMap` 多次调用、传入不同的虚拟地址，为同一分配创建多个虚拟内存映射（或称“代理”）。这叫做虚拟别名（virtual aliasing）。除非 PTX ISA 中另有说明，对某分配的一个代理的写入，在写操作所在的设备操作（网格启动、`memcpy`、`memset` 等）完成之前，与同一内存的任何其他代理之间都被视为不一致、不连贯。在写设备操作完成之前已在 GPU 上的、但在写设备操作完成之后读取的网格，也被视为具有不一致、不连贯的代理。

例如，假设设备指针 A 和 B 是同一内存分配的虚拟别名，下面的代码片段是未定义的：

```c
__global__ void foo(char *A, char *B) {
  *A = 0x1;
  printf("%d\n", *B);     ∕∕ 未定义行为！*B 可能是旧值，也可能是中间的某个值。
}
```

假设这两个核函数单调有序（由流或事件保证），下面是已定义行为：

```c
__global__ void foo1(char *A) {
  *A = 0x1;
}

__global__ void foo2(char *B) {
  printf("%d\n", *B);     ∕∕ *B == *A == 0x1，假设 foo2 等待 foo1
∕∕ 完成后才启动
}

cudaMemcpyAsync(B, input, size, stream1);                 ∕∕ 在操作边界处允许使用别名，
∕∕ 允许 foo1 访问 A。
foo1<<<1,1,0,stream1>>>(A);
cudaEventRecord(event, stream1);
cudaStreamWaitEvent(stream2, event);
foo2<<<1,1,0,stream2>>>(B);
cudaStreamWaitEvent(stream3, event);
cudaMemcpyAsync(output, B, size, stream3);              ∕∕ foo2 和 cudaMemcpy（两者都是
                                                        ∕∕ 读操作）都等待 foo1（写操作）
                                                        ∕∕ 完成后再继续
```

如果需要在同一个核函数中通过不同的“代理”访问同一分配，可以在两次访问之间使用 `fence.proxy.alias`。上面的例子可以用内联 PTX 汇编改写成合法形式：

```c
__global__ void foo(char *A, char *B) {
  *A = 0x1;
  cuda::ptx::fence_proxy_alias();
  printf("%d\n", *B);    ∕∕ *B == *A == 0x1
}
```
